# 计划必错，信赖技术洞见（战略的根基与过滤器）

## R — 原文 (Reading)

> "如果你有商业计划，那你的计划一定是错误的。……风险投资家应永远遵守投团队而不投计划的准则。既然计划会错，那么人就得对。" / "所谓的技术洞见，是指用创新方式应用科技或设计，以达到生产成本的显著降低或产品功能和可用性的大幅提升。"
>
> — 施密特、罗森伯格，第二章《你的计划是错误的》/《信赖技术洞见，而非市场调查》

---

## I — 方法论骨架 (Interpretation)

这套方法论的起点是一个反直觉默认值：**计划必错**。不是因为计划者蠢，而是因为计划建立在对未来的可预测假设上，而新兴行业里这种确定性不存在。没有任何团队的表现能超越既定计划——计划设定的目标本身就成了天花板。

计划退位后，接住战略的是两样东西。**一是技术洞见**：用新方式运用科技或设计，使成本显著降低、或功能与可用性大幅跃升。它是每个产品必过的第一道过滤器——"请阐述你的技术洞见"答不出有说服力的答案，产品大概率平庸。**二是人**：计划会错，人得对；评估事业看团队的发现与调整能力，不看计划的严密程度。

**记录方式随之改变**：把计划所依据的"不变基本原则"写成一页纸（计划可变，基础岿然不动），而不是写死路线图。**市场调查被降级**：它只能触及用户已意识到的需求、且常常漏算技术演进（如摩尔定律），可用于改进产品，不可用于定方向。

**洞见从哪来**：把现成科技要素组合起来攻击行业问题；或从一个具体问题的解法向外拓展；最短路径是"找到你的极客，看看他们在研究什么"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 芬兰计划——一份对抗微软的"非计划"
- **问题**: 董事莫里茨要求谷歌针对微软的进攻（代号"芬兰"）提交一份全面的传统商业计划。
- **方法论的使用**: 乔纳森交出的"计划"只讲聚焦用户、卓越产品与技术平台——没有财务估测、没有市场调研、没有路线图、没有预算。
- **结论**: 抵御巨头靠的是顶尖工程师与产品卓越，不是计划的完备性。
- **结果**: 微软投入近 110 亿美元的攻势未能撼动谷歌，"计划"的威力反而超出想象（c01）。

### 案例 2: 拉里退回"过关制"产品计划
- **问题**: 乔纳森带着大企业验证过的"过关制"方法论入职，提交了含步骤、审核、两年路线图的教科书式计划。
- **方法论的使用**: 拉里三问否决——"你见过哪个团队的表现能超越既定目标？你的团队研发过比计划更出色的产品吗？如果是这样，计划还有什么意义？"
- **结论**: 计划只是在拖后腿；遇到问题"去和工程师谈谈"。
- **结果**: 乔纳森放弃过关制，转成这套理念的布道者（c03）。

### 案例 3: 2009 年技术洞见大检验
- **问题**: 如何系统甄别哪些产品有真本事、哪些只是借品牌的人气。
- **方法论的使用**: 复盘发现"最优秀的产品靠技术因素取胜"的规律后，要求所有主要产品负责人写出产品背后的技术洞见。
- **结论**: 许多人无从下笔——"请阐述你的技术洞见"成为试金石。
- **结果**: 该检验成为产品评估的常规工具；昙花一现的产品均被证实缺少洞见支撑（c32）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 写商业计划书/BP/立项报告，纠结财务预测和路线图要做多细才"靠谱"。
2. 新产品立项评审：市场方拿调研数据说需求很大，工程方说做不出来，没人问"凭什么做得成"。
3. 年度路线图执行到一半，环境已经变了，团队在"按计划交付"与"转向"之间摇摆。
4. 复盘一个失败产品，想找系统性的原因而不是单点失误。
5. 战略会上有人提议"先做一轮市场调查/竞品分析再定方向"。

### 语言信号 (用户的话里出现这些就应激活)

- "商业计划书 / BP / 路线图 / roadmap / 里程碑 milestone"
- "市场调查显示 / 用户调研说 / 竞品分析 / market research"
- "计划赶不上变化 / plans are worthless / 计划还要不要守"
- "技术洞见 / technical insight / 凭什么赢 / 凭什么是我们做成"
- "投团队不投计划 / bet on the team"

### 与相邻 skill 的区分

- 与 `focus-user-think-10x` 的区别：那个管"为谁做、做多大"（用户立场与 10 倍量级）；本 skill 管"凭什么做成"（技术根基与计划姿态）。立项评审先过本 skill 的洞见之问，再用那个放大目标。
- 与 `open-as-strategy` 的区别：开放/封闭判定里的前提①"产品有明显技术洞见优势"，正是由本 skill 的洞见之问来回答——两个 skill 串联。
- 与 `ask-hard-questions` 的区别：那是组织级"5 年后可能会怎样"的自造不安；本 skill 是产品级的过滤器，粒度更小、更前置。

## E — 可执行步骤 (Execution)

1. **撤回计划问题，改写评审第一问**
   - 完成标准：把"怎么完善这份计划"改写为"哪些是不变的基本原则"；评审不再以财务预测与里程碑的精细度论质量。
   - 判停条件：若议题是成熟业务的季度运营排期/预算 → 本 skill 退出，正常做计划。
2. **过技术洞见之问**
   - 完成标准：让产品负责人写几句话阐述洞见，并检验是否符合严格定义（以新方式运用科技/设计 → 成本显著降低或功能大幅跃升）。
   - 判停条件：写不出有说服力的答案 → 不进入后续计划，砍掉或重构产品。
3. **沿三条路径找洞见**
   - 完成标准：分别检查——可组合的现成科技要素有哪些；手头具体问题的解法能否向外拓展；"你的极客"最近在实验室里研究什么。三条至少走完一轮再下结论。
4. **用一页原则文替代路线图**
   - 完成标准：写下计划所依据的基本原则（如成本曲线、平台逻辑）并全员对齐；具体计划标注"临时"并随环境推翻重写。
5. **给市场调查降级**
   - 完成标准：调查结论只进入"改进现有产品"的清单，不进入"方向选择"的依据；方向之争回到洞见与极客事实上解决。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **成熟稳定业务的运营计划**——供给排期、财务预算这类场景里"计划必错"的假设不成立，别拿它否定一切计划。
- **强监管行业的合规文书**——该准备的计划性文件一份不能省，"先干了再说"不适用。
- **把"计划必错"当"不做任何思考"的借口**——作者仍要求基本原则一页纸与快速迭代；扔掉的是路线图迷信，不是战略思考本身。

### 作者在书中警告的失败模式

- "过关制"流程：层层评审把决策权从一线抽走，计划目标成为团队表现的天花板（ce01）。
- "实现失败"：按存在致命缺陷的计划一步步走下去，执行越彻底死得越干净（ce02）。
- 品牌救不了没有洞见的产品：iGoogle、Notebook、Knol 等昙花一现，向纸媒/广播/电视的扩张三连败（ce04）。
- 市场调查把 Excite@Home 引向错误卖点：调查没把摩尔定律算进去，用户真正离不开的是"保持在线"而非问卷高频词"高速"（ce05）。

### 作者的盲点 / 时代局限

- "产品卓越自动胜出"是未被证明的假设：渠道、网络效应、监管同样决定胜负，微软输给谷歌是特例而非定律（BOOK_OVERVIEW 批判节）。
- 成功归因无法分离：技术洞见的胜利里掺着先发优势与搜索业务的垄断性利润引擎；在不具备类似引擎的组织里，"计划必错"的试错成本可能无法承受。

### 容易混淆的邻近方法论

- 精益创业 MVP：`ship-iterate-fail-well` 管发布节奏与失败善后；本 skill 管立项根基——先有洞见，再谈迭代。
- 艾森豪威尔式"计划毫无价值"的名言：结论相近，但本书给出可执行过滤器（洞见之问）、洞见的严格定义和"原则文替代计划书"的记录形式——是流程不是感慨。
