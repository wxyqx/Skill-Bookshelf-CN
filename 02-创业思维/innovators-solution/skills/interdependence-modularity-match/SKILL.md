# 互依性-模块化情境匹配：先定位，再决定整合还是外包

## R — 原文 (Reading)

> IBM这么做的目的是为了专注做自己最擅长的事情……而在它将这些业务外包出去的过程中，它所放弃的东西却成了两家接包公司的核心成长力量，成为行业内最成功的赚钱机器。
>
> — 克里斯坦森 & 雷纳, 第5章 选择正确的业务范围

---

## I — 方法论骨架 (Interpretation)

自制还是外包，不是先问"我们擅长什么"，而是先问"这款产品现在对客户来说够不够好"。把技术改良轨迹的斜率与客户实际需求/吸收能力的斜率放在一起比：两条线相交之后，产品就"好得过头"，客户开始只按价格挑选。判断情境（不够好 / 好得过头）是决策的前置条件，架构与整合范围都由此推出。

- 产品"不够好"（性能仍不达标、客户愿为改进付溢价）→ 采用交互式、受专利保护的架构，垂直整合所有关键接口，把性能牢牢握在手里。
- 产品"好得过头"（客户只比价格、看不出你比对手好在哪）→ 采用模块化架构，把非关键环节分包出去，拥抱行业标准，换取速度与灵活性。
- 把"这是不是我们的核心竞争力"这类静态问法，替换成"我们现在和未来应该掌握什么、如何沿客户在意的方向上升"。
- 该钟摆可预测：当需求断层上移、客户开始在意一个新的子系统，行业会被拉回整合情境，此时谁先整合关键接口谁获益。
- 过度服务的典型信号：销售抱怨"客户看不出我们的好、把我们当大路货"。

## A1 — 书中的应用 (Past Application)

### 案例 1: IBM 以"核心竞争力"外包微处理器与操作系统
- **问题**: 20 世纪 80 年代初，IBM 要快速进入 PC 市场，需决定哪些环节自制、哪些外包。
- **方法论的使用**: IBM 按"专注做最擅长的事"（设计、装配、推广）把微处理器交给英特尔、操作系统交给微软。
- **结论**: 当时看似明智，缩减了研发成本与时间，媒体交口称赞。
- **结果**: 被放弃的互依性关键子系统日后成为 PC 行业利润最丰厚处，英特尔与微软成为行业最赚钱的公司；IBM 的"非核心"分类法被证明可致命。

### 案例 2: 戴尔整合"不够完善"的客户接口
- **问题**: PC 组件已高度模块化、好得过头，整机厂该整合什么？
- **方法论的使用**: 戴尔判断对客户而言"直销/客户关系"这一接口仍不够完善，遂垂直整合客户接口，而对已过度服务的组件间模块化接口放手外包。
- **结论**: 利润增长点位于面向客户的接口与子系统接口，而非组装。
- **结果**: 90 年代末戴尔凭客户接口整合战胜康柏，其来自零售/直销接口的利润远超组装业务。

### 案例 3: 微软随需求断层重新整合 Office
- **问题**: 单机字处理、电子表格已好得过头、行业走向模块化分散，客户新出现的需求是应用间互操作。
- **方法论的使用**: 微软判定需求虚线上移，重新进入"不够好"情境，独立研发 Office 套件并与 Windows 整合。
- **结论**: 需求断层会把行业拉回整合情境，窗口属于顺应时势者。
- **结果**: WordPerfect、Lotus 1-2-3 迅速从市场蒸发，Office 成为垄断性套装。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 企业要决定某关键部件（电池包、芯片、算法模块、客服系统）自研自制还是采购/外包，团队各执一词。
2. 有人以"这不是我们的核心竞争力"为由主张剥离业务，需要判断该理由在当下情境是否成立。
3. 产品销量下滑但说不清原因，客户只比价格、销售抱怨"客户看不出我们好在哪"。
4. 行业从垂直整合走向分工，或反之出现再整合浪潮，企业要判断站哪一边。

### 语言信号 (用户的话里出现这些就应激活)

- "这块业务该自研还是外包？"
- "我们要不要垂直整合 / 做全产业链？"
- "这算不算我们的核心竞争力，该不该剥离？"
- "客户只比价格，不为性能多付钱了" / "我们是不是被做成了大路货？"
- "make or buy / vertical integration / modular architecture"

### 与相邻 skill 的区分

- 与 `modular-outsourcing-conditions` 的区别: 本 skill 决定"该不该把这块交出去、整合范围划到哪"（定位与架构决策）；后者是在已决定外包某个模块后，逐条检验接口是否已成熟到可分包。
- 与 `commoditization-positioning` 的区别: 本 skill 关注企业自身的整合/架构选择；后者关注利润在价值链上迁移到哪里、企业应把资源重新定位到哪个"不够好"的环节。
- 与 `rpv-capability-audit` 的区别: 本 skill 解决"业务范围边界"；后者解决"组织能力是否匹配新业务、该用何种组织结构"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **定位性能情境（不够好 / 好得过头）**
   - 完成标准: 明确给出结论并列出证据（客户是否愿为性能改进付溢价、销售是否反馈被当大路货、竞争是否已转向价格）。
   - 判停条件: 若证据自相矛盾、无法判断情境，则先补做需求观测，不要直接进入架构决策。

2. **画出两条斜率并找交点**
   - 完成标准: 分别描述技术改良轨迹与客户需求/吸收能力轨迹的方向与快慢，指出当前处于交点前还是交点后。

3. **按情境匹配架构与整合范围**
   - 完成标准: 给出"不够好→交互式专利架构+整合关键接口"或"好得过头→模块化+分包+标准"的明确建议，并逐一点名哪些接口必须掌握、哪些可放手。

4. **用问句替换法复核理由**
   - 完成标准: 把决策理由从"是不是核心竞争力"改写成"我们现在与未来应掌握什么、如何沿客户关注的方向上升"，确认结论不依赖静态分类。

5. **设置需求断层监测**
   - 完成标准: 列出会导致行业重新整合的需求变化信号，并给出触发重新评估的条件。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户只是问某个模块/供应商的市场报价或合同条款，未涉及业务范围与架构决策。
- 用户在做纯财务的资产剥离测算，但已排除竞争情境与性能缺口的考量——此时本 skill 的结论无输入可依。
- 产品性能明显仍"不够好"却因短期 ROA 压力急于分包，本 skill 会否决该做法，而非为其背书的工具。

### 作者在书中警告的失败模式

- **用"核心竞争力"话术决定业务范围**（ce07）：以"这是不是我们的核心竞争力"替代"竞争基础在何处"，把看似非核心、实则代表未来利润增长点的业务让给供应商（IBM 外包微处理器与操作系统）。
- **在"不够好"的情境过早模块化分包**（ce08）：性能/可靠性仍不足、接口存在不确定互依时就按专业分工与行业标准外包（CLEC 的 DSL、欧美厂商过早押注 WAP），跨组织协调成本吞掉收益。
- **把品牌溢价当抗货品化护城河**（ce10）：产品已过度服务仍不迁移投入，品牌溢价随竞争基础转移而萎缩。

### 作者的盲点 / 时代局限

- 案例集中于 2003 年前的美国上市大企业，对平台/生态型组织、扁平小团队的整合-模块化边界未必适用。
- "技术进步恒快于需求吸收"是理论前提而非已被普遍验证的定律；需求线（是否过度服务）在实践中难以精确观测，两条斜率常是事后才看得清。
- 用"是否过度服务"判定整合时机，对强监管行业与标准由监管而非市场决定的行业适用性未验证。
- 该框架给出的是方向判据，不解决整合后的组织执行与文化问题。

### 容易混淆的邻近方法论

- 交易成本经济学（威廉姆森）：从资产专用性与机会主义解释自制/外包，与本 skill 的"性能缺口"视角互补但不相同。
- "核心竞争力"（普拉哈拉德 & 哈默）：本 skill 正是要修正这一静态分类法。
