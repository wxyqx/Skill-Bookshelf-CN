# 模块化外包三条件检验：接口不成熟，分包必失败

## R — 原文 (Reading)

> 绝大部分的CLEC都失败了。因为在当时，DSL服务还处于图5–1所示的"交互式"领域。CLEC在客户的终端上建立DSL连接后，要接入到电话公司并获得回应，这中间有太多的微妙和不确定的依赖关系。
>
> — 克里斯坦森 & 雷纳, 第5章 选择正确的业务范围

---

## I — 方法论骨架 (Interpretation)

把某个模块交给外部（外包、分包、联盟、采用行业标准接口），能不能效率更高，取决于接口本身是否已经"模块化"到位。作者给出三条必须同时满足的条件，缺一不可：

1. **专业性（specifiability）**——双方都清楚哪些功能指标是系统必需的、哪些与整体性能无关，边界可明确写出。
2. **可衡量性（measurability）**——供应商熟悉产品属性的衡量标准，能按规格验收并稳定交付。
3. **可预测性（predictability）**——接口处不存在任何不确定的相互依赖；不会因为一方的改动而逼另一方反复调整。

三者齐备，才算有效的模块化接口，分散协作才有净收益；三者不齐，跨组织协调成本会吞掉专业分工的收益，强行分包注定失败。因此行业标准和联盟策略只在功能可靠性达标后的情境才有效，过早标准化是真实的浪费。推论：先内部整合到接口稳定，再考虑分包。

## A1 — 书中的应用 (Past Application)

### 案例 1: CLEC / Northpoint 的 DSL 分包失败
- **问题**: 1996 年美国电信法允许私营企业租用电话公司设施提供 DSL 服务，CLEC 获大量注资，指望轻资产分包运营。
- **方法论的使用**: 作者指出 DSL 当时仍处"交互式"领域——接入电话公司、计费系统软件架构都是交互式的，接口存在大量不确定的相互依赖，"插入式"接入几乎做不到。
- **结论**: 三条条件均不满足（规格不清、计费难以衡量对接、接口不可预测），模块化分包不成立。
- **结果**: 绝大部分 CLEC 失败；交互式接口反而成为谙熟自家网络与 IT 架构的电话公司的竞争优势。

### 案例 2: 欧美厂商过早押注 WAP 标准
- **问题**: 移动上网萌芽期，欧美厂商热衷制定统一的 WAP 行业标准并结成联盟。
- **方法论的使用**: 按三条件检验，此时功能可靠性尚未达标、接口仍在剧烈变动，标准化为时过早。
- **结论**: 过早标准化是真实的浪费，联盟策略在情境不成熟时无效。
- **结果**: WAP 阵营未获预期成功；对照 NTT DoCoMo 在本土把内容商与手机商接口内部整合，反而成效显著。

### 案例 3: SAP 实施——"需整合而非模块化"的例外
- **问题**: 企业软件部署该标准化外包还是深度整合？
- **方法论的使用**: 用三条件反推：接口（客户流程、数据、组织）高度不确定，须反复人工协调。
- **结论**: 属于"需整合而非模块化"的例外，不能当标准化模块外包。
- **结果**: 佐证接口未成熟时整合优于分包。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 企业计划把某模块（理赔 AI、支付、物流、客服）外包给第三方，但对接口稳定性没底。
2. 团队正推动"开放架构/行业标准/生态联盟"，需要事前判断时机是否成熟。
3. 外包试点后出现接口频繁变动、数据字段对不上、需反复人工核对，怀疑是不是分包错了。
4. 决定某合作是"分包模块"还是"深度联合开发"，需要客观判据而非直觉。

### 语言信号 (用户的话里出现这些就应激活)

- "这个模块能不能外包出去？"
- "我们想接行业标准 / 搞生态联盟，靠谱吗？"
- "接口老变动，数据字段和规则要反复人工核对。"
- "规格说不清，供应商交付总对不上。"
- "outsourcing readiness / modular interface / 该不该标准化"

### 与相邻 skill 的区分

- 与 `interdependence-modularity-match` 的区别: 后者回答"业务范围该不该整合、整合到哪"（先定位性能情境）；本 skill 回答"已经决定把这块交出去，接口是否够格外包"，是更靠近接口层的前置检验。
- 与 `commoditization-positioning` 的区别: 后者关注利润迁移到哪个环节、企业该重新定位到哪；本 skill 只判断某接口能否安全模块化拆分。
- 与 `asymmetric-motivation-test` 的区别: 后者检验在位者会不会反击；本 skill 检验协作接口本身是否成熟。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **明确待外包对象与接口清单**
   - 完成标准: 写出要交出去的功能/模块，并列出它与内部其余部分的全部接口（数据、规则、计费、合规、运维）。

2. **逐条检验三条件**
   - 完成标准: 对每个接口分别就"专业性 / 可衡量性 / 可预测性"给出是/否判断与证据。
   - 判停条件: 若出现任一"否"，直接跳到步骤 4（建议先内部整合），不要继续推进分包。

3. **评估协调成本是否吞掉收益**
   - 完成标准: 估算接口变更频率与人工协调负担，判断专业分工的收益是否被跨组织协调成本抵消。

4. **给出结论与前置动作**
   - 完成标准: 明确输出"可外包 / 暂不可外包"，若不可外包则给出应先内部整合到接口稳定的哪些具体动作。

5. **重估标准化/联盟时机**
   - 完成标准: 给出重新检验三条件的触发条件（如功能可靠性达标信号），避免过早押注标准。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户尚未决定是否外包，只在权衡业务范围该整合到哪——应先用 interdependence-modularity-match 定位。
- 用户问的是纯采购比价、供应商资质审查等流程问题，不涉及接口成熟度。
- 通用 IT 项目管理问题（排期、验收流程），与本框架的接口三条件无关。

### 作者在书中警告的失败模式

- **在"不够好"的情境过早模块化分包**（ce08）：性能/可靠性未达标、接口存在不确定互依时就分包（CLEC 的 DSL、欧美厂商过早押注 WAP），协调成本吞掉收益。
- **用"核心竞争力"话术做业务范围决策**（ce07）：把接口是否成熟误当成"是否擅长"，把关键互依子系统拱手让人。
- **供应商的不对称动机**：当供应商主动愿意接手某"非核心"业务且开始向上游设计扩张时，需警惕其为逐级吞食搭梯子。

### 作者的盲点 / 时代局限

- 三条件基于 2003 年前电信/软件等案例归纳，对微服务、开源生态、API 经济等新协作形态的适用性未验证——现代标准化工具可能部分降低协调成本。
- "接口无不确定相互依赖"在复杂系统中常是渐近目标而非二元达成，实操判定易受主观影响。
- 案例样本集中于美国上市电信企业，结论受案例选择影响；"过早标准化是浪费"在标准具有网络效应的行业可能被打破。

### 容易混淆的邻近方法论

- 交易成本经济学（威廉姆森）：从资产专用性/机会主义解释边界，与本 skill 的接口三条件互为补充。
- 模块化理论（鲍德温 & 克拉克）：讲模块化设计原理，本 skill 提供"何时才能模块化"的情境闸门。
