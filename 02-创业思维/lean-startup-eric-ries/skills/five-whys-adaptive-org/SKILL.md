# 五个为什么与自适应组织：追到人的问题，按比例投入

## R — 原文 (Reading)

> "这就是丰田著名的'安灯'拉绳的源起，任何工人一旦发现任何问题，都可以拉绳请求帮助，比如当部件的缺陷无法马上修正之时，就要停下整条生产线。"
>
> —【作】埃里克·莱斯，第9章

> "像这样反复询问五次'为什么'，可以帮你找到问题的根本原因并加以改正。……问题的真实缘由常常被其他更明显的表现症状掩盖，而通过提出和回答五次'为什么'，我们可以直达根源。"
>
> —【引】大野耐一（作者在书中转述其机器停机案例），第11章

> "每一个看似技术问题的根本原因是人的问题。'五个为什么'提供了探讨究竟是什么人为问题的机会。"
>
> —【作】埃里克·莱斯，第11章

> "当基础体系或流程投资收到效果的时候，危险的严重程度和数量就会降低，团队又能重新加速。对新创企业而言，团队运行得太快是一种危险……'五个为什么'可以防止这种情况，让团队找准他们的最佳步速。"
>
> —【作】埃里克·莱斯，第11章

> "我让团队采用这样两条简单的原则：1.对第一次错误要容忍。2.不允许同样的错误发生两次。"
>
> —【作】埃里克·莱斯，第11章

## I — 方法论骨架 (Interpretation)

新创企业跑得快，缺陷和事故是常态；危险的不是出问题，而是每次都只修表象、同样的错误反复重演。本书把丰田生产方式的"安灯拉绳"搬进新创企业，给出一套根因分析与速度调控机制：

1. **安灯源头：为了发现质量而"停止生产线"**：小批量工作的最大好处是能早早发现质量问题。任何工人发现问题即可"拉绳"，当缺陷无法马上修正时就停下整条生产线——与"流水线最佳状态是流畅运转"的直觉相反，但更快发现和解决问题的好处超过代价。
2. **连问五个"为什么"，直达被症状掩盖的根源**：对任何失败（技术故障、业绩不达标、顾客行为意外变化）反复追问"为什么"。大野耐一的机器停机案例：停机→保险丝熔断→轴承润滑不足→油泵抽压失效→旋转轴磨损→没装过滤器致金属碎屑掉入——根源从技术故障一路转为人为失误。
3. **核心洞见：每个看似技术问题的根本原因是人的问题**：新创企业多数问题的典型根源是培训缺失或流程缺陷，而非个人无能。分析停在"换个保险丝"，几个月后问题必然重演。
4. **按比例投入：五级问题、五级投入**：对追问出的每一级原因按严重程度投入相应解决方案——症状轻则少投入，症状重则多投入，除非重大问题不作大笔投入（小故障只值得做"八周计划中第一个小时的工作"），问题重现则继续深入。
5. **机制自带"自动速度调节器"**：问题越多、投入越多，速度自然放缓；基础体系投资见效后危险下降，团队重新加速——它防止团队为争取时间牺牲质量、跑得太快，让团队找准最佳步速。
6. **落地四规则**：①环境尚缺信任与授权时，先用简化双原则——"对第一次错误要容忍""不允许同样的错误发生两次"；②根因会议必须让所有发现、诊断、修复问题者及相关决策者齐聚一堂，缺席者会变成替罪羊；③每个领域委派一位"五个为什么"负责人——要有资历权威保证任务完成，又不能太高层以致缺席会议；④从小处、具体的一类问题起步（作者首次成功即用于内部测试工具），规则简单明了、不选模棱两可的，先易后难再扩展。
7. **终点是自适应组织**：按比例投入加上安灯式的"遇问题即停"，让组织的投入随真实危险自动伸缩——这就是自适应组织：不是在"重流程"与"无流程"间拍板，而是让流程强度成为问题频率的函数。

## A1 — 书中的应用 (Past Application)

### 案例 1: IGN 娱乐的四次"五个为什么"实战（ch11，主线案例）
- **问题**: 新闻集团旗下游戏媒体，超 4500 万玩家、约百名工程师。第一次"五个为什么"会议开了一小时，虽有些心得，但流程上"简直是场灾难"——最了解情况的相关人员没参加、没有遵循应有形式、时常离题万里。
- **方法论的使用**: 领导层重整流程纪律：委派工程开发总监托尼·福特（原 TeamXbox 创始人，2003 年公司被收购后加入）任"五个为什么"负责人；只针对新问题开会、相关人员必须出席、会前热身。典型案例：博客 API"500 错误"五问到底，从 gem 版本不兼容一路问到"为什么周五晚上做开发改动"（因为没人说不可以）。
- **结论**: 根因分析的价值全在流程纪律上；五问的终点是"周五晚不该改代码"这条人为规则，而非某个技术零件。负责人制度让会议不跑题、结论可落地。
- **结果**: 方案包括 gem 改捆绑管理、自动化安装、周五六日不做开发改动（特例须副总裁批准）；此后类似问题再未出现。托尼体会："'五个为什么'的效果正好相反"于"问题使人疏离"——它让团队形成统一理解、把人聚拢。

### 案例 2: IMVU 的五问链与自适应组织演化（ch11/ch12，作者亲历）
- **问题**: IMVU 收到新版本关闭顾客功能的投诉；更早前，新版本上线暴露出团队没有成形的培训与流程体系，问题反复出现。
- **方法论的使用**: 五问之下从服务器挂掉一路问到"经理认为太忙了不需要培训"——纯技术故障揭示出管理层面的人为问题；此后组织在流程演化中自然长出培训制度：每个新晋工程师配一位导师（导师与学徒绩效相连），新工程师入职第一天就被安排去改动产品开发环境。
- **结论**: 五问追到的是"人没被培训"，解法也是对人的投入（导师制）；当被问"弄坏流程会不会有事"时，作者答"如果我们的开发流程脆弱到你第一天上班就能把它攻破，那我们该反省为什么把系统设置得如此简单"，并让其牵头修复、防止重演。
- **结果**: 新员工入职第一天即可有效工作；面对员工"回到老办法"式的建议，用三重科学质询（能否预测结果、能否小团队试、能否衡量影响）取代折中妥协，很多精益技巧正是员工经由质询自己创造的。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 线上出了缺陷或事故，修完表象了事，几周后同样的问题又来一遍——想知道怎么追到真正的根子。
2. 团队天天救火：修一个 bug 冒出三个，新员工不会弄却没人教，想建一套"出了问题怎么处理"的组织机制。
3. 根因复盘会开变了味：与会者互相指责、缺席者背锅，或者反过来领导想"折中一下别搞太重"，不知道规则该怎么定。

### 语言信号 (用户的话里出现这些就应激活)

- "五个为什么""根因分析""根本原因""追根到底""为什么又出同样的问题"
- "按比例投入""五大罪状""安灯拉绳""自动速度调节器""自适应组织""最佳步速"
- "救火""总在修表象""技术故障背后是不是管理问题""对第一次错误要容忍""同样的错误不能犯两次""根因会议怎么开""该派谁负责复盘"

### 与相邻 skill 的区分

- 与 `small-batch-acceleration` 的区别：后者是压缩循环时长的**提速手段库**（单件流、持续部署等），假设"问题将来一次性暴露"由批次大小决定；本 skill 管**问题已经发生之后**的组织级根因治理与速度调控。一句话若在问"怎么跑得更快"归前者，在问"出了问题怎么追、组织怎么变"归本 skill。
- 与 `startup-quality-philosophy` 的区别：后者管"质量该做到几成"的哲学之争（不知顾客即不知质量、八成产品、不为时间牺牲会拖慢循环的质量）；本 skill 管具体缺陷的技术性治理与根因流程。争论"要不要做完美再上"归前者，事故已发生要追责归本 skill。
- 与 `internal-innovation-sandbox` 的区别：后者设计大企业**创新业务**的机制（沙盒、架构、考核），本 skill 管的是主业务**缺陷响应**的机制（安灯、五问、按比例投入）——同属组织机制但服务对象不同。
- 与 `mvp-design-patterns` 的区别：实验失败本身如何解读归循环类 skill；只有当失败暴露的是"流程/培训缺陷"并需要组织层面根治时才归本 skill。

## E — 可执行步骤 (Execution)

1. **拉绳：把事故从"修完拉倒"改为登记议题**：缺陷或事故出现时，把"立即修复表象"与"根因追查"拆成两件事，后者立项跟进
   - 完成标准：每次缺陷都有登记（触发时间、症状、影响），明确"表象修复 ≠ 结案"。
2. **连问五个为什么，追到人的问题**：从症状层层追问，直到答案落在具体的人为原因（培训缺失、流程缺陷、规则缺失）而非某个技术零件
   - 完成标准：五问链条书面可见，末级是一个可改变的人为问题；能回答"为什么几个月前没被发现"。若停在"换个零件"即未完成。
3. **全员到场的根因会议**：所有发现、诊断、修复问题者及相关决策者必须出席；由级别最高者在场申明"对系统易错感到羞愧"，把基调定在流程而非个人
   - 完成标准：会议纪要含全体相关者名单；全程无相互指责（出现"五大罪状"苗头即纠正）；缺席者补席而非事后定罪。
4. **按比例投入解决方案**：对五问链条上每一级原因分别决定投入多少——小故障小投入，问题重现则升级投入
   - 完成标准：每一级"为什么"对应一项投入决定及其比例理由；没有"大炮打蚊子"，也没有"只修第一级"。
5. **落实双原则与负责人，用问题频率调节步速**：宣布"对第一次错误要容忍、不允许同样的错误发生两次"；为该领域指定一位有资历但不缺席会议的"五个为什么"负责人；此后把问题增减当速度表——危险多则减速投入，体系见效后重新加速
   - 完成标准：负责人有名有实；同类问题未重现（重现则触发更深入一轮）；团队发布步速随问题率有过一次有意识的升降调整。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户只是想压缩交付周期、挑选提速工具（单件流、持续部署、换型时间）——那是批次与流程问题，转 `small-batch-acceleration`。
- 用户争论的是"产品该做到几成质量"的哲学取舍（要不要完美再上、八成够不够）——转 `startup-quality-philosophy`。
- 没有追根因意愿、只想找人背锅了事的场合——本 skill 的前提是"问题在流程不在人"，强行使用只会开出批斗会。

### 作者在书中警告的失败模式（按家族速查）

- **e13 "五大罪状"之魔咒（F5）**：沮丧的团队成员不问为什么而开始相互指责、把系统性失败归咎于他人的部门或个性——找错病因又摧毁坦诚，同样的错误必然重演。对策：全员出席 + 最高级别申明。
- **e18 IGN 第一次"五个为什么"会议的灾难（F9）**：最了解情况的人没参加、不循形式、离题万里，还试图直接啃积攒多年的"历史包袱"——失败的不是方法而是走样的执行，但足以让组织给方法本身判死刑。教训：只针对新问题、人人出席、会前热身。
- **e19 "做一点点计划"的折中陷阱（F9）**：在"重流程"与"无流程"间取中庸拿不出可辩护的因果逻辑，还诱导下属站极端立场博弈——正确出路是按比例投入的自适应流程，而非折中仲裁。
- **e17 过度构架与"交友网效应"（F8）**：为想象中的各类问题搭防护体系耽误推出产品，或零设防被增长压垮——两个极端都错，正确做法是随真实增长按比例投入。
- **e12 归罪团队（F5）**：业务无起色时"合乎逻辑"地把战略错误归罪于团队不够努力，触发"规格更细、批次更大、反馈更迟"的下行循环——人事变动解决不了"计划本身无意义"。

### 作者的盲点 / 时代局限

- 机制根植于丰田制造业与 2000 年代互联网软件语境（持续部署、每天 50 次改动），"停线成本可控"的前提在硬件、强监管、长交付周期行业需重新核算"拉绳"的代价。
- "每个技术问题背后是人的问题"是追因的方向性洞见而非严格因果律：现实中确有纯技术性偶发缺陷，一律追问到人可能造成过度归因与仪式化会议；层级数以"直达人为根源"为准，不必凑满五次。
- 落地依赖心理安全前提（缺席者会变成替罪羊的反面：在场者必须敢说真话）；在问责文化强的组织中，简化双原则只是过渡态，作者自认长期不够用。

### 容易混淆的邻近方法论

- **六西格玛 / 正式 RCA（鱼骨图、8D 报告）**：工业质量领域的正规军，重统计验证与表格化输出；"五个为什么"更轻、直指人的问题并联动按比例投入与速度调节，二者可互补但节奏不同。
- **丰田生产方式（TPS）的安灯本尊**：书中是隐喻迁移——新创企业停的不是流水线而是"发布与迭代"，照搬车间规则（如全员停下等修复）会在软件语境中失真。
- **无指责复盘（blameless postmortem，现代工程实践）**：与"容忍第一次错误"同源，但通常止步于技术归因；本书要求再往下问一层到管理与培训，并以按比例投入把复盘变成组织演化的引擎。
