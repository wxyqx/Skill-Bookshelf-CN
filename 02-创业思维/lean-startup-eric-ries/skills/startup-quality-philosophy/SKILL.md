# 新创企业质量观：尽早发布，但不错待质量

## R — 原文 (Reading)

> "如果我们不知道谁是顾客，我们也不知道什么是质量。"
>
> —【作】埃里克·莱斯，第6章

> "他们接受——甚至更乐意接受一个只完成了八成的作品。你不需要用一个完美的解决方案去俘获他们的兴趣。"
>
> —【作】埃里克·莱斯，第6章

> "任何超出早期使用者需要的额外功能或修饰，都是资源和时间上的浪费。"
>
> —【作】埃里克·莱斯，第6章

> "之前的失败让我们更担心另一种情况：开发出的产品没人要。这要比推出差劲儿的产品更糟糕。因此我们牙一咬心一横，作好道歉的思想准备，面向公众推出了产品。"
>
> —【作】埃里克·莱斯，第3章

> "这是精益生产中最重要的发现之一：不能为了时间牺牲质量。如果你现在引起（或忽视）了质量问题，导致的缺陷将会在之后减慢你的速度。"
>
> —【作】埃里克·莱斯，第11章

## I — 方法论骨架 (Interpretation)

"先把产品做完美再上线"与"糙快点糙发布"是两个都错的极端。本书给出第三条路——一套只属于新创企业的质量观：

1. **质量悖论的根源：不知顾客即不知质量**：现代质量哲学（戴明、六西格玛、精益生产）有个隐含前提——企业已知哪些特质对顾客有价值。新创企业连谁是顾客都不确定，此时执着于"高质量"，等于替想象中的顾客做主。
2. **"低质量"MVP 可以服务于开发高质量产品**：若顾客认为 MVP 低质，应视为了解顾客在意什么品质的机遇，而不是返工指令。低质是实验的必要成本，不是终局品质标准。
3. **尽早发布的真正理由：没人要比差劲更糟**：IMVU 第一版"糟糕透顶、漏洞百出"仍按时收费发布——延期才最危险，因为新创企业将得不到所需的反馈。发布早期版本是把产品当实验的体现；但要区分"在顾客那里实验"与"迎合顾客奇思怪想"——IMVU 并不按顾客建议逐条修改。
4. **早期使用者接受"八成"产品**：他们用想象填补产品不足，在意"第一个用上"，对过度精致反而心存芥蒂。因此任何超出早期使用者需要的额外功能或修饰，都是资源和时间上的浪费——这是很多完美主义者难以接受的真相。
5. **但质量有底线：不能为时间牺牲质量**：这是精益生产最重要的发现之一——现在引入或忽视的质量问题，日后会以返工、顾客投诉的形式减慢速度、蚕食资源。会拖慢开发—测量—认知循环、扰乱学习的缺陷不容纵容。
6. **出路不是折中，而是自适应流程**："做一点点计划"式的折中只会两头不讨好。正确做法是让流程该慢则慢（出现影响学习的缺陷时按比例投入修复），防御收效后再自然加速——质量投入本身是循环内置的速度调控器。

## A1 — 书中的应用 (Past Application)

### 案例 1: IMVU 的 180 天期限与"糟糕透顶"的首发（ch03/引言，主线案例）
- **问题**: 团队定下 180 天发布期限，第一版产品"糟糕透顶、漏洞百出"，存在稳定性问题、随时会让系统崩溃——按传统质量观根本不该见人。
- **方法论的使用**: 之前的失败让团队更怕"开发出的产品没人要"——这比推出差劲产品更糟糕；于是作好道歉的思想准备，面向公众按时推出，且收费。发布后逐月让真实顾客行为揭示真相；同时不迎合顾客的逐条修改建议，而是在顾客那里做实验。
- **结论**: 尽早发布低质版本换来的是战略级真相——原战略被顾客"批得体无完肤"，方向得以彻底修正。
- **结果**: 转型后顾客创造 6000 多万个虚拟人像，2011 年年收入逾 5000 万美元（此长期数据出自引言语境）。

### 案例 2: 桌上美食——"八成"产品与推迟的自动化（ch06）
- **问题**: 团队在奥斯汀杂货店找到第一位顾客时，没有软件、没有协议、没有厨师；按传统标准该怎么起步？
- **方法论的使用**: 贵宾式 MVP——CEO 与产品副总裁每周登门，人工查折扣、选菜谱、递包裹，收 9.95 美元手写支票；把自动化投入刻意推迟到人力服务忙不过来之时。
- **结论**: 传统标准下"效率太烂、毫无规模化"，但超出早期使用者需要的"修饰"（提前写软件）被识别为浪费，而会拖慢学习的服务缺陷（无人服务顾客）不容存在。
- **结果**: 每周都更懂产品如何成功，最终支持全美几千家杂货店，开发浪费远低于同类传统企业。

### 案例 3: SGW 设计公司——快，但不牺牲最终质量（ch09）
- **问题**: 实体产品设计业按传统流程打样周期极长；早期快速迭代会不会注定交付低质产品？
- **方法论的使用**: 用三维打印样机 1 天成像、3 天 CNC 原型、以 5 天为节奏反复迭代"八成"版本收集反馈，再进入正式生产。
- **结论**: 尽早发布与高质量不矛盾——粗糙只存在于过渡形态的实验品上，会拖慢循环的关键质量一项不少。
- **结果**: 3 周半后，40 个完整的第一批产品已准备好交付使用。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队为"要不要做到完美再上线"吵架：一方说再打磨三个月，一方说先发布个糙版本收集反馈。
2. 产品上线后被批评太糙，用户/老板要求返工做精致——不知道哪些质量必须修、哪些是白费劲。
3. 曾经为赶时间裸奔，现在缺陷缠身、越跑越慢；或反过来被完美主义拖到迟迟无法上市。

### 语言信号 (用户的话里出现这些就应激活)

- "要不要做到完美""先做完美再上""八成质量""太糙了怎么办""丢不丢人"
- "尽早发布""先上线再说""质量悖论""MVP 是不是就是粗制滥造"
- "为赶时间牺牲质量""bug 越积越多越跑越慢""返工还是先收集反馈"

### 与相邻 skill 的区分

- 与 `mvp-design-patterns` 的区别：后者管"第一个版本做成**什么形态**"（视频/贵宾/绿野仙踪），本 skill 管"做到**几成质量**"的哲学之争。问"拍视频还是人工跑流程"归前者，问"要不要做完美再上"归本 skill。
- 与 `small-batch-acceleration` 的区别：后者管**发布节奏与批量大小**（批次切多小、换型多快），本 skill 管**每批里的质量取舍**。问"怎么把发布批次切小"归前者，问"这批糙一点行不行"归本 skill。
- 与 `five-whys-adaptive-org` 的区别：缺陷已经发生后的**根因分析与治理流程**归后者；"哪些缺陷该容忍、哪些不容纵容"的**事前取舍**归本 skill。
- 与 `leap-of-faith-assumptions` 的区别："为什么要发布糙版本"的答案在本 skill（尽早获取反馈），"发布出去要**验证什么假设**"归后者。
- 与 `pivot-or-persevere` 的区别：糙版本拿到差评后"要不要换方向"归后者；"差评里哪些是质量问题"归本 skill。

## E — 可执行步骤 (Execution)

1. **先问顾客是谁，再谈质量**：任何"质量够不够"的争论，先检查团队是否已明确当前版本的实验对象（早期使用者）与待验证假设
   - 完成标准：能一句话说出"本版本给谁用、验证什么"；说不出则先回到假设识别，质量争论暂停。
2. **给"八成"划出明确范围**：列出计划砍掉或简化的功能/修饰清单，逐项确认"超出早期使用者需要"
   - 完成标准：一张"故意不做"清单，每项注明省下的理由；团队对"糙在哪里"达成书面共识，避免被误读为偷工减料。
3. **守住质量底线**：从"故意不做"清单中剔除会拖慢循环的质量项——影响学习判断的关键功能、会让顾客无法完成实验的阻断性缺陷
   - 完成标准：清单中每一项都能回答"若缺失，本实验还能不能产生有效数据"；不能回答的移回必做项。
4. **定下发布日期并按时发布**：以"没人要比差劲更糟"为准绳对冲完美主义，作好道歉的思想准备
   - 完成标准：发布日期公开承诺且未被推迟；对早期使用者明示"这是早期版本、欢迎吐槽"的预期管理话术已备好。
5. **把质量投诉路由到正确通道**：顾客说"低质"时先分类——是在意某种品质的信号（机遇，转入验证）？还是拖慢循环的缺陷（按比例投入修复）？还是超需修饰（忽略）
   - 完成标准：每条投诉有三类归属之一；属于缺陷治理的批量问题转 `five-whys-adaptive-org` 做根因分析，不逐条打补丁。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户问的是 MVP **形态选择**（视频/贵宾/绿野仙踪怎么做）——转 `mvp-design-patterns`；问的是**发布批次与节奏**——转 `small-batch-acceleration`；缺陷已批量发生要**根因追责与流程改进**——转 `five-whys-adaptive-org`。
- 产品已过产品/市场契合、进入主流市场运营阶段：此时"八成"哲学不再适用，应回到现代质量哲学的常规要求（书中自限：新创企业质量观只针对极端不确定阶段）。
- 强监管/高风险领域（医疗、金融、安全）的合规性质量：不在"可延后的修饰"之列，须按行业底线执行——本书案例均为互联网软件与轻实验场景。

### 作者在书中警告的失败模式（按家族速查）

- **e17 过度构架与"交友网效应"（F8）**：为防止一切可能问题而过度构架，最终耽误公司推出产品；反向的零设防则被增长压垮（Friendster 前车之鉴）——质量与速度的两个极端都错。
- **e02 Webvan 与 Pets.com（F1）**：先建完整网站、全面涵盖仓储分销再上线——在验证价值假设之前就把"完美"当事实投入的电商先烈。
- **e07 "零的愚勇"（F3）**：以"产品还不够好"为由推迟数据收集，直到确认能成功才见顾客——"再打磨打磨"常常是逃避反馈的体面借口。
- **e06 把"学习"当借口（F3）**："糙是故意的，我们在学习"——没有以真实顾客实证数据为基础的低质发布不构成学习；"你无法把学习拿去银行"。

### 作者的盲点 / 时代局限

- 案例集中于 2000 年代互联网软件业（IMVU 等），"发布即实验"的前提是顾客接触与迭代成本极低；在硬件、长交付周期、强口碑传播的行业，低质首发的品牌损失可能不可逆，书中仅以四大减速路障部分回应。
- "早期使用者接受八成"依赖存在高容忍度的早期使用者群体；直接面向大众一次性体验的产品（低复购、低反馈渠道）难以照搬。
- 作者对"低质"的辩护针对**修饰性**质量，但书中未给出"阻断性缺陷"的定量判定标准，实际操作仍依赖团队按比例投入的自适应判断。

### 容易混淆的邻近方法论

- **六西格玛/戴明质量体系**：同为"质量"话语，但前提是已知顾客与价值定义——适用于已验证后的规模化阶段；在新创阶段套用会诱发过度构架。精益创业质量观是其前置补充而非替代。
- **"快速行动，打破陈规"式糙快文化**：只取了"尽早发布"半句，丢掉了"不为时间牺牲质量"的另一半与自适应减速机制——纯裸奔正是 e17 的"交友网效应"。
- **MVP 被误读为粗制滥造方法论**：MVP 是"每个回合开发过程最低档"，解决的是学习问题，不是终局品质标准；把 MVP 等同于差产品是对本书最常见的讹传。
