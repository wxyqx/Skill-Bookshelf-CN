# 口碑验证三原则：打破信息茧房与刻舟求剑

## R — 原文 (Reading)

> MIUI团队就习惯性地按照以往的操作方式，先发布功能，在手机上市后再通过OTA升级的形式，把这项功能交付给用户。
>
> — 雷军，第六章 七字诀（口碑的反面教训；对象为面向高端商务人群的万元折叠屏 MIX FOLD，上市即口碑受挫）

---

## I — 方法论骨架 (Interpretation)

作者在口碑篇给出了观测口碑的三条纪律，防止管理者被扭曲的反馈误导：

1. **多路交叉验证**：管理者定期下一线（站店、直面用户）；多部门独立监控汇总而非单一部门报数；用 NPS、满意度、第一推荐度等指标量化"沉默的大多数"。要警惕三类失真——官微互动只来自固定核心群、推荐算法制造的茧房、水军刷评。
2. **区分关注点**：核心用户看的是"意见点"（功能细节、参数），大众用户看的是"印象面"（整体认知与档位感）。用核心群的声音代表大众是常见误判。
3. **直面真实口碑**：可怕的不是骂得凶，而是没人骂——无人讨论意味着大众认知尚未成形或阵地已失效；对差评"态度真诚+改善迅速"本身就是口碑建设动作。

配套**阈值律**：口碑=体验−预期，而预期阈值随客群、价位段、行业整体水平不断跳升。过去验证有效的惯例（如"先发布后 OTA"）在新客群的新阈值下就是失误——经营者若不持续更新口碑基准线，就会刻舟求剑。

## A1 — 书中的应用 (Past Application)

### 案例 1: MIX FOLD 刻舟求剑——没做错什么，口碑却崩了
- **问题**: 万元折叠屏 MIX FOLD 面向高端商务人群，团队沿用 MIUI 发烧友时代"先发布、后 OTA 补功能"的成熟惯例。
- **方法论的使用**: 该客群对"开箱即用"的预期阈值与发烧友完全不同——旧惯例在新阈值下构成失误；品控与努力没有变，口碑基准线却已跳变。
- **结论**: 口碑下滑但内部自评"我们没做错什么"，正是阈值漂移未被追踪的典型症状。
- **结果**: 产品上市即口碑受挫，成为书中口碑篇的点名反面教材。

### 案例 2: 社区荒废——组织失去真实口碑信号源
- **问题**: 2015-2016 危机前，小米大量与用户密切沟通的阵地（社区等）被荒废，"用户的很多声音我们听不到了"。
- **方法论的使用**: 违反三原则第一、三条——没有多路观测与直连用户的阵地，产品决策退化为内部视角，问题在内部最后才被察觉。
- **结论**: 用户沟通阵地是口碑验证的基础设施，荒废阵地等于拆掉传感器。
- **结果**: 成为"失速四征兆"之一，2016 年逆转期被列为必须补的课。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新品上市评论区一片好评，决策者想庆祝或据此追加投入——需要先甄别好评来源结构。
2. 差评汹涌、团队沮丧，纠结要不要公关删帖或反击——需要"直面真实口碑"的原则与应对姿势。
3. 口碑在下滑，但内部各部门自评"我们没做错什么"——需要用阈值律检查基准线是否漂移（刻舟求剑）。
4. 高价位/新客群产品沿用旧客群的交付与服务惯例，需要重新核验该客群的预期阈值。

### 语言信号 (用户的话里出现这些就应激活)

- "这些好评是真的吗 / 是不是水军 / feedback authenticity"
- "沉默的大多数怎么听到 / NPS 可信吗"
- "没人骂也没人夸，正常吗"
- "以前这么干都行，现在用户为什么不买账了"

### 与相邻 skill 的区分

- 与 `word-of-mouth-design` 的区别: 本 skill 是事后核验与观测（数据真伪、阈值漂移、差评应对），design 是事前设计与制造超预期。问"怎么做出口碑"归 design，问"这些口碑可不可信"归本 skill。
- 与 `downturn-remediation` 的区别: downturn 处理增长失速的整体组织诊断（四征兆+补课）；本 skill 只做口碑信号这一条的专项核验。社区荒废既是口碑验证基础设施问题也是失速征兆，按用户主诉归属：主诉口碑数据归本 skill，主诉增长失速归 downturn。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **建立多路观测**
   - 布置至少三条独立信息源：管理者一线走访、多部门独立汇总、NPS/满意度/第一推荐度等量化指标。
   - 完成标准: 三类来源的数据相互印证或矛盾点被明确标出。

2. **甄别失真源**
   - 检查好评/差评的来源结构：是否集中于固定核心群？是否存在水军特征（账号、话术、时间分布）？推荐渠道是否制造茧房？
   - 完成标准: 写出好评与差评各自的来源构成，标注可信度。

3. **区分意见点与印象面**
   - 把反馈分成两列：核心用户的功能细节意见（意见点）与大众的整体认知评价（印象面）。
   - 完成标准: 两列清单分开，且明确本次决策依据哪一列。

4. **更新阈值基准线**
   - 对照当前客群、价位段、行业水平重新标定预期基准，检查是否有旧惯例需要废止。
   - 完成标准: 写出当前基准线与过去的差异，列出因阈值跳升而失效的旧做法。
   - 判停条件: 若发现"既没人骂也没人夸"，先解决触达与阵地问题（重建用户直连），再谈口碑评估。

5. **直面口碑并输出动作**
   - 对差评不删不辩，给出"真诚态度+快速改善"的公开响应方案。
   - 完成标准: 每类主要差评有响应口径与改善负责人，改善本身作为口碑动作对外可见。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 产品尚未发布、没有任何用户反馈——此时该做的是口碑设计（word-of-mouth-design）与种子用户验证，不是观测核验。
- 用户要的是舆情监测系统的技术选型或爬虫实现——工具问题，不属本方法论。
- 用户主诉是整体经营失速、增长下滑——归 downturn-remediation 的四征兆诊断。

### 作者在书中警告的失败模式

- **刻舟求剑**（MIX FOLD）: 阈值已跳升而运营仍按旧标准——口碑下滑但内部自评"没做错什么"。
- **被固定核心群绑架**: 官微互动、社区声音只来自少数发烧友，误把意见点当大众印象面，产品方向被少数人带偏。
- **怕骂而回避**: 把差评当公关问题处理，错过"真诚+快速改善本身也是口碑"的正循环机会。

### 作者的盲点 / 时代局限

- **"口碑永远对"是价值宣示**: 书中对口碑自身失真的严肃反例（水军产业、平台操纵、评价体系被刷穿）仅在"警惕"层面带过，缺乏系统性应对方案。
- **验证手段依赖小米特有组织文化**: 管理者站店、全员直面用户等做法植根其参与感文化，书中未讨论无此文化的组织如何落地。
- **NPS/第一推荐度等数据无第三方口径**: 书中引用的口碑指标均出自小米自述，且 2016 年前的失察正是由其自身复盘披露——验证体系的有效性缺乏独立检验。

### 容易混淆的邻近方法论

- 传统舆情监测: 只做采集与告警；本 skill 强调交叉验证、印象面/意见区分与阈值更新，是判断层而非采集层。
- A/B 测试与用户研究: 验证的是功能因果；本 skill 验证的是口碑信号的代表性与真伪。
