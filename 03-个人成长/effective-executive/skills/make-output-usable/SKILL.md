# 交付设计：让专业产出为他人可用

## R — 原文 (Reading)

> "这意思是说，知识分子有责任让别人了解自己。有些专业人员认为，普通人应该并且可以做出努力来理解他们……这真是傲慢的自大。"
>
> — 第3章，L880

> "他们会向机构内部人员（包括他们的上司、下属，特别是其他部门的同事）提出这样的问题：'为便于你为机构做出贡献，你需要我做些什么贡献？需要我在什么时候，以哪种形式，用什么方式来提供这些贡献？'"
>
> — 第3章，L882

> "知识工作者并不生产本身具有效用的产品。……他生产的是知识、创意和信息。这样的产品本身并无用途，只有通过另一位知识工作者，把他的产品当做投入，并转化为另一种产出，它们才具有实际的意义。"
>
> — 第1章，L276

---

## I — 方法论骨架 (Interpretation)

这条方法从知识工作的一条结构性事实出发：知识工作者的产品（构想、信息、观念、分析）本身没有用途，只有被另一位知识工作者当作投入、转化成别的产出，才产生意义。因此，"有没有效"不取决于产出的精良程度，而取决于**下游能不能用**。

德鲁克由此把责任明确归给产出者一方："知识分子有责任让别人了解自己。"把"被理解"推给使用者（"普通人应该努力来理解专家"）被他直斥为傲慢的自大；他已识别的恶果是：专业知识变成卖弄玄虚的手段，工作变成无用。

落地动作是一个四问的交付设计清单——主动向使用者（上司、下属，尤其是其他部门的同事）问清：为便于你做出贡献，你需要我做什么？**什么时候**要？以**哪种形式**？用**什么方式**提供？这四个参数往往与产出者自己的默认习惯差别很大：成本会计会发现自己一目了然的数据，对经理完全陌生；有些数字他自己觉得重要，经营部门却用不上；而别人天天需要的资料，他的报表里反而没有。生物化学家的研究报告应采用临床医师熟悉的语言；政府科学家必须把科学趋势与影响向政策决定人说明。

于是"通才"被重新定义：不是样样都懂的人，而是能把自己的专精领域与整体需要连接起来的专家——知道别人的需要、方向、限度与理解方式，使别人能用上他的成果。

## A1 — 书中的应用 (Past Application)

### 案例 1: 成本会计的四问——一目了然的数字对经理完全陌生

- **问题**: 成本会计人员习惯以本专业的口径提供数据，报表清晰、逻辑自洽，但用不上的人越来越多。
- **方法论的使用**: 如果他向需要这些数字的经理人问那四个问题（你需要我做什么？什么时候？什么形式？什么方式？），就会有三项发现：对他来说一目了然的数据，对经理来说完全陌生；在他看来很重要的数字，经营部门却用不上；而不少别人每天都需要的资料，他的报表里根本没有。
- **结论**: 交付不是"把我知道的写清楚"，而是按使用者的决策场景重新组织。
- **结果**: 书中把它列为"专业人士重视贡献即可发现"的第一例；第 1 章的结构判断是：产品只有被别人当投入才有效用（L276）。

### 案例 2: 生物化学家与临床医师——语言必须换成使用者熟悉的

- **问题**: 制药工厂的生物化学家完成了研究报告，但研究能否发展成新药，要经临床试验才能决定。
- **方法论的使用**: 问了四问之后就会发现：他的研究报告应采用**临床医师熟悉的语言**，而不能采用生物化学的语言。
- **结论**: 决定成果的不是本专业表述的精确度，而是下游能否据此行动——临床试验的执行者是临床医师。
- **结果**: 书中与政府科学家案例并列：后者必须把科学发展趋势及可能影响向政策决定人说明，并打破"科学家不猜测调查结果"的一般禁忌（L888）。

### 案例 3: 公立科研所出版部主任——"为我们写"变成"把我们当成写的对象"

- **问题**: 出版部主任换人：前任不是科学家、文笔平平，继任者是科学家、学术水准高。
- **方法论的使用**: 前任坚持"我能为本所贡献什么"，把交付对象定为外界的年轻科学家，并以他们的用途为成功标准。
- **结论**: 交付设计一旦转向使用者，专业圈子内部的"水准"就不再是唯一评价维度。
- **结果**: 学术水准提高之后，一向阅读该所书刊的科学团体反而停止订阅——"出版的书刊都是'为'我们而写的，而现在的新主任，却把我们当成了写的对象。"（L801）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 数据分析/研究报告/评估报告提交后无人使用，或只在被追问时才被打开。
2. 用户被反馈"太难懂/太专业/太长"，第一反应是"他们水平不够"。
3. 跨部门协作中，用户提供的材料对方用不上、还要二次加工，反复返工。
4. 用户准备一份面向非同行决策者的材料（给管理层、给客户、给政策部门），不确定该用什么语言与形式。
5. 用户是专业人员转管理岗，仍习惯用同行语言对外交付。

### 语言信号 (用户的话里出现这些就应激活)

- "我做的分析没人看"/"nobody reads my reports"
- "他们看不懂/这是他们的水平问题"/"they just don't get it"
- "怎么让业务部门用上我的模型/报告"/"how to make my work usable"
- "交付物该用什么形式"/"what format should I deliver"
- "我讲得很专业，但会议上没人响应"

### 与相邻 skill 的区分

- 与 `contribution-question` 的区别: 那边问"贡献什么"（方向）；这边解决"产出怎么被用上"（交付设计），是专业人员的具体落地。
- 与 `three-domains-of-contribution` 的区别: 后者检查成效的三条线配比；本 skill 只处理交付环节，不涉及价值观与人才。
- 与 `manage-your-boss` 的区别: 那个 skill 专门处理"向上司提建议的陈述顺序与形式"；本 skill 面向所有使用者（含旁系同事与下属），范围更宽，但管理上司的完整版仍以那边为主。
- 与 `results-outside-the-organization` 的区别: 后者是"成果只能在组织外部产生"的定向定律；本 skill 是专业人员把产出交给下游（含内部旁系同事）时的具体交付设计。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **先定"使用者与用途"，再谈内容**
   - 动作: 列出该产出的实际使用者（含旁系同事），并写下他们各自要用它做什么决定/动作；若用户答不出使用者，先补这一项。
   - 完成标准: 每个使用者对应至少一个具体决策或行动。
   - 判停条件: 若确实没有下游使用者（纯存档/纯礼节汇报），不需要本 skill，改为按场合最小化投入。

2. **过四问交付清单**
   - 动作: 逐项问清——需要我做什么贡献？什么时候要？以哪种形式（页数、图表、摘要先行、数据口径）？用什么方式提供（面谈、演示、文档、口头）？
   - 完成标准: 四个参数都有使用者确认过的答案，而不是产出者的默认值。

3. **做语言与口径的翻译检查**
   - 动作: 检查术语（是否同行语言）、口径（是否与使用者现有报表/习惯一致）、重要性与相关性（产出者看重的是否是使用者需要的，使用者需要的现有产出是否缺失）。
   - 完成标准: 至少修正一处"专业语言/错口径/缺项"；对无法翻译的概念给出通俗说明。

4. **附带决策所需的最小结论**
   - 动作: 让产出以"使用者能据此行动"的形式收口（明确结论、影响、可选行动），并把方法与细节收进附录或备询位置。
   - 完成标准: 使用者能只读首段/首页就做出对应决定；细节可追溯。
   - 判停条件: 若使用者需要参与推演过程（如某些法律与管理场景），改为完整推演版，不强行压缩。

5. **复核与共建**
   - 动作: 交付后主动回收"你用它做了什么"的反馈，并把使用者的实际用法固化进下一次的交付模板；参照连锁店式做法，把"落实"变成可抽查的动作而不是一次性说明。
   - 完成标准: 至少一轮使用后的反馈被用来修改模板。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户只是要排版、美化、做 PPT：形式改善可能有用，但不是本 skill 的判据；本 skill 要求先确定使用者与用途。
- 读者是同行评审/学术共同体：那时"同行语言"正是正确选择，误用本 skill 会把专业精确性削成通俗化。
- 组织对信息的拒用源于权力或激励（如部门不愿共享数据）：这不是"翻译"能解决的，须先处理制度与激励（可转 `time-waste-institution-scan` 的信息功能项）。

### 作者在书中警告的失败模式

- **专业人员的傲慢自大**（ce12）: "普通人应该并且可以做出努力来理解他们"是傲慢的自大；这种习气"会毁灭知识，会损害知识的完美和效用"。征兆是报告只有同行看得懂，且认为"看不懂是他们的水平问题"。
- **把交付等同于"写清楚我知道的"**: 四问若缺位，就会出现"我重要的别人用不上、别人需要的我没有"的错配（成本会计案例）。
- **只与同行沟通就满足**: "认为他们只要能够和同行的少数专业人员沟通就够了"——下游断裂，产出作废。

### 作者的盲点 / 时代局限

- **秘书与文员假设**: 书中提到"研究所为了发布研究成果的新闻，得由主持该项研究的高级研究员来撰写新闻稿……如果由别人写，写出来一定文笔流畅"（L629）——把"翻译与润色"当作可委派事务；当代无此支持时，专业人须自己具备或善用工具完成翻译。
- **单向责任反转可能被滥用**: "被理解是产出者的责任"在权力不对等的组织里，可能被上级用来说明"你做得不好是因为你不会讲"；本 skill 的正确用法是把它作为产出者的自律，而不是他人问责的工具。
- **文化语境差异**: 全书假设直接、可质询的沟通氛围；在高语境/等级严格的组织中，"主动问使用者需要什么"可能被视为越界，需先建立提问的许可。
- **证据等级**: 三个专业场景均为举例（成本会计、生物化学家、政府科学家），无实证研究与失败率数据。

### 容易混淆的邻近方法论

- "用户思维/以客户为中心": 方向一致，但德鲁克的特有机制是知识工作的产物结构（必须被当作投入）与**责任归属的反转**，并配四问清单。
- 金字塔原理/结构化表达: 关注表达结构（结论先行、分层论证）；本 skill 关注"交付给谁、何时、何种形式"，结构只是其中一项。
- 设计思维/服务设计: 也强调使用者，但以流程与体验为对象；本 skill 的对象是知识产出的下游可用性。

## 相关 skills

**depends-on**（使用前提）: 无 — 四问交付清单可独立使用；与贡献主题配套时先有方向再设计交付。

**contrasts-with**（同境况二选一）:

- `manage-your-boss` — 同为"让内容被接受"，看对象选入口：对方是上司、要解决"如何提出建议的顺序" → 转那边；对方是平级/客户/下游使用者、要解决"产出怎么被用上" → 用本 skill。
- `correct-before-compromise` — "被接受"问题的两种解法：改交付形式与时机（本 skill）vs 在目标上预支折中（那边）；若方案因"怕不被接受"越改越软，先转那边算清"正确"。

**composes-with**（配合使用/先后接力）:

- `contribution-question` — 先问"贡献什么"定方向，再用本 skill 把产出交付到使用者手里（被理解的责任在提供方）。
