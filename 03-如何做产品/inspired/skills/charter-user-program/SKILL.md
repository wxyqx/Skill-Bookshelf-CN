# 特约用户计划

## R — 原文 (Reading)

> "使用特约用户是确保产品不偏离用户需求最简单有效的办法，同时也是向潜在用户宣传、推荐产品的最佳手段。……如果在寻找特约用户时遇到困难，很可能是因为产品要解决的问题不像产品经理想象的那么重要，将来也很难销售出去。"
>
> — Marty Cagan，第15章《特约用户》

---

## I — 方法论骨架 (Interpretation)

特约用户计划同时解决产品经理的两个老难题：**同时和太多用户打交道不现实**，而**大众又不愿第一个吃螃蟹**——没人推荐的产品，再高明的销售策略作用都有限。解法是在项目之初物色 6 位（大众互联网服务 10~15 位）积极、活跃、乐于分享、在目标用户中有影响力的真实用户，先招 8~10 人再筛选，把他们当开发伙伴对待，合作贯穿研发每个环节：构思创意、试用原型、参加测试、请教细节、帮忙部署测试待发布版本。作为回报，他们的需求会被认真考虑，满意者会在发布后公开向大众推荐。

三条硬约束构成它的身份标签，缺一条性质就变了：**不收费**（收了钱，开发伙伴就变成了客户，你会沦为"为特约用户开发产品"）；**人数绝不超过十个**（再多就没有精力与每位深入沟通，需求收集流于形式）；**必须是真实目标用户而非尝鲜者**（尝鲜者能容忍缺陷，按其需求做出的产品很可能只适合他们自己）。

它还有一个反向用法：**招募这件事本身是产品价值的免费试纸**。招不到特约用户，多半说明产品要解决的问题没有你以为的那么重要——这完成了产品创意价值的初步验证，应该重新考虑产品计划，而不是降低标准凑数。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 二十年前惠普的实践
- **问题**: 既想深入洞察目标用户的需求，又想赢得用户对产品的公开推荐，怎么办？
- **方法论的使用**: 项目之初物色至少六位积极、有影响力的目标用户（先招 8~10 人再筛选），作为开发伙伴全程参与——展示原型、参加测试、请教细节、部署测试版本。
- **结论**: "这不是什么新方法，我二十年前就在惠普用过"——它是被验证过二十年的老办法，不是新发明。
- **结果**: 正式发布前特约用户全部满意，发布后坚定地向大众推荐；许多人结下深厚持久的友谊。

### 案例 2: 招不到特约用户＝需求不成立
- **问题**: 寻找特约用户时遇到困难、招募反应冷淡，该不该降低标准继续凑数？
- **方法论的使用**: 不降标准，把招募结果本身当验证信号来读。
- **结论**: "很可能是因为产品要解决的问题不像产品经理想象的那么重要，将来也很难销售出去"——这可以初步验证产品创意是否有价值。
- **结果**: 出现这种情况，产品经理应该重新考虑产品计划；招募困难免费地救下了整个项目。

### 案例 3: 发布前的满意度门禁
- **问题**: 特约用户参与了全程，怎么把"参与"兑换成发布后看得见的口碑？
- **方法论的使用**: 正式发布前先请每位特约用户试用，逐一确认每个人都满意，再发布。
- **结论**: "一旦发布，他们会坚定不移地向大众推荐产品。"
- **结果**: 大众对无人问津的产品非常谨慎；知名用户的公开推荐大大降低潜在用户的顾虑，发布因此事半功倍。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新产品/新功能要启动，想在定义阶段就有真实目标用户参与，而不是开发完再找反馈。
2. 发布前发现产品缺社会证明：没有用户愿意第一个吃螃蟹，担心发布无人问津。
3. 发帖招募试用用户，报名寥寥或没人报名，想判断这说明什么。
4. 销售部门要求把特约用户扩编到几十人，或要求向用户收费。
5. 分不清报名者是目标用户还是产品尝鲜者，担心按他们的反馈做偏产品。

### 语言信号 (用户的话里出现这些就应激活)

- "想找一批种子用户 / 内测用户 / 体验官"
- "发布前有没有办法让用户深度参与？"
- "招试用用户没人报名，是不是需求不行？"
- "销售想让我们多招点顾问用户，还能收费"
- "charter user program" / "user advisory board" / "target users as partners"

### 与相邻 skill 的区分

- 与 `prototype-testing-playbook` 的区别：特约用户是常设的开发伙伴，也是物色测试者的第一渠道；单场测试怎么招人怎么主持，交给后者——两者是" reservoir 与单场测试"的关系。
- 与 `persona-driven-focus` 的区别：人物角色是抽象出的虚拟典型，用来筛选功能、决定谁不是目标用户；特约用户是真实的人，用来共创、验证与背书。
- 与 `special-product-defense` 的区别：特约用户的需求"会被认真考虑"，但产品始终是面向大众的通用产品——必须向特约用户讲明这一点；一旦反过来为某一家定制，就滑向特例产品。
- 与 `irrational-user-signals` 的区别：那边解释为什么尝鲜者/技术爱好者的需求清单不能优先；本 skill 给出制度化的排除动作——物色阶段就确认"产品的潜在目标用户"身份。

## E — 可执行步骤 (Execution)

1. **项目启动时物色并筛选**：目标 6 位（互联网服务 10~15 位），积极、活跃、乐于分享、在目标用户中有影响力；先招 8~10 人再筛；逐一确认是"产品的潜在目标用户"而非尝鲜者；讲明这是大众通用产品并承诺不昙花一现；不收任何费用。
   - 完成标准：6 位目标用户确认参与，理解自己"开发伙伴"的身份与产品的通用性承诺。
   - 判停条件：招募困难——视为产品价值的免费验证，重新考虑产品计划，而不是降低标准或加钱凑数。
2. **让合作贯穿研发全程**：每轮迭代向他们展示原型、请其参加测试、请教细节问题、请其帮助部署测试待发布版本；定期组织小组讨论；人数绝不超过十个，销售要求扩编时用发布预览版承接心急的用户。
   - 完成标准：每位特约用户在每轮迭代都有具体的反馈记录；产品经理与每位都有过深度沟通。
   - 判停条件：合作关系变味——发现自己开始"为某一家开发产品"，或人数失控无暇深谈；立即收缩人数并重申大众产品承诺，必要时重选人选。
3. **发布前的满意度门禁**：正式发布前请每位特约用户试用，确保每个人都满意；发布后邀请他们公开推荐（署名评价、案例、向同行引荐）。
   - 完成标准：六位全部表示满意；至少落实一条公开推荐的渠道。
   - 判停条件：有特约用户不满意——优先解决其问题再发布，不绕过门禁硬上，否则口碑引擎反噬。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 想直接从特约用户手里拿"需求清单"：他们不能直接给出产品需求，只能帮助产品经理确定产品需求。
- 付费 beta、人数越多越好、把名单当销售线索池：三者都违反硬约束，性质立刻从"伙伴"变成"客户"。
- 纯营销造势的"用户体验官"称号：只发奖不共创，是市场活动，不是开发伙伴关系。
- 公司禁止产品经理接触用户又不愿改变政策：先解决授权问题，否则任何用户计划都是空转（作者的建议是"另谋高就"）。

### 作者在书中警告的失败模式

- 向特约用户收取参与费用——"合作关系将会变味"，你变成"为特约用户开发产品"。
- 应销售部门要求无限扩编——人数超过十个，没有精力与每位深入沟通，且这些用户不一定符合要求。
- 把产品尝鲜者误当成特约用户——他们能容忍缺陷，按其建议研发的产品很可能只适合他们自己，无法满足大众。
- 不向特约用户说明这是面向大众的通用产品，被个别需求拖成定制开发。

### 作者的盲点 / 时代局限

- "6~10 人"的硬约束来自产品经理个人精力的时代前提；今天有社区工具辅助管理，但"与每位深入沟通"的时间约束没有变——约束的本质是沟通深度而非工具，放宽人数仍是自欺。
- 书中的物色渠道是邮件列表、网站征集与展销会；社交媒体时代可以公开建社区，但公开社区极易混入尝鲜者，电话筛选与身份确认比 2008 年更重要。
- "招不到＝需求不成立"的判据在 ToB 长销售周期、强关系市场可能失灵——招募难可能来自人脉壁垒而非需求弱，此时应换渠道验证而非直接判死。

### 容易混淆的邻近方法论

- 一年开两次意见会的"用户顾问委员会"：作者允许组织小组讨论，但特约用户的核心是全程参与研发，不是定期听取抱怨。
- 种子用户／内测名单：数量导向、营销导向；特约用户质量导向、开发伙伴导向，人数恰恰要少。
- 大客户的 advisory board：企业销售里的客户委员会常绑定采购意向，容易滑向为单一客户定制——用 special-product-defense 划界。
