# 机会评估十问

## R — 原文 (Reading)

> "评估产品机会的目的在于：淘汰馊主意，避免浪费时间和金钱；挑选合适的产品机会，团结团队，理解产品，整合资源。……产品经理往往把待解决的问题和解决方案放在一起考虑，当具体解决方案遇到困难时，他们会放弃产品机会。这是典型的'把洗澡水和孩子一起泼掉'的做法。"
>
> — Marty Cagan，第11章《评估产品机会》

---

## I — 方法论骨架 (Interpretation)

一个产品想法出现在你面前时，最常见的死法不是"做砸了"，而是**没问过"要不要做"就直接开始想"怎么做"**。这套方法把立项决策压缩成十个问题：①产品要解决什么问题（产品价值）②为谁解决（目标市场）③成功的机会有多大（市场规模）④怎么判断成功（度量指标）⑤有哪些同类产品（竞争格局）⑥为什么我们最适合做 ⑦时机合适吗 ⑧怎么推向市场（营销组合）⑨成功的必要条件是什么 ⑩综合给出"继续或放弃"的结论。

两条铁律让它区别于普通的可行性报告。第一，**十问全部只问问题，不碰解决方案**——一旦混入方案讨论，方案做不下去时你会连机会一起扔掉；第二，**第一问最难也最致命**：多数产品经理被问到"要解决什么问题"时，只能泛泛报出一堆功能和特色，答非所问。十问答完，要么淘汰一个馊主意（这是成功，不是失败），要么带着明确的目标与度量指标进入探索。

## A1 — 书中的应用 (Past Application)

### 案例 1: CEO 硬塞的项目也要过十问
- **问题**: 如果 CEO 说"不管你愿不愿意，这个都必须做"，评估还有意义吗？
- **方法论的使用**: 迅速照常跑完十问。
- **结论**: 即使改变不了 CEO 的决定，"至少你能明确产品目标，大大提高产品成功的可能性"。
- **结果**: 作者把它作为机会评估的兜底用法——评估的产出（目标与指标）在任何决策下都有价值。

### 案例 2: 9% 注册成功率翻倍
- **问题**: 该投人力做全新产品，还是打磨现有产品？
- **方法论的使用**: 把两者都当成"产品机会"用同一套标准比较收益与成本。
- **结论**: "100 位打算注册使用的用户最后只有 9 人顺利完成注册，如果设法把人数提高到 18，就能让产品的收益翻倍"——好机会常在眼皮底下，完善蹩脚的现有特性往往事半功倍。
- **结果**: 每当作者指出这类机会并帮公司实现，"都会被看做英雄"；而公司往往因自负看不见它。

### 案例 3: 借财务同事确认商业可行性
- **问题**: 十问里的市场规模与收益模式，产品经理自己估不准怎么办？
- **方法论的使用**: 让 CFO 引荐一位财务同事，请他分析投入是否划算、提供交易记录与客户数据。
- **结论**: "我曾经问财务部的朋友，为什么其他人不知道这样的机会？他回答说，因为没有人问过他。"
- **结果**: 财务数据里藏着绝佳的产品机会，且讨论可行性时能得到财务背书。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 有人（老板/客户/同事/自己）提出一个产品想法，要决定"做不做"。
2. 准备写市场需求文档（MRD）或立项报告，想要比 MRD 更快的替代。
3. 团队为"这个想法靠不靠谱"争论，缺乏共同的评估框架。
4. 要在新产品机会与打磨现有产品之间分配资源。
5. 被动接下"必须做"的项目，想把它拉回有目标、有指标的正轨。

### 语言信号 (用户的话里出现这些就应激活)

- "这个想法/需求值不值得做？""要不要立项？"
- "帮我把把关，这个机会怎么样"
- "写个 MRD / 机会评估 / 立项分析"
- "should we build this?" / "is this worth pursuing?"
- "老板让我做 X，我觉得不靠谱，怎么论证？"

### 与相邻 skill 的区分

- 与 `user-research-limits` 的区别：那是"调研数据能不能当需求"的证据法；本 skill 是拿到任何想法后的**立项过滤闸门**，先于一切调研与设计。
- 与 `discovery-execution-two-modes` 的区别：本 skill 决定"要不要进入探索"；后者管探索与开发两阶段怎么切换。
- 与 `special-product-defense` 的区别：大客户带着"七个功能"来的，先用本 skill 的第①问问"他到底要解决什么问题"；确定是定制化勒索时切换到 `special-product-defense`。

## E — 可执行步骤 (Execution)

1. **逼问第一问：产品要解决什么问题？**
   - 完成标准：得到一句"谁的什么麻烦"，而不是任何功能/特色/技术名词；若答不出，直接给出"放弃或重述机会"的建议。
2. **依次回答第②–⑨问**（目标市场→市场规模→度量指标→竞争格局→为什么是我们→时机→营销组合→必要条件）。
   - 完成标准：每问有具体答案，规模估算"务必谨慎，避免浮夸，不是所有产品都有十亿美元的市场"；必要条件描述的是依赖与约束（如渠道商对扩展性的要求），不是功能清单。
   - 判停条件：第①问答不出或第④问（度量指标）定义不出——结论即为"放弃"，无需走完全部十问。
3. **写出结论并明确下一步**：继续 / 放弃；若继续，交付物是"待解决的问题 + 成功指标"，明确声明"解决方案另行探索"。
   - 完成标准：结论呈报决策者（高管/评审团），并约定探索阶段的出口标准（与 `product-validation-trio` 衔接）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 解决方案已定型后的"事后论证"——十问的前提是方案未定；带着方案填十问，等于把洗澡水和孩子一起泼掉。
- 纯执行类问题（排期、人手、技术选型）——十问不回答"怎么做"。
- 日常微小迭代（文案、按钮）——过十问的成本高于收益，用 `metric-driven-improvement` 的指标检验即可。

### 作者在书中警告的失败模式

- 跳过机会评估，"只要大客户提出要求，项目就直接上马"（第11章）。
- 把市场需求文档误写成产品规范文档，或写完束之高阁不闻不问。
- 市场规模评估浮夸——"不是所有产品都有十亿美元的市场"。

### 作者的盲点 / 时代局限

- 作者的十问经验来自 2008 年前的硅谷互联网产品；对平台型、AI 型机会（技术不确定性主导）与长销售周期 ToB，第⑦问"时机"与第⑤问"竞争格局"需补充现代分析维度。
- 作者推崇的机会评估取代 MRD，在强合规行业（金融、医疗）可能仍需正式文档外壳。

### 容易混淆的邻近方法论

- 商业计划书 / 精益画布：本 skill 只过滤机会，不经营模式画布的全景。
- 需求评审会：评审的是方案质量；本 skill 判断的是机会价值，先后不可颠倒。

## 相关 skills

- **composes-with** `discovery-execution-two-modes`：十问裁决"要不要进入探索"，两阶段切换接着管探索期怎么运转——同一条流水线的上下游两节。
- **composes-with** `user-research-limits`：十问做价值判断，调研收集事实（谁在用、怎么用）——立项评估以调研为输入，但调研不能代替第一问。
- **composes-with** `new-old-thing`：十问第⑤问回答"市场里已有什么"，新瓶装老酒回答"巨头环伺时凭什么还能进"——评估之后的进攻性后续。
- **contrasts-with** `special-product-defense`：同样面对"要不要接"，十问过滤机会本身的价值，特例防御拦截"有收入但会把公司带偏"的定制化勒索。
