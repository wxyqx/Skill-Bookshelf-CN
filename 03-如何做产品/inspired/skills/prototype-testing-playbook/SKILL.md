# 原型测试操作法

## R — 原文 (Reading)

> "用户如果知道自己想要什么，设计产品就不会这么麻烦了。所以应该多观察用户的操作，少听他们的抱怨。……如果有连续六位测试者理解和欣赏产品的价值，而且能完成关键的测试项目，就算完成了原型测试任务。"
>
> — Marty Cagan，第22章《原型测试》

---

## I — 方法论骨架 (Interpretation)

原型测试回答的问题是：**怎么把产品创意呈现给真实用户**。作者把它拆成三段流水线——物色测试者、准备与主持、判停与更新——并断言让真实用户验证产品设计是产品经理最重要的工作：没有预算外包不是借口，测试十位用户一两万美元的门槛可以用亲手做来打破。

贯穿全程的一条主轴是**观察重于询问**。测试者嘴上的"这里加个 XX 就好了"不可信——用户如果知道自己想要什么，设计产品就不会这么麻烦；真正有效的信号是他们能否完成任务、卡在哪里、是否欣赏产品价值、肢体语言和语气如何。所以测试的重心是操作行为，不是意见收集。

几条可执行的独门纪律把"多观察少引导"落成动作：开场五分钟还没开始测试就是话太多；先声明被测的是原型不是测试者，他才敢说真话；保持缄默，用鹦鹉技巧（口述其动作、重复其问题）代替引导与"好极了"式的价值判断；两三位用户反映同一问题就动手改；连续六位理解并欣赏价值、能完成关键项目即宣告测试结束；反过来，无法让测试者产生兴趣就立马收手放弃创意——收手是在为公司省钱，不是承认失败。

## A1 — 书中的应用 (Past Application)

### 案例 1: 星巴克餐桌上的测试
- **问题**: 没有带单向透明镜和摄像机的专业实验室，能不能自己开展原型测试？
- **方法论的使用**: 星巴克餐桌——一张放得下笔记本电脑的桌子加几把椅子，就地测试。
- **结论**: "从某种意义上讲，这比专业实验室更好，因为测试者更放松，回答问题更坦诚和开放。"
- **结果**: 破除"测试必须外包、必须有实验室"的门槛迷思，产品经理可以随时随地进行。

### 案例 2: 鹦鹉技巧替代引导
- **问题**: 测试者安静不动或卡住求助时，怎么帮而不变成引导？
- **方法论的使用**: 像鹦鹉一样自言自语——口述测试者正在做的事（"我看见你在浏览右侧的列表"）；被求助时把他的问题重复回去反问（"点击这里会不会创建新条目？"）；想说"好极了"时改口说"你创建了一个新条目"。
- **结论**: 既避免引导用户，又避免诱导性的价值判断。
- **结果**: 测试者继续尝试自己的想法并给出答案；主持人的复述还能帮记录员记下测试要点。

### 案例 3: 两三人动手、连续六位收工
- **问题**: 要不要等 6~8 位测试者完整测完一轮才下结论？测试何时算结束？
- **方法论的使用**: 对反馈迅速响应——只要两三位测试者反映同一情况就动手解决；判停则看是否有连续六位理解并欣赏产品价值、能完成关键测试项目。
- **结论**: "你不用等到连续受到八位用户的打击后，才意识到需要解决问题。"
- **结果**: 显著加快完善产品的速度；无法让人产生兴趣时立马收手，"为公司省下了一大笔成本"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 原型做出来了，要拿给真实用户测，但公司没预算外包用户研究。
2. 要自己主持测试，担心提问方式带偏测试者、测出"假反馈"。
3. 拿不准要测多少位用户、什么时候才能停下来改原型。
4. 测试者全程在点评"该加什么功能"，不知道这些口头需求该不该记下来做。
5. 几轮测下来用户始终不感兴趣，纠结要不要放弃这个产品创意。

### 语言信号 (用户的话里出现这些就应激活)

- "帮我们设计一下可用性测试 / 用户测试流程"
- "测试者净提功能建议，感觉被带偏了"
- "要找多少个用户测才算数？"
- "要不要继续做下去，测了也没人喜欢"
- "usability testing" / "prototype testing" / "parrot technique" / "how many test users"

### 与相邻 skill 的区分

- 与 `product-validation-trio` 的区别：三验证是考试大纲（测价值、可用性、可行性，且都在写代码前）；本 skill 是考场操作手册（怎么招人、怎么主持、何时停）——不含可行性测试。
- 与 `hi-fi-prototype-as-spec` 的区别：那里定义原型作为文档的形态与纪律；本 skill 假定原型已就绪，管测试全程的操作。
- 与 `charter-user-program` 的区别：特约用户是全程参与的 6~10 位开发伙伴，物色测试者的第一渠道；原型测试者是按次招募、用完即散的普通目标用户——前者管关系，本 skill 管单场操作。
- 与 `user-research-limits` 的区别：那支讲"为什么问卷与访谈定义不出产品"的边界论证；本 skill 给出替代动作——亲手把原型放到用户面前观察操作。

## E — 可执行步骤 (Execution)

1. **物色并邀约测试者**：渠道按序取用——特约用户、企业产品的展销会、分类信息网站征召、亲友（避开过近者与科技从业者）、用户邮件列表、公司网站征集、去用户聚集的场所、上门测试；电话逐个筛选，避免全是尝鲜者；测试前一天致电提醒。
   - 完成标准：落实 3 位以上符合目标用户画像的测试者并确认到场；前一天致电把约 30% 的爽约率压到 5%~10%。
   - 判停条件：应征者全是尝鲜者、公司同事或过于亲密的亲友——推倒重来，不将就。
2. **准备并主持测试**：拟定主要测试项目与打分问题（0~10 分/NPS/愿付多少钱）；先给空白浏览器看测试者原会如何解决该问题，再看其能否从首页读出产品价值；寒暄后声明"被测的是原型不是你"；保持安静，用鹦鹉技巧应对求助与沉默；遇死胡同问"接下来希望发生什么"。
   - 完成标准：每位测试者的关键任务结果（顺利完成／反复尝试后完成／受挫放弃）与各题打分都有记录；全程未出现引导性提问。
   - 判停条件：发现自己在帮测试者解围或不停让他"说说想做什么"——立即闭嘴回到鹦鹉技巧；五分钟还没开始测试就是话太多。
3. **判停与更新原型**：两三位测试者反映同一问题就动手改；连续六位理解并欣赏产品价值、能完成关键项目即宣告测试结束；无法让任何人产生兴趣或无法让原型简单易用，则放弃该创意。
   - 完成标准：缺陷清单转化成原型修改并进入下一轮；或形成书面的"放弃该产品创意"结论与理由。
   - 判停条件：连续六位仍未欣赏价值——立马收手；这为公司省下一大笔成本，不算失败。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 可行性测试：那是请架构师和开发人员评估技术方案、寻找难以克服的障碍，不找用户。
- 定价研究、市场容量测算：问卷与数据分析的事，原型测试回答不了。
- 没打算根据结果改原型的"交作业式"测试：测了不改，浪费所有参与者的时间。
- 把测试开成设计评审会：测试者点评元素好看难看属于跑题，不是测试产出。

### 作者在书中警告的失败模式

- 误导性提问（"你觉得页面上哪三个元素该换掉"）让测试者陷入吹毛求疵的状态（第22章）。
- 事前与测试者聊太多，泄露产品线索，测不出第一印象——五分钟还没开始测试就是话太多。
- 克制不住帮测试者解围的冲动，无法习惯缄默，测出的是"被搀扶的假通过"。
- 征集来的全是产品尝鲜者，或用公司同事、过于亲密的亲友凑数——其需求不代表大众。
- 不愿承认失败，明知无人感兴趣仍硬着头皮开发——作者的立场是及时收手在为公司省钱。

### 作者的盲点 / 时代局限

- 2008 年的远程测试工具"无法观察用户的表情和肢体动作"，作者由此断言面对面测试不可替代；今天视频会议加屏幕录制能捕捉大部分非语言信号，但"测试越多越好、观察重于询问"的原则不变。
- 书中场景以网页产品为主，测试动作是滚动、点击、搜索；移动端手势与对话式 AI 界面没有这些可观察动作，鹦鹉技巧需改造成口述用户当前任务，判停标准仍可用。
- 奖励标准（五十美元购物券、印标志的帽子）是美元与 2008 年的行情，照搬需按当地语境换算，"补偿时间损失但不诱导"的原则才是本体。

### 容易混淆的邻近方法论

- 焦点小组／用户研讨会：一群人互相影响、听大家怎么说；原型测试是一对一观察怎么做——群体互动失真是作者批评过的调研弊端。
- 外包可用性测试公司：十位用户一两万美元，且第三方收集的结果会遗漏细微的犹豫与困惑；本 skill 的立场是产品经理亲手做，即使外包也要亲临现场。
- A/B 测试与产品使用分析：需要已上线的真实流量；原型测试发生在写代码之前，两者是探索期与运行期的分工。
