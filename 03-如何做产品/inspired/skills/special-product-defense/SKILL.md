# 特例产品防御（说"不"的框架）

## R — 原文 (Reading)

> "特例产品到底有什么问题呢?它混淆了客户需求和产品需求，必然会使公司偏离正轨。……因为产品经理的任务是满足大众的需求——这是产品公司和定制软件公司的区别。如果一年之后市场需求发生变化，产品必须快速应对。签订合约后，产品就被合同绑住了，难以应变。"
>
> — Marty Cagan，第32章《提防有特殊要求的产品》

---

## I — 方法论骨架 (Interpretation)

销售拎着大单走进来：客户答应签七位数合同，条件是首页改成他们的布局；或者大客户放话，加上七项功能就在合同上签字。钱是真的，理由看起来也站得住——公司缺资金，CEO 妥协情有可原。作者把这类"有特殊要求的产品"定义为必须抵制的陷阱，诊断分三层。

第一层，产品需求不能用户说了算：用户在见到产品之前很难知道自己要什么；用户不知道什么在当前技术条件下可行；用户之间缺少沟通，需求难以统一。第二层，就算这单没问题，添加特殊功能会挤占更重要的工作，长远损失不是这笔收入填得回来的。第三层是本质：产品公司的任务是满足大众需求，接特例等于改行做定制软件商——合同一签，产品被绑住，市场需求变化时动弹不得，每个版本的开发、测试、发布、维护、文档、技术支持链条会把公司拖垮。网络广告版的特例同理：以牺牲长远信誉换短期访问流量，不划算。

防御靠制度而非勇气：事先立好产品原则，关键时刻按原则决定接不接；与客户一起梳理需求本质——多数用户其实更喜欢通用产品（兼容性、数据移植性、改进速度、技术支持都更好）；实在要满足定制，让系统集成商或解决方案供应商投标承接，同时统一对客户的接口。

## A1 — 书中的应用 (Past Application)

### 案例 1: 七位数广告合同换改版
- **问题**: 广告销售提议——同意修改布局、整合站点，合作伙伴就签七位数合同。接不接？
- **方法论的使用**: 先识别这是特例产品的典型场景，再检查广告与网站服务目标是否一致。
- **结论**: 大部分广告商的目标是把你的流量转移到他们的网站，盲目放置广告多半与自己的业务冲突，"以牺牲长远的信誉为代价换取短期的访问流量，实在是不划算"。
- **结果**: 拒绝该形式；确有合作空间时改用共赢方式——制定合理的营销策略、清晰描绘广告商的作用，"他们和你一样迫切需要更好的营销手段"。

### 案例 2: "加七项功能，否则不买"
- **问题**: 销售代表向 CEO 转达客户提议：产品增加七项功能，否则拒绝购买。这种情况企业软件公司和大众网络公司都遇到过。
- **方法论的使用**: 走三层诊断——需求不能用户说了算的三条理由、精力错配、被合同绑死的大众需求使命；再对照第38章的极端版本：客户支票已备好，"一旦妥协，你就变成了定制软件商，开发出来的产品无法被广泛应用"。
- **结论**: 客户拿到产品后没准会发现"这不是他们想要的"；必须坚持原则才能拒绝特例产品的诱惑，对急需资金的小公司尤其如此。
- **结果**: 开发满足广大用户需求的产品始终是首要任务——拒绝七项功能，转而与客户梳理需求本质、提供通用方案。

### 案例 3: 用产品原则拒绝
- **问题**: 每来一个特殊要求都吵一轮，拒绝成本太高也难服众，怎么办？
- **方法论的使用**: 事先根据企业文化树立产品原则，关键时刻按原则裁决。某电影网站的原则是"社区用户的影评比专业人士的影评更有价值"。
- **结论**: 制片厂希望借网站发表评论时，团队援引这条原则即可直接决定，无需逐次争论。
- **结果**: 产品原则成为特例防御的前置条件——先有原则，才有说"不"的依据（第32章明确指向第13章）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 销售带着大额合同和一张定制功能清单进会议室。
2. 广告主/合作伙伴要求改首页布局、整合站点、调整信息架构。
3. 公司现金流紧张，CEO 想接一笔定制项目"先活下来"。
4. 大客户续约谈判，条件是"给我们单独做 X 功能"。
5. 评审会上争论"这个客户很大，能不能为他开个特例"。

### 语言信号 (用户的话里出现这些就应激活)

- "客户答应签了，但要我们先改 XX"
- "这个单子七位数/大几百万，加几个功能而已"
- "大客户要求 / 定制需求 / 特殊处理一下"
- "specials" / "customization request" / "big customer demands" / "seven-figure deal"
- "先接下来，以后再产品化"

### 与相邻 skill 的区分

- 与 `opportunity-assessment-ten-questions` 的区别：那个是立项第一闸门，判断机会本身值不值得做；本 skill 处理"看起来有收入、但会把公司带偏"的诱惑。客户带着要求来，先用十问第①问问"他到底要解决什么问题"，确认是定制化勒索后切换到本 skill。
- 与 `product-principles-priority` 的区别：那个管怎么制定产品原则；本 skill 是原则的消费场景——关键时刻按原则拒绝。公司还没有成文原则时，先回那个 skill 补课，否则拒绝只剩"老板拍板"。
- 与 `persona-driven-focus` 的区别：人物角色在产品内部砍"只服务山姆的功能"；本 skill 防御的是外部合同压力把产品拖向单一大客户，两者常在同一场会上先后出现。
- 与 `minimal-product-definition` 的区别：基本产品管版本内的功能完整性（不砍）；本 skill 管产品方向不被合同买走（不拐）——一个对内，一个对外。

## E — 可执行步骤 (Execution)

1. **定性：客户需求还是产品需求？** 把对方的要求翻译回"他要解决什么问题"，检查这个问题是否已在通用产品中出现。
   - 完成标准：得到一句问题陈述（不是方案描述）；明确判断该要求属于"本质需求"还是"预设方案"。
   - 判停条件：若本质需求确实是大众需求（多个客户/人物角色都提过），转回正常需求池评估（衔接 `opportunity-assessment-ten-questions`），不按特例处理。
2. **对照产品原则给出结论**：接、不接、还是有条件接。
   - 完成标准：结论明确引用具体原则条目；若公司没有成文原则，本轮先按"满足大众需求"这条底线判断，并立刻启动原则制定（衔接 `product-principles-priority`）。
3. **为拒绝配上替代路径**：与客户梳理需求本质、提供更合理的通用方案；或保持产品通用用途，让系统集成商/解决方案供应商投标承接定制，统一对客户的接口；广告类合作改为共赢方式。
   - 完成标准：给客户与销售的答复中至少包含一条替代路径；若最终拒绝，能向 CEO 呈现代价清单（被合同绑住难以应变、每版本数月的全链路成本、偏离大众需求使命）。
   - 判停条件：CEO 已在资金压力下拍板妥协时——按第32章，此事决定权在 CEO，产品经理的职责转为协助决策、记录风险并设计损害最小的执行方式，不越权对抗。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 你本来就在定制软件公司——为特定客户提供专用解决方案是它的本业，作者明确表示并非贬低这一行（第32章）。
- 产品化的可配置能力设计——把配置、自定义、集成做进产品（Salesforce.com 式做法，第38章）是产品能力，与接代码级特例是两回事。
- 平台产品对应用供应商的接口与扩展诉求——那是平台形态的一部分（第39章），不是特例。

### 作者在书中警告的失败模式

- "只要大客户提出要求，项目就直接上马"——跳过机会评估的典型诱饵（第11章）。
- 特例产品是劣质收益：它会降低用户满意度，拉低 NPS（第7章）。
- 一旦妥协，"你就变成了定制软件商，开发出来的产品无法被广泛应用"——客户拿到产品后没准发现这并不是他们想要的（第38章）。
- 网络广告与网站服务目标不一致，严重破坏用户体验——牺牲长远信誉换短期流量（第32章）。

### 作者的盲点 / 时代局限

- 经验来自 2008 年前的 eBay/网景式产品公司；现代 SaaS 的元数据驱动配置让部分"定制"可以产品化收敛，特例与产品化的边界比当年模糊——第38章作者自己也承认配置/自定义/集成可以做得更完善，判断时别机械套用"一律拒绝"。
- 对资金链将断的初创公司，作者只说"对急需资金的小公司尤其要坚持"，没有给出濒死情境下的权衡框架——现实中"接单养产品"是常见的过渡策略，代价是自觉设定期限与退出条件（此点超出书中内容，使用时须自行补充）。
- 书中假设产品原则能约束 CEO；组织现实里，若 CEO 本身销售驱动，防御首先是个治理问题，不只是方法问题。

### 容易混淆的邻近方法论

- 客户成功/大客户管理：AM 的职责是让客户用好产品，不是替产品部门接特例；把客户成功的诉求导回通用产品路线才是正解。
- 企业服务的可配置性设计：把高频定制需求抽象成产品能力是进化，接一次性定制是退化——判据是"是否仍满足大众需求"。
- 战略客户共创：有原则约束、双向投入、共赢设计的深度合作（第32章末尾承认其存在）与单向勒索式的特殊要求是两回事。

## 相关 skills

- **depends-on** `product-principles-priority`：拒绝特例的依据来自事先排序的产品原则——公司没有成文原则时，防御只剩"老板拍板"，先回那个 skill 补课。
- **contrasts-with** `opportunity-assessment-ten-questions`：同样面对"要不要做"——十问过滤机会本身的价值，本 skill 拦截"有收入但会把公司带偏"的定制化诱惑；先用十问第①问定性，再决定是否切换。
