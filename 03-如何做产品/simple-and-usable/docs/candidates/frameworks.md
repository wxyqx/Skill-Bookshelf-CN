  type: mental-model

  source_quote: |
    "最大的一个用户群体是主流用户。他们自己不会因为你的技术而使用你的产品，使用你产品的目的是完成某项任务。""主流用户占绝对的主体地位，专家型和随意型用户只是少数派。"（第2章"三种用户"）
  summary: |

    关键推论：用户类型标签不随使用年限升级（用了5年Excel的人多数只会求和）；对技术的态度比使用时长更有解释力；主流用户占绝对主体（专业相机仅占9%销量）。
    为什么有效：它给"为谁设计"提供了可判定的立场——感觉简单的体验正是主流用户喜爱的体验。
    用法：需求争论时先问"这是哪类用户的声音"，为主流用户设计、敢于忽略专家噪音。

  title: "然后呢"追问法（从掌控感到感情需求）
  type: reasoning-method
  source_chapter: 第2章
  source_quote: |
    "用户需要感觉自己掌控着自己的生活——从这种需求出发，还应该更进一步问：'然后呢？'""像这样反复问自己'然后呢'，最终会发现用户的感情需求、合理需求，直至解决方案。"（第2章"简单意味着控制"）

    为什么有效：表层的功能诉求（任务列表+复选框）之下是感情需求（一切尽在掌握、轻松自在）；Things 应用正是靠回答这一层脱颖而出。
    用法：对任何用户需求连问几轮"然后呢"，挖到感情需求与隐性需求为止，再与真实用户验证。

  type: decision-framework
  source_chapter: 第2章
  source_quote: |
    "要想简单，务必把目标定得高些再高些，不要使用常规的可用性目标。""争取你不可能达成的目标有一个重要的好处：保持正确的方向。"（第2章"极端的可用性"）
  summary: |

    用法：设定极端目标，明知达不到也要设——它不用于验收，用于让每次设计会议上的妥协都朝正确的方向。

- id: f12
  title: 环境-角色-情节三层故事法
  type: reasoning-method
  source_chapter: 第2章
  source_quote: |
    "可信的环境（故事中的'时间'和'地点'）、可信的角色（'谁'和'为什么'）、流畅的情节（'什么'和'怎么样'）。""电影是从外而内构思的，开始是设置环境……接着添加角色和动机……最后描述情节。"（第2章"环境、角色、情节"，皮克斯方法）
  summary: |
    把"认识"转成故事的固定结构：先环境、再角色、后情节，由外而内构思。
    遇到情节麻烦就回到角色（他会怎么做），角色做不出文章就深挖环境（环境如何影响角色）——回退路径也是固定的。
    为什么有效：很多复杂设计源于没考虑现实压力或漏掉环节；故事能把约束条件浓缩成寥寥数语，人人能复述、能检验设计是否与故事契合。
    用法：为设计写简短、具体、可信（以真人为原型）、只含要紧细节的故事，用它检验每个设计决定。
  tags: [reasoning-method, storytelling, user-research]

  title: 问题理解三阶段（简单→复杂→优雅）
  type: mental-model
  source_chapter: 第2章
  source_quote: |
    "乍一看到某个问题，你会觉得很简单，其实你并没有理解其复杂性。当你把问题搞清楚之后，又会发现真的很复杂，于是你就拿出一套复杂的方案来。实际上，你的工作只做了一半，大多数人也都会到此为止……"（第2章"明确认识"，乔布斯语）
  summary: |
    对问题的认识呈三段曲线：看似简单→看清后真的很复杂→大多数人止步于复杂方案，而真正伟大的人继续向前找到关键与深层原因，拿出优雅方案。
    作者的经验佐证：任何项目的前3个方案大约都是"对真正重要问题的描述"，此阶段复杂性看似与日俱增且毫无想法。
    为什么有效：它把"坚持理解、不要匆忙动手"从美德变成阶段判断——复杂感上升恰恰说明走在路上。
    用法：察觉自己拿出复杂方案时，把它标记为"第二阶段"，继续追问关键与深层原因。
  tags: [mental-model, problem-solving, patience]

  type: reasoning-method
  source_chapter: 第4章

    "我们的做法是对用户的要求做逆向工程——搞清楚用户到底遇到了什么问题，仔细斟酌这个问题是不是应该由我们的软件来解决。"（第4章"但我们的用户想要"，Cultured Code）

- id: f17
  title: "为什么要留着它"翻转（沉没成本判定）
  type: decision-framework
  source_chapter: 第4章
  source_quote: |
    "用于创建这部分功能的成本是不可能收回来的，因此判定这种功能的唯一方式就是看它能够发挥几分作用，看保留它会额外导致多少成本。""所以说，问题绝非'为什么应该去掉它'，而是'为什么要留着它'。"（第4章"砍掉残缺功能"）
  summary: |
    把删功能的默认问题从"为什么去掉"翻转为"为什么保留"。
    底层是沉没成本误区：开发成本已不可收回，不构成保留理由；功能保留的真实代价是用户精神负担+维护开支。
    为什么有效：默认问题决定了举证责任——翻转后，残缺功能必须自己证明存在价值，否则删除（TUI Ski 删掉半生不熟的筛选和短列表后转换率反而上升）。

  type: reasoning-method
  source_chapter: 第4章
  source_quote: |

    简单不意味着最少化、欠缺或低劣：夏克椅与潘顿椅都把组件减到最少，却因解决的问题不同（耐磨vs堆叠）而各有特征和个性。
    为什么有效：装饰应紧密贴近设计本身，无关要素才剔除——特征与个性来自方法、产品和任务，用户能识别这些差异并赋予价值（Google 与 Bing 的差异）。
    用法：简化时问"这个元素是无关装饰，还是产品的特征？"前者删，后者留；防止简化滑向千篇一律。
  tags: [mental-model, minimalism, design-philosophy]

- id: f36
  title: 分类标准判定（是非分明/最少重叠）
  type: decision-framework
  source_chapter: 第5章
  source_quote: |
    "简单的组织模式具有清晰的界限——是非分明。""要多找一些用户，询问他们的分类标准。如果众口不一，或者根本就难以回答，你就有麻烦了。""所谓最简单的分类，通常指的是重复交叉最少的分类方法。"（第5章"是非分明"）
  summary: |
    为"按什么标准组织"给出三重判定：①标准对用户是非分明（标致网站用"内饰/外观/性能"替代内部人才能懂的"功能/选项/配件"）；②标准来自多数用户的一致回答，众口不一即告警；③候选标准中选重复交叉最少的。
    为什么有效：品质、特点类标准仁者见仁，用户无法判断东西在哪；看得见摸得着的标准（汽车布局）人人能定位。
    用法：列候选分类标准→找几位用户问他们的分法→取一致且重叠最少者；字母序和按格式分类是看似简单的劣解。
