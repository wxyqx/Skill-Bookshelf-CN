# 简化的商业论证

## R — 原文 (Reading)

> "只要他说去掉某项功能，就总会有销售人员反对说：我的一个客户极为看重那项功能。"（第1章）
>
> "到了2008年经济危机，突然，没有人再需要不必要的功能了。"（第1章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第1章

---

## I — 方法论骨架 (Interpretation)

作者在第1章回答了一个尴尬的问题：简化明明对用户好，为什么在组织里推不动？因为公司不按用户体验说话，按赚钱和增长说话。解法是彼得·梅洛兹（Adaptive Path）的技巧：先搞清这家公司靠什么赚钱，写成方程式（如 汽车销量×单价−成本=利润），再分析你提议的简化会影响哪一项——卖更多、卖更贵，还是省成本。设计判断由此变成商业命题。

光有方程式还开不完会，因为评审上的争论常是"这个功能重要"对"那个功能重要"的口水仗。配套工序是强制分档：让所有相关方按固定档次（不是无限打分）给每个功能的重要性与可行性评级，画成两轴矩阵，右上角的先做。分档的真正作用是堵住"什么都重要"——当一切都被标成重要，就等于没有优先级。

两个工具合起来的定位：简化从来不缺用户侧的理由，缺的是能通过组织这一关的理由。这个 skill 就是把"对用户好"翻译成"对公司好"的转换器——也是作者给"简化引发内部冲突"指出的出路：用公司自己的语言给管理层算账。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: "最重要的客户"与公司方程式
- **问题**: 一位汽车公司主管每提删一项功能，就有销售以"我最重要的客户极为看重它"反对，即使该客户对总销量毫无影响；矛盾非得更资深的人介入才能裁决。
- **方法论的使用**: 引入公司方程式技巧——先写清公司怎么赚钱，再分析简化影响方程式哪一项；然后按重要性与可行性分档排序，取右上角的改变。
- **结论**: 简化的阻力是组织内人的问题；用公司自己的语言给管理层算账，就能为简化找到充足理由。
- **结果**: 做出重要/可行性评估之后，简化提案有了在组织内立足的依据。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 砍功能/简化提案被"重要客户需要它""先加上再说"否决，需要比口头上更硬的理由。
2. 要向 CEO/管理层汇报简化的价值，需要把用户收益翻译成收入与成本。
3. 多个功能改进争夺资源，需要排出"重要性×可行性"的优先级。

### 语言信号 (用户的话里出现这些就应激活)

- "说服老板 / CEO 不批 / 砍功能被拒 / 怎么向上汇报"
- "重要客户就要这个 / 销售不让删 / 都很重要 / 优先级排不出来"
- "business case / ROI / 公司方程式 / 优先级矩阵 / stakeholder"

### 与相邻 skill 的区分

- 与 `remove-strategy` 的区别：删除策略回答"这个功能该不该删"（判断标准在用户价值与沉没成本）；本 skill 回答"删的决议怎么在组织里通过"（判断标准在公司方程式）——先有前者的事实，再用后者开路。
- 与 `four-strategies` 的区别：四策略是简化的技术路径；本 skill 是简化的组织路径。
- 与 `mainstream-user-lens` 的区别：主流用户立场提供"为谁简化"的证据（9% 数据、iPod 案例），可以在算账时被引用；但组织政治本身由本 skill 处理。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **写出公司方程式**
   - 搞清这家公司/这条产品线靠什么赚钱，写成"量×单价−成本"的形式
   - 完成标准: 方程式每个变量都对应公司真实关注的一项（销量、客单价、续费率、支持成本…），且干系人认可
2. **推演简化影响哪一项**
   - 对每个候选简化，说明它让哪个变量升、哪个降（如：支持工单降、续费升；短期改版成本升）
   - 完成标准: 每个提案都能落到至少一个方程式变量上；说不出影响的提案先挂起
3. **强制分档排序**
   - 让相关方（含销售、支持、产品）按固定档次给每个功能的重要性与可行性评级，画两轴矩阵
   - 完成标准: 没有任何功能逃出分档（防"什么都重要"），矩阵产出右上角清单
4. **判停检查**
   - 例外: 若管理层仍然否决——回事实层补数据（使用率、工单量），或转 `mainstream-user-lens` 检查反对声音是否来自被过采样的专家，不再重复算账
   - 完成标准: 明确下一步是"补证据""换论证"还是"接受暂不简化"

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 公司处在"靠功能数卖溢价"的短期窗口（夸耀效用红利期），管理层明确选择赚快钱——算账会算出"现在不简化"，这是诚实的结论而非方法失败
- 简化不改变销量、单价、成本中任何一项——此时理由在品牌与口碑，方程式覆盖不了，别硬套
- 内部工具（用户与公司是同一拨人）——方程式翻译这步可以跳过，直接用用户体验证据

### 作者在书中警告的失败模式

- "最重要的客户"免疫反应：任何功能都有销售声称有客户极为看重，个案证词不可证伪又情感上难拒绝，简化沦为立场辩论、决议久拖不决
- 数据缺位：反对者拿不出该功能使用率的数据，评审靠嗓门——分档工序被绕过
- 功能堆砌的账单延迟到账：加功能时人人都爽（夸耀效用原理），维护成本与垃圾功能的代价要等环境突变才爆发（2008 汽车业濒临绝境）——方程式里漏掉"未来维护成本"就会算错

### 作者的盲点 / 时代局限

- 公司方程式把品牌与口碑的网络效应简化掉了——简化的最大收益有时恰在方程式之外（BOOK_OVERVIEW 未证假设）
- 作者把组织冲突的解法归结为"给管理层算账"，未处理"简化伤害少数重度用户利益"的分配正义问题（BOOK_OVERVIEW 最强反对意见）

### 容易混淆的邻近方法论

- `remove-strategy`：判断层（该不该删）与组织层（怎么通过）——两步经常都需要，但顺序不能乱
- `mainstream-user-lens`："重要客户"论既能用三分类拆（他是哪类用户）也能用方程式拆（他影响哪个变量）——先分型再算账
