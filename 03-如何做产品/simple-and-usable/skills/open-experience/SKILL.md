# 开放式体验

## R — 原文 (Reading)

> "让用户自己定义成功（可能是完整的旅行规划，也可能是一堆零散的想法）很重要。"（第7章）
>
> "开放性界面的秘诀在于，尽量减少仅适合中级用户的'便捷'特性。"（第7章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第7章

---

## I — 方法论骨架 (Interpretation)

作者用菜刀与钢琴定义了开放性界面的最高境界：新手第一次拿菜刀能切出"能够接受"的土豆片，大厨用同一把刀精确切丝雕花；初学者能在钢琴上弹出曲调并觉得简单，演奏家能弹奏鸣曲——区别只在用户的技术水平，不在界面。专家和主流用户各自设定目标，都知道怎么达成。

对照组是洋葱切丁机、打蛋器、自动伴奏电子琴——给"中级用户"的便捷产品。中级用户看得懂专家做的却做不到，于是这类产品两头不讨好：专家嫌累赘，新手够不着，主流用户被迫走固定流程。

落到设计上是两条路：① **削减中级便捷特性**——凡是"聪明地替用户做了一半"的东西（预设模板、自动分类、强制流程），逐个检查它是不是只服务想象中的中间层用户；② **合并相似功能为多用途工具**——像购物车里可命名的文件夹、兼作收音机天线的后挡风玻璃电阻丝：找一个比在几个里选容易，学一个比学多个容易，维护一个比维护多个容易。

给用户的提示只需一句："可以给清单起名字"就足以让他们想到用法。前提是信任：容忍模糊性、放弃对结果的预设，让用户发明自己的用法。

## A1 — 书中的应用 (Past Application)

### 案例 1: 旅行规划程序的两版迭代
- **问题**: 第一版"智能型"规划程序：用户在地图上选景点，程序自动算停留时间、排行程、对安排过满给出警告——结果用户反馈很差，产品未上线。
- **方法论的使用**: 几年后重做改用"剥皮策略"：让用户自建文件夹、随意命名、想放什么放什么。规划本就充满模棱两可（时间有限但有弹性、预算不多但可变），把设定目标和组织记录留给人（人擅长估算、想象、控制结果），机器只负责存储。
- **结论**: 让用户自己定义成功，把模糊性留在用户头脑中，界面反而简单。
- **结果**: 用户起的名字有的在意料中（周几、地点），有的出乎意料却很有道理（"10 英镑以下""雨天"）；有人排精确行程，有人只列几个想法，各自合适。

### 案例 2: 亚马逊式"一物多存"的多合一方案
- **问题**: 购物车、"保存商品"、意向清单、婚礼/生日专列并存——大多数时候用户只做一件事：存起来以后买。用户要了解多种功能、记住用了哪个、记得去哪找；商店要维护多套代码。
- **方法论的使用**: 合并为购物车里可命名的文件夹（婚礼、生日、旅游书），可选是否让朋友看到——一个功能完成四项工作。
- **结论**: 让组件多用途、把相似功能绑定在一起。
- **结果**: 功能、学习、维护三重成本同时下降。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 纠结要不要做"智能推荐/模板/向导"，替用户把内容生成出来。
2. 同一类任务散落多个功能入口，用户记不住自己上次用了哪个。
3. 用户群体差异大（新手到专家），一套固定流程照顾不了所有人。
4. 设计新工具类产品，在"预设流程"和"给空白工具"之间摇摆。
5. 中级便捷特性越加越多，专家嫌累赘、新手被排除。

### 语言信号 (用户的话里出现这些就应激活)

- "智能推荐 / 预设模板 / 自动生成 / 帮用户做对 / 要不要做向导"
- "多合一 / 合并功能 / 功能重复 / 收藏夹太多 / 用户自己定义"
- "开放式体验 / open-ended / 菜刀 / 让用户自由发挥 / 工具类产品"

### 与相邻 skill 的区分

- 与 `transfer-strategy` 的区别：分工表回答"这一步谁做"；本 skill 回答"要不要把定义成功本身的模糊性留给用户"——它是转移策略的进阶形态，不是分工执行。
- 与 `complexity-placement` 的区别：四问分配消不掉的复杂性；本 skill 是一种工具设计理念（开放 vs 预设）。
- 与 `remove-strategy` 的区别：合并相似功能常伴随删除，但目的是通用性（一项顶四项），不是单纯做减法。
- 与 `control-and-emotion` 的区别：那是挖感情需求的访谈法；本 skill 把信任与自由落成工具形态。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **判定目标是否可写死**
   - 问：这个任务的成功结果能不能提前定义？写得死的（付款、查路线）走固定流程；写不死的（收藏、笔记、旅行规划、健身记录）才适合开放工具
   - 完成标准: 明确判定"目标模糊/清晰"，模糊才继续
2. **削减中级便捷特性**
   - 列出所有"聪明地替用户做了一半"的特性（预设模板、自动分类、强制字段、固定流程向导），逐个问：专家嫌不嫌累赘？新手够不够得着？
   - 完成标准: 每个"仅适合中级用户"的特性被砍或降级为可选；无强制中间流程
3. **合并相似功能为多用途工具**
   - 找出同一心智任务的多个入口，合成一个可命名、可自定义的通用工具；用一句提示告诉用户"可以起名字"，把用法留给用户发明
   - 完成标准: 一个任务一个入口；存在用户可见的命名/自定义空间；学习成本从 N 降为 1
4. **两头用户验证并判停**（判停条件：若任务目标其实明确且高频，固定流程+阶段展示更好，转 hide-strategy / organize-strategy）
   - 完成标准: 新手能做出"能接受"的结果且不觉受限；专家能做出精确结果且不嫌累赘

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 目标明确的高频任务（结账、挂号、报销）——开放工具把本可一次完成的事变成设计题
- 错误代价高的领域（用药剂量、金融操作）——模糊性不能交给用户
- 用户是被动使用者（被要求用、无动机探索）——开放空间只会变成空白恐惧

### 作者在书中警告的失败模式

- **洋葱切丁机式"便捷"产品**：给中级用户的电动切菜设备两头不讨好——专家嫌它不能精确控制，新手根本用不上，"厨房里净是电动切菜设备却没有菜刀"
- **一物多存**：多个单用途功能并存，用户要学多种功能、记住当初用了哪个、再找到上次存的东西——支持问题集中在"我上次存到哪儿了"
- **把用户当孩子**：开放体验以信任为前提——处处代劳、剥夺决定权的设计给不出开放空间，用户只会回报怨恨

### 作者的盲点 / 时代局限

- 书中假设用户愿意且有能力定义自己的成功——新手引导（onboarding）与用户分层运营这类中间态未讨论
- "忽略专家"的立场对专业工具不成立：专业工具的"专家"就是主流用户，其复杂度是需求本身

### 容易混淆的邻近方法论

- 专业软件的"开放"（IDE、DAW）不是本 skill 的场景——那里的复杂是需求，不是待转移的复杂性
- `transfer-strategy`：机器接住结构化的活（识别、格式化）与本 skill 的"留白给用户"是互补动作，先分工再开放
- 极简主义：开放工具 ≠ 极简风格，它靠通用性而非元素数量取胜 → `simplicity-boundaries`
