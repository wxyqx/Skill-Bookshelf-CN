## I — 方法论骨架 (Interpretation)

判断一个体验简不简单，最有效的载体不是指标清单，而是一个**能看到画面的用户故事**：读完故事，你就知道什么算简单、什么算跑偏。

结构上借用皮克斯"从外而内"的创作法，固定三层：**先环境**（何时何地、什么干扰、什么状态）、**再角色**（谁、动机、当时的心理）、**最后情节**（做什么、分几步完成）。配套固定的回退路径：情节编不下去，退回角色检查动机；角色立不住，退回环境检查情景——不许凭空硬编。

好故事有四条标准：**简明、具体、可信、展示而非讲述**。"她注重细节"是讲述，"她反复按备注核对"才是展示。描述行动另有三规范：用用户的语言（不出现系统术语）、不漏步骤（包括怎么进入、怎么回来）、聚焦行为（写做了什么，不写怎么看）。

一条硬规则：**不编造**。故事必须有真人真事原型（来自观察或访谈），并大声讲出来反复修改——讲不圆的故事说明素材不够，不是文笔问题。

## A1 — 书中的应用 (Past Application)

### 案例 1: 帕丽斯·希尔顿的故事与皮克斯方法
- **问题**: 如何用一小段话把 Flip 摄像机的全部设计约束讲清楚，让团队记住并复用？
- **方法论的使用**: 作者用朋友亲身经历改编的故事——街头偶遇名人，掏出 Flip 交给路人帮忙拍摄。寥寥数语推出全部约束：小到随身带、开机快、路人拿到就会拍、上传无需软件和数据线、拍视频是为了分享。
- **结论**: 故事要有可信的环境、可信的角色、流畅的情节；结构与皮克斯一致（先环境、再角色、最后情节，卡住就逐层回退）。
- **结果**: 一个故事即可推出关键设计要求，易记、易传播、易套用到其他情境。

### 案例 2: "讲述"与"展示"的正反示范
- **问题**: 用户故事写成"她注重细节"，评审时人人点头却没有人知道该设计什么。
- **方法论的使用**: 按四标准改写为展示式情节——"她反复按备注核对订单"，行为具体可见，直接指向界面要支撑的动作。
- **结论**: 展示而非讲述是故事可信、可用的分水岭。
- **结果**: 抽象形容词变成可设计的具体情节。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 需求文档全是功能列表，评审没人有感觉、没有共识。
2. 要给"简单"写基准描述（使用情景是两种基准方式之一）。
3. 设计新功能前，需要确认目标用户在真实场景里怎么用它。
4. "作为…我想要…"式 user story 太干瘪，评审对不上话。

### 语言信号 (用户的话里出现这些就应激活)

- "需求文档没人看 / 评审没感觉 / 功能列表太空 / 太抽象"
- "用户故事怎么写 / 使用情景 / 场景描述 / user story / journey"
- "描述一下用户怎么用 / 目标用户在什么场景下用 / 环境角色情节 / 展示而非讲述"

### 与相邻 skill 的区分

- 与 `field-observation` 的区别：那是去现场**收集**素材；本 skill 把素材**组织成故事**——没有素材就先观察，不编造。
- 与 `simplicity-baseline` 的区别：基准是成文的判断标准（产出物）；本 skill 是产出基准的方法之一（也是最完整的一种）。
- 与 `mainstream-user-lens` 的区别：那是选定为谁设计；本 skill 把选定的主流用户写成可信的故事。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **定环境**
   - 一句话写清何时、何地、何种状态（被打断？匆忙？单手？）
   - 完成标准: 环境描述包含至少一个会干扰任务的现实因素；能说出素材来自哪次观察/访谈（真人真事原型）
2. **定角色**
   - 写清谁、动机、当时的心理状态
   - 完成标准: 动机用"他想要什么结果/感觉"表述；角色经主流用户视角校验（可借助 `mainstream-user-lens`）
3. **写情节**
   - 从用户视角写完整步骤，聚焦行为、用用户语言
   - 完成标准: 每步是用户做的事（不是系统做的事）；不漏进入与恢复的衔接步骤
4. **四标准自检与回退**
   - 逐项检查简明/具体/可信/展示而非讲述；任何一项不过，按回退路径修正（情节问题回角色，角色问题回环境）
   - 完成标准: 四项全过，且大声讲一遍仍然顺畅
   - 判停条件: 反复修改仍"不可信"（自己都不信用户会这么做）——说明素材不足，停下来先补观察（转 `field-observation`）

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 没有任何真实观察素材——硬写必然编造，先去观察
- 纯技术中间件/无人类交互点的系统——没有"用户的故事"可写
- 需要全局触点地图而非单个情景——旅程图才是合适工具

### 作者在书中警告的失败模式

- **编造情节**：没有真人真事原型的故事是设计师的想象，评审通过也做不对（第2章讲故事规则）
- **讲述而非展示**："她注重细节"式形容词堆砌，读者无从判断设计该做什么
- **用术语写故事**："点击提交触发异步校验"不是用户的语言；漏掉进入与恢复步骤同样常见

### 作者的盲点 / 时代局限

- 方法针对消费级单人任务，未覆盖多人协作、B2B 多角色的情景故事
- "展示而非讲述"需要写作技巧，书中未给出练习路径
- 生动的故事可能压倒数据（代表性偏差），书中未讨论故事与量化证据冲突时听谁的

### 容易混淆的邻近方法论

- 用户旅程图（journey map）：全局触点地图 vs 本书单个情景的叙事，粒度不同
- 敏捷 user story 卡（as a…I want…so that…）：有格式但缺环境层、回退路径与四标准
