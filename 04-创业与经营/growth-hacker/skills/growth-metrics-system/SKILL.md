# 增长指标体系：North Star 共识、分析纪律与指标字典

## R — 原文 (Reading)

> "这就需要一套自上而下推行的核心指标作为共识，来凝聚团队劲往一处使。在Facebook，马克·扎克伯格在公司内部大力推行的核心指标是月活跃用户数，而非像其他社交网络那样关注注册用户数量。"
>
> — 范冰，《增长黑客》第1章（一切用数据说话）

---

## I — 方法论骨架 (Interpretation)

"数据驱动"若没有体系，就退化为各部门各报各的数。骨架是三层：

1. **一个 North Star**：全公司自上而下只推一个（通常一个就够）核心指标，它的定义必须锚定品类的核心价值——社交看月活而非注册量、IM 看消息发送量而非启动次数、电商看成交商品价值量。它的作用是：领导者不在场、部门利益冲突时，全员仍能自行判断什么必须恪守、什么可以妥协，甚至终结一场无意义会议。
2. **两条分析纪律**：①先有假设和目标再取数据——"拉个数看看"没有价值，杜绝意义不明的索取；②结论要能与其他数据相互印证（一侧婴儿车销量上涨，应能在奶粉销量中得到印证），孤立数字不作决策依据，同时要弄清指标定义、采集点与上报机制，否则无法感知数据异常。
3. **一本带陷阱注解的指标字典**：把常用指标（PV/UV/跳出率/留存率/ARPU/LTV/K 因子等）逐项写清定义、统计口径与作弊识别——可被零成本刷出来的数字（嵌 iframe 刷 PV、老版本升级算新增、常驻后台算活跃）一律存疑。

一句话：选对一个数、立两条纪律、写一本字典，"数据驱动"才可执行。

## A1 — 书中的应用 (Past Application)

> 注：聚类总表中本单元未挂接独立案例 id，以下取 verified.md 单元内的书中场景作 A1 证据。

### 案例 1: Facebook 月活 vs 竞品注册量（第1章）
- **问题**: 社交网络早期普遍拿"注册用户数"汇报，数字大但说明不了产品健康度。
- **方法论的使用**: 扎克伯格在公司内部强行推行"月活跃用户数"为唯一核心指标——把共识锚定在"真的有人在用"这一品类核心价值上。
- **结论**: 核心指标选错，全公司的努力方向就会整体偏航。
- **结果**: 月活成为后来社交行业通用的健康度标尺，也被作者列为 North Star 式共识的原型。

### 案例 2: "活跃"的定义因产品而异（WhatsApp/陌陌，第1章+附录A）
- **问题**: 即时通讯与陌生人社交若都按"启动 App"定义活跃，度量不出真实价值。
- **方法论的使用**: WhatsApp 只公布消息发送量；陌陌把活跃定义为"登录并提交地理位置一次"——各自锚定产品成立所依赖的关键行为。
- **结论**: 活跃定义由团队自己定，但必须指向品类核心价值，且全公司统一口径。
- **结果**: 同一套"DAU/MAU"词汇下，各家可度量出对自己有意义的行为。

### 案例 3: 数据互证与异动预警（婴儿车-奶粉 / LinkedIn，第1章）
- **问题**: 单一指标上涨可能失真；重大事件冲击只看一个数会漏掉预兆。
- **方法论的使用**: 电商侧用婴儿车销量与奶粉销量互证消费数据真实性；LinkedIn 通过访客数据异动察觉雷曼破产后求职流量骤增——跨指标交叉验证既用来证真，也用来预警。
- **结论**: 数据的效力来自互证与口径透明，不是来自单个大数。
- **结果**: 作者将"先假设后取数+相互印证"立为增长团队的分析纪律。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品、市场、运营各报各的数，周会为"哪个指标更重要"反复争吵。
2. 从零搭建数据看板/指标体系，不知道该放哪些指标、口径怎么定。
3. 汇报数字很漂亮（PV/下载量/总用户数）但业务没有起色，怀疑虚荣指标。
4. 怀疑数据被刷量或口径有水分，要建立作弊识别。
5. 数据突增/突降，团队不知道从哪里查起。

### 语言信号 (用户的话里出现这些就应激活)

- "核心指标 / North Star / 北极星指标怎么选"
- "虚荣指标 / vanity metrics / 数据有水分 / 刷量"
- "指标口径 / 指标字典 / 数据看板该看什么"
- "ARPU / LTV / 转化率怎么定义 / DAU MAU 哪个重要"
- "各部门数据打架 / 周会吵指标"

### 与相邻 skill 的区分

- 与 `retention-diagnosis` 的区别：本 skill 管**看什么数字、口径怎么定**（度量底座）；留存诊断管**拿数字归因流失问题**。先有本 skill 的口径，才有对方的可信归因。
- 与 `aarrr-funnel-diagnosis` 的区别：漏斗诊断管**增长停滞时定位卡在哪个环节**（转化链视角）；本 skill 管**指标共识与口径体系**（度量视角）。前者输出"瓶颈在留存环节"这类定位，后者输出"该盯什么数、怎么防止自欺"。
- 与 `freemium-decision` 的区别：付费率、ARPU 的**定义与水分识别**归本 skill；免费/收费**模式决策**（要不要砍免费版）归 freemium-decision。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **选定并定义 North Star**
   - 回答"这个产品成立所依赖的核心价值行为是什么"（IM=消息量、社交=月活、电商=成交额、工具=完成任务次数），据此选定一个指标，写出精确定义（分子分母、去重口径、时间窗）与一票否决的反例（明确不计入什么）。
   - 完成标准: 一句话 North Star + 无歧义定义文档 + 管理层确认。

2. **立分析纪律**
   - 写入团队规范两条：①任何取数需求先陈述假设与用途；②关键结论必须给出至少一个可互证的旁证数据，并注明采集点与上报机制。
   - 完成标准: 规范成文并有一次实际执行记录（如某次周报按新纪律重写）。

3. **用字典搭指标体系并排雷虚荣指标**
   - 参照"网站 13 项+移动 13 项"字典选核心看板指标，逐项标注口径陷阱；把"可零成本刷出来的数字"（可 iframe 刷的 PV、升级算新增、后台常驻算活跃）标红降权或改造口径。
   - 完成标准: 指标字典初稿（指标名/定义/口径陷阱/责任人），含至少一项针对自家产品的防刷设计。
   - 判停条件: 若团队连埋点与上报机制都不具备，先停在"打通数据采集"这一步，不要先买看板工具。

4. **建异动预警与互证机制**
   - 为 North Star 与两三个伴生指标设波动阈值；异动时按"先查口径与上报、再查渠道与版本、最后查业务"的顺序排查，并要求跨指标互证。
   - 完成标准: 一份异动排查 SOP，且经历过至少一次演练或真实异动复盘。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **用指标体系替代归因诊断**：数字对了之后"为什么掉"的问题属留存诊断/漏斗诊断；本 skill 不回答业务归因。
- **为汇报美化为指标服务**：发现自己在"调整口径让数字好看"时，立即停——这是虚荣指标的制造现场。

### 作者在书中警告的失败模式

- 刷量产业链之鉴（x19）：刷榜固化为部分手游公司的长效机制；嵌不可见 iframe 刷 PV、长文拆多页凑阅读量、升级下载算新增、后台常驻算活跃——指标一旦成为 KPI，造假就从个人行为固化为组织机制。
- 总用户数之鉴（附录A）：累计相加得来的数字有水分，体现不了已流失与极不活跃的用户，属典型虚荣指标。

### 作者的盲点 / 时代局限

- 书中未展开 CAC 的完整定义与 LTV:CAC 模型（仅在用户价值指标处带过），也全书无统计显著性/样本量讨论——指标体系需由使用者补齐实验统计学。
- **2015 年快照时效警示**：附录 A 的 26 项指标口径按当代度量环境重查——第三方 cookie 与设备标识受 ATT/GDPR/个保法约束、归因依赖 MMP/服务端埋点、隐私合规改变采集边界；"以行为为中心 vs 以访问为中心"的选型思想保留，**具体指标清单与采集手段按当期重查，skill 只保留"North Star 选型判据+分析纪律+口径排雷"的逻辑层。**

### 容易混淆的邻近方法论

- 指标体系（本 skill）≠ 漏斗诊断（`aarrr-funnel-diagnosis`，瓶颈定位）≠ 留存诊断（`retention-diagnosis`，流失归因）。三者是"度量→定位→归因"的递进关系，用户问题落在哪一层就调用哪一层。
