# PRFAQ / 逆向工作法（先发布虚构新闻稿再生产）

## R — 原文 (Reading)

> "整个过程从PRFAQ（即新闻稿+常见问题）技能的演练开始……在PRFAQ中，团队要准备一份新闻稿（类似于亚马逊的那种做法）和一个供用户使用的常见问题文件，内容包括产品首发日期和价格（至少是一个差不多的预估价）。然后，团队成员需要跟拿到新闻稿的用户谈话，并听取反馈。"
>
> — 埃里克·莱斯，第 4 章（行 1476-1478）

> "亚马逊使用了一种'逆向工作法'，保证团队必须将发现用户真正关心的问题放在最前面解决。……如果团队不能真正地从用户的角度说明问题，那么最好什么都不要生产。"
>
> — 埃里克·莱斯，第 1 章（行 1000-1002）

---

## I — 方法论骨架 (Interpretation)

这是"动手生产之前"的最后一道、也是成本最低的闸门：连纸板样机都还不做，先写文档、跟真人谈话。

- **工件要求**：新闻稿以"产品已发布"的口吻写成，必须含两个常被省略的硬信息——发布日期与预估价格；FAQ 预答最尖锐的反对问题（成本、切换、风险）。日期与价格逼作者把"大概也许"换成可被检验的承诺。
- **测试动作**：把新闻稿发给将被影响的真实用户（内部用户也算），请他们反应——毫无兴趣、迫不及待、提出团队没想到的需求，三种反馈都有明确走向。
- **三分支决策**：冷场→放弃或改写（这个"拒绝"是全流程最便宜的教训）；追问→立项，追问者即首批合著者；新需求→回炉改写新闻稿再测。
- **与正传 MVP 的关系**：MVP 回答"造出来后用户做不做"，PRFAQ 回答"还没造时用户要不微要"——它把第一次暴露给现实的时间点又往前推了一大步，成本趋近于零。
- **亚马逊版的纪律**："如果团队不能真正地从用户的角度说明问题，那么最好什么都不要生产"——写不出"更好"，就是最有价值的测试结果。

## A1 — 书中的应用 (Past Application)

### 案例 1：Twilio——每个机会先过 PRFAQ，再决定造不造
- **问题**：公司快速扩张，团队不断发现新机会（呼叫中心、视频聊天、彩信），若每个机会都直接立项开发，资源会被拍脑袋想法烧光。
- **方法论的使用**：管理者要求每个团队测试一个机会时不许先造产品，整个过程从 PRFAQ 演练开始——写含日期与预估价的新闻稿+FAQ，跟拿到新闻稿的真实用户（内外皆有）谈话；用户说毫无兴趣的，就记录这个最便宜的教训；迫不及待的，才继续挖掘并立项。
- **结论**："我们尽量搜集用户对最终产品的意见，之后再花时间生产"（产品管理副总裁帕特里克·马拉塔克）；PRFAQ 成为把想法第一次暴露给现实的标准手段，且不搞一刀切的时间要求，只要求同样的学习标准。
- **结果**：机会经此闸门筛选后做成"非常非常基本的"可立即迭代产品；公司自 2008 年成立至 IPO 市值 25.6 亿美元（第 4 章，行 1476-1484；V1 证据，无独立案例条目）。

### 案例 2：亚马逊内部新闻发布会——"更好"是关键词
- **问题**：内部项目（IT、HR、财务流程）容易自说自话：解决的是部门的问题，不是用户的问题。
- **方法论的使用**：项目启动先开一场内部"新闻发布会"，资料发给新产品或更新产品的真实用户（内外皆有），必须说清问题本身、现有方案、新方案如何更好。
- **结论**：只是解决用户的问题还不够——硅谷式公司要提供"明显优于任何现有方案"的方案；说不清"更好"的团队，最好什么都不要生产。
- **结果**：该方法成为本书引用的组织级纪律：把"发现用户真正关心的问题"制度化为项目的前置条件（第 1 章，行 1000-1002）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 有一个产品/功能/新流程的想法，想在投入开发或消耗政治资本之前，先知道组织或市场的真实意愿。
2. 团队又进入"先造出来再说"模式，需要一个比 MVP 更早、更便宜的闸门。
3. 想推动公司换一套协作流程/新制度，担心强推会雷声大雨点小，想先测谁真的想要。
4. 立项材料千篇一律是内部视角的功能清单，想把它换成用户视角的可测试工件。

### 语言信号 (用户的话里出现这些就应激活)

- "PRFAQ" "新闻稿" "逆向工作法" "working backwards"
- "先写个虚构发布" "还没开发怎么测需求" "要不要做这个功能" "先探探风向"
- 英文：working backwards / press release FAQ / test the idea before building / is this worth building

### 与相邻 skill 的区分

- 与 `leap-of-faith-assumption-audit`（信仰飞跃假设审计）的区别：`leap-of-faith-assumption-audit` 先列假设清单、挑最不舒适者排序；`prfaq-working-backwards` 把假设物化成一份"已发生"的工件去让现实回应——PRFAQ 通常是假设审计之后的第一个零代码实验，一个想、一个测。
- 与 `mvp-trio-and-scorecard`（MVP 三件套头脑风暴与记分卡）的区别：`mvp-trio-and-scorecard` 在设计"造什么"（哪怕纸板），`prfaq-working-backwards` 连纸板都不造（只有文档与对话）；`prfaq-working-backwards` 是 MVP 之前的闸门，产出直接决定要不要进入 `mvp-trio-and-scorecard`。
- 与 `pivot-persevere-cadence`（转型/坚持会议节奏设计）的区别：`pivot-persevere-cadence` 决定"多久看一次证据并做决定"，`prfaq-working-backwards` 是生产证据的手段之一；转型/坚持会上带的证据，可以正是 PRFAQ 反馈。
- 与 `one-page-preapproval`（一页纸预批文件）的区别：两者都是一页纸，但 `one-page-preapproval` 把把关规则参数化给团队用，`prfaq-working-backwards` 把产品设想新闻稿化给用户测——一个是制度工件，一个是需求工件。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **写虚构新闻稿**
   - 完成标准：一页以内、以"已发布"口吻写成、面向将被影响的用户；必须包含发布日期与预估价格（或成本分摊方式），并说清相对现有方案"更好"在哪一点；写不出"更好"即停止（亚马逊纪律）。

2. **写 FAQ**
   - 完成标准：预答 5 个以上最尖锐的反对问题（成本谁担、怎么切换、失败了怎么办、为什么现在做），不回避风险项。

3. **交给真实用户收反馈**
   - 完成标准：至少 5 个真实用户（内部用户有效）给出了反应；记录三分类——冷场/追问/新需求，并保留原话。
   - 判停条件：若发现用户群体无法触达（拿不到真实用户），停下——把稿子发给同事或领导评审不是测试，转 `three-tier-support-structure` 争取支持结构后再测。

4. **三分支决策**
   - 完成标准：冷场→写下这次拒绝证明了什么假设为假，正式放弃或改写；追问→列出追问者名单（首批合著者）并立项；新需求→回炉改写新闻稿，回到步骤 1。每个分支都有书面记录。

5. **衔接后续方法**
   - 完成标准：立项项目进入 `mvp-trio-and-scorecard` 的 MVP 三件套与 `value-and-growth-hypotheses` 的价值假设量化；PRFAQ 反馈中被验证/证伪的内容回写进假设清单（`leap-of-faith-assumption-audit`）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 需求已明确、参数清楚的执行型项目——直接排期，写"新闻稿"是表演。
- 把 PRFAQ 当立项汇报模板写给领导而非用户——那会退化成美化文档，恰好消灭了这个方法的信息价值。
- 用户拿不到、不敢打扰、或反馈会被追责的场景——没有真实用户的 PRFAQ 是写作练习。
- 用 PRFAQ 替代价值假设的量化验证——口头兴趣不等于行为；"迫不及待"之后仍要 MVP 行为数据（`value-and-growth-hypotheses`/`mvp-trio-and-scorecard`）。

### 作者在书中警告的失败模式

- 写不出"更好"硬要做："如果团队不能真正地从用户的角度说明问题，那么最好什么都不要生产"——这句是闸门本闸，常见失败是把"我们觉得更好"混充"用户觉得更好"。
- 无视"毫无兴趣"的反馈：Twilio 流程中冷场反馈必须当真——拒绝是最便宜的教训；最常见的堕落是把新闻稿越写越动听来说服自己。
- 以"内部用户没有选择"为由跳过真实用户：第 1 章的 IT 案例证明员工"总有自己的选择"（用替代品、手工抄数据），内部项目的 PRFAQ 尤其必须发给真实的内部用户。

### 作者的盲点 / 时代局限

- 亚马逊与 Twilio 均为与作者有投资或合作关系的公司（BOOK_OVERVIEW 立场盲点：案例存在系统性幸存者偏差与推广动机），PRFAQ 在普通组织的失败率无数据。
- "先发布虚构新闻稿"依赖组织容忍公开讨论未立项想法的文化；对政治敏感场景（如内部制度变革的 PRFAQ 触怒既得利益者）书中未讨论。
- 书中未给出"多少份反馈才算数"的样本标准；方法默认用户愿意反馈，未覆盖 B2B 长决策链场景。

### 容易混淆的邻近方法论

- 产品需求文档（PRD）：PRD 是给开发团队的规格说明（打算做什么）；PRFAQ 是给用户的虚构事实（假装已发生），索取的是真实反应——受众、语态、目的都不同。
- 电梯演讲/路演稿：向投资人陈述以获取资源；PRFAQ 向用户发放以获取反馈——受众与成功判据相反。
- 《精益创业》正传：正传无 PRFAQ/逆向工作法（亚马逊方法由本书第 1、4 章引入组织场景）；正传的 MVP 起点在"造"，本 skill 起点在"写与谈"，是零代码的前置闸门。
