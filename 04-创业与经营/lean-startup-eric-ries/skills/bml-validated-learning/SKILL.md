# 经证实的认知：把开发—测量—认知循环跑对跑快

## R — 原文 (Reading)

> "成功地执行一项无意义的计划是导致失败的致命原因，而经证实的认知则是解决这个问题的首要方法。"
>
> —【作】埃里克·莱斯，第3章

> "如果创业团队的计划是'先推出产品，再来看会发生什么情况'……那么准保成功，因为他们一定会看到发生的情况，但却并不一定能获得证实的认知。这是科学方法中的重要一环：如果你无法失败，就学不到东西。"
>
> —【作】埃里克·莱斯，第4章

> "尽管我们把反馈循环按活动发生顺序写成'开发—测量—认知'，但我们制订计划的工作却是相反的：先确定需要知道什么，再用创新核算方法来确定需要评估什么、是否获得了经证实的认知，最后确定需要开发什么产品来进行实验，并获取那些评估。"
>
> —【作】埃里克·莱斯，第5章

> "实际上，这些活动本身并不是最重要的。我们要做的是集中精力，尽量把反馈循环流程的总时间缩减到最短。这就是驾驭新创企业的精髓所在……"
>
> —【作】埃里克·莱斯，第5章

> "虽然我们根据活动发生先后，把反馈循环写成开发—测量—认知，我们却应该以相反的顺序来安排计划：先找出需要知道什么，再倒回去看为了获得这个认知，要用什么产品进行实验。因此，不是顾客，而是我们'对顾客的假设'拉动了产品及其他功能特性开发的工作。除此之外的工作都是浪费。"
>
> —【作】埃里克·莱斯，第9章

## I — 方法论骨架 (Interpretation)

新创企业最危险的不是执行慢，而是高效地执行错误的东西。本书把"进展"重新定义为**经证实的认知**，并给出一台可操作的机器：

1. **进展的新单位是经证实的认知**：不是"我们学到了很多"的口头说法，而是以真实顾客的实证数据为基础、能发现商业前景真相的严格展示。它比市场预测或商业计划更快速、更切实；"把学习拿去银行"式的学习不算数。
2. **顾客无法直接告诉你答案**：大多数时候顾客事先不知道自己想要什么；他们以实际"行动或按兵不动"揭示真相。所以认知必须来自让真实顾客接触真实产品的实验，而非访谈与调查的转述。
3. **计划顺序与执行顺序相反**：执行时按"开发→测量→认知"走，计划时倒过来——先确定**需要知道什么**，再确定**要评估什么**，最后才确定**开发什么产品去做实验**。
4. **实验本身就是第一项产品**：实验不是理论探寻，而是可以招募早期使用者、可以失败的产品；"如果你无法失败，就学不到东西"。每项实验服务于建立围绕愿景的可持续业务。
5. **对顾客的假设拉动开发**：不是顾客需求拉动开发，而是"我们对顾客的假设"拉动开发——任何与验证假设无关的工作都是浪费。
6. **唯一重要的速度指标是整个循环的总时间**：不要优化某个环节做到极致，而要把"开发—测量—认知"跑完一圈的总时间压到最短。
7. **每圈循环的终点是一个决策**：数据回来后回答"改弦更张还是坚守不移"——深度裁决转 `pivot-or-persevere`，但循环必须以回答这个问题收口，否则只是空转。

## A1 — 书中的应用 (Past Application)

### 案例 1: IMVU 的 180 天与首次转型（ch03，主线案例）
- **问题**: 作者的 IMVU 按错误战略开发：产品"糟糕透顶、漏洞百出"，顾客干脆拒绝邀请朋友使用（17 岁女孩直言"从来没听说过，我的朋友们也没听过"），而团队曾以"零的愚勇"推迟数据收集。
- **方法论的使用**: 绝望中改为直接把早期版本交到真实顾客手里——顾客以行动揭示真相；随后用量化目标激发定性调查，逐步验证每一项假设，最终把原产品撤出市场、完成转型。
- **结论**: 经证实的认知不是事后诸葛亮，而是让团队在极端不确定中发现真相的严格方式；早拿不完美的产品接触顾客，胜过完美计划。
- **结果**: 转型后 IMVU 取得巨大成功——6000 多万虚拟人像、2011 年年收入逾 5000 万美元（引言语境）。

### 案例 2: Intuit 的实验文化（ch02/ch05）
- **问题**: 七千人的成熟企业如何判断新想法值不值得做？斯考特·库克反思经理人们当初"编造数字"过关的日子。
- **方法论的使用**: 库克要求："当你进行了500个测试……"把争论变成实验——税季两个半月内测试 500 多种想法、每周近 70 项、周四改版周末运行周一出结论。
- **结论**: 认知必须以实验计数来证明；大企业同样能用"实验即产品"的方式运转。
- **结果**: SnapTax 3 周内被下载 35 万多次；新业务面市一年取得的收入超过旧模式 5 年半的 5000 万美元。

### 案例 3: 字母能源的"假设拉动"（ch09）
- **问题**: 清洁技术新创企业字母能源靠政府拨款做研发，概念到实物周期极长；其原假设未经验证就投入多年。
- **方法论的使用**: 用"对顾客的假设"拉动开发：先做最小实验，概念到实物只花 6 周；当目标电力公司以低风险承受度否决原假设后，用 3 个月调查重新定位。
- **结论**: 与其假设拉动更早暴露"没人要"，胜过多年研发后才发现方向错误。
- **结果**: 及时转型避免了更大的沉没成本，公司仅用约 100 万美元就完成了这次方向修正。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队很忙但说不清"这轮到底验证了什么、学到了什么"，想知道怎么把工作组织成完整的验证循环。
2. 要向老板/投资人证明"我们有进展"，但拿不出收入增长，想知道经证实的认知怎么算数。
3. 纠结"先做什么功能"：听用户的还是听自己的？想知道产品开发应该被什么拉动。

### 语言信号 (用户的话里出现这些就应激活)

- "经证实的认知""BML""开发—测量—认知""验证循环""学到东西算不算进展"
- "计划顺序相反""先想清楚要学什么再开发""实验也是产品""如果你无法失败就学不到东西"
- "是用户需求拉动还是假设拉动""循环太慢""怎么证明我们学到了"

### 与相邻 skill 的区分

- 与 `lean-startup-five-principles` 的区别：后者讲"体系适不适用、总纲是什么"（入门判断），本 skill 讲"循环具体怎么跑对跑快"（执行主轴）。一句话若在问"该不该用精益创业"归前者，在问"怎么跑循环/算不算学到"归本 skill。
- 与 `leap-of-faith-assumptions` 的区别：后者只管循环的**起点**（把赌什么说清楚），本 skill 管**整圈循环**的组织与收口。
- 与 `mvp-design-patterns` 的区别：知道要学什么之后选实验载体（视频/贵宾/绿野仙踪）归后者；"要不要学、学什么、算没学到"归本 skill。
- 与 `innovation-accounting` 的区别：循环内"测量"环节的核算框架与阶段性目标归后者；本 skill 是循环的整体逻辑。问"怎么证明进展"若指要建体系→innovation-accounting，若指"学到的东西怎么算数"→本 skill。
- 与 `small-batch-acceleration` 的区别：后者是压缩循环总时间的**手段库**（批量、持续部署）；本 skill 讲循环本身该跑什么。

## E — 可执行步骤 (Execution)

1. **把点子翻译成待验证的认知需求**：从愿景出发，写下"现在最需要知道什么"
   - 完成标准：一句话假设陈述（一般现在时），指明"若为真/若为假各意味着什么"。
2. **倒排计划**：从"需要知道什么"倒推"要评估什么、开发什么实验"，砍掉与验证无关的工作
   - 完成标准：一张三列清单（要学什么→评估什么→开发什么）；每项待开发工作都能指向某个假设，否则标为浪费。
3. **用最小产物跑完一圈**：做出能接触真实顾客的最小实验，收集其实际行为数据
   - 完成标准：拿到以真实顾客行动（或按兵不动）为形式的结果，包含允许失败的数据点；"无法失败"的实验不算数。
4. **判定是否获得经证实的认知**：对照假设陈述检验数据是否证实或推翻了它
   - 完成标准：能说出"我们原以为 X，数据表明 Y"；经不起"这是不是拿学习当借口"的追问即重来。
5. **收口并加速下一圈**：记录本轮循环总时长，回答"改弦更张还是坚守不移"，并找出下一轮缩短总时间的一处改动
   - 完成标准：本轮总时长有记录、下一圈提速点已确定；若数据显示核心假设错误，转 `pivot-or-persevere` 做方向裁决。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户只是要选 MVP 形态、搭指标体系或做转型决策——这些是循环中的单点工具，转对应 skill。
- 用户做的是风险与不确定程度已知、仅靠执行即可推断成败的常规生意（ch02 自限场景）——循环验证的价值极低。

### 作者在书中警告的失败模式（按家族速查）

- **e06 把"学习"当借口（F3）**："你无法把学习拿去银行"——没有以实证数据为基础的"学习"不构成进展。
- **e07 "零的愚勇"（F3）**：推迟数据收集直到确认能成功——IMVU 早期正是这样，错失了本可及早发现的战略错误。
- **e05 分析瘫痪症（F2）**：立足的事实点错了且无休止分析——不在真实顾客身上实验，理论分析永远察觉不到。
- **e04 "想做就做"陷阱（F2）**："看看会发生什么"准保成功，因为一定会看到情况——但不一定获得证实的认知。
- **e11 产品开发的伪科学（F4）**：挂着实验名义却做无法被数据推翻的事——精益创业自身也会退化为新伪科学。

### 作者的盲点 / 时代局限

- 案例以 2000 年代互联网软件业为主（IMVU 每天 50 次改动等），"顾客接触成本低"的前提在硬件、强监管、长交付周期行业需大幅变通（书中亦承认四大减速路障）。
- 书中自限：已验证引擎下的纯优化运营阶段收益来自持续式创新工具，而非本循环。

### 容易混淆的邻近方法论

- **敏捷开发**：优化"开发"环节的交付效率，但缺"经证实的认知"的进展定义与转型决策——敏捷跑得快也可能高效地做错事（书中对 Grockit 的敏捷软肋批评）。
- **客户开发（Steve Blank）**：本方法的上游来源，聚焦"走出办公大楼"的顾客发现；BML 循环在其上补齐了衡量与核算（ch14 列为必读，互补而非等同）。
- **PDCA/包以德循环**：结构同构，但缺"计划顺序相反"与"实验即产品"两个关键反转，易退化为例行质检。
