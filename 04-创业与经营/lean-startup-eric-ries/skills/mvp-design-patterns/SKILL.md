# MVP 设计模式：把假设变成最小实验

## R — 原文 (Reading)

> "传统的产品开发通常要耗费很长的筹划时间，反复推敲，尽量把产品做到完美。与之相反，最小化可行产品的目的则是开启学习认知的流程，而不是结束这个流程。与原型或概念测试不同的是，最小化可行产品并非用于回答产品设计或技术方面的问题，而是以验证基本的商业假设为目标。"
>
> —【作】埃里克·莱斯，第6章

> "在这个案例中，一段视频就是最小化可行产品。它证实了休斯顿'信念飞跃'的假设，即顾客确实需要他正在开发的产品。这不是因为顾客在小组座谈中那么说，也不是因为它比其他业务更具有希望，而是由顾客真实的注册数量决定的。"
>
> —【作】埃里克·莱斯，第6章

> "在贵宾式最小化可行产品的情形中，个人化服务不是产品，而是企业增长模式的一种学习认知活动，用于检测信念飞跃式的假设。"
>
> —【作】埃里克·莱斯，第6章

> "他们使用了'即时反应的测试向导'（Wizard of Oz testing）进行模拟。在这种测试法中，顾客相信他们是和真正的产品互动，但在后台工作的其实是真人。"
>
> —【作】埃里克·莱斯，第6章

> "开发最小化可行产品具有风险，既有真实的风险，也有想象的风险。如果事先没有充分了解，它们足以令一家新创企业的努力付诸东流。最常见的减速路障是法律问题、对竞争对手的恐惧、品牌风险，以及对士气的影响。"
>
> —【作】埃里克·莱斯，第6章

## I — 方法论骨架 (Interpretation)

MVP 不是"省事版的正式产品"，而是**验证基本商业假设的最小实验装置**。本书给出一套从选型到排障的完整设计法：

1. **MVP 的目的：开启学习流程，而非结束它**：它不回答产品设计或技术问题，只以真实顾客的行为数据回答"基本商业假设是否成立"。它与概念测试/焦点小组的本质区别在于：判定依据是顾客真实的行动或按兵不动，不是嘴上怎么说。
2. **复杂度靠判断，但默认方向是化繁为简**：MVP 可以从一次极简单的"冒烟测试"（作用比广告多不了多少）到存在问题、缺失功能的早期原型。无法用公式确定该多复杂，但"大多数创业者和产品开发人员大大高估了一个最小化可行产品所要具备的功能。当遇有疑问，就化繁为简。"
3. **视频式 MVP——产品无法原型化时先卖"体验"**：当真实产品需要攻克重大技术障碍才能运行，用一段 3 分钟演示视频向早期使用者展示技术如何工作，以真实注册数量（而非口头兴趣）验证"如果我们能提供这种体验，人们会不会用"的假设。
4. **贵宾式 MVP——用人工服务模拟未来产品**：由创始人亲手为极少数早期顾客提供端到端服务（甚至 CEO 每周登门），目标由顾客真实行为衡量。关键定性：个人化服务不是产品，而是学习认知活动——它测的不只是价值假设，还有增长模式；"即便最初的最小化可行产品让公司赢利，也不意味着原定模式一定有效"。
5. **绿野仙踪测试——前台像真产品，后台是真人**：顾客以为在和真正的产品互动，实际由人实时应答。低效、不可规模化，但能在不解决底层技术难题的情况下回答"假如我们能解决这个问题，人们会用吗"。配套纪律：断然拒绝在实验早期就解决技术难题。
6. **共同判据：早期使用者接受"八成"产品**：超出早期使用者需要的额外功能或修饰，都是资源和时间上的浪费；早期使用者反而对太精致的东西心存芥蒂。
7. **四大减速路障各有化解之道，但真正的取胜之道是学得更快**：法律（专利窗口期自发布起计时，发布前寻求法律咨询）；对竞争对手的恐惧（做"让大公司盗用你的主意试试"的作业——成熟企业的经理人对接到的构想应接不暇，其瓶颈是排优先级和执行）；品牌风险（换一个不同品牌名发布，借"不起眼、少得可怜的曝光"埋头实验）；士气影响（MVP 常带来坏消息，须事先承诺无论结果如何都不放弃希望）。若竞争对手能更好地执行同样的创意，保密也救不了这家公司——"唯一的取胜之道是比任何人学得更快"。

## A1 — 书中的应用 (Past Application)

### 案例 1: Dropbox 的 3 分钟视频（ch06）
- **问题**: 文件同步产品需要整合多平台操作系统、后台服务须高度可靠，"根本不可能以原型产品形式来展示一个运行的软件"；投资人不相信文件同步是重要问题，休斯顿一次次路演仍无法让对方想象产品。
- **方法论的使用**: 拍一段针对技术圈早期使用者的 3 分钟演示视频，亲自配旁白、埋圈内人才懂的幽默文件命名，用它验证"如果能提供超级顾客体验，人们会不会试用"的信念飞跃假设。
- **结论**: 判定依据不是观众说好，而是真实的注册行为——视频式 MVP 用最低成本把"体验"先卖给了早期使用者。
- **结果**: "这个视频吸引了几十万人访问我们的网站。产品公测版的等候名单一夜之间从5 000人上升到75 000人。"（休斯顿【引】，ch06）公司后来身价超过 10 亿美元。

### 案例 2: 桌上美食的贵宾式 MVP（ch06）
- **问题**: 公司要做"每周菜单+杂货清单+本地比价"的服务，真软件尚未开发，如何验证顾客愿意为此付费、增长模式是否成立？
- **方法论的使用**: CEO 罗素和产品副总裁每周亲自登门为一位早期顾客服务：查她常去杂货店的折扣、按其喜好开菜单，人工递上装有购物清单和菜谱的包裹——"最关键的是，每周他们会收到一张9.95美元的支票"。
- **结论**: 收了钱不是重点，重点是个人化服务是学习认知活动而非产品；若靠人工就盈利便沾沾自喜，反而会掩盖"原定增长模式无效"的真相。
- **结果**: 公司以此逐个积累真实付费顾客、验证增长模式成立后，才投入自动化开发。

### 案例 3: Aardvark 的六个原型与真人后台（ch06）
- **问题**: 虚拟助手的答案需要人的判断，背后的人工智能是棘手的技术难题——先攻克技术还是先验证需求？
- **方法论的使用**: 麦克斯和戴蒙连续做了六个便宜的原型（Rekkit、The Webb 等），每个工作量仅 2~4 周，"我们尽可能用人工替代后台运行"（麦克斯【引】，ch06），邀请 100~200 位朋友试用并统计复用率；选中方向后，用绿野仙踪测试把真人后台持续了 9 个月、雇 8 个人应答分类，才逐步自动化。
- **结论**: MVP 的任务是把"技术能不能做"和"人们要不要用"解耦——先用真人后台验证后者，再投入前者。
- **结果**: 前五个原型"全是一边倒的负面结果"，第六个原型 Aardvark 验证了需求并据此筹得种子期和成长期投资，最终以 5000 万美元卖给谷歌。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 已经明确要验证哪个假设，但纠结"第一个版本做成什么样才最小、又真的测得到"——做全了浪费、做浅了测不出。
2. 产品涉及复杂技术或线下服务，没法先做出真东西，想知道有没有"假产品真数据"的测法（视频/人工后台/简陋收费版）。
3. 被"怕被大公司抄""要不要先过法务/专利""会不会砸牌子""团队士气受打击"四类顾虑卡住，迟迟不敢发布 MVP。

### 语言信号 (用户的话里出现这些就应激活)

- "MVP 怎么做""第一个版本做成什么样""最小可行产品""冒烟测试"
- "视频 MVP""拍个演示视频""贵宾式""人工先跑流程""绿野仙踪""后台是真人""假门/冒烟"
- "怕被抄袭/怕大公司抄""要不要等法务""专利窗口期""先悄悄开发憋大招""砸不砸牌子""发布会不会打击士气"

### 与相邻 skill 的区分

- 与 `leap-of-faith-assumptions` 的区别：后者管循环**起点**——把"赌什么"（价值/增长假设）找对说清；本 skill 管假设已明确之后**选实验载体**。一句话在问"我们到底在赌什么"归前者，在问"这个假设用什么形态测"归本 skill。
- 与 `bml-validated-learning` 的区别：后者管整圈开发—测量—认知循环的组织逻辑；MVP 只是循环中"开发"环节的载体选择。
- 与 `actionable-vs-vanity-metrics` 的区别：MVP 上线后"数据怎么解读、指标怎么搭"归后者；本 skill 止于把实验发出去并拿到真实行为数据。
- 与 `startup-quality-philosophy` 的区别：后者管"MVP 阶段质量做到几成"的哲学之争（八成产品、尽早发布）；本 skill 管实验的**形态选择与排障**，不裁决质量取舍。
- 与 `innovation-accounting` 的区别：MVP 测试结果出来后怎么建基准线、定阶段性目标归后者。

## E — 可执行步骤 (Execution)

1. **把假设翻译成行为判据**：写下要验证的商业假设，并规定"什么真实行为算数"（注册、复用、付费、推荐），杜绝用口头兴趣充当证据
   - 完成标准：一句话假设 + 一个由顾客行动（或按兵不动）构成的判定标准；写不出行为判据说明还没到选 MVP 的阶段，转 `leap-of-faith-assumptions`。
2. **按"假设类型 × 接触成本"选最小变体**：难以原型化→视频式；服务型/流程型→贵宾式；技术门槛高→绿野仙踪；只测兴趣→冒烟测试；以上都不够→缺失功能的早期原型
   - 完成标准：能说清"为什么这个变体够最小、又测得到目标假设"，并写下替代方案为何被否。
3. **化繁为简裁剪功能**：逐项审功能清单，砍掉一切与验证假设无关的部分；用早期使用者的标准而非主流市场的标准衡量"够用"
   - 完成标准：保留的每项功能都能指向某个待验证假设；拿不出对应假设的功能标为浪费并删除。
4. **逐项排查四大减速路障并写明对策**：法律（发布前咨询专利窗口期）、竞争恐惧（做"让大公司盗用你的主意"作业检验恐惧是否成立）、品牌（换品牌名发布、低调实验不办高调发布）、士气（事先承诺无论结果如何都不放弃希望）
   - 完成标准：四项各有一行书面对策或"已评估、不适用"的理由；任何一项未评估不得发布。
5. **发布并收口到衡量环节**：把 MVP 交到真实顾客手里，收集行为数据，对照行为判据宣布假设成立/被推翻，进入创新核算
   - 完成标准：拿到真实行为数据并给出"原以为 X，数据表明 Y"；无论结果好坏，项目按事先承诺继续循环，数据解读转 `actionable-vs-vanity-metrics`，基准线与决策转 `innovation-accounting`。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户还说不清要验证什么假设——先转 `leap-of-faith-assumptions`，载体选择是下游问题。
- 用户要的是"MVP 上线后数据怎么解读"或"质量该做到几成"——分别转 `actionable-vs-vanity-metrics` 与 `startup-quality-philosophy`。
- 风险与不确定程度已知、靠执行即可推断成败的常规生意——花哨的最小实验没有认知增量。

### 作者在书中警告的失败模式（按家族速查）

- **e02 Webvan 与 Pets.com 先建完整网站（F1）**：与 Zappos 的手工"假店"构成原文自带正反对照——一次到位的完整投入赌上了全部资源，而非先验证基本商业假设。
- **e05 分析瘫痪症（F2）**：立足的事实点错了且无休止分析调整——不做真实顾客接触的 MVP，理论分析永远察觉不到立足点错误。
- **e07 "零的愚勇"（F3）**：推迟数据收集直到确认能成功——以"产品还不配见人"为由无限期延后发布，错失唯一的低成本学习窗口。
- **e10 Votizen 意向书（F4）**：把意向书这类过早乐观信号当成已验证需求——MVP 的判定必须是真实行为（付费/注册/复用），不是口头承诺。
- **e17 过度构架（F8）**：为想象中的规模化过度构架、耽误上市——正是"大大高估 MVP 所需功能"的工程版，Friendster 即前车之鉴。

### 作者的盲点 / 时代局限

- 案例集中于 2000 年代互联网软件（视频获客、后台真人应答、快速改版），"真人后台可长期维持、换品牌名即可隔离品牌风险"在硬件、强监管、线下重资产行业成本结构完全不同；作者自己也承认专利法律对发布时机的制约"应该作为公共政策问题加以修正"。
- "早期使用者接受八成产品"的前提是能识别并触达早期使用者；面向大众市场的产品若误把普通顾客当早期使用者测试，会得到假阴性结论。
- 书中强调士气路障的解法是"事先承诺不放弃希望"，但未给出与"错的坚持"（ch08）相冲突时的裁决机制——需要创新核算与转型会议补位。

### 容易混淆的邻近方法论

- **概念测试 / 焦点小组**：问顾客"会不会用"；MVP 要求顾客以真实行动作答——原文明确二者目标不同（设计/技术问题 vs 商业假设）。
- **营销"冒烟测试"落地页**：只测兴趣与转化，是 MVP 光谱的最低配；若假设涉及留存与增长模式，冒烟测试不够，需贵宾式或原型。
- **敏捷开发的 spike / 技术原型**：回答的是技术与设计问题，恰恰不是 MVP 的目标；做出漂亮原型 ≠ 验证商业假设。
- **A/B 测试**：在已有流量的产品上比较两个版本；MVP 阶段往往尚无可分流的真实流量，二者是循环不同阶段的工具。
