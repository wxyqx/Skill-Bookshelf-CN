# 快的四能力与快慢律：战略快不得，战术慢不得

## R — 原文 (Reading)

> 因为对'快'的片面追求，而没能下决心及时对团队进行调整，解决当时已经存在的硬件研发团队管理问题，由此造成了产品规划、交付等系统能力的严重落后，这是我们犯下的最严重、最致命的错误。
>
> — 雷军，第六章 七字诀（快的反面教训，复盘 2015 年危机）

---

## I — 方法论骨架 (Interpretation)

作者把"互联网思维里的快"从口号拆成两部分：

**四能力拆解**：快不是一种态度，而是四种可分别对标、分别改造的组织能力——洞察快（发现用户需求与问题的速度）、响应快（从洞察到行动的时滞）、决策快（内部拍板的链条长度）、改善快（从反馈到修复/迭代的周期）。MIUI 的每周迭代是把"实现快的机制"本身当创新产品做：固定迭代周期、反馈指标化、用户投票排优先级。

**快慢律**：快的边界由事项层级决定——战略积累快不得，组织能力、技术体系、重大决策这类慢变量无法靠战术提速绕过，重大节点宁可慢、想明白再决策；战术演进慢不得，功能迭代、用户响应要用机制锁定速度。一句话：局部的、阶段性的慢，换取全局的快。片面追求一切动作都快（连该做的组织手术都怕慢而不做），欠账会在最脆弱的时刻集中爆发。

## A1 — 书中的应用 (Past Application)

### 案例 1: MIUI 每周迭代机制——把"快"做成产品
- **问题**: 操作系统行业惯例是数月到一年一个版本，用户反馈到修复的周期极长。
- **方法论的使用**: MIUI 固定每周五更新（"橙色星期五"），用户反馈指标化、投票决定功能优先级，把响应快与改善快变成制度而非个人努力；先有倾听与参与再放大（响应快的入口是用户直连）。
- **结论**: 快的机制可以像产品一样被设计与迭代。
- **结果**: MIUI 一年做到 30 万用户，每周迭代成为小米方法论"快"的原型机制。

### 案例 2: 2015 危机——片面求快拖垮战略积累（反面）
- **问题**: 硬件研发团队管理问题早已显形，产品规划与交付系统能力严重落后。
- **方法论的使用**: 用快慢律复盘——组织能力是战略层慢变量，本应"宁慢想明白、及时动手术"；当时却因怕影响势头迟迟不下决心调整，用促销和营销掩盖缺口，恰是"把快用错了层"。
- **结论**: 该慢的事拖、该快的事也慢，两头都错。
- **结果**: 成为作者自认"最严重、最致命的错误"，2016 年被迫由创始人接管手机部全面补课。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 组织响应/改善速度慢：从发现用户抱怨到修复要数周，决策要层层汇报，想诊断瓶颈在哪。
2. 节奏之争："这波机会要不要抢跑还是等想清楚"，或老板要小步快跑、CTO 要一次想透，需要判层定速。
3. 设计迭代机制：想让团队像 MIUI 那样有固定的快节奏迭代与反馈闭环。
4. 复盘"因为怕慢而拖延的重大调整"（换人、换架构、砍产品）造成的损失。

### 语言信号 (用户的话里出现这些就应激活)

- "太慢了 / 决策链太长 / 迭代周期怎么提上来"
- "该抢跑还是该想清楚 / move fast or think it through"
- "小步快跑还是一步到位"
- "为什么以前很快，现在越来越慢"

### 与相邻 skill 的区分

- 与 `sunk-cost-restart` 的区别: restart 处理"方向/定义错误后要不要推倒重来"的止损判定；本 skill 处理"对的事该用什么节奏做"。红米案例的归属按主诉：问快慢节奏归本 skill（改善快），问 4000 万沉没成本该不该沉归 restart。
- 与 `endgame-reasoning` 的区别: endgame 论证"要不要做"（大额不可逆决策的内容），本 skill 管"决定了之后用什么速度推进"；造车案例里 75 天论证属战略层宁慢（endgame），官宣后产品推进属战术层快（本 skill）。
- 与 `downturn-remediation` 的区别: downturn 是失速后的全面组织诊断与补课；本 skill 是常态下的节奏设计。若慢的根源是系统性能力欠账且已酿成危机，转 downturn。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **判层**
   - 把眼前事项按快慢律归类：战略层（组织能力、技术路线、重大决策、不可逆投入）还是战术层（功能迭代、用户响应、日常改善）。
   - 完成标准: 每个事项有层级标签与归类理由。
   - 判停条件: 若事项被判定为"方向/定义层面的错误正在发生"，转 sunk-cost-restart 处理止损，不在本流程内。

2. **战略层：宁慢想明白**
   - 重大节点允许并要求慢：补齐反面论证、做关键依据核验，不因竞争压力抢拍板。
   - 完成标准: 决策文档同时载明正反两面论证与"想透"的证据；禁止用战术动作（促销、加班）替代战略补课。

3. **战术层：四能力对标诊断**
   - 对洞察/响应/决策/改善四项分别找瓶颈：需求发现时滞、行动启动时滞、审批链条长度、反馈到修复周期。
   - 完成标准: 四项各有现状时长数据（或合理估计）与瓶颈环节定位。

4. **机制化提速**
   - 把"实现快的机制"当产品做：固定迭代周期、反馈指标化、授权前置（减少审批层级）、投票/数据排优先级。
   - 完成标准: 产出带周期与指标的迭代机制方案，并明确指标复盘节奏；"局部的慢换全局的快"作为总原则写入方案。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户要的是个人时间管理/效率工具（GTD 等）——本 skill 针对组织层节奏，非个人效率。
- 事项本身是"要不要进入某行业"的大额决策——先走 endgame-reasoning 论证，本 skill 只管其后的推进节奏。
- 产品已判定方向性错误——归 sunk-cost-restart，继续提速迭代只是加大损失。

### 作者在书中警告的失败模式

- **片面求快牺牲战略积累**（2015 危机）: 怕影响势头而拖延组织手术，用营销掩盖系统能力缺口，欠账在最脆弱时刻集中爆发。
- **把快用于为拖延辩护**: "再观察观察"式的决策拖延与"抢跑"是同一种判层错误——该慢的拖与该快的等都是错层。
- **快而无口碑**: 只提速不改善，交付更快但质量更差，加速用户流失（对照口碑篇与低谷教训）。

### 作者的盲点 / 时代局限

- **进行时假设**: MIUI 每周迭代在软件形态成立，书中将其外推到造车等硬件重业务（战略层慢/战术层快的分野）属 2022 年进行时的未充分验证假设。
- **窗口期红利被弱化**: 小米的快得益于 2010 年移动互联网换机潮+社交媒体红利，方法论的普适性被幸存者叙事放大。
- **四能力缺乏量化基准**: 洞察/响应/决策/改善的"快"在书中无第三方可比数据，诊断时须自行建立基线，勿直接引用书中成效数字。

### 容易混淆的邻近方法论

- 精益创业/敏捷开发: 与"战术层快"高度同构；本 skill 的增量是快慢律的判层规则——战略层不适用迭代逻辑，这是与"一切皆可敏捷"的关键差异。
- 第一性原理决策: 都反对惯性，但本 skill 只裁节奏，不裁方向对错。
