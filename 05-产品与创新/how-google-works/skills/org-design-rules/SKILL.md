# 组织设计三律（7 的法则 + 两个比萨 + 影响力中心）

## R — 原文 (Reading)

> "在谷歌，我们要求每位管理者的桌上至少要放7份直接报告……这一原则会让企业的组织结构趋于扁平，减少管理层的监督并赋予员工更多自由。" / "找出最有影响力的人物，组织就以此人为中心。不要把岗位或经验作为选择管理者的标尺，而要看他的表现和热情。"
>
> — 施密特、罗森伯格，第一章《7 的法则》/《组织要以最有影响力的人物为中心》

---

## I — 方法论骨架 (Interpretation)

三条硬规则各管一件事，方向都和直觉相反。

①**7 的法则管层级**：传统经验是"管理幅度别超过 7 人"，本书反转为**至少** 7 份直接报告——管理者忙到没有闲工夫事事插手，微观管理失去物理条件，授权和扁平是被动发生的，不是喊出来的。它来自"解散组织"实验的教训：结构不能没有，但要压扁。

②**两个比萨管团队**：一个协作单元的人数以两个比萨喂得饱为上限。小团队效率高、内耗少；大团队可以存在，但前提是不阻碍原有小团队做突破性创新。

③**影响力中心管结构形状**：组织围绕最有影响力的人搭建，而不是围绕岗位、职能或资历划块；选管理者看表现和热情。配套动作：高管会议至少一半席位给产品专家，保证决策层的注意力落在产品而非运营要素上。

诊断工具是"产品痕迹检验"：打开 iPhone 包装盒，你推不出苹果的内部权力地图——产品里一旦能看出部门利益的痕迹，说明组织结构先出了问题。重组纪律是配套细则：速战速决、敲定前就开始实施。

## A1 — 书中的应用 (Past Application)

### 案例 1: "解散组织"实验与 7 的法则的诞生
- **问题**: 两位创始人试过极端扁平——彻底取缔全部管理层。
- **方法论的使用**: 工程负责人韦恩·罗辛一度收到 130 份直接报告，被例行汇报淹没；实验证明"没有结构"不是自由，而是把协调成本转嫁个人。
- **结论**: 创意精英也需要正规结构，正确方向是"保留结构但压扁"。
- **结果**: 由此敲定"至少 7 份直接报告"的下限规则，成为谷歌组织设计方针（c18）。

### 案例 2: 太阳公司"行星"结构的反面教训
- **问题**: 太阳公司按业务单元（"行星"）划分并自负盈亏，总收益却几乎全来自硬件。
- **方法论的使用**: 公司被迫专设保密的会计团队做内部收益分配，各单元负责人盘算会计等式而非产品。
- **结论**: 分部损益制造就"各成一家"，扼杀人员与信息的自由流动。
- **结果**: 行星结构重创生产力；谷歌据此长期坚持职能制，工程/产品/财务/销售直接向 CEO 汇报（c19）。

### 案例 3: 尼科什数周完成数千人重组
- **问题**: 广告产品线扩张让销售团队困惑，尼科什要打造"一个谷歌"，重组牵扯数千人。
- **方法论的使用**: 速战速决——在细则敲定之前就把决定透露给团队并开始实施。
- **结论**: 让成员融入重组反而使其更稳固；一拖就烂。
- **结果**: 数周内完成重组，初衷实现且效果超预期（c20）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计或调整组织架构：该不该加层级、设 COO、按业务线还是按职能分部门。
2. 重组推进不动：方案讨论几个月、人人观望、跨部门扯皮。
3. 团队规模失控：项目组越滚越大、开会人越来越多、突破性创新变慢。
4. 董事会/管理层以"管理幅度太宽"为由建议增设中间层级。
5. 发现产品里留着组织结构的痕迹：每个业务部门都坚持要自己的入口，说明书/界面像内部权力地图。

### 语言信号 (用户的话里出现这些就应激活)

- "管理幅度 / 直接汇报几个人 / span of control / 要不要设 COO"
- "扁平化 / flatter organization / 层级太多 / 微观管理"
- "重组 / reorg / 组织架构调整 / 两个比萨 / two-pizza team"
- "按业务线还是按职能 / 事业部制 / 各自为政"
- "产品里全是部门的影子 / 每个部门都要一个入口"

### 与相邻 skill 的区分

- 与 `hippo-resistance` 的区别：河马是**话语权**问题（谁的意见在会上被高估），本 skill 是**结构**问题（汇报线、团队规模、组织形状）。扁平结构（本 skill）会削弱河马的信息霸权，但会议里仍需防河马机制，两者组合使用。
- 与 `expel-villains-protect-stars` 的区别：那个处理"具体某个人的品行与去留"；本 skill 处理"人与人的连接方式"。结构烂不等于人有问题，别用整人替代改结构。

## E — 可执行步骤 (Execution)

1. **诊断管理幅度**
   - 完成标准：列出每位管理者的直接汇报数，判断是否达到"至少 7"的下限；给出加层/减层的建议及理由。
   - 判停条件：若诉求是"彻底取消管理层"，先复述"解散组织"实验教训（结构不可无），把问题改写为"如何压扁"再继续。
2. **检验团队规模与影响力中心**
   - 完成标准：逐个项目组回答"两个比萨喂得饱吗"；指出组织事实上的中心是谁——看表现与热情，不看岗位资历；核对高层会议是否一半席位是产品专家。
3. **产品痕迹检验（iPhone 包装测试）**
   - 完成标准：回答"用户能否从产品结构反推出内部权力地图"；能→列出每个痕迹对应的部门利益，决定是重构产品还是重构组织。
4. **若在重组，执行三条纪律**
   - 完成标准：压缩时间线（理想一天内、至多数周）；方案敲定前就让团队参与实施；预先抵消各职能的系统性偏好（工程要复杂、市场要层级、销售要助理）。
5. **守住"不加流程"的闸门**
   - 完成标准：每次增设审批/门槛都附带强业务理由，否则默认说"好"；资源分配用二分法——办公室面积之类的面子工程从简，计算能力/工具/数据等生产资料顶配。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **3–5 人初创团队**——人人互为管理者，管理幅度是伪问题；两个比萨和影响力中心倒是可以用来组项目。
- **劳动密集、强合规、排班制团队**——作者的默认员工模型是工程师型创意精英，"忙到无法插手"对安全攸关场景是缺陷不是特性（作者盲点，见下）。
- **以"扁平"为名取消管理层的诉求**——那是要被实验证伪过的极端，不是本 skill 的内容。

### 作者在书中警告的失败模式

- "解散组织"实验：单个负责人被 130 份直接报告淹没，扁平走极端反而吞掉创意精英的全部时间（ce12）。
- 太阳公司"行星"结构：分部损益表让领导者从做产品转向盘算内部结算，自扫门前雪（ce13）。
- 产品藏着组织图：服务器里 6 份互不相让的使用说明书、又大又醒目的点播键——每个设计决定背后是一个部门的 KPI（ce14）。

### 作者的盲点 / 时代局限

- 全书以工程师/产品人才为默认员工模型，对劳动密集型、强合规、线下运营行业的可移植性基本未讨论（BOOK_OVERVIEW 批判节）。
- 案例来自谷歌式高利润引擎；"职能制直接向 CEO 汇报"在多元化巨型集团中是否成立，书中未验证。

### 容易混淆的邻近方法论

- 传统"管理幅度 7±2"经验值：方向相反——本书的 7 是**下限**（逼授权），不是上限（控制范围）。
- `hiring-ops` 的招聘委员会：那是把录用决策权去利益相关化；本 skill 是汇报结构与团队规模，别把"组织设计"扩大到招聘流程。
- 两个比萨 ≠ 少招人：招人标准是 `hiring-quality-bar` 的事，比萨只管协作单元的规模上限。
