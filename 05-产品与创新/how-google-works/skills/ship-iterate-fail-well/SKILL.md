# 交付—迭代与败得漂亮

## R — 原文 (Reading)

> "打造一款产品，投放市场，看看反响如何，设计并加以改进，再重新投入市场。这就是交付和迭代，在此方面最为眼疾手快的公司，才能成为赢家。" / "修改创意，而不要否决创意……不要拿失败的团队问罪……因为下一批创新者正在静观其变，想看看失败的团队会不会受到惩罚。"
>
> — 施密特、罗森伯格，第六章《创新：缔造原始的混沌·交付，迭代／败得漂亮》

---

## I — 方法论骨架 (Interpretation)

发布不是终点，而是获取真实反馈的手段：交付→看数据→改进→再交付，谁转得快谁赢——实验与失败的成本骤降后，"快"本身就是产品成功的秘诀。但它有两个常被漏掉的前提。其一，**性能必须卓越、功能可以有限**：迭代修补的是覆盖面，不是烂底子；拿糟糕产品赌品牌，营销救不回来。其二，**低调上市**：别靠公关造势，让产品自己积累升力——被吹捧上天的产品更容易让用户觉得名不符实，资源只在产品展现"胜者锋芒"后才投入。

另一半是失败的处理学，两条规则构成一个闭环。**止损要快**：预先建立检验标准，看每次迭代有没有把产品一步步推向成功；当你需要"一连串的奇迹"才能成功时，就该打住——且只认未来数据，不认已投入的沉没成本。**善后要讲究**：解剖失败产品、移植其中可用的技术（修改创意而非否决创意），团队不问罪、妥善安置——因为下一批创新者正看着你如何对待这一批。

两半合起来的目标不是"容忍失败"的姿态，而是打造一个不会因风险和失误而垮台的组织（反脆弱）：愿景上固执，细节上灵活。

## A1 — 书中的应用 (Past Application)

### 案例 1: Chrome 悄然上市——7000 万用户后才打广告
- **问题**: 2008 年浏览器大战，新产品上市要不要配营销与公关造势？
- **方法论的使用**: Chrome 基于"网站变复杂、浏览器应提速"的技术洞见，在几乎没有营销资金的条件下悄然上市，完全靠性能积累动力；用户突破 7000 万后，团队才决定投入营销甚至电视广告。
- **结论**: 低调上市、先飞再喂——只给展现胜者锋芒的产品投资源。
- **结果**: Chrome 从问世第一天起在速度与安全上占据首位，逐步成为主流浏览器（c86）。

### 案例 2: Wave 的失败——败得漂亮的完整样板
- **问题**: 悉尼小团队用 20% 时间探索"电子邮件若是今天发明会怎样"，做出被吹捧上天的 Wave，上市后用户却始终不成气候，怎么办？
- **方法论的使用**: 不把大笔投资砸在没有前途的产品上——一年后果断宣布放弃；团队没有任何人被炒、多数被重用；解剖产品把技术移植进 Google+ 和 Gmail。
- **结论**: 速战速决喊停、不拿失败团队问罪、修改创意而不否决创意。
- **结果**: Wave 2010 年关闭，但技术资产被继承、团队获重用；"下一批创新者正在静观其变"的示范效应保住了（c87）。

### 案例 3: Google Instant——没有财务分析就发布核心功能
- **问题**: 即时搜索会在用户敲回车前展示结果，可能冲击广告点击收入；要不要先算清账再上？
- **方法论的使用**: 乔纳森问团队有没有数据能预测收入影响，答案是没有；但技术洞见（省掉用户等待）足够有力，团队决定继续发布——为用户质量牺牲短期收益。
- **结论**: 迭代决策锚定用户价值与数据反馈，而非内部审批与预测模型。
- **结果**: Google Instant 如期问世，对利润影响不大（c72）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 上线决策纠结：产品"再打磨一个月更完美"，团队吵着先发布收集反馈。
2. 迭代多轮但核心数据一直平坦，不知道是继续改还是该砍。
3. 项目/产品刚失败：要不要公开承认、团队怎么安置、沉没的投入怎么面对。
4. 新品上市方案评审：市场部要求大造势，产品负责人担心吹过头。
5. 想建立"失败不追责"的迭代文化，但担心变成"失败无所谓"。

### 语言信号 (用户的话里出现这些就应激活)

- "要不要先上线 / MVP / 快速迭代 / ship early / release early"
- "低调发布 / 静默上线 / 别搞发布会 / quiet launch"
- "迭代了好几轮还是没起色 / 何时止损 / kill criteria"
- "已经投了几百万，放弃可惜 / 沉没成本 / sunk cost"
- "失败团队怎么办 / 复盘追责 / fail well / 败得漂亮"

### 与相邻 skill 的区分

- 与 `resource-70-20-10` 的区别：那个回答"这个项目该占多少资源"，本 skill 回答"这个项目怎么发布、何时喊停、失败后怎么收场"；10% 项目止损后资源回流，是两个 skill 的衔接点。
- 与 `innovation-chaos` 的区别：那个管创意怎么冒出来（环境），本 skill 管创意做出来之后怎么处理（节奏与善后）；混沌负责"生"，交付-迭代负责"养与葬"。
- 与 `decision-timing-discipline` 的区别：马背原则管"信息不全时敢不敢拍板"，本 skill 管"拍板之后的发布-反馈循环"；前者是决策时点，后者是产品节奏。

## E — 可执行步骤 (Execution)

1. **发布前自检：卓越与否**
   - 完成标准：回答"核心性能是否卓越、覆盖面是否有限"——底子卓越可上线（功能有限可接受），底子糟糕则退回打磨，明确禁止用营销补产品（Excite@Home 之鉴）。
2. **低调上市**
   - 完成标准：上线方案中营销预算为零或最小化，无预热造势；产品靠真实使用数据积累升力；写明触发条件——出现"胜者锋芒"信号（留存/复购/自然增长）后才追加营销资源。
3. **迭代并盯检验标准**
   - 完成标准：为迭代设立可验证的推进指标（每次迭代后指标是否向成功移动），数据系统先于迭代存在，"是否成功"由数据而非投入者自评。
   - 判停条件：连续迭代后指标平坦、兴奋点只集中在极客圈层、或成功需要"一连串奇迹" → 停止迭代，转步骤 4。
4. **败得漂亮：止损与善后**
   - 完成标准：以最快速度喊停（决策理由只引用未来回报，不引用已投入量）；解剖产品列出可移植技术与组件（修改创意不否决创意）；团队成员有明确安置去向，不问罪。
5. **把失败变成公共信号**
   - 完成标准：失败案例在组织内如实复盘并公开"团队未被惩罚、技术被继承"的结果——检验"下一批创新者"是否仍敢动手（观察者效应）；若无人再提自选项目，说明善后失守，回查步骤 4。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **安全/合规底线领域**：医疗、金融核心系统、航空等场景里"先上线再改"的代价不可逆——迭代适用于可回滚、可灰度的对象，底线问题必须前置验证。
- **一次性、不可迭代的产品**：婚庆、大型活动等无"再投市场"机会的对象，迭代循环无从运转。
- **个人品牌豪赌**：内容创作者可以把题材覆盖做有限，但质量必须卓越——不能拿糟糕作品赌个人信誉（V2 推演的边界）。

### 作者在书中警告的失败模式

- **交付-迭代并非总是有效**：Wave 拼命迭代一年仍失败——概念与主流用户习惯错位时，迭代修不回需求侧的真空（ce48）；这正是"检验标准+奇迹判据"存在的原因。
- **用资源补贴失败者**：Excite 把弱板块挪到首页救点击量——数据被用来达标而非取舍，强者被抽税（ce49）。
- **沉没成本谬误与承诺升级**：以已投入量决定继续、报喜藏忧、用追加预算冒充进展——掌权者用组织的钱保卫自己的声誉（ce50；苹果牛顿是同源反例，c78）。

### 作者的盲点 / 时代局限

- 谷歌眼镜：90 分钟做出模型（c10）被引为快速原型的荣耀，但产品最终未能大众化——"快速迭代"只保证了起点，不保证终点，引用案例时应把结局一并交代。
- 原则之间的张力未被调和：速度（眼疾手快）与共识流程（第四章）在真实组织中互相拖扯，书中未给出谁让位。
- 幸存者偏差：Chrome、Gmail 的低调上市被铭记，而被砍掉的产品名单（Notebook/Knol/Wave/Buzz）只在证明"营销救不了平庸"时才出场。

### 容易混淆的邻近方法论

- 精益创业 MVP（Ries）：循环形态几乎相同；本书独特在善后的机制化——"修改创意不否决创意""失败团队不问罪（下一批创新者静观其变）""7000 万用户后才投广告"的低调上市参数。
- "fail fast"口号：只含止损半边；本书强调败得**漂亮**——速战速决与体面善后缺一不可，且善后是给未来创新者的信号。
