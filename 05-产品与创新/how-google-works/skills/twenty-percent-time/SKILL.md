# 20% 时间制（重点在自由，不在时间）

## R — 原文 (Reading)

> "谷歌的'20%时间'工作方式，允许工程师拿出20%的时间来研究自己喜欢的项目……该制度的重点在于自由，而不在时间长短。" / "这个制度对那些看管严格的管理者起到了制约平衡的作用。" / "来自外部的奖励非但不能激发创意，反倒会将一件原本能给人带来满足感的事情变成赚钱的差事，从而阻滞灵感。"
>
> — 施密特、罗森伯格，第六章《创新：缔造原始的混沌·20%时间制》

---

## I — 方法论骨架 (Interpretation)

把"创意来自自主权"翻译成一条制度：允许工程师把一部分工作时间花在自己选的项目上。但它真正的标的是**自选目标权**，不是那 20% 的工时——时间可攒可散，实际常常变成夜晚和周末的"120%"；如果组织把它做成每周五下午必须填表的福利，制度就已经死了。

运行机制有三条。①**去考核、去奖金**：不写进绩效、不发钱——外部奖励会把"满足感的事"变成功利交易，工作本身的意义就是报酬。②**原型是社交货币**：想到好点子不难，吸引同事投入才难；先做出看得见的原型，才能吸引别人把他们的 20% 投到你的 20% 上（第一追随者的入场券）。③**演示日把孤胆英雄变成团队**：一周冲刺建原型、周末公开展示、至少两人成组、孤军奋战不允许。

这个制度还有一层容易被忽略的功能：它是**给看管严格的管理者的制衡器**——只要制度在，管理者就无法用日常排期把员工的全部时间没收。

## A1 — 书中的应用 (Past Application)

### 案例 1: Google Suggest——原型引来第一追随者
- **问题**: 工程师凯文·吉布斯想到"输入前缀就提示搜索词"的点子，不在任何人的 OKR 里，怎么让它活下来？
- **方法论的使用**: 他用 20% 时间建出模型，把项目简介群发给爱分享点子的邮件群（他的提案排第 917 个，榜上点子超 1.5 万个），用原型吸引"第一追随者"加入。
- **结论**: 20% 时间的重点在自由而非时长；原型是吸引合作者的最佳工具。
- **结果**: Google Suggest 上线，几年内成为全球用户的默认搜索习惯（c80）。

### 案例 2: 保罗·布赫海特"入侵"广告服务器
- **问题**: 保罗用 20% 时间做的邮箱（Gmail 前身）想按邮件内容显示广告，管理层让他先完善产品、别急着赢利——他不听。
- **方法论的使用**: 保罗擅自"入侵"内部系统接通 AdWords 服务器，让全员一觉醒来看到邮箱里的广告（而且那广告还真帮上了忙）；公司没有惩罚他的擅自行动。
- **结论**: 20% 制度容纳越界：对正确的人的固执应予容忍，惩罚自选项目里的"违规"等于杀死制度。
- **结果**: Gmail 问世（现几亿用户），其广告匹配技术改良后成为几十亿美元 AdSense 的基石（c82）。

### 案例 3: 卡特里娜飓风——工作本身就是奖励
- **问题**: 2005 年卡特里娜飓风席卷墨西哥湾，人手不多的"地理"团队怎么响应救灾？
- **方法论的使用**: 无人指派，团队自发连晚加班发布 8000 张卫星图像；管理层唯一的参与是埃里克到"作战室"说了一句"继续把工作进行下去"——不设奖金、不计报酬。
- **结论**: 20% 项目不发钱：外部奖励反而阻滞灵感，工作本身就是动力。
- **结果**: 项目演变为隶属 Google.org 的专业危机应对团队，后参与多国救灾（c88）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想在公司/团队里设立"自由时间/自选项目"制度，不知道细则怎么定才不走样。
2. 制度已存在但名存实亡：没人真的在用，或被 manager 的排期悄悄收走。
3. 想用奖金、积分、排行去"激励"员工做创新，担心适得其反。
4. 组织内部黑客松/演示日/创新周的规则设计（冲刺时长、展示、组队规则）。
5. 管理者抱怨下属"拿公司时间干自己的事"，想判断该禁止还是疏导。

### 语言信号 (用户的话里出现这些就应激活)

- "20% 时间 / 自由时间 / 自选项目 / pet project / side project（公司内）"
- "谷歌的 Gmail 是怎么冒出来的 / 20 percent time"
- "黑客松 / 演示日 / demo day / 创意周规则"
- "要不要给创新发奖金 / 悬赏创意"
- "制度变成摆设 / 没人用 / 名存实亡"

### 与相邻 skill 的区分

- 与 `innovation-chaos` 的区别：那个讲创新环境的总纲（创新不可指派、CEO 兼任首席创新官），本 skill 是其中一条可落地的具体制度——先有"给自由"的环境哲学，再谈时间制的细则。
- 与 `resource-70-20-10` 的区别：70/20/10 分配的是组织的预算与人力（自上而下），20% 时间制保护的是个人的自由时间（自下而上）；前者要拍板，后者要的是"别管"。
- 与 `ship-iterate-fail-well` 的区别：原型做出来之后的交付、迭代与止损是那个 skill 的事；本 skill 只负责让原型有机会被做出来。

## E — 可执行步骤 (Execution)

1. **检查前提：保护的是"自选目标权"**
   - 完成标准：制度文本不写"每周必须满 N 小时、需审批项目内容"；明确时间可攒可散（包括夜晚与周末的 120% 也算数）；项目方向由员工自选。
   - 判停条件：组织要求先审批"做什么"才能用时间 → 制度已变质为指派，回到 `innovation-chaos` 先修环境，不要继续做细则。
2. **去考核、去奖金**
   - 完成标准：自选项目不计入 KPI、不发项目奖金、不设采纳提成（创意积分榜只作交流用，不作金钱兑换）；对外解释"与钱无关"的理由（外部奖励阻滞灵感）。
3. **立"原型先行"规则**
   - 完成标准：想做 20% 项目的人先交付可见原型（哪怕土法拼装）；用原型在邮件群/内网招募伙伴，而不是先写方案说服。
4. **设演示日机制**
   - 完成标准：定期一周冲刺+周末展示；会前清空普通会议与发布日程；规则明文"至少两人成组，孤军奋战不允许"；鼓励与不常共事的人组队。
5. **跑存活条件自检（防名存实亡）**
   - 完成标准：每季度回答三问——过去一季有几个人真的用了 20%？有没有 manager 用排期事实性没收它？有没有出现"越界但未被惩罚"的容忍案例？三问有两问为否，则制度已空心化，先修管理层承诺。
   - 判停条件：核心业务进入全员救火期 → 明确宣布暂停而非名义保留，恢复时重启。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **员工下班后的副业管理**：20% 时间制是"公司时间内的自主权"，不是副业合规问题——拿它去规范业余时间属于误用。
- **把制度当福利做门面**：如果组织实际要求逐日打卡、按周汇报"20% 进展"，自由已被流程吃掉，别再加细则。
- **无自主性基础的人群硬性摊派**：制度假定成员有创意精英式的自驱（见 BOOK_OVERVIEW 人才前提）；对纯执行岗位强推会变成形式主义负担。

### 作者在书中警告的失败模式

- **名存实亡**：作者自己承认，书出版时 20% 时间制在谷歌已越来越难执行——不设管理层承诺与存活条件自检，制度会静默死亡（BOOK_OVERVIEW 批判节；本 skill E5 即为此设计）。
- 外部奖励的挤出效应：把创意变成"赚钱的差事"（采纳奖金、悬赏），内在动机被功利交易替换（p207；历史上丹尼/帕特森的采纳奖金模式正是作者对照的反差——c84）。
- 大企业激励失衡：冒险的奖励归公司、失败的惩罚归个人时，理性人选择自保，20% 时间无人敢用（ce55）。

### 作者的盲点 / 时代局限

- 幸存者偏差：Gmail、AdSense、Google Suggest 被反复引用，而 c89 自己承认"大多数原型止步于演示日"——产出谱系被选择性展示，推广预期应据此打折。
- 自选项目的最大赌注 Google+（维克自发启动，c91）也在 2019 年关停——自由探索不保证方向正确，制度只提高"出现率"不提高"成功率"。
- 工程师中心：制度默认员工模型是工程师；计费制行业（律所、医院）需把"时间"翻译成"自选目标权"并重建余量，照搬工时必失败。

### 容易混淆的邻近方法论

- 谷歌式的"创新日/黑客松"（业界通行）：一次性活动不等于 20% 时间制——后者是常设的自主权制度，黑客松只是它的演示日组件。
- "弹性工作制"（flex time）：弹性管的是"什么时候工作"，20% 时间管的是"为什么工作"；两者毫无承接关系。
