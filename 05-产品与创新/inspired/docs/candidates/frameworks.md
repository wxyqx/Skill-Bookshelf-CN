  type: framework
  source_chapter: 第7章
  source_quote: |
    "计算出推荐者所占的比例，再减掉贬损者的比例，就得到了NPS，它反映用户对产品的态度。"

    适用于产品健康度监测、商业决策与用户满意度的权衡。

- id: f09
  title: 巴顿原则（说做什么，不说怎么做）
  type: framework
  source_chapter: 第8章
  source_quote: |
    "永远不要告诉别人怎么做。告诉他们做什么，他们自然会发挥天赋，给你惊喜。……你留给用户体验设计师和开发人员的空间越大，
    他们就越有可能打造出用户喜爱的产品。"
  summary: |
    定义协作接口的思维模型：向客户、设计师、开发人员提出要求时，只描述"要解决什么问题/要做到什么"，
    不规定"用什么方法实现"。对客户：他们描述的"怎么做"只是他们想到的一种方案，产品经理应还原出
    背后的"做什么"；对设计师和开发人员：保留实现空间，他们会找到远超你想象的多条解决路径。
    运作方式：每次沟通前自检——我给出的是问题陈述还是实现指令？
    适用于需求收集、跨职能协作、授权与委托。

- id: f12
  title: 机会评估十问
  type: framework
  source_chapter: 第11章
  source_quote: |
    "评估产品机会的目的在于：淘汰馊主意，避免浪费时间和金钱；挑选合适的产品机会，团结团队，理解产品，整合资源。
    为了评估产品机会，我要求产品经理回答如下十个问题。1.产品要解决什么问题?(产品价值) 2.为谁解决这个问题?(目标市场)"
  summary: |
    在投入任何资源之前评估产品机会的结构化问卷：①产品要解决什么问题（价值）；②为谁解决（目标市场）；
    ③机会有多大（市场规模）；④怎样判断成功（度量指标）；⑤有哪些同类产品（竞争格局）；
    ⑥为什么我们最适合做；⑦时机合适吗；⑧如何推向市场（营销组合）；⑨成功的必要条件是什么；
    ⑩给出继续或放弃的结论。关键纪律：十问只讨论待解决的问题，不涉及具体解决方案，
    避免把"方案遇到困难"误判为"机会不存在"。
    适用于立项决策、淘汰馊主意、向高管论证机会。
  tags: [decision, framework, product]

  title: 产品探索-执行两阶段模型
  type: framework
  source_chapter: 第12章
  source_quote: |
    "软件项目可以划分为两个阶段：弄清楚要开发什么产品(定义正确的产品)；开发该产品(正确地开发产品)。

  summary: |
    把软件项目切分为性质相反的两个阶段：先"定义正确的产品"（探索），后"正确地开发产品"（执行）。
    探索阶段是创造性的艺术工作，不可预测、不可压缩，产出是经用户验证的有价值、可用、可行的产品定义；
    一旦进入执行阶段，重心必须切换为排除干扰、按时交付，产品经理要克制"继续改需求"的创造冲动，
    否则自己会成为产品上市的最大障碍。
    运作方式：明确判定切换点（产品定义通过验证），切换后冻结需求。
    适用于项目节奏管理，纠正"边设计边开发"的混乱。
  tags: [process, mental-model, project-management]

  title: 流水线并行开发法
  type: framework
  source_chapter: 第12章
  source_quote: |
    "我有个方法可以解决这种冲突：采用流水线方式并行开发产品。也就是说，一旦1.0版本的产品进入项目执行阶段，

  summary: |
    解决"探索者人格与执行纪律冲突"的版本流水线方法：当第 N 版进入执行阶段、创造冲动无处安放时，
    立即启动第 N+1 版的探索定义，把新点子、高管的新要求全部纳入下一版本，而不干扰正在执行的项目。
    运作方式：探索与执行错位并行——1.0 执行时定义 2.0，2.0 执行时定义 3.0；
    唯一约束是不能让下一版的构思反噬当前版本的需求。
    适用于持续迭代的产品的节奏管理，也是应对"高管临时加需求"的缓冲机制。

    两个典型错误要避开：原则写得过于空泛失去指导作用；把"清晰导航"这类设计原则误当产品原则。

- id: f17
  title: 目标优先级共识冲突解决法
  type: framework
  source_chapter: 第13章
  source_quote: |
    "在我看来，每当团队内出现严重的意见分歧时，并非是大家对事实的认定有争议，而是对目标和目标的优先级有不同的理解。

  summary: |
    化解产品决策争论的程序：先确认分歧的真正来源通常不是事实，而是目标及其优先级的理解不一致。
    运作方式：讨论方案前先就四点达成共识——①究竟要解决什么问题；②为哪类人物角色解决；
    ③产品要达到什么目标；④每项目标的优先级是什么；然后把目标按"最重要→次重要→……"强制排序
    （不许所有目标都标"关键"），写在白板上让决策依据对所有人透明。
    共识建立后再讨论各方案的合理性，争论自然收敛。
    适用于团队僵持不下、高管空降意见、评审会跑题。
