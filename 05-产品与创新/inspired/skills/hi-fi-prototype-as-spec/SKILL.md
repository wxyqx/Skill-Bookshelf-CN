# 高保真原型即文档

## R — 原文 (Reading)

> "在我看来，只有一种形式的产品说明文档可以满足以上所有要求，那就是高保真产品原型。"高保真"的含义是原型应该真实地体现用户体验。……你可以把它放到真实用户面前，观察他们是否清楚如何使用(可用性)，是否渴望使用你的产品(价值)。只有通过这两项测试，产品说明文档才算合格，产品才值得开发。"
>
> — Marty Cagan，第18章《重新定义产品说明文档》

---

## I — 方法论骨架 (Interpretation)

纸质产品说明文档的死穴不是写得不够认真，而是三个结构性缺陷：**没人读、无法测试、把问题推迟到开发期才暴露**。文档不完整、含糊不清，项目要么反复调整（文档不断变更、延期、士气低落），要么开发人员凭空猜测、交付一团糟——无论哪种，上市时间都被拖后。作者因此把"产品说明文档"重新定义：主体不是文档，而是**高保真产品原型**，它同时承担功能需求、信息架构、用户体验、交互设计、视觉设计的表达。

三条纪律让它区别于"先画张设计图"。

第一，**"高保真"指体验真实度，不是视觉精细度**：覆盖所有页面和主要用例，甚至模拟后台处理流程和数据，否则测不出真实的可用性与价值。

第二，**原型是用完即弃的设计工具**：原型代码与产品代码毫无关系、全部废弃；产品按原型另起炉灶实现。迭代结果和公开测试中的产品也不能当原型用——它们改不动。

第三，**合格标准是测试通过**：原型放到真实用户面前通过可用性与价值测试，文档才算合格，产品才值得开发。这是纸质文档永远做不到的事，也是"原型反而缩短上市时间"的原因——问题在写代码之前就暴露、就修完。

原型体现不了的产品行为（业务逻辑、性能与扩展性等发布要求、安装与兼容性等平台交付要求），用用例补充，注释放进 wiki 或内部网站，保证信息只有一个最新来源。

## A1 — 书中的应用 (Past Application)

### 案例 1: 异地团队把原型当交流语言
- **问题**: 产品经理与开发团队分处不同国家，讨论文档内容与设计修改来回扯皮；文档是非母语时沟通效率更低。
- **方法论的使用**: "如果你与开发团队相隔很远……一定要借助高保真原型进行交流"——把原型作为异地沟通的基础，配合本地唯一接口人与每季度面对面交流。
- **结论**: 阅读文档不轻松，原型让双方看同一个东西，歧义当场暴露。
- **结果**: 作者据此协作的分布式精英团队，打造出支撑两千万用户的平台（第5章）。

### 案例 2: "原型的所有代码都是要废弃的"
- **问题**: 从开发团队借人做原型，开发者会习惯性地想把手上的原型代码直接演化成产品。
- **方法论的使用**: 事先直截了当讲明——原型代码和产品代码毫无关系，绝不能用在实际产品里，所有原型代码都要废弃（第4章）。
- **结论**: 原型是设计工具，不是产品地基；被迫在原型基础上开发产品，"最终的产品质量可想而知"（第21章）。
- **结果**: 团队敢随意修改、用完即弃，原型迭代速度快；正式产品另起炉灶，质量不受废弃代码拖累。

### 案例 3: 创业公司用原型代替文档再招程序员
- **问题**: 创业公司拿到投资就招程序员秘密开发，约半年做出漏洞百出的内测版，资金渐渐耗尽。
- **方法论的使用**: 初期只设产品经理、交互设计师、原型开发三个职位，用几周到两个月迭代出高保真原型并请真实目标用户验证，确定后再招程序员开发。
- **结论**: "用鲜活的产品原型代替死板的产品说明文档作为开发产品的基础"，开发人员能更直观、高效地领会设计要求。
- **结果**: 大幅缩短开发时间——与第18章"使用高保真原型可以大大缩短产品上市时间"互相印证（第28章）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品经理接到任务"写份 PRD / 需求文档"，或上版本的 PRD 没人读、开发靠猜。
2. 与异地/外包开发团队合作，需求文档来回邮件扯皮、反复返工。
3. 团队争论"原型要做到什么程度才算数""线框图够不够"。
4. 开发估算完说"文档写得太含糊"，或有人提议直接在原型代码上继续开发。
5. 产品要进入开发前，想把设计先拿给真实用户验证一遍。

### 语言信号 (用户的话里出现这些就应激活)

- "帮我写个 PRD / 需求文档 / 产品规格书"
- "开发说文档看不懂，需求又改了"
- "外包团队完全没理解我们要什么"
- "原型做到多细才算高保真？"
- "high-fidelity prototype" / "prototype as spec" / "kill the spec / 安息吧纸质文档"

### 与相邻 skill 的区分

- 与 `prototype-testing-playbook` 的区别：本 skill 回答"交付给开发的文档长什么样"；后者回答"怎么拿原型找用户测"。原型一物两用——制作时用本 skill，测试时切换到后者。
- 与 `product-validation-trio` 的区别：三验证定义"测什么"（价值/可用性/可行性）与"何时测"（写代码前）；本 skill 提供"用什么测"的载体。原型没通过价值与可用性测试，就不配当文档。
- 与 `minimal-product-definition` 的区别：基本产品管"范围减到不能再减"；本 skill 管"定义的载体与形式"。先定出基本产品，再用原型把它呈现出来。

## E — 可执行步骤 (Execution)

1. **给现有文档做五条要求的体检**：完整描述用户体验／准确描述软件行为／面向所有受众直观传达／可以修改／只有一个主体代表产品。
   - 完成标准：逐条打分并指出当前文档缺哪几条；给出"主体换成高保真原型"的改造清单。
   - 判停条件：产品极简单、无复杂界面且不打算做用户测试——可暂缓迁移，但"未经测试不开发"的红线不豁免。
2. **与设计师一起把文档主体改造成可交互高保真原型**：覆盖所有页面与主要用例，模拟后台流程和数据；原型体现不了的业务逻辑、发布要求、平台要求写成用例，注释放 wiki。
   - 完成标准：拿着原型走完主要用例，无需口头补充就能让开发、测试、市场各方理解产品行为；明确声明"原型代码全部废弃"。
   - 判停条件：团队异地且语言不通时，此步优先级最高——先有原型，再谈其他沟通手段。
3. **测试通过后才交付开发**：把原型放到真实用户面前测可用性与价值（操作细节交给 `prototype-testing-playbook`），通过后以原型为主文档交付开发。
   - 完成标准：原型通过真实用户测试；开发确认可据此另起炉灶实现，而不是沿用原型代码。
   - 判停条件：原型未通过用户测试——回到设计迭代，禁止进入开发；管理层要求在原型代码上开发——引用第4/21章的废弃纪律拒绝。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性小改动（文案、按钮微调）：做全套高保真原型的成本高于收益。
- 纯后台服务、算法组件：没有可交互的用户体验，改用可行性测试加接口文档。
- 已有稳定的可交互规格流程且开发随时可问的小团队：形式可灵活，"可测试才合格"的标准不变。

### 作者在书中警告的失败模式

- 管理层不明白原型和真实产品的区别，产品团队被迫在原型代码的基础上开发产品，质量可想而知（第21章）。
- 把迭代结果和公开测试的产品当原型用——开发中的产品以固定版本为基础，改不动，验证不了设计思路（第19章）。
- 原型只包含关键体验组件——作者自述后来升级了要求：尽可能覆盖所有页面和主要用例（第18章）。
- "纸上原型"看似省事，实际上不足以真实体现用户体验（第18章）。

### 作者的盲点 / 时代局限

- "如今使用工具创建高保真原型既简单又快捷，成本也不高"是 2008 年的工具语境；今天 Figma 类工具更便利，但"高保真=体验真实度（可交互）而非视觉精细度"的定义仍然成立。
- 作者断然不建议纸上原型；对极简改版，低保真草图先行的效率优势仍在，可以吸收其精神（快速迭代、用完即弃、必须可测）而不必拘泥形式。
- 书中范例以网页与客户端为主；对话式 AI 界面、多端适配的"体验真实度"需要扩充到会话流与跨端一致性，第18章清单不自动覆盖。

### 容易混淆的邻近方法论

- 视觉设计稿／mockup：静态图片，没有交互，测不了可用性与价值。
- 线框图／wireframe：低保真布局草图，作者明确不建议以其替代原型。
- 瀑布式 PRD：评审通过即冻结、问题推迟到开发期；原型法的核心恰恰是把问题提前到写代码之前解决。
