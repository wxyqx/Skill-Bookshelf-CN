# 价值·可用性·可行性三验证

## R — 原文 (Reading)

> "产品经理向产品团队提供最终的产品说明文档前，需要进行以下三项重要的验证。……仅仅知道产品能够开发出来、方便使用，这还不够。同样要紧的是知道用户是否觉得你的产品有用，是否愿意购买。"
>
> — Marty Cagan，第21章《产品验证》

---

## I — 方法论骨架 (Interpretation)

产品经理在把最终产品定义交给开发团队之前，必须完成三项证明：**可行性**——现有技术条件下能否成功开发出来，请架构师和开发人员深度参与技术调研，现在发现死胡同远比烧完时间资金后发现来得好；**可用性**——真实用户能否明白如何使用，必须请真实用户试用原型，产品经理和设计师自己琢磨代替不了；**价值**——用户是否渴求这个产品、是否愿意购买、有多喜欢它的设计。

这三项不是三个可以分别打分的独立检查项，而是"缺一即败"的整体：前言规律十条把"探索产品的价值、可用性、可行性"列为产品经理任务的第 1 条，又用第 10 条封死退路——一旦认定产品符合基本要求，它就是一个完整的概念，去掉任何因素都不可能达到预期结果。少验任何一项，都是把"能不能做出来、会不会用、想不想要"三问中的一问留给运气。

关键操作结构是**一次完成三证**：价值测试与可用性测试同场进行，用的是同一个高保真原型，区别只在观察重点——可用性看用户如何设法完成必要操作，价值看用户是否喜欢这些功能、满意其实现方式。可行性验证则发生在更早的时刻：开发人员在探索定义初期就参与评估设计，因为只有开发团队最清楚哪些构思可行。整套纪律的类比是：不能因为开发人员相信代码没问题就允许发布，同理不能因为团队相信产品有价值就跳过用户测试。时机上一切往前压——一旦进入开发阶段，修改产品设计的难度和成本越来越高，越早发现问题越好。

## A1 — 书中的应用 (Past Application)

### 案例 1: 让开发人员早期参与评估可行性
- **问题**: 产品经理常犯一类错误——完成产品定义后便扔给开发团队置之不理，贻误协调需求与可行性的最佳时机，等开发深入才发现方案根本做不出来，为时已晚。
- **方法论的使用**: 让开发人员在探索（定义）产品的初期阶段参与评估产品设计、协助策划方案；邀请开发人员直接面对用户参加原型测试；向开发了解最新技术动向、头脑风暴哪些新技术能解决手头的问题。
- **结论**: "开发人员可以帮助产品经理完善产品定义。别忘了，他们最清楚你的产品设计是否可行。"
- **结果**: 各项功能孰去孰留在原型阶段就透明化，开发团队心里有底，可行性风险在写代码之前出清。

### 案例 2: 价值测试与可用性测试同场进行
- **问题**: 验证是不是要分三轮、请三拨人、做三套原型，成本太高？
- **方法论的使用**: 用同一个高保真原型、同一场测试完成两项观察——可用性测试重在观察用户如何设法完成必要的操作，价值测试重在观察用户是否喜欢这些功能、是否满意功能的具体实现方式。
- **结论**: "价值测试可以和可用性测试同时进行，使用的原型也是一样的。"
- **结果**: 如今创建仿真原型的成本已经非常低，"如果还有不做产品验证的团队，我会感到非常惊讶"——验证不再有成本借口。

### 案例 3: 创业公司用真实产品做昂贵原型的反面对照
- **问题**: 不设验证环节、直接把真实产品做出来投放到市场上检验，行不行？
- **方法论的使用**: 作者把它作为三验证的反面教材——不是利用产品原型完成探索，而是孤注一掷用实际产品搭上全部开发时间做产品探索。
- **结论**: 这么做等于"开发一款非常昂贵的原型，让不知情的用户掏钱参与原型测试"——把本该在原型上发现的"没人想用"，推迟到发布之后才知道。
- **结果**: 这些公司需要一两年（发布几个版本）才能赢利，资金撑不到验证完成就耗尽，作者点名"这也是很多处于创业阶段的公司失败的原因"；正确顺序是先用原型完成三验证，再全面转入执行。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 原型做完了、准备排开发计划，团队在争论"还要不要测试、要测什么"。
2. 开发负责人担心设计方案不可行、技术风险大，想在投入前摸底。
3. 发布前或复盘时发现"功能全做完了，就是没人想用/用户看不懂怎么用"，倒查流程缺陷。
4. 想压缩验证成本：纠结要不要分别请人做价值、可用性两轮测试。
5. 创业团队在"直接上线试试水"和"先验证再做"之间摇摆。

### 语言信号 (用户的话里出现这些就应激活)

- "这个方案到底有没有人要""先测测用户反应再开工"
- "技术上能不能实现""让架构师评估一下"
- "做出来用户会不会用""怕没人买"
- "开发前要不要验证""验证什么才算过关"
- "value test" / "usability testing" / "feasibility" / "validate before build"

### 与相邻 skill 的区分

- 与 `opportunity-assessment-ten-questions` 的区别：十问在投入资源前做纸面过滤（只问问题不谈方案）；本 skill 是有了方案后在真实用户与开发面前的**实证**——先过闸门，再上验证台。
- 与 `prototype-testing-playbook` 的区别：那是"怎么主持一场测试"的操作手册（物色测试者、鹦鹉技巧、判停标准）；本 skill 定义**测什么、何时测、三项全过才准开发**的验证框架。
- 与 `hi-fi-prototype-as-spec` 的区别：那解决"用什么载体描述产品"；本 skill 解决"在这个载体上必须完成哪三项证明"。
- 与 `minimal-product-definition` 的区别：那规定被验证的对象必须是"减无可减的基本产品"；本 skill 规定验证内容是三要求本身。
- 与 `discovery-execution-two-modes` 的区别：本 skill 就是探索阶段的出口标准与判停条件，管"探索何时才算完成"。

## E — 可执行步骤 (Execution)

1. **立三项验证清单**：对当前方案分别写下——可行性由哪位架构师/开发人员评估、可用性请哪些真实用户测（人数与来源，排除同事与纯尝鲜者）、价值用什么问题问（是否渴望、是否愿意购买）。
   - 完成标准：三项各有负责人与日期，写在原型评审纪要上。
   - 判停条件：找不到开发人员评估可行性，或找不到真实目标用户——先解决资源，不进入下一步。
2. **一场测试同时测三样（可行性前置）**：先让开发人员检查原型、估算成本、指出设计误区与不可行项；随后同场进行可用性与价值观察——记录用户能否完成关键操作（可用性），并追问"是否愿意用/买、为什么"（价值）。
   - 完成标准：每个关键任务都有操作观察记录＋价值问答记录，可行性疑点有书面回应。
   - 判停条件：连续多名用户无法理解产品价值或明确不愿使用，立即收手、放弃或重构该创意（判停标准衔接 `prototype-testing-playbook`），不得以"开发做了再说"放行。
3. **出口裁决**：三项全过才允许进入开发，把"通过三验证的原型"作为交给开发的最终产品定义。
   - 完成标准：价值、可用性、可行性各有书面结论；结论与原型一起交付开发团队。
   - 判停条件：任何一项未过即返回探索迭代——修改设计的成本随开发推进陡增，"先做出来再说"是本 skill 唯一不可逾越的红线。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已进入开发甚至已发布后的"验收测试"——三验证必须在写代码前；事后验证只能算验收，发现问题的代价已完全不同。
- 纯技术组件、基础架构改造等无用户体验属性的工作——价值/可用性测试不适用，只剩可行性评估。
- 不要用它替代市场调研——调研回答"谁在用、怎么用、卡在哪"，三验证回答"该不该按这个方案做"，两者互补不可互替。

### 作者在书中警告的失败模式

- 过于自信跳过验证——"产品团队对自己的产品往往过于自信，不愿意验证产品，只顾埋头开发，总想等到公开测试时再收集反馈意见。毫无疑问，到那时再想大幅修改产品是不可能了"（第21章）。
- 定义完就扔给开发——贻误协调需求与可行性的最佳时机，"等到发现问题时，为时已晚"（第5章）。
- 管理层不明白原型和真实产品的区别，产品团队被迫在原型代码的基础上开发产品——"最终产品的质量可想而知"（第21章）；原型代码全部废弃，绝不进入正式产品（第4章）。

### 作者的盲点 / 时代局限

- 2008 年的"价值"验证主要靠小样本定性观察；今天可补充 A/B 测试、落地页预热、预售等定量手段，作者未涉及。
- 三验证假设"先有一个完整原型"；对机器学习等输出不确定的系统，可行性本身要靠小规模实验逐步确认，与"原型模拟后台数据"的假设有张力。
- 作者未讨论验证结论的保质期——市场变化后，通过验证的定义也可能过期，需要重新验证的触发条件书中未给出。

### 容易混淆的邻近方法论

- QA/软件测试：测的是代码质量与缺陷；三验证测的是产品定义本身（价值/可用性/可行性），发生在开发之前而非之后。
- MVP 上线试错：MVP 把真实产品当验证工具，作者视之为"用实际产品做昂贵原型"——三验证用原型，成本差一个数量级。
- 用户验收测试（UAT）：验收已开发完成的功能；三验证决定要不要开发这些功能。

## 相关 skills

- **depends-on** `hi-fi-prototype-as-spec`：三验证的载体是能放到真实用户面前的高保真原型——原型即文档提供"用什么测"，本 skill 规定"必须测什么、何时测"。
- **composes-with** `discovery-execution-two-modes`：本 skill 就是探索阶段的出口标准，两阶段切换定义探索与执行的边界，两者合成完整的探索纪律。
- **composes-with** `minimal-product-definition`：被验证的对象必须是减无可减的基本产品——三验证定"怎么验"，基本产品定"验多大的东西"。
