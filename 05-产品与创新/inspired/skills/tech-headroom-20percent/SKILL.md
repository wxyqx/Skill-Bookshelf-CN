# 20% 技术余量

## R — 原文 (Reading)

> "开发团队往往沦为替罪羊。这类问题通常是由产品管理失误引发的，比如，产品经理一直迫使开发团队满负荷工作，开发尽可能多的功能。所有软件架构都存在功能极限，如果忽视这个事实，一旦系统越过崩溃的临界点，就会造成无法挽回的结局。"
>
> — Marty Cagan，第5章《产品管理与软件开发》

---

## I — 方法论骨架 (Interpretation)

开发人员抱怨"代码库一团糟，必须停下来重写代码"，是产品经理最怕听到的话。作者的归因出人意料：这**通常不是工程事故，而是产品管理事故**——产品经理长年迫使团队满负荷堆功能，而一切软件架构都有功能极限，越过崩溃临界点就无法挽回。责任在产品侧，这是整套方法论的地基。

预防的处方 eBay 称为**余量（headroom）**：在产品管理上为开发团队预留 20% 的自主时间，让他们自由支配于重写代码、重构有缺陷的部分、更换数据库、提升性能，为用户数量增长、事务增长、新增功能分别留出技术空间。第37章把它重申为大众网络服务的铁律：从设计第一天起持续考虑扩展性，分配约 20% 的开发与运维资源专门为扩展做准备，"不到万不得已不要满负载运行"。

如果已经身陷重写危机，作者给出三条军规：第一，计划要切实可行——普通开发估算八九不离十，唯独重写代码例外，多数团队没有重写经验，估计无一例外过于乐观；第二，把重写分成几大块递增推进，让用户持续看到产品改进，哪怕九个月的活拖成两年，用户可见的改进要占用 25%~50% 的开发资源，这是保住市场占有率的关键；第三，资源所剩无几，必须谨慎选择用户可见特性，确保产品定义正确。一句话总结：临渴掘井不如未雨绸缪。

## A1 — 书中的应用 (Past Application)

### 案例 1: eBay 1999 濒临崩溃
- **问题**: eBay 成立四年后系统逼近架构极限，"公司濒临崩溃的情形超出所有人想象"，险些倒闭——谁的责任？
- **方法论的使用**: 作者诊断根因：产品经理一直迫使开发团队满负荷工作、开发尽可能多的功能，从不预留技术空间，忽视了一切架构都有功能极限。
- **结论**: "开发团队往往沦为替罪羊"，这类问题通常由产品管理失误引发；解药是产品侧主动预留余量。
- **结果**: eBay 起死回生后"发誓绝不重蹈覆辙"，把余量固化为流程原则（第37章再度引用此次危机作为"创业难，守业更难"的铁证）。

### 案例 2: eBay 三次重写起死回生
- **问题**: 不停下服务、不丢失用户的前提下，怎么把一个数十倍规模压力下濒临崩溃的系统重建起来？
- **方法论的使用**: 边运营边按军规递增重写——由于发展迅速，eBay 先后三次重写代码，最后一次采用完全不同的编程语言和架构；开发团队花几年时间大规模改写几百万行代码，同时在不影响用户群的情况下持续开发大量新功能。
- **结论**: 递增式重写让用户看到改进，是保住市场占有率的关键；这正是第②条军规（哪怕九个月拖成两年）的实践来源。
- **结果**: "这是我知道的最惊心动魄的中途重建网站的故事"——重建完成，eBay 成为行业标杆。

### 案例 3: Friendster 与网景的同类危机
- **问题**: 同样的危机落到别的公司头上，结局如何？
- **方法论的使用**: 作者列出对照组：Friendster 在向 MySpace 开放社交网络用户时发生同样的崩溃；网景与微软打浏览器大战时也遭遇类似困境。
- **结论**: "事实上，没几家公司能渡过难关"——重写期间用户看不到任何改进，只能坐视用户流向不断改进产品的竞争对手。
- **结果**: MySpace 和 Facebook 乘虚而入占领社交网络市场（第37章重述）；网景输掉浏览器大战。反面组证成"预防优于重写"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 开发团队正式提出"必须停下来重写代码/架构撑不住了"，要决定答应还是拒绝、怎么答应。
2. 版本排期永远 100% 满负荷，重构与技术债申请一再被"先做功能"顶回去。
3. 用户量、事务量即将激增（大促、病毒式传播、渠道放量），评估系统能不能扛住。
4. 已经陷入重写泥潭：工期一再失控、用户看不到改进、竞品在抢用户。
5. 复盘 eBay/Friendster 式崩溃事故，或要向管理层论证"技术余量是产品保险，不是工程福利"。

### 语言信号 (用户的话里出现这些就应激活)

- "开发说代码库一团糟，得停下来重写，批不批？"
- "技术债/架构债越欠越多，但永远排不上期"
- "这波流量来了系统怕扛不住，要不要提前做点什么"
- "headroom" / "tech debt" / "rewrite the codebase" / "refactor" / "scalability" / "running at full capacity"
- "为什么不能像 eBay 那样边重写边发新功能？"

### 与相邻 skill 的区分

- 与 `discovery-execution-two-modes` 的区别：那个管探索与执行两阶段的重心切换；本 skill 管执行期内部的资源配比——20% 余量是执行阶段的固定开销，不是可选项。
- 与 `minimal-product-definition` 的区别：那个管功能定义的不可削减；本 skill 管架构承载力。两者在"资源不够怎么办"上互补——基本产品超支只延工期，重写危机则必须递增推进并占压 25%~50% 资源。
- 与 `smooth-deployment` 的区别：那个管版本更新如何不惊扰用户；本 skill 管发布之前系统性的技术风险，两者分属"发得稳"与"撑得住"。
- 与 `rapid-response-window` 的区别：那个是发布后的黄金响应窗口；本 skill 的危机处方恰恰决定发布之后产品还活不活得成。

## E — 可执行步骤 (Execution)

1. **先判断处境，再开处方**：回答三个判断题——团队是否长期满负荷（没有自主重构时间）？系统是否逼近架构极限（性能劣化、故障频发、压测余量耗尽）？是否已有人提出"必须重写"？
   - 完成标准：处境归入三档之一——余量健康 / 危机初现端倪 / 已身陷重写，且每一档有数据或事件佐证，不是感觉。
   - 判停条件：只是个别模块难维护、团队能在正常迭代内消化——按常规技术债排期处理，不动用本 skill 的处方。
2. **未雨绸缪处方（前两档）**：在产品管理上为开发团队预留 20% 自主时间，自由支配于重写、重构、更换数据库、提升性能；为用户增长、事务增长、新增功能分别预留空间；从设计第一天起持续考虑扩展性，不到万不得已不满负载运行。
   - 完成标准：20% 写进资源计划并获管理层认可；余量花在哪里有清单（架构改进项），每季度可核对。
   - 判停条件：管理层连 20% 都不愿给——向其呈现 eBay/Friendster 的后果推演（第5章："如果你已经身陷重写代码的困境，说明公司危在旦夕"），仍被拒则记录风险敞口并升级，而不是默默认命。
3. **危机处方（第三档）**：按三条军规组织递增式重写——①计划以团队估算法为基础并刻意上浮（重写估算无一例外过于乐观）；②把重写分成几大块递增交付，让用户持续看到改进，哪怕九个月拖成两年，用户可见改进占用 25%~50% 开发资源；③谨慎选择剩余的用户可见特性，确保产品定义正确。
   - 完成标准：重写计划分块且每块附带用户可见的改进；资源占比（≥20%，危机中 25%~50%）有明确账目；特性取舍经产品评审（衔接 `product-principles-priority`）。
   - 判停条件：无法组织递增交付、只能停机大爆炸式重写——按"没几家公司能渡过难关"如实上报风险，先补建用户可见改进通道，再启动重写。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 个别模块难维护、审美性重构、"用新框架重写一遍才潮"——这些不是架构逼近极限，动用 20% 处方是浪费弹药。
- 把余量当"冻结新功能"的理由——第③条军规恰恰要求谨慎选择用户可见特性（占 25%~50% 资源），重写与改进必须并行，而不是无限期停摆。
- 团队规模小到架构远未触顶——初创期的瓶颈在验证需求（`product-validation-trio`），不在余量。

### 作者在书中警告的失败模式

- 产品经理迫使开发团队满负荷工作、开发尽可能多的功能，忽视一切软件架构都存在功能极限——这是重写危机的根源（第5章）。
- 开发团队沦为替罪羊：公司把产品管理失误误诊为工程无能，错上加错（第5章）。
- 重写估算过于乐观："你可能认为重写代码至多也就几个月，但是实际时间无一例外要多得多"（第5章）。
- 大爆炸式重写：重写期间用户看不到任何改进，"你只能坐在一旁，眼睁睁看着用户投奔竞争对手"（第5章）。

### 作者的盲点 / 时代局限

- 经验锚定在 1999—2008 年的 eBay 式单体架构；云弹性伸缩、微服务、可观测性已改变"架构极限"的形态，20% 的具体配比与"更换数据库"式的重构动作需按新技术栈重新校准。
- 作者只给了资源比例，没有给出"余量是否充足"的量化度量方法（容量规划、SLA、错误预算等属后续工程实践），落地时需自行补齐。
- 危机处方假设管理层可以被后果推演说服；在增长压力压倒一切的语境下，"20% 都不愿意给"的组织现实书中着墨不多。

### 容易混淆的邻近方法论

- 第29章"20% 法则"：那是给员工（含产品经理、设计师）做自主创新研究的时间，源于惠普/谷歌；本 skill 的 20% 是给开发团队处理技术债务的余量——同为 20%，用途与归属完全是两回事。
- 迭代内还债惯例（每迭代固定留 10%~20% 还技术债）：常见工程惯例；作者的立意更高——这是产品管理对架构极限负责的制度，危机时还要升级为占用 25%~50% 资源的递增重写工程。
- 技术架构评审/ADR：那是设计时点的把关工具；本 skill 是跨版本、跨季度的资源制度，两者层次不同。
