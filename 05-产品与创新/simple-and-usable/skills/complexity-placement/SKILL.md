# 复杂性放置

## R — 原文 (Reading)

> "任何应用程序都会有一些无法消除的复杂性。关键的问题在于：谁会面对这些复杂性？"（第8章）
>
> "简化设计的过程有时候颇似玩'打地鼠'游戏。这边刚按下复杂性的'脑袋'，那边又冒出了头。"（第8章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第8章

---

## I — 方法论骨架 (Interpretation)

四策略轮番用完还复杂的部分，多数团队的下一个问题是"还能怎么更简单"。本书把这个问句换掉了：**复杂性消不掉，只能决定谁面对它**——这是 Larry Tesler 的"顽固的复杂性法则"，一条守恒律，不是又一条技巧。

它先解释了简化中的诡异现象（打地鼠）：把对账单日期控件改简单后，写代码的人更麻烦、服务器负载更高——这边刚按下复杂性的"脑袋"，那边又冒出了头。复杂性没有消失，只是换了承担者。所以简化的收尾不是"消灭"，而是"分配"。

四问是分配的操作台，每组都是"谁面对复杂性"的具体化：

1. **自动化还是用户控制？**（Flip 自动对焦 vs iPhone 触屏对焦）
2. **专用按钮还是通用按钮？**（高保真音响的一键一功能 vs iPod 的转盘）
3. **一次完成还是分段完成？**（登录一次到位 vs 定制 Tumblr 博客）
4. **有意识处理还是无意识感知？**（用控件筛选结果 vs 看伦敦地铁图自动聚焦一条线）

放置标准：把残留复杂性放到总代价最小、最好让用户无感（无意识）的位置——但代价要算全：用户认知、代码、服务器、客服，都在同一条账上。四策略本质都是复杂性的重新分配，所以本 skill 是四策略用尽后的收尾，不是第五个策略。

## A1 — 书中的应用 (Past Application)

### 案例 1: 网上银行对账单控件
- **问题**: 用户从月、年两个下拉菜单选日期再点 Go 查对账单：选将来日期被讥讽般报错，选超过 12 个月又提示不存在——匆忙的客户极易选错。
- **方法论的使用**: 看出复杂性可以被"搬家"：用户只需从过去 12 个月里选，却被要求输入日期——把两个日期控件换成可用对账单的下拉列表，让代码和服务器去承担约束。
- **结论**: 复杂性没有消失——用户简单了，写代码的人更麻烦、服务器负载更高，关键是谁面对它。
- **结果**: 错误消息被整体消除，维护更简单；第 8 章重提此例引出 Tesler 法则。

### 案例 2: 复杂性放哪：四组对比
- **问题**: 收尾章需要一个框架把四策略统合起来，回答"简化到头了吗"。
- **方法论的使用**: 用四组产品对照给出决策问句：自动对焦（机器承担）vs 触屏对焦（用户承担）；功能特定按钮 vs 通用按钮；一次完成 vs 分段完成；有意识处理 vs 无意识感知。
- **结论**: 设计简单体验的最后，问的不是"怎么更简单"，而是"复杂性放到哪里"。
- **结果**: 四个决策问句统摄全书四策略，成为设计终局检查表。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 删除、组织、隐藏、转移轮番用过，某功能还是复杂，团队卡在"到此为止了吗"。
2. 简化一处后别处负担陡增（代码、服务器、客服），怀疑简化失败。
3. 新功能在吵"做成全自动一键，还是给用户分步控制"。
4. 复盘发现复杂性只是换了位置，想系统地决定该放哪。

### 语言信号 (用户的话里出现这些就应激活)

- "还是复杂 / 消不掉 / 没救了吗 / 到底还能怎么简化"
- "打地鼠 / 按下这边那边冒头 / 代码变难了 / 客服工单涨了"
- "自动化还是手动 / 谁来面对 / Tesler / 复杂性守恒 / 放到哪"

### 与相邻 skill 的区分

- 与 `four-strategies` 的区别：四策略处理"怎么简化"（路径选择）；本 skill 是四策略用尽后的终局问题（"消不掉的复杂性放到哪里"）。
- 与 `transfer-strategy` 的区别：分工表是转移策略的执行层；四问是更高层的分配决策框架。
- 与 `details-carry-simplicity` 的区别：那处理可消除的小瑕疵的定价；本 skill 处理消不掉的复杂性的分配。
- 与 `remove-strategy` 的区别：还能删的先删，删无可删才进终局分配。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确认复杂性真的消不掉**
   - 对照四策略检查记录：该删的删了吗？分组合理吗？非核心收了吗？分工最优吗？
   - 完成标准: 四策略逐项过检并留有结论；区分"残留复杂性"与"还没删干净"
2. **逐项过四问**
   - 对每项残留复杂性回答：自动化还是用户控制 / 专用还是通用 / 一次完成还是分段 / 有意识还是无意识
   - 完成标准: 每项有四个答案及理由
3. **算总账选落点**
   - 评估各去向的代价：用户认知、代码、服务器、客服、错误放大风险，选总代价最小且用户最好无感的位置
   - 完成标准: 落点有记录（放到哪+为什么+代价对比）
4. **复检打地鼠并判停**（判停条件：若发现"残留"其实可再删，回 remove-strategy；若属可消除的小瑕疵，转 details-carry-simplicity）
   - 完成标准: 改动后复查别处（代码、客服、其他界面）负担未陡增

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 四策略没做过就直奔"放哪"——四问会沦为保留多余功能的借口
- 用户处于高压环境（匆忙、被打断）时，"交给用户"的那一问要格外保守
- 团队用"功能变少了"衡量简化进展——该衡量的是"用户面对的复杂性变少了没"

### 作者在书中警告的失败模式

- **打地鼠错觉**：误把转移当消灭——复杂性换位置后（用户简单了、客服翻倍了）误判简化失败而回摆
- **转嫁给最没议价权的人（内部网案例）**：管理人员"自动生成报告"沾沾自喜，销售人员逐页填表苦不堪言——"谁面对复杂性"答错了人
- **自动化无代价假设**：自动纠错、自动推荐把错误一起放大且用户更难察觉——"自动化"不等于"代价最小"

### 作者的盲点 / 时代局限

- 书中把自动化近乎写成无代价——现实里自动化放大错误且更难察觉，本书未给出兜底设计
- 成书于 2011 年：AI 界面、订阅制 SaaS 的复杂性形态（模型行为不确定、灰度与开关）未被覆盖

### 容易混淆的邻近方法论

- 技术债（tech debt）：只算工程内部账；本 skill 要求用户侧与系统侧一起算
- `transfer-strategy` / `four-strategies`：执行层与选路层，本 skill 是收尾层
- 极简主义：追求元素最少 ≠ 选对复杂性的承担者 → `simplicity-boundaries`
