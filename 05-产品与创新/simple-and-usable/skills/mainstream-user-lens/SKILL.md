# 主流用户立场

## R — 原文 (Reading)

> "他们自己不会因为你的技术而使用你的产品，使用你产品的目的是完成某项任务。"（第2章）
>
> "专家并不是典型用户，他们的判断会出现偏差。"（第2章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第2章

---

## I — 方法论骨架 (Interpretation)

作者把用户分成三类：专家型（愿意探索、提改进建议、想要量身定做的技术，占少数）、随意型（愿意试新功能但必须够简单）、主流型（不会因为技术而用产品，目的是完成任务；掌握重要功能，但永远不会想学所有功能）。三类里主流用户最大也最稳定——专业单反的销量只占相机市场的 9%，就是少数派直观的度量。

三条判据支撑"为主流用户设计"的立场。第一，标签不升级：产品用了很多年，用户类型也不会变——用 Excel 五年的人大部分只会对金额求和。第二，渠道过采样：访谈、论坛、投诉、投资人都由专家主导，他们在组织内的音量与人数完全不成比例。第三，判断有系统偏差：专家体验不到主流用户遇到的问题，追求主流用户根本不在乎的功能。

结论不是"专家说的都错"，而是"专家的样本有偏"。iPod 发布时被专家博客集体嘲讽"没什么意思"，最后卖出 2.4 亿台——市场投票的是主流用户。还有一个压力推论：任何人一旦匆忙、有压力，就退化成主流用户——所以简单的体验也是"压力之下的主流用户的体验"。

## A1 — 书中的应用 (Past Application)

### 案例 1: iPod 遭专家嘲讽与福特 T 型车
- **问题**: iPod 发布时，Slashdot 等专家社区嘲讽它"不能无线上网，内存比 Nomad 还少，没什么意思"，MacRumors 讥讽"不就是一个 MP3 播放器吗"——按专家意见，这产品不该成功。
- **方法论的使用**: 作者用三分类解释这场集体误判：专家要"会飞的汽车"，主流用户只想要能用的 MP3 播放器；再用两组数据佐证——用 Excel 五年的用户大多只会对金额求和（标签不升级），2009 年专业单反销量仅占数码相机市场 9%（专家是少数派）。
- **结论**: 专家的判断有系统性偏差；先听专家的产品，会让主流用户觉得太复杂难用。
- **结果**: 截止 2010 年 1 月苹果卖出 2.4 亿台 iPod；正面参照是福特 T 型车——不是第一辆汽车，却是第一辆为平民大众造的车，彻底改变了汽车业。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 功能请求/改进建议主要来自论坛、社群、大客户里的资深用户，要决定做不做。
2. 评审中有人以"资深用户会喜欢 / 重要客户需要"为复杂功能辩护。
3. 给产品定位目标用户，或需要解释"为什么不为高级用户做 X"。

### 语言信号 (用户的话里出现这些就应激活)

- "资深用户想要 / 论坛上都在要求 / 发烧友说 / power user"
- "专家意见 / 大客户提的 / 核心用户的声音 / 老用户都说"
- "该听谁的 / 为主流用户还是高级用户 / expert bias / vocal minority"

### 与相邻 skill 的区分

- 与 `four-strategies` / `remove-strategy` 等策略 skill 的区别：策略回答"怎么简化"，本 skill 回答"为谁简化"——是所有策略 skill 的前置立场，不处理具体删藏组转。
- 与 `business-case-for-simplicity` 的区别：本 skill 提供立场与证据（谁是主流、专家有偏），商业论证把它翻译成方程式语言；"重要客户"论常常两者一起拆——先分型，再算账。
- 与感情需求挖掘（"然后呢"追问，第2章相邻方法，阶段 3 确认 slug）的区别：本 skill 判断"听哪类用户的"，感情需求挖掘下钻"某类用户到底要什么"——先定人群，再下钻。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **分型：声音来自哪类用户**
   - 判断需求来源属于专家型/随意型/主流型中的哪类（渠道证据：论坛/社群=专家过采样；支持工单=混合；静默流失数据=接近主流）
   - 完成标准: 每条关键需求都标了来源用户类型
2. **过三判据**
   - 该群体占多大比例（有没有 9% 式的度量）？使用年限有没有被当成类型升级？需求是"完成任务"还是"量身定做技术"？
   - 完成标准: 三问都有答案，且写明证据来源
3. **用主流用户口径重述需求**
   - 把"资深用户要自定义快捷键"翻译成主流用户的任务（"想更快用到某功能"→放到更顺手的位置是否已经够）
   - 完成标准: 能给出为主流用户设计的替代方案，或明确说明原需求与完成任务无关
4. **判停检查**
   - 例外: 分型显示目标用户整体就是专家（开发者工具、IDE 等专业产品）——立场反转，专家需求即主流需求，此时转 `four-strategies` / `remove-strategy` 做简化而非拒绝简化；需求来自付费大客户——转 `business-case-for-simplicity` 算账
   - 完成标准: 立场选定并记录理由

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 产品本身面向专家（IDE、开发者工具、专业音视频软件）——"忽略专家"直接反转；此时该警惕的反而是"为了新手指做过度简化"
- 把"主流"当成铁板一块：不同行业、岗位的主流用户任务差异真实存在——看任务的共性，而不是只看人数
- 专家在报告真实故障（"这里会崩"）——问题报告往往可信，错的是他们开的药方；拆开"问题"与"解决方案"再处理

### 作者在书中警告的失败模式

- 听信专家导致集体误判：iPod 被嘲讽"没什么意思"仍卖出 2.4 亿台；改进需求主要来自老用户、论坛与投资人时，产品会朝主流用户觉得复杂难用的方向漂移
- 期待用户升级：以为用得久的用户会变成专家——用 Excel 五年的人大部分只会对金额求和；按"他们会成长"设计等于按想象设计
- 专家追求"会飞的汽车"：为发烧友加的量身定做功能，主流用户根本不在乎，却要为其复杂度买单

### 作者的盲点 / 时代局限

- 作者未讨论用户分层运营的中间态（新手上路、渐进式披露体系），把选项简化为"忽略专家 vs 迁就主流"（BOOK_OVERVIEW 立场盲点）
- "主流用户占绝对主体且类型稳定"是未充分论证的假设，产品生命周期内用户构成会变化（BOOK_OVERVIEW 未证假设）
- 结论来自大众消费产品视角（iPod、相机、汽车）；B2B 与专业工具域需要重新分型后再用

### 容易混淆的邻近方法论

- "平均用户"直觉：主流≠平均——主流是"以完成任务为目的"的最大稳定群体，不是各维度取中位数的人
- "最活跃用户=最重要用户"直觉：活跃度恰是专家型的信号，正是过采样的来源；重要性与活跃度要分开验证
