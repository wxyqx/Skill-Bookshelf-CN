# 删除策略

## R — 原文 (Reading)

> "问题绝非'为什么应该去掉它'，而是'为什么要留着它'。"（第4章）
>
> "一样东西，不管它有多么差，只要是花钱买的，没有谁愿意把它白白地扔掉。"（第4章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第4章

---

## I — 方法论骨架 (Interpretation)

作者把删除列为四策略之首，因为它是唯一彻底移除复杂性的手段，而且"通过删除来简化设计屡试不爽"。

它的核心动作是**举证责任反转**：日常评审默认问"为什么要删它"，任何功能都有人辩护；本书要求反过来问"为什么要留着它"——举证责任在保留方。配套三个判断工具：

1. **沉没成本无关原则**：开发已花的钱收不回来，与去留无关。判定一个功能唯一有意义的方式，是看它现在能发挥几分作用、保留它额外造成多少成本（用户认知负担 + 维护开支）。"当年投入三个月"不构成保留理由。
2. **需求逆向工程**："假如用户想要"和"客户要求加"都不是问题陈述，只是解决方案的猜测。对每条请求找到它背后的真问题，再问：目标主流用户经常遇到这个问题吗？现有功能或更简单的方式能不能解决？
3. **按用户价值排优先级**：与日常体验相关、能消除挫折感的功能最优先；没有用户需求支撑的功能，再有钱支持、再容易实现也不该做。

一条长鸣警钟：当一个设计引出一大堆非正常操作、新状态和错误细节时，说明你在**为流程而非目的设计**——退一步问客户的真实目的，找替代方案。

边界：删除的终点不是"越少越好"，而是"减到不能再减"——掌控感是底线（见 B 段）。

## A1 — 书中的应用 (Past Application)

### 案例 1: TUI Ski 删掉半生不熟的功能
- **问题**: 滑雪度假网站有"筛选搜索结果"和"创建短列表"两个功能，实现得都不好，属于"勉强能用"的体验；沉没成本心理让没人愿意扔。
- **方法论的使用**: 放下"已经投入"的念头，只评估它现在还能发挥几分作用、保留它额外花多少成本——答案是负数。
- **结论**: 残缺功能还带来精神负担和维护开支，问题绝不是"为什么应该去掉它"。
- **结果**: 从英国站点删掉这两个功能后，转换率反而上升了。

### 案例 2: 银行"存钱罐"：退回到目的
- **问题**: 储蓄部经理要求加"存钱罐"功能——把存款分成可命名的罐子（节日、燃气）以鼓励储蓄。一进设计就复杂化：存钱要先划转入罐（一步变两步）、不知情者存错罐、取钱要选从哪个罐提、从某罐提太多即使别的罐有钱也被拒付。
- **方法论的使用**: "一个功能带出一大堆非正常操作和细节"触响警钟——这是在为流程而非目的设计。退一步回到客户目的（为目标储蓄、可辨识），发现允许客户直接命名存款账户就能达到同样效果。
- **结论**: 聚焦目的问"还有其他解决方式吗"，比盯着流程造新功能更能实现简化。
- **结果**: 命名账户方案实现、解释、支持成本都更低，客户也更好理解。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 争论旧功能去留，保留理由是"当年投入很大/删了可惜/已经花了钱"。
2. 客户或业务方要求加功能，团队直觉觉得会搞复杂，需要评估方法。
3. 评审会上"可是假如用户想用呢"让砍功能计划反复被打回。
4. 选项/设置太多，用户在相似选项间犹豫或干脆放弃。
5. 需要向管理层证明"删功能"的价值。

### 语言信号 (用户的话里出现这些就应激活)

- "删了可惜 / 花了那么多钱做 / 当年投入很大 / sunk cost"
- "客户要加 / 老板让加 / 假如用户想 / feature request"
- "选项太多 / 不会选 / 这个功能没人用 / 要不要砍 / feature cut / de-scope"

### 与相邻 skill 的区分

- 与 `declutter` 的区别：本 skill 管**功能层**取舍——哪些功能/选项整个该删（沉没成本、逆向工程、优先级、掌控感边界）；减速带清理管功能定了之后界面仍累的感知细节（装饰、干扰链接、错误消息、冗余文字）。
- 与 `four-strategies` 的区别：总纲回答"该走哪条策略"，本 skill 是删除这一条的执行细节与陷阱。
- 与 `hide-strategy` 的区别：删除是彻底去掉；隐藏是收起非核心项。"先隐藏着以后再决定删不删"是书中点名的拖延。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **列候选清单，反转举证责任**
   - 对每个候选功能回答"为什么要留着它"，而不是"为什么要删它"
   - 完成标准: 每项都有"目标主流用户多久遇到一次它解决的问题"的答案；答不出即进入待删区
2. **按沉没成本无关原则裁决**
   - 完成标准: 每项标为 删/留/合并；保留项能说出"现在发挥什么作用 + 保留它额外花多少成本（用户负担+维护）"；"当年投入"不得作为保留理由出现
3. **逆向工程新增请求**
   - 把每条"要加X"翻译成它要解决的真实问题，再评估
   - 完成标准: 每条请求都找到真问题，并确认现有功能或更简单方式能否解决；若一个需求引出一串新状态、新错误情形（在为流程而非目的设计），退一步问客户真实目的与替代方案（如"存钱罐"→直接命名账户）
4. **检查掌控感边界与组织落地**（判停条件：若核心体验仍复杂但已删无可删，转入 organize-strategy / hide-strategy）
   - 完成标准: 被删项不伤控制感——用户仍能预期系统行为并获得操作反馈；关键操控、法律要件、已售存量依赖的能力保留；组织阻力用使用数据与商业语言重述删除提案后重过一遍

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 删除决策由"实现难度/资源紧张"驱动而不是用户价值驱动——那是错删，砍掉的往往是差异化所在
- 目标用户就是专家本人（专业工具软件、开发者工具），删减会伤核心生产力
- 被删项是法律要件（金融/医药声明），或已售存量设备深度依赖的能力

### 作者在书中警告的失败模式

- **错删核心功能**：交期紧、预算紧时按"太难实现"砍功能，换成平庸内容凑数——最难实现的往往正是灵魂（节电网站砍掉用电量跟踪，上线后毫无吸引力）
- **沉没成本误区**：花钱做的残缺功能舍不得扔，长期拖累体验；TUI Ski 删掉后转换率反而上升
- **轻信口头说法**："假如用户想……"让每个待删功能复活；直接问用户"愿不愿意删"答案永远是"不"；未试用者重功能数量，试用后偏好立刻转向可用性
- **过度删除**：东京苹果店无按钮电梯删掉全部操控装置，用户失去控制感与反馈，"让人觉得它神经错乱"——掌控感是删除的底线，删除的目标是让人掌控，不是把控制删光
- **只盯流程忘了目的**：为"存钱罐"设计出划转/选罐/拒付一整串新流程，没人问"还有其他解决方式吗"

### 作者的盲点 / 时代局限

- "简单"可能成为砍功能的遮羞布：删除引发的组织冲突只给了"给管理层算账"一条解法，未处理"简化伤害少数重度用户利益"的分配正义问题
- "忽略专家"的结论不适用于开发者工具等专业产品——那里的专家就是主流用户，删除要格外保守
- 删除收益主要从用户感觉角度论证，被删功能的支持成本、数据迁移等组织侧代价着墨少

### 容易混淆的邻近方法论

- 隐藏（hide-strategy）：隐藏不减少维护成本，只是推迟删除决策——"欲删，从速"
- 极简主义/极简审美：删的是复杂性，不是特征与个性 → simplicity-boundaries
