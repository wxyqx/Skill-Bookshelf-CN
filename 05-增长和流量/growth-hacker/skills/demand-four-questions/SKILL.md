# 需求真伪四问检验器

## R — 原文 (Reading)

> 起初产品人员做了一个新特性，能将用户收到的所有邮件里的附件单列出来……虽然这个东西很高级，但需求本身并不存在。果然，产品上线一天后用户的使用情况确实没什么增长。这个功能随后就被撤下了。
>
> — 范冰，《增长黑客》第2章 2.4（QQ邮箱附件聚合功能，引张小龙复盘）

---

## I — 方法论骨架 (Interpretation)

在投入任何开发资源之前，把一个候选需求依次通过四道过滤网，任何一问不过即出局或降级：

1. **真伪**：这个需求有没有可观察的客观行为证据（用户现在正在用什么笨办法绕这个问题），还是只是产品人员的主观臆断？"很高级"不等于"有人要"。
2. **刚性**：把方案涨价 20%，用户还会用吗？不解决会怎样？有没有替代品？刚性不足的需求属于"锦上添花"，优先级天然靠后。
3. **量与肥**：目标用户基数有多大 × 他们的付费能力 × 付费意愿预算，乘出来的市场够不够养活这个产品？
4. **变现**：到底谁付钱？从使用到掏钱的路径是否成立？

支撑这套过筛的量化依据是"需求成本定律"：方向性错误的问题拖到上线后才发现，修复代价是立项阶段就发现的 68~200 倍。四问是全书最便宜的一道质量关——花十分钟纸面推演，省的是几个月开发加推广。

## A1 — 书中的应用 (Past Application)

### 案例 1: Sendwithus 用行为投票替代臆断（c06）
- **问题**: 创始人对邮件优化工具该做哪些功能毫无概念，直接开发可能数月心血打水漂。
- **方法论的使用**: 不靠拍脑袋回答"真伪/刚需"，而是搭一个 28 美元的假门网站，把候选功能做成按钮，用用户的真实点击作为需求投票，配合 GA 点击追踪定性定量结合。
- **结论**: API 与 A/B 测试模板的呼声合计占一半——功能优先级由行为数据给出。
- **结果**: 24 小时 803 个独立访客、92 人留下邮箱成为首批种子用户，随后获 230 万美元天使投资。

### 案例 2: QQ邮箱附件聚合——四问缺失的直接证伪（x02）
- **问题**: 产品人员做了一个"看起来很高级"的特性：把所有邮件附件单列、分组、可翻页。
- **方法论的使用**: 复盘发现"真伪"一问从未被回答——用户找附件时并不会逐个翻看，分组浏览的需求根本不存在。
- **结论**: 需求应源自客观实际而非主观臆断，判断价值只看真实使用数据。
- **结果**: 上线一天数据毫无增长，随即撤下；若立项前过一遍真伪问，这个成本为零。

### 案例 3: 叮咚小区——四问全不过还砸钱推广（x01，代价极端化）
- **问题**: 社区 O2O 未验证需求即大干快上，功能贪大求全、注册繁琐、小区需 100 人注册才能激活。
- **方法论的使用**: 作者以此作为反面教材：需求从真伪到设计全是硬伤，每一问都答不上来。
- **结论**: "强行让残破的二手车在高速上全速冲刺，开得越快越容易倾覆散架。"
- **结果**: 1 亿元融资半年烧穿，京沪裁员 70%，几近破产。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 创意/立项评估：用户有了一个产品点子（尤其 AI 时代一句话就能生成一个"看起来需求很真"的创意），决定要不要投入做。
2. 需求评审会：团队在争论某个候选功能该不该排进下个版本，正反双方各执一词。
3. 接到"老板需求/客户需求"：来源是领导意志或单个大客户的口头要求，缺少独立佐证。
4. 仿竞品功能：看到竞品上了某功能，在犹豫要不要跟进。

### 语言信号 (用户的话里出现这些就应激活)

- "这个需求是不是真的？""是不是伪需求？"
- "值不值得做？""要不要立项？""prio 怎么排？"
- "有没有人真的会用/付费？""is this a real need？""demand validation"

### 与相邻 skill 的区分

- 与 `pmf-gate` 的区别: 层次不同——四问审**单个需求/功能**的真伪与肥瘦；pmf-gate 审**产品整体**是否已达成 PMF、能不能开始放量推广。评估一个功能用四问，决定"能不能开始砸钱增长"用 pmf-gate。
- 与 `mvp-validator` 的区别: 四问是**纸面推演**，零成本、先行；mvp-validator 是**动手做验证载体**（假门/视频/公众号）去收集行为数据。顺序：四问全过 → 才轮到 MVP 花钱验证。
- 与 `actions-over-words` 的区别: actions-over-words 是解读**已有调研数据**时"信行为不信口头"的加权原则；四问是**没有数据时**对需求本身的结构化拷问。做用户访谈该信什么找 actions-over-words。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **过"真伪"问：找行为证据**
   - 列出"现在有谁、在什么场景、用什么笨办法（Excel/微信群/人肉/第三方工具）绕这个问题"的至少一条可观察证据。
   - 完成标准: 要么给出具体行为证据，要么明确判"臆断"出局。
   - 判停条件: 判为伪需求 → 终止，不进入后续问题，把结论书面化即可。

2. **过"刚性"问与"量与肥"问**
   - 刚性: 回答"涨价 20% 还用吗？不解决会怎样？现有替代品是什么？"
   - 量与肥: 给出目标用户基数 × 付费能力 × 意愿预算的粗估，哪怕数量级估算。
   - 完成标准: 两问各有书面答案，其中量与肥的估算可复算。

3. **过"变现"问并给出裁决**
   - 写清谁付钱、从使用到掏钱的路径；若路径依赖"以后再说"，标记为高风险。
   - 完成标准: 四问各有一行结论 + 总裁决（做 / 降级 / 放弃）；裁决为"做"时，明确移交 `mvp-validator` 设计验证方案，而非直接开发。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已上线功能的微调与取舍——那有真实行为数据和 A/B 可用，走 `ab-testing-protocol`，不需要纸面拷问。
- 判断公司级"现在能不能开始推广/扩张"——那是 `pmf-gate` 的决策门，不是单需求问题。
- 需求方有强外部约束（合规、法务、平台政策强制）时，四问不构成否决依据。

### 作者在书中警告的失败模式

- x02: 产品人员臆想的"高级"伪需求上线一天即撤——真伪问的证伪场景。
- x01: 叮咚小区四问全不过仍重金推广，1 亿元买来"未达 PMF 推广=加速垮塌"的教训。

### 作者的盲点 / 时代局限

- 作者自认"需求分析四问"对早期团队操作性一般（阶段 0 批判：方法内伤之一）；书中未给出样本量与统计口径。
- 68~200 倍成本定律与 42% 失败首因等数字系转引，作量级参考而非精确依据。
- **时效警示（2015 年快照，全集群通用）**: 本 skill 只保留判断逻辑层（四问序列 + 成本定律思想）；书中案例涉及的获客成本、平台环境参数已变（开放平台红利枯竭、买量成本结构重写、SEO-ASO 权重规则更新），任何引用案例数据时按当期重查，并记住幸存者偏差——案例全是赢家。
- 幸存者偏差提示: 四问全过的项目仍可能死于执行与竞争（外卖库之鉴），四问是必要条件不是充分条件。

### 容易混淆的邻近方法论

- 精益创业的"价值假设/增长假设"（Eric Ries）: 那是 MVP 验证的假设框架（见 `mvp-validator`）；四问是在写假设之前更靠前的需求筛选。
- Kano 模型: 同为需求分类工具，但 Kano 面向已有用户的功能满意度分层，四问面向零到一阶段的立项裁决。
