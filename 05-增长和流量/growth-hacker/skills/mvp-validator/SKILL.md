# MVP 验证器

## R — 原文 (Reading)

> MVP 是指将产品原型用最简洁的实现方式开发出来，过滤掉冗余杂音和高级特性，快速投放市场让目标用户上手使用……它并不意味着"便宜"、"难看"或是"核心功能残破"，而应是能帮助用户完成任务的最小功能合集。
>
> — 范冰，《增长黑客》第2章 2.5 用最小化可行产品验证需求

---

## I — 方法论骨架 (Interpretation)

MVP 的目的不是"省着做产品"，而是用最小成本回答两个假设：**价值假设**（这个产品是否真的满足某类需求）与**增长假设**（用户是否愿意买单/传播）。验证分三步走：

1. **先写假设再选形态**：没有写清假设的 MVP 是赶时髦。形态跟着验证目标走——测需求热度用宣传视频；测功能偏好用假门网站（按钮全是摆设，点击即投票）；测真实服务交付用微信公众号或纯手工服务；美术稿拼图测玩法（暴力拼图法）。
2. **最小 ≠ 残破**：能帮用户完成任务的最小功能合集才是 MVP。砍的是冗余特性，不是质量底线。
3. **三大模块第一天就带**：用户反馈渠道、官方公告看板、自动升级/通知机制。否则验证一旦成功，你无法触达那些验证用户——早期省的小功夫会变成后期指数级的返工。

验证结果对照预设阈值裁决：达标则投入正式开发，不达标则调整假设或放弃，而不是含糊地"再看看"。

## A1 — 书中的应用 (Past Application)

### 案例 1: Dropbox 的 3 分钟视频 MVP（c05）
- **问题**: 云同步想法前卫、技术障碍大、开发成本无法预估，直接开发风险太高。
- **方法论的使用**: 不写一行代码，先在目标人群高度集中的 Digg 发布一段"虚构产品功能"的演示视频，验证价值假设。
- **结论**: 用真实市场反馈决定是否立项。
- **结果**: 视频蹿升热文榜首，等候名单从 5000 人暴涨至 75000 人（15 倍），据此确认需求后才开始开发。

### 案例 2: Sendwithus 的 28 美元假门网站（c06）
- **问题**: 对邮件优化工具该做哪些功能毫无概念。
- **方法论的使用**: 搭"Sendwithus Zero"假门网站，后台界面煞有介事但按钮均为摆设；用户点击功能时弹框请其留邮箱并记录点击，作为功能需求投票，配合 GA 点击追踪。
- **结论**: API 与 A/B 测试模板呼声合计占一半，功能方向由行为数据给出。
- **结果**: 24 小时 803 个独立访客、92 个种子邮箱，整站成本 28 美元、一周建成，随后获 230 万美元天使投资。

### 案例 3: 悠泊用微信公众号"产检"（c07）
- **问题**: 代客泊车要验证"用户是否愿意把车托付给别人"，直接开发 App 周期长。
- **方法论的使用**: 一周开发微信 MVP（一键停车/取车/查看状态/绑定手机）；第一周只请内部与邻居公司有车族试用（自称"产检"版），第二周到最堵的医院门口地推。
- **结论**: 跳出"一定要做个应用"的思路，用现成的轮子换时间。
- **结果**: 首日在朝阳医院门口接到 10 个订单，用户画像浮现（30 万以上车型者约占 70%），验证通过后才开发 iPhone 原生应用。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想验证一个想法但不想/不能写代码：典型如"想验证宠物主是否愿意为 AI 体检 App 付费，怎么零代码验证"。
2. 团队争论 MVP 该做成什么样：有人要做完整 App，有人要做小程序，有人只肯做落地页。
3. MVP 已上线但不知道怎么算"验证通过"：缺预设阈值与判据。
4. 复盘失败：验证"成功"了却联系不上当初参与验证的用户。

### 语言信号 (用户的话里出现这些就应激活)

- "怎么用最小成本验证？""MVP 该包含什么？"
- "不写代码能不能测需求？""做个假门/落地页试试？"
- "fake door / smoke test / landing page validation / concierge MVP"

### 与相邻 skill 的区分

- 与 `demand-four-questions` 的区别: 顺序在前——四问是零成本的纸面过筛，若需求在纸面就被否决，根本不需要做 MVP；mvp-validator 是四问通过后**花钱动手**收集行为数据的环节。
- 与 `actions-over-words` 的区别: actions-over-words 是**解读数据的原则**（信行为不信口头、付费意愿加权）；mvp-validator 是**构造能产生行为数据的载体**。一个管怎么读数，一个管怎么造实验。
- 与 `pmf-gate` 的区别: MVP 是达成 PMF 的**手段**，pmf-gate 是判定 PMF 是否达成的**门禁**。验证进行中找 mvp-validator，决定能否放量找 pmf-gate。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **锁定双假设与判据**
   - 用一句话各写：价值假设（谁、在什么场景、需要什么）、增长假设（他们愿意以什么方式买单/传播）；并预设通过/放弃的量化阈值（如"假门按钮点击率 ≥X%"或"一周收到 N 个留资"）。
   - 完成标准: 双假设各一句 + 阈值可复算，写下来才算完成。
   - 判停条件: 若假设在 `demand-four-questions` 四问层已被否决，则不做 MVP，直接终止。

2. **按验证目标与成本选形态**
   - 对照选型：测热度→宣传视频（Dropbox）；测功能偏好→假门网站（Sendwithus）；测真实交付→手工服务/微信公众号（悠泊）；测玩法→美术稿暴力拼图。选型依据写明"为什么这个形态能产生对应假设的数据"。
   - 完成标准: 选型有理由、有成本预算、有时间盒。

3. **带上三大模块上线并裁决**
   - 反馈渠道、公告看板、自动升级/通知机制第一天必备（云诺之鉴）；发布前在目标人群的主流运行环境跑通核心流程（多啦口袋之鉴）。
   - 完成标准: 数据对照步骤 1 阈值，输出"投入开发 / 调整假设重验 / 放弃"三选一裁决；选择"投入开发"时确认验证用户可被触达。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已有产品在身、要验证的是单个新功能——优先用假门/灰度但走 `ab-testing-protocol` 的实验纪律，不必重构为 MVP 叙事。
- 需求在纸面四问就被否决——MVP 救不了伪需求。
- 把"MVP"当作低质量上线的挡箭牌——那是本书明确反对的误用。

### 作者在书中警告的失败模式

- x04: 云诺网盘 iOS 客户端漏掉反馈/推送/自动升级三模块，新版本无法触达老用户，被迫长期维护旧版接口——MVP 漏掉必备模块的自食其果。
- x05: 多啦口袋只在 iOS 7 测试，最先尝鲜的种子用户恰恰升级了 iOS 8，付费转化环节 100% 崩溃——公开发布前必须在目标人群的主流环境跑通核心流程。

### 作者的盲点 / 时代局限

- 阶段 0 批判：低质量 MVP 上线即差评的反面风险、pivot 的判据与次数上限，书中均未讨论；对"验证成功"的统计显著性只字未提。
- **时效警示（2015 年快照，全集群通用）**: 本 skill 只保留"双假设 + 形态选型逻辑 + 三大必备模块"的判断层；微信公众号作为低成本验证载体是 2015 年生态的产物，当期应按平台生态重选（小程序/私域/落地页工具等），案例中的成本数字与平台规则按当期重查，引用时带幸存者偏差前提。

### 容易混淆的邻近方法论

- Eric Ries 精益创业: MVP 概念源自 Ries，本书贡献是形态选型器与三大必备模块清单；引用概念时区分出处。
- Prototype / Demo: 原型给人看、不收集决策数据；MVP 的定义性特征是**产生可用于裁决假设的行为数据**。
