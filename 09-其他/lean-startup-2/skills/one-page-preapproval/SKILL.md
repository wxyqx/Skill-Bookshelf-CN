# 一页纸预批文件（把关规则参数化并当 MVP 迭代）

## R — 原文 (Reading)

> "1.如果你做的是一个很小的最小化可行产品，可能涉及的用户少于X，总负债低于Y，成本低于Z，你就将得到预批。2.如果实验成功，你想做一个'扩大版最小化可行产品'……就可以视为预先得到了批准，但前提条件是……得到管理层签字同意。"
>
> — 埃里克·莱斯，第 8 章（行 2928-2932）

> "你也许不会吃惊，这一页纸的文件，法务部撰写的初稿有……十页。这个时候，我们开始运用精益工作法进行改革。……我们把原来很长的文件当作最小化可行产品做了一系列实验，压缩之后给团队看（在这种情况下，他们实际上是我们的'用户'）。"
>
> — 埃里克·莱斯，第 8 章（行 2936-2938）

> "它能发挥激励机制的作用，鼓励团队把实验做得更好。……他们会意识到从小处着手还是容易一些。比如，实验产品只给100个用户看，而不是给10000个用户看，因为给10000个用户看要征得法务部门的同意。"
>
> — 埃里克·莱斯，第 8 章（行 2944）

---

## I — 方法论骨架 (Interpretation)

一刀切的审批禁令把所有实验当成同等风险，结果是合规成本杀死小实验、团队转入地下。一页纸预批文件做两件反直觉的事：

- **把禁令改写成参数区间**：问把关部门"什么情况下你会秒批"，把答案写成显性参数（用户数 X、负债 Y、成本 Z）加三档动作——区间内免审、超一档需签字（且必须建立在上一版 MVP 之上）、再超需面谈。风险大的多审，风险小的放行，规则从"身份与免责符号"变回"风险与动作的对应表"。
- **把关规则本身当 MVP 迭代**：文件初稿无论十页还是更长，都当作产品交给真实"用户"（要过审的团队）试用，按反馈压缩重写，直到团队不看说明书也能说出自己落在哪一档。
- **副作用即设计意图**：预批参数反向激励团队把实验做小——与其为 10000 个用户过审，不如先给 100 个用户免审。把关部门从降速者变成提速者。

## A1 — 书中的应用 (Past Application)

### 案例 1：一页纸法务文件——十页初稿压成一页
- **问题**：软件团队做国际市场实验，怕找法务，只好打电话碰运气；这次破例获批后，没参加培训、不敢打电话的团队怎么办成了死结。
- **方法论的使用**：部门负责人提出"把首席法律顾问和整个法务团队招入麾下"；召集法务全员后发现他们"讨厌难为人，不喜欢总说不"，只是被降低风险的老制度绑住。解法是把预批规则参数化（X/Y/Z 三档），再把十页初稿当 MVP 向团队迭代压缩。
- **结论**：规则参数化 + 文件本身用 MVP 方法迭代，才能让预批通道可信赖；少数合规复杂的项目仍应走认真评审。
- **结果**：一页纸文件上线，团队获得早期征求法务建议的可信渠道；小实验自激励出现（选 100 个用户而非 10000 个）（第 8 章，行 2919-2944，案例 c26）。

### 案例 2：毕威拓红黄绿协议过滤器——另一家公司的同构设计
- **问题**：开源软件公司版权/IP 风险成堆，法务对每个代码库逐个人工审查，速度跟不上工程节奏。
- **方法论的使用**：法务部把审查流程本身做成产品——先用线上问题清单建"预检、预验证的开源代码库"作为 MVP，再做红黄绿协议过滤器并自动化。
- **结论**：法务不退到后面制定政策，而是"以科学家和专家的身份参与实验"，把关规则就成了赋能工具。
- **结果**：两名兼职律师支撑起原本需要"律师军团"的合规规模，合规速度追上工程节奏（第 8 章，行 2959-2974，案例 c16）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 组织因怕担责干脆一刀切禁止自主实验（学校禁学生实验、公司禁未经审批的试点），想用显性边界替代禁令。
2. 审批流程对大小项目一视同仁地慢，团队排队等审，把关部门自己也说"我们也想说好，但制度如此"。
3. 要为创新通道写合规框架：什么免审、什么签字、什么面谈，且希望规则本身能持续改进。
4. 把关规则多年未更新，想用实验方法改造内部制度本身（把制度当产品）。

### 语言信号 (用户的话里出现这些就应激活)

- "审批太慢" "能不能免审" "绿色通道" "预批" "豁免条件怎么定"
- "一刀切禁止" "把规则参数化" "合规文件太长没人看"
- 英文：pre-approval / parameterized compliance / fast track / approval thresholds / simplify the gate

### 与相邻 skill 的区分

- 与 `wield-the-sword`（舞动宝剑）的区别：宝剑是一次性清障谈判（个案豁免），预批是把规则参数化的常设制度（批处理）；GE 的实际顺序是先过堂会换豁免，第 8 章才把豁免沉淀成一页纸。
- 与 `gatekeeper-to-enabler`（把关部门→赋能部门改造路径）的区别：`gatekeeper-to-enabler` 是五职能（法务/财务/IT/HR/采购）通用改造路径；`one-page-preapproval` 是其中合规审批场景的具体工件——问"法务部整体怎么改"用 `gatekeeper-to-enabler`，问"审批文件怎么写"用 `one-page-preapproval`。
- 与 `train-the-veto-holders`（培训要覆盖"能喊停的人"）的区别：`train-the-veto-holders` 是培训对象规则；一页纸预批常是喊停者被培训、被争取之后的制度化产物（两者是先后关系不是替代关系）。
- 与 `accountability-method-culture`（责任制→方法→文化）的区别：若把关部门人员的不配合根源在考核与问责（改了会损害其职业资产），预批文件会被架空——先回 `accountability-method-culture` 诊断责任制层。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **诊断把关规则的真触发条件**
   - 完成标准：通过访谈审批人（关键问题："什么情况下你会秒批？什么情况你绝对不放？"）列出不超过 3 个真正驱动审批的参数（用户数、负债、成本、数据去向等），并确认把关部门有人愿意参与设计。

2. **参数化：禁令改写为区间 + 三档动作**
   - 完成标准：每个参数有显性边界；三档动作完整（区间内预批 / 超一档签字且须基于上一版 MVP / 再超面谈），无"视情况而定"式模糊词；档与档之间可判断、可复核。
   - 判停条件：若把关部门拒绝参与参数设计（不回答"什么情况秒批"），则停下——先转 `wield-the-sword` 换高层施压或 `train-the-veto-holders` 培训喊停者，单方面写的预批无效。

3. **把文件当 MVP 迭代**
   - 完成标准：初稿交给 3-5 个真实"用户"团队试用并按反馈重写，2-3 轮内压缩到一页；测试判据是团队不看说明也能说出自己落在哪一档。

4. **验证反向激励**
   - 完成标准：上线后出现"为免审主动把实验做小"的行为证据（如选择 100 人而非 10000 人的用户组），而非出现"贴着参数上限套利"的博弈。

5. **定期复审参数**
   - 完成标准：约定复审周期（如每季度），按实际审批数据调整 X/Y/Z；文件有版本号与变更记录。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 风险不可参数化的重大安全/伦理事项——书中明言"有些项目一开始就应该咨询法务，有些项目合规事宜比较复杂，应该请法务做一次认真评审"；预批只覆盖可归档为参数的常规风险。
- 想用一页纸绕过必要审查——那不是预批而是免责文件，出事时反而加重责任。
- 没有把关部门参与、单方面写给领导看的"流程优化方案"——没有执剑人参与的规则是废纸。

### 作者在书中警告的失败模式

- ce08"这是规定"：规则与其触发条件脱钩后变成身份与免责符号（"这跟多少台没关系"），合规成本超过被保护对象的价值——预批正是把脱钩的规则重新挂回触发条件的解法；若参数化后仍只得到"一直是这么做的"，说明问题在规则异化而非文件长度。
- 制度反噬：法务老制度"目的是降低风险，但制度不仅没有保护公司，反而损害了公司的利益"——只压缩页数不改参数结构的简化无效。
- 预批文件不迭代：十页压不成一页，说明把关部门并未把自己当服务方，先回 `gatekeeper-to-enabler` 诊断其定位。

### 作者的盲点 / 时代局限

- 书中展示了 X/Y/Z 参数化后的成品，但没有给出参数怎么推导的方法（阈值设定依赖法务部的专业判断与善意，"我们讨厌难为人"是被引用而非被论证的前提）。
- 案例来自作者深度合作的公司（GE、毕威拓），存在幸存者偏差与利益关联；预批参数在强监管行业（金融、医疗）的适用性未被书中案例覆盖。
- 未讨论把关部门自身的问责压力：若审批人个人要为放行事故担责而从不为延误担责，参数化激励仍会失灵。

### 容易混淆的邻近方法论

- 通用"流程简化/绿色通道"：通常只压缩环节与时长；本 skill 的两个独特点是把关规则本身用 MVP 方法对内部用户迭代、预批参数反向激励团队把实验做小（V3 判定的可区分机制）。
- 《精益创业》正传：无此概念——正传的 MVP 面向外部用户，本 skill 把 MVP 方法反向用于内部制度工件，是 2.0 第 8 章"深层机制改造"的增量。
- 风险分级/分级审批制度（如银行内评分级）：形式相似，但分级审批的档位由监管或风险模型外生给定；本 skill 的参数由"把关部门秒批意愿 + 内部用户试用反馈"迭代而来，且以激励实验做小为设计目标。
