# 时间浪费的制度检修四项

## R — 原文 (Reading)

> "1.首先要做的是，找出由于缺乏制度或远见而产生时间浪费的因素。应注意的现象，是机构中一而再、再而三出现同样的'危机'。同样的危机如果出现了第二次，就绝不应该再让它出现第三次。"
>
> — 第2章，L668

> "如果一个高级管理人员，尤其是经理，不得不将他工作时间的1/10花在处理所谓'人际关系问题'上……那么这个单位就嫌人数过多了。"
>
> — 第2章，L692

> "一个人人都随时开会的组织，必是一个谁都不能做事的组织。……如果发现开会太多——例如参加会议的时间占总时间1/4以上，那一定是一个浪费时间的不健全组织。"
>
> — 第2章，L702

---

## I — 方法论骨架 (Interpretation)

德鲁克把"时间不够用"分成两类：一类是个人选择问题（由三问处理），另一类是**管理不善与机构缺陷**——这类浪费不修制度就会年年复发，而且主要浪费的是主管本人的时间。他给了四条检修项，每条都带可观察的判据：

一、**重复危机**。机构里一而再、再而三出现同样危机。判据极硬：出现了第二次，就绝不能有第三次。可预见的重复危机说明缺乏制度或远见；解法是"例行作业化"——把本来要靠专家判断的事，设计成人人可按步骤处理的作业。反向标志：管理好的工厂"总是单调无味"，高潮迭现、人人忙得不可开交反而是管理不善。

二、**人员过多**。多人的代价不是工资而是协调成本：彼此侵犯、处处说明、随时解释。判据：经理有 1/10 的工作时间耗在处理人际关系纠纷与摩擦上，单位就嫌人多。用人的标准是"每天的工作都需要他"；"偶尔才需要"的专家应外购而非正式聘用。

三、**组织不健全**。其表现就是会议太多。会议是对组织缺陷的补救措施——本应由一个职位或单位做完的工作被拆到几个部门，才需要靠会议缝合。判据：会议时间占总时间 1/4 以上；且会议会衍生会议。

四、**信息功能不健全**。信息不送到需要的人手里，或表达形式不对（只给会计需要的"平均产量"，而作业部门要的是范围与组合）。判据是"需要的人能否随时拿到可直接使用形式的信息"。

四项的共同逻辑：时间浪费常常是结构症状，不是个人意志问题；因此要改的是制度设计（把重复变例行、把岗位并回、把信息补上），而不是要求人更努力。

## A1 — 书中的应用 (Past Application)

### 案例 1: 每年 12 月的"盈余预估危机"——把精确预估改成区间预估即解

- **问题**: 某季节性公司每年第四季为淡季，销售利润难以预测；但公司规定中期报告须预估全年盈余，于是每年年底前三五个星期，全公司为凑达成目标而忙碌，管理层没法做任何其他事情。
- **方法论的使用**: 按第一项检修"重复危机"：这是可预见、每年重复的危机，说明是制度设计问题（精确预估的要求本身）而非不可抗力。
- **结论**: 解决办法只是"动一动笔"——预估数字不必过于确定，给出一个上下范围即可，且这完全符合董事会、股东与金融界的要求。
- **结果**: 每年 12 月的危机不复存在，"几乎没有人知道了"；管理者不必再浪费时间配合预估，第四季业务绩效反而比过去更好。

### 案例 2: 三部门各占一摊的会议灾难——归并为一个单位

- **问题**: 一家大公司因历史沿革（蒸汽涡轮机、航空发动机、原子能）分设三个部门，各有办法制度却服务同一个能源市场；多年来三个部门忙于永无止境的会议，会议还侵入公司高层，最高当局老是要在会议中当裁判员。
- **方法论的使用**: 按第三项检修"会议太多=组织不健全"：会议数量是职位结构与单位设置的指标——本应一个单位做的工作被分散到几个单位。
- **结论**: 需要的是能源战略与一个配合"只有一个能源市场"现实的组织。
- **结果**: 三个部门归并为一个组织单位、由一位经理管辖；虽有策略问题待决，但会议时间大为减少，最高当局不必老是当裁判员。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 同一种危机/赶工/事故以"突发"的名义年复一年出现（年末冲刺、库存告急、季度合规火线）。
2. 用户觉得团队"人不少但事推不动"，整天在协调、对齐、解释。
3. 用户所在组织会议密度极高，大家靠开会推进一切，会后又生出新会。
4. 数据/报表总在需要时拿不到，或拿到了却不能用（口径不对、形式不对），反复要人手工重算。

### 语言信号 (用户的话里出现这些就应激活)

- "每次到这个时候都要救火"/"we're firefighting every quarter"
- "同样的问题去年也发生过"/"the same problem keeps recurring"
- "会开不完，会议占了我大半时间"/"meetings eat my whole week"
- "人明明不少，效率却很差，都在扯皮"/"too much coordination overhead"
- "数据对不上/口径不对，得自己重算"

### 与相邻 skill 的区分

- 与 `time-diagnosis-questions` 的区别: 那边裁"这件事我要不要做"；这边判"这类毛病是不是组织的结构病"，动作是改制度而非删活动。
- 与 `know-thy-time` 的区别: 那边在采集个人时间样本；这边的证据是集体现象（危机频次、会议占比、人际耗时），不依赖个人记录（但也常以记录为证）。
- 与 `consolidate-free-time` 的区别: 那边处理"删完之后怎么集中"；这边处理"为什么会源源不断产生浪费"。
- 与 `problem-classification` 的区别: 那边判问题是否经常性（决定决策类型）；这边是组织健康度检修清单，二者可能并用但对象不同。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **把症状改成"重复性判定"**
   - 动作: 对用户抱怨的每一类浪费，先问它出现过几次、是否可预见。
   - 完成标准: 每类症状被标为"首次/偶发"或"重复且可预见"。
   - 判停条件: 若确为真正偶发（如自然灾害级事件），跳到步骤 6，只做个案处置。

2. **第一项检修：重复危机 → 例行作业化或改规则**
   - 动作: 对重复危机，找出"为什么它可预见却仍复发"的制度原因，给出两条路：设计成无需研究判断、人人可处理的例行作业；或修改产生它的规则本身（如把精确指标改成区间）。
   - 完成标准: 有一条具体设计（谁、何时、按什么步骤处理）或一条规则改动；并约定"若它第三次出现即为检修失败"。

3. **第二项检修：用 1/10 判据查人员**
   - 动作: 估算管理者用于人际纠纷、摩擦、解释的时间占比；同时检查是否有"偶尔才需要"的专家被正式长期聘用。
   - 完成标准: 得出"是否超 1/10"的判断；对长期闲置型岗位给出外购/调整方案。

4. **第三项检修：用 1/4 判据查会议**
   - 动作: 统计会议时间占比；对超标组织，追查"本应由一个职位或一个单位完成、却被拆到几个单位"的职责重叠，优先做组织归并而非会议技巧改良。
   - 完成标准: 指出至少一处职责重叠/单位设置问题，并给出归并或授权方案。

5. **第四项检修：查信息直达与形式**
   - 动作: 列出使用者需要的信息与实际送达的信息，比对"是否送到、是否是可直接使用的形式"。
   - 完成标准: 至少一处具体补救（如增一份副本、改口径、改报表形式使作业方可直接使用）。

6. **收束与复查**
   - 动作: 把四项结论写成一份检修清单，每隔几个月复核一次（德鲁克建议用检查表定期检查）。
   - 完成标准: 有清单、有责任人、有复查周期。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 真正的偶发事件（一次性事故、外部冲击）：不能强行"例行化"，那不经济也不现实；只有重复的才配得上制度性解决。
- 用户要的是个人时间管理建议：本 skill 的对象是制度与组织，不是个人意志。
- 用户想用它来裁人：1/10 判据是"人手是否过多的诊断信号"，不是裁员的裁决依据；涉及人事调整必须依当地劳动法规与组织程序，并另按用人所长的方法评估人。

### 作者在书中警告的失败模式

- **重复危机不根治（救火英雄主义）**（ce07）: 同样的问题年复一年以"突发"名义处理；表彰救火者却无人负责把火源制度化消除；"同一个危机如果重复出现，往往是疏忽和懒散造成的"。
- **人员过多的"养兵千日"借口**（ce08）: 为"偶尔才需要"的专长常年正式聘用，理由永远是"他总得先熟悉我们的业务""将来可能用得上"。
- **会议泛滥**（ce09）: 用会议弥补职位结构缺陷，会议再衍生会议；"会议是组织缺陷的一种补救措施"。

### 作者的盲点 / 时代局限

- **大公司科层语境**: 四项检修假设组织有可调整的职位与单位边界，且管理者有足够权力推动归并。矩阵型、平台型、外包/项目制组织里"归并"往往不可行，须改成"减少接口"或"明确单一责任人"等替代表达。
- **无时间自主权岗位的替代动作（强制声明）**: 若用户既无下属可调整、也无权改流程（一线服务、客服、基层执行岗），四项检修只能降级为"记录与举证"——列出重复危机与会议占比的事实，向上级提交一份带数据的检修建议；不要要求用户凭个人努力消化制度性浪费。
- **"单调无味的工厂"是制造业隐喻**: 服务、创意、危机响应行业（医院急诊、媒体、运维）的"高潮迭现"可能确是业务特性，不宜一律读成管理不善；需要区分"可预见却复发"与"本质上不可预见的波动"。
- **电脑与信息判断的时代性（强制声明）**: 书中"电脑"指大型机批处理时代，其"外部情况无法量化"的判断已被部分推翻；本 skill 引用它时只作"信息设计要贴合使用者形式"的边界说明，不作当代技术结论。
- **证据等级**: 全部为顾问观察与轶事（某公司 12 月危机、三部门会议、医院床位、麦克纳马拉预算），无对照实证；1/10 与 1/4 为经验阈值，非统计结果。

### 容易混淆的邻近方法论

- 精益/六西格玛/流程再造: 以流程与浪费为对象、追求计量化改善；本四项是"管理者的时间体检"，目的是释放知识工作者的时间，判据是组织症状而非流程指标。
- 组织设计（矩阵/平台/敏捷小组）: 提供结构方案；本 skill 只给出"从会议与协调内耗反推结构问题"的诊断入口。
- 敏捷回顾/事后复盘（postmortem）: 面向单次事件的改进；本 skill 的判据是"同类事件是否第二次、第三次出现"。

## 相关 skills

**depends-on**（使用前提）: 无 — 证据是集体现象（危机频次、会议占比、人际耗时），不依赖个人时间记录。

**contrasts-with**（同境况二选一）:

- `time-diagnosis-questions` — 症状相同、层次不同：个人活动取舍走三问（取消/授权/问相关人）；重复危机、会议 1/4、人员 1/10 这类结构病走本 skill 检修。

**composes-with**（配合使用/先后接力）:

- `know-thy-time` — 时间记录是本四项检修的常用证据来源（记录到手后按病灶分流：个人活动 → 三问，制度病灶 → 本 skill）。
- `problem-classification` — 第一项检修（重复危机 → 建规则/例行作业）是"经常性问题"分类法在时间领域的应用；需要更一般的定性方法时转那边。
