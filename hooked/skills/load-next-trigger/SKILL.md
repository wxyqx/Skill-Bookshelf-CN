# 加载下一个触发：投入内生生成下一次召回

## R — 原文 (Reading)

> "习惯养成类技术利用用户过去的行为为今后启动一个外部触发。在投入阶段，用户设置未来触发为公司提供了一个让用户再次参与的机会。"

## I — 方法论骨架 (Interpretation)

上瘾模型前三阶段结束于酬赏，但循环要重新开始，必须有一个新的触发把它接起来——这个合页就是"加载下一个触发"。核心思想：最好的召回触发不是运营日历排出来的群发，而是用户上一次投入自己生成的——发消息，对方的回复就成了通知；定日程，会前那一刻就成了推送时机；滑动匹配，匹配成功本身就是提醒。它带两条硬设计要求：其一，触发必须由用户自己的行为内生生成（个性化、和用户在乎的事绑定），而非外生排期；其二，触发时机要对准内部触发最活跃的瞬间——焦虑、好奇、期待出现的那个时点。这两条使它与一切运营推送有结构区别：群发打扰所有人，内生触发只在用户自己安排的时刻出现，被感知为服务而非骚扰。

## A1 — 书中的应用 (Past Application)

### 案例 1: Any.do 的会后通知
- **问题**: 移动应用留存极难——2010 年约 26% 的应用下载后只被使用一次，如何让任务管理应用被反复使用？
- **方法论的使用**: Any.do 在第一次使用时就引导用户连接日历（投入），授权后应用会在"下一个定期会议结束之后"发送通知，提示用户回来记录后续任务——外部触发恰好落在内部触发（怕忘事的焦虑）最活跃的时刻。
- **结论**: 用户的一次投入（连接日历）为未来所有循环装上了触发器；触发时机对准情绪才算真正"加载"。
- **结果**: 成为书中投入阶段"加载下一个触发"的教科书案例（L1753–1763）。

### 案例 2: Tinder 与 Snapchat：把闭环压进单次会话
- **问题**: 高频社交产品如何在每次使用中都埋下回访的理由？
- **方法论的使用**: Tinder 用户每点击一次，匹配成功率就累积一分，"每一次匹配都会向中意的双方推送通知"；Snapchat 每条阅后即焚照片都隐含"要求回应"的提醒，双击即可回复——每发送一条就加载下一个触发。
- **结论**: 投入→触发的闭环可以压缩到单次会话之内完成，用户行为本身即召回引擎。
- **结果**: 两例支撑"高频产品靠用户自己的投入持续再进入循环"的论证（L1765–1779）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 推送没人理：通知打开率、召回率差，团队想优化推送策略——先检查触发是不是用户自己的投入生成的。
2. 设计"第二天还会回来"的机制：产品用完即走，缺少让用户回访的内生钩子。
3. 新功能评审：做完某动作之后，什么事件会自然产生下一次提醒？评估功能的回访闭环是否成立。
4. 用户自我保护视角：识别哪些通知是"自己安排的"（内生），哪些是运营群发（可关）。

### 语言信号 (用户的话里出现这些就应激活)

- "推送没人点 / 打开率低 / 召回率差"（push open rate, re-engagement, win-back）
- "用完即走 / 怎么让他第二天回来"（come back tomorrow, retention loop, next-session trigger）
- "加载下一个触发 / 触发闭环 / 召回机制"（loading the next trigger, self-generated trigger）

### 与相邻 skill 的区分

- 与 `f04-external-triggers-four-types` 的区别：f04 回答"选哪类外部触发拉新/留存"（四分类），f16 是其中自主型触发的升级形态——专指由用户投入内生生成的召回机制。问"预算该投哪类触发"用 f04；问"让用户的行为自己生成下次召回"用 f16。
- 与 `f05-internal-trigger-anchoring` 的区别：f05 挖"什么情绪让用户自己想起产品"（内部触发），f16 设计"产品在什么时刻递上外部触发"（时机承接）。f16 的推送必须落在 f05 找到的情绪点上，找不到情绪锚点就先退回 f05。
- 与 `f17-investment-timing-granularity` 的区别：f17 管投入何时提出、拆多细；f16 管投入沉淀后如何变成下一次召回。设计顺序是先 f17（把投入做对）再 f16（让投入闭环）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **盘点用户的自然投入点**
   - 完成标准: 列出 ≥3 个会产生"未来某时刻需要提示"的用户行为（创建日程、发消息、收藏、设置目标、关注他人），并写明每个行为对应的未来事件。

2. **为每个投入点定义内生的后续触发**
   - 完成标准: 触发由用户行为生成（非运营日历），且下一步动作清晰（通知里说得出"回来做什么"）；说不出下一步动作的触发不合格。

3. **对准内部触发时机**
   - 完成标准: 写出情境句"每当用户感到 X（如怕忘事的焦虑），触发 Y 恰好出现"。
   - 判停条件: 若找不到任何情绪锚点，停止时机设计，转 f05 挖内部触发后再回来。

4. **检查许可与频率**
   - 完成标准: 用户在投入时明确授权（如连接日历、开启通知），通知数量与用户行为量成正比，不随运营 KPI 加码。

5. **伦理复核（判停条件）**
   - 完成标准: 过 f18 操纵矩阵两问；若发现所谓"内生触发"实为群发伪装、或靠放大焦虑提高打开率，立即停止该设计——内生性的判定标准是"触发事件来自用户行为"而非文案个性化。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 拉新阶段的触发选型问题（该投信息流还是做内容）——那是 f04 四分类的领地，本 skill 只处理投入端的召回闭环。
- 内部触发尚未定位就先排推送时机——时机没有情绪锚点，属于空转，先做 f05。
- 产品价值不成立时用高频推送硬撑召回——推送是补丁不是药，价值问题须回 f01/f12 解决。

### 作者在书中警告的失败模式

- 爆品陷阱（ce21）：有触发、有酬赏、无投入的产品热度自然衰减——没有储存价值与内生触发的闭环，循环断在第四环。
- 一次性应用陷阱（ce14/c36）：26% 的应用下载后只用一次；Any.do 的对策是首次使用就开始投入并装好触发，召回机制必须在第一个循环就位。
- 付费型触发的长期依赖（ce03 的教训）：若召回全靠投放与群发，停投即断流——外生触发不建立情绪绑定，只有内生触发才渗透习惯。

### 作者的盲点 / 时代局限

- 2014 年移动红利期语境：案例全是 App 推送与首屏图标；算法推荐时代，"无穷多变酬赏"可以无须用户投入即由系统工业化生成（刷推荐流），本书"投入→储存价值→依赖"的链条在算法产品中被部分短路；对"超级 App 内嵌生态的嵌套推送"完全未预见（阶段 0 批判节）。
- 设计者本位：把召回触发当作增长资源讨论，未讨论通知过载对用户的消耗；通知分级、一键关闭等用户侧工具在书中缺位——用本 skill 时应同时为用户保留关闭权。

### 容易混淆的邻近方法论

- 运营常识"精确推送时间 / A/B 测试推送文案"：本书判据不是"什么时候发效果好"（那是运营优化），而是"触发由谁生成"——内生（用户投入）vs 外生（运营排期）是结构区别，前者才闭合上瘾循环。
- `f04-external-triggers-four-types` / `f05-internal-trigger-anchoring` / `f17-investment-timing-granularity`：见 A2 区分——分类（f04）、情绪锚点（f05）、投入时机粒度（f17）与本 skill（投入→召回的合页）各管一段。
