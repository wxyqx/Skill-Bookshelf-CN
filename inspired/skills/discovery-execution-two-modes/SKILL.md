# 产品探索与执行两阶段切换

## R — 原文 (Reading)

> "软件项目可以划分为两个阶段：弄清楚要开发什么产品(定义正确的产品)；开发该产品(正确地开发产品)。第一个阶段探索产品，第二个阶段则强调执行。……产品经理必须在执行阶段转换工作重心；否则，产品经理自己很可能成为产品上市的最大障碍。"
>
> — Marty Cagan，第12章《产品探索》

---

## I — 方法论骨架 (Interpretation)

一个项目表面上是"一条流水线"，实际上是两种性质完全不同的工作拼接而成。前一段是**产品探索**：分析创意、制作原型、请真实用户验证，探索出有价值、可用、可行的方案；后一段是**执行**：开发、测试、发布，把已定方案按时交付。作者特意弃用"需求和设计"这个说法，因为探索本质是创造性工作，更像艺术而不是科学——不可预测、无法像建筑施工那样设定期限。

两段的重心正好相反。探索期要发散：创意每天变化，原型迭代的循环周期可以短到一天好几次。执行期要聚焦：产品经理的任务从"想新点子"换成"捕捉开发中不可避免的问题并迅速解决、屏蔽竞争对手与组织变动的干扰、保证按时发布"。最危险的失效方式是带着探索期的习惯进入执行期——产品经理或高管不断往进行中的项目里塞新点子，结果是延期、砍功能或质量下滑，作者断言此时"产品经理自己很可能成为产品上市的最大障碍"。

制度化解法是**流水线并行**：1.0 版本一进入执行阶段，就把创造热情投入 2.0 版本的产品定义。新想法、高管的新要求一律纳入下一版本，不干扰当期范围。这背后还有一个隐藏论断：所有公司其实都在做产品探索——区别只是用便宜的原型做，还是孤注一掷用真实产品加全部开发时间做"昂贵的原型"，让不知情的用户掏钱参与测试。在敏捷环境下，这套切换表现为：产品经理和设计师的进度领先开发团队一两个迭代周期，绝不一边设计一边开发。

## A1 — 书中的应用 (Past Application)

### 案例 1: 流水线并行开发法
- **问题**: 产品进入开发阶段后，产品经理自己时不时冒出新点子，高管也认为产品说明文档还可以继续修改，导致开发要求大幅变更——不是发布日期一推再推，就是某些功能被迫取消，或者产品质量下滑。
- **方法论的使用**: 一旦 1.0 版本进入项目执行阶段，就开始定义 2.0 版本，把创造热情投入下一个版本；唯一注意是"不要让这种做法干扰正在执行的项目"。
- **结论**: 高管再要求增加新功能时，"也不会影响正在开发的产品，因为你已经开始构思新版本，可以把新功能纳入其中"——挡回需求的理由从"我不想改"变成"我们有版本节奏"。
- **结果**: 作者自评"我个人觉得这个方法很管用"，把它作为探索/执行冲突的标准解法。

### 案例 2: 创业公司的烧钱探索
- **问题**: 创业公司拿到启动资金就招程序员，在"秘密状态"下边做边改，通常半年后才拿出漏洞百出的内测版；资金渐渐耗尽，产品依旧未成。
- **方法论的使用**: 承认"不管大家意识到没有，所有的公司都会执行探索产品的流程"；创业初期只设产品经理、交互设计师、原型开发三个职位，先用几周到两个月迭代高保真原型并请真实目标用户验证，确定方案后再招程序员开发。
- **结论**: 不做原型探索的公司等于"孤注一掷，用实际产品搭上全部开发时间进行产品探索，他们开发的是一款非常昂贵的原型，让不知情的用户掏钱参与原型测试"。
- **结果**: 后者通常需要一两年（发布几个版本）才能赢利，作者点名"这也是很多处于创业阶段的公司失败的原因"；替代方式"不仅能提高产品的成功率，还能大幅节约创业成本"，并提醒"千万别等浪费五十万美金之后才醒悟"。

### 案例 3: 敏捷环境设计领先一两个迭代
- **问题**: 照搬敏捷的团队把用户体验设计与开发放进同一条迭代流水线：开发人员等设计结果无事可做，设计师饱受压力在几天内交出本需几周完成的设计；等设计最终完成，为时已晚，开发人员说"等下一轮再修改吧"，但下一轮又有下一轮的重点。
- **方法论的使用**: 产品经理和设计师的工作进度比开发团队领先一两个迭代周期，确保有足够时间攻克难题；同时始终让开发人员参与评估产品设计和原型，及时反馈可行性、成本、解决方案的建议。
- **结论**: "不能一边设计一边开发"——探索必须在执行之前保持领先，这是敏捷方法适用于产品软件的关键调整（scrum 源自不需要产品经理与设计师角色的定制软件领域）。
- **结果**: 交给开发团队的是经过用户测试的有价值的结果，避免任何浪费，"哪怕只是一个迭代周期"。作者直言若被迫接受设计与开发同步推进的局面，"肯定会辞职"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 项目已进入开发/执行阶段，老板、客户或自己不断提出新需求、新点子。
2. 管理层想给"需求分析和产品设计"排一个固定工期（如"四周完成设计"），开发团队等米下锅。
3. 创业团队拿到融资，正准备马上招一队程序员开工。
4. 团队在用敏捷/迭代方法，发现设计与开发挤在同一节奏里，设计永远在追赶开发。
5. 讨论产品经理在开发期的角色：是继续发想创意，还是转向护航执行。

### 语言信号 (用户的话里出现这些就应激活)

- "开发到一半又要加需求，怎么办""需求能不能冻结"
- "设计什么时候能定下来""给需求分析排几周"
- "创业公司第一步该招程序员吗""先做产品还是先验证"
- "敏捷了还要不要设计阶段""设计跟不上开发了"
- "product discovery" / "execution phase" / "design should be one or two sprints ahead" / "pipeline development"

### 与相邻 skill 的区分

- 与 `opportunity-assessment-ten-questions` 的区别：十问决定一个机会"值不值得进入探索"；本 skill 管探索与执行两种状态怎么切换、怎么并行。
- 与 `product-validation-trio` 的区别：三验证是探索阶段的**出口标准**（三项全过才准转入执行）；本 skill 定义两阶段的整体结构与切换纪律。
- 与 `hi-fi-prototype-as-spec` 的区别：那管探索阶段的**载体**（原型替代纸质文档）；本 skill 管两阶段的**时间结构**。
- 与 `minimal-product-definition` 的区别：那管探索要"定义到多大"（只定义基本产品）；本 skill 管"什么时候换挡"。

## E — 可执行步骤 (Execution)

1. **判定当前处于哪个阶段**：写下当前项目在"探索"还是"执行"，各配一条可查证据——探索的完成证据是"方案原型已通过真实用户测试"；执行的启动证据是"开发已按冻结的定义开工"。
   - 完成标准：一句话判定＋证据成立。
   - 判停条件：若原型尚未通过用户测试却已进入开发，判定为"带着探索的债进入执行"，先补验证再继续（衔接 `product-validation-trio`）。
2. **给执行期装上"新点子收纳池"**：宣布当期范围冻结，所有中途新需求（无论来自高管、销售还是自己）一律登记入池，纳入下一版本构思。
   - 完成标准：每条新需求有入池记录和标准回复（"已纳入 2.0 构思"）；当期范围零变更（开发暴露的可行性缺陷的必要修复除外）。
   - 判停条件：若新需求源于方向性错误（如三验证漏项），升级为正式的范围变更评审，不得默默入池。
3. **启动流水线的下一节**：1.0 进入执行之日即 2.0 探索启动之时——排 2.0 的机会评估与原型迭代（通常几周至两个月），敏捷环境下保持设计领先开发一两个迭代。
   - 完成标准：2.0 的机会评估与原型排期已上日程，且不占用执行期救火人力。
   - 判停条件：若执行期问题频发、连续两个迭代抽不出人做 2.0 探索，先解决执行质量问题（技术余量、快速响应），流水线暂停。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 目标明确、按图施工的纯技术项目（基础设施迁移、架构升级）——没有"定义什么产品"的不确定性，两阶段切换没有着力点。
- 日常小修小补与例行发布——切换成本高于收益。
- 不要把它当成"设计可以无限拖期"的挡箭牌——作者要求帮管理层理解探索的本质，而不是取消交付节奏。

### 作者在书中警告的失败模式

- 执行阶段不停冒新点子、高管反复修改产品文档——"结果不是发布日期一推再推，就是某些功能被迫取消，或者产品质量下滑"（第12章）。
- 像制订建筑施工计划一样给产品探索设定期限——时间一到开发团队等米下锅，"只好让他们开发有缺陷的产品……那是你产品经理的错"（第12章）。
- 孤注一掷用实际产品做探索——"开发一款非常昂贵的原型，让不知情的用户掏钱参与原型测试"（第12章）。
- 用户体验设计与软件开发同步进行——"等设计师最终完成设计，为时已晚"（第19章）。

### 作者的盲点 / 时代局限

- 作者的流水线以版本号（1.0/2.0）为节拍；持续交付时代很多团队已无大版本概念，切换逻辑需改写成以迭代/特性簇为粒度。
- 作者假设有专职产品经理与交互设计师分工；早期创业团队常常一人身兼，切换机制要落到个人时间块管理，书中未展开。
- "探索不可设定期限"对有硬窗口的业务（展会、合规、合同死线）缺乏变通指导，需要自行设探索预算上限。

### 容易混淆的邻近方法论

- 瀑布式阶段划分（需求→设计→开发→测试）：瀑布假设前期文档确定即可交付；作者的两阶段以"原型通过用户测试"为探索出口，不是文档评审通过。
- Scrum 的 sprint 划分：scrum 源自定制软件领域，照搬到产品软件会设计混乱；必须加上"设计领先一两个迭代"等产品软件特有的调整。
- 双轨开发/并行工程：本 skill 讲的是两种工作**性质**与重心切换，不是把同一个团队拆成两班人马。
