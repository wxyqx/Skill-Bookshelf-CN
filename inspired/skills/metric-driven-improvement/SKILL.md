# 指标驱动改进现有产品

## R — 原文 (Reading)

> "大多数产品团队实际上只是功能加工厂，附带制作补丁，修补缺陷。说白了，他们就只会一味地添加新功能。很多情况下，添加新功能不仅不会为产品增色，反而会让产品性能变得更糟糕。……改进产品不是简单地满足个别用户的要求，也不能对用户调查的结果照单全收。能提高指标的功能才是你关注的重点。"
>
> — Marty Cagan，第23章《改进现有产品》

---

## I — 方法论骨架 (Interpretation)

改进一个已经上线的产品时，团队最常见的堕落轨迹是：画路线图→记用户要求→排期开发→再画路线图。作者给这条轨迹起了个名字——**功能加工厂**，并且断言新功能常常让产品变得更糟，因为改进根本没有方向。方向从哪里来？从**关键指标**里来。

操作骨架分三步。第一，**明确目标即明确数字**：选一个与商业业绩直接挂钩的指标（如投保申请完成率），把它拆成漏斗——每一步各有多少用户进入、多少用户放弃。第二，**用漏斗定位病灶**：流失集中的环节就是改进的候选地，而且流失原因往往指向体验问题（例如注册时索要的信息太多，用户不信任你就不敢给）。第三，**用指标过滤改进清单**：个别用户的要求、用户调查的结果都只是线索，不是任务；每一项拟做的改进必须能回答"它预计推动哪个指标"，答不上来的降权或放弃。

支撑这套方法的数据来源很宽：网站分析、用户测试、客服与销售的反馈、盈亏分析、净推荐值——互联网服务甚至能拿到几乎实时的数据反馈。作者把它称为"事半功倍"的改进方式：改对一处漏斗，胜过加十个功能。

## A1 — 书中的应用 (Past Application)

### 案例 1: 保险网站投保流程 7%→15%
- **问题**: 保险公司的投保申请网站，只有 7% 的访客完成整个申请流程，改进从何下手？
- **方法论的使用**: 先跟踪漏斗各级——多少用户访问起始页、每个页面各有多少人放弃注册、多少人拒绝提供私人信息、多少人完成申请——把"完成率 7%→15%"定为目标，再从指标反推体验问题（如注册阶段索要信息过多导致不信任）。
- **结论**: "如果把这个数字提高到15％，将大幅提升公司的业绩！"改进什么、怎么改，取决于能在多大程度上提升各项指标，而不是取决于功能清单的长度。
- **结果**: 这是作者在第23章给出的标准示范——改进方向来自指标分析，而非罗列新功能。

### 案例 2: 9% 注册成功率翻倍
- **问题**: 该投人力做全新产品，还是完善现有产品？
- **方法论的使用**: 把两者一视同仁地当成"产品机会"比较收益与成本；100 位打算注册的用户只有 9 人完成，把成功率提到 18% 就能让收益翻倍，且"只要做一些原型测试和用户测试，很快就能找出存在的问题"。
- **结论**: 好机会常在眼皮底下，完善蹩脚的现有特性往往事半功倍。
- **结果**: 作者每指出这类机会并提高公司利润后"都会被看做英雄"——公司却常因自负（认为产品已足够好、宁愿花钱投广告）看不见它。

### 案例 3: 易用性吃掉上百人客服成本
- **问题**: 客服支出被视为必不可少的运营成本，能压缩吗？
- **方法论的使用**: 把"减少客服依赖"转译为易用性指标：产品公司往往雇用上百人的客服团队，若提高产品易用性，就能大幅减少客服人数、降低成本。
- **结论**: 成本指标与体验指标是一体两面——改进易用性同时提高用户满意度和净推荐值。
- **结果**: 作者借此说明公司常有的三个自负借口（无法改进、满足于 9%、客服支出必不可少）往往掩盖着真正的病灶：产品本身缺乏竞争力。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 季度/版本规划时，用户、销售、客服提来一堆功能请求，要决定先做哪个。
2. 产品功能越加越多，但用户抱怨越来越难用，怀疑"加功能"这个动作本身。
3. 要在"做全新功能"与"打磨现有功能"之间分配开发资源。
4. 注册、下单、续费等关键转化率偏低，要定位问题出在哪一步。
5. 需求池塞满用户调查结论，想给它们排一个靠谱的优先级。

### 语言信号 (用户的话里出现这些就应激活)

- "需求池堆了一堆请求，怎么排优先级？"
- "注册/下单转化率上不去，帮我分析分析"
- "加了一堆功能，用户反而说难用了"
- "conversion funnel / registration drop-off / feature factory / metrics-driven"
- "该做新功能还是把旧的做好？"

### 与相邻 skill 的区分

- 与 `opportunity-assessment-ten-questions` 的区别：那是给**新想法**立项的过滤闸门；本 skill 面向**已上线产品**的改进决策——作者明确说新旧项目应一视同仁地用机会标准比较，指标是共同的硬通货。
- 与 `user-research-limits` 的区别：那是论证"调查结果为什么不能当需求"；本 skill 给出替代物——调查结论只能作为线索进入指标检验，能提高指标的改进才立项。
- 与 `rapid-response-window` 的区别：那是发布后几天内的应急响应；本 skill 是常态化的、按规划周期进行的指标改进，窗口期结束后无缝衔接。
- 与 `special-product-defense` 的区别：面对"某大客户要这个功能"，前者用产品原则说不；本 skill 用指标映射检验——对个别用户的要求同样先问"它推动哪个指标"。

## E — 可执行步骤 (Execution)

1. **定出关键指标并排定轻重缓急。**
   - 完成标准：能用一句话说出"哪个数字的提升代表这次改进成功"，且该数字与商业业绩（收益/成本/留存）直接挂钩；同时写出成功与失败的分界线。
   - 判停条件：团队说不出自己关心哪个指标——先补指标定义，禁止直接进入功能排期；只有功能愿望清单而没有指标，就是功能加工厂的前兆。
2. **把指标拆成漏斗，定位流失最严重的环节。**
   - 完成标准：列出每一步的进入/放弃数据，并对最大的流失点给出原因假设（如"注册阶段索要信息过多，用户不信任"），假设有数据或用户测试佐证。
   - 判停条件：漏斗各级数据拿不出来且短期无法补测——改为先小范围用户测试定位，不凭想象动手。
3. **用指标过滤改进清单，改进后复查指标。**
   - 完成标准：清单上每一项都能注明"预计推动哪个指标、预计推多少"；无法映射的请求明确降权或拒绝；改进上线后对照第 1 步的成败分界线复盘。
   - 判停条件：某轮改进后指标纹丝不动——停止继续加功能，回到第 2 步重新定位，而不是换一批功能再试。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 全新产品立项阶段——没有漏斗可拆，先用 `opportunity-assessment-ten-questions` 判断值不值得做。
- 发布后几天的应急处理——那是 `rapid-response-window` 的战场，规则是"多快解决问题"而非"推动哪个指标"。
- 用虚荣指标（纯 PV、累计下载）代替与商业目标挂钩的指标——作者要求指标"取决于产品的商业目标"，挂不上钩的数字只会把团队引回功能加工厂。

### 作者在书中警告的失败模式

- 沦为"功能加工厂，附带制作补丁"——一味添加新功能，反而让产品性能更糟糕（第23章）。
- "简单地满足个别用户的要求"或"对用户调查的结果照单全收"（第23章）。
- 公司过于自负看不见眼皮底下的机会：认为产品已足够好、宁愿花钱投广告也不修复 9% 的注册漏斗、认为客服支出必不可少（第11章）。

### 作者的盲点 / 时代局限

- 作者的示范基于 2008 年的网站分析工具时代；对移动端、离线场景、多端数据打通的现代产品，漏斗埋点与归因远比当年复杂，需要补充现代数据基础设施的讨论。
- "能提高指标的功能才是重点"若被极端化，可能滑向只看数字、无视情感需求的功利化改进——需与 `emotion-based-demand` 互补：数字告诉你用户在哪里流失，情感分析告诉你为什么。
- 作者未展开实验设计（A/B 测试的显著性、多重检验），只说"分析各步转化"，落地时需要现代实验方法论补位。

### 容易混淆的邻近方法论

- 增长黑客 / AARRR 模型：同用漏斗语言，但作者的前提是"先有正确的产品"——指标改进不能替代产品定义与验证。
- 北极星指标 / OKR：现代目标管理框架与作者精神一致，但作者更强调**过滤功能请求**这个决策动作，而非目标对齐仪式。
- 用户体验走查：靠专家经验找问题；本 skill 要求每个改进点先由数据定位，经验只是辅助证据。
