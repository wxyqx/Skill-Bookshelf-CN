# 基本产品定义法

## R — 原文 (Reading)

> "不再试图定义最终产品，转而定义只满足基本要求(价值、可用性、可行性)的产品，简称基本产品。一旦基本产品定义完成，通过了用户测试，它就是一个不可分割的整体，去掉任何元素，都不可能获得预期的效果。"
>
> — Marty Cagan，第20章《基本产品》

---

## I — 方法论骨架 (Interpretation)

老式流程的默认做法是：先定义一个"最终产品"，开发一估算，工期超了，双方坐下来砍功能凑时间。作者号召整个放弃这条路，换成一个反直觉的定义标准——一开始就只定义**满足基本要求**（价值、可用性、可行性）的产品。只设计基本功能可以把复杂度降到最低、把开发时间减到最少，这一步本身就是最大的工期节省。

定义基本产品的三步：与设计师合做一个只含实现商业目标的最基本功能、又有良好用户体验的高保真原型；邀请一位开发人员（架构师或主程序员）参与检查原型，估算各功能的直接与间接成本、指出设计误区、评估尚不确定是否可行的功能；请真实用户验证原型。三步走完，各项功能孰去孰留对各方透明。

随后是一条硬约束——**不可削减律**：基本产品一旦通过目标用户的测试，就是一个不可分割的整体，再砍任何元素都会破坏预期效果；"如果还能削减，那说明你定义的不是基本产品"。因此当估算仍然超支时，唯一的答案是延长工期而不是削减功能，因为已经没有东西可削减了。配套纪律是：进入软件开发环节后，产品经理不能再随意修改设计——过去反复改设计，多半因为一开始构思不全面、不彻底，原型迫使产品经理把问题想透。要提防的是把敏捷方法当成替代解：scrum 解决不了这个问题，反而可能带来新问题；敏捷环境下目标仍然是"设计出符合基本要求的产品"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 砍功能还是延工期
- **问题**: 产品经理制作了详细标注功能重要等级的产品说明文档，剔除开发团队力不能及的功能后，估算出的进度仍比设想多几个月；于是双方争论估算是否准确，接着削减功能、缩小测试范围、减少公开测试时间、要求雇佣额外开发人员。
- **方法论的使用**: 换一种产品设计方式——只做含基本功能的高保真原型，邀请开发人员参与估算成本、评估可行性，请真实用户验证；估算超支时延长工期而不砍功能。
- **结论**: "一旦基本产品确定，通过了目标用户的测试，就不可能再削减任何功能。如果还能削减，那说明你定义的不是基本产品。"
- **结果**: 因为"你已经没有东西可削减了"，超支只延工期；且估算依据从一纸文档变成精减功能的原型，精度大大提高，"即使延长工期，情况也远没有以前严重"。

### 案例 2: 过滤多余功能反而更受欢迎
- **问题**: 几乎所有产品都有一些不那么重要的功能，它们对提高销量和用户满意度毫无作用，却不断拉长研发时间。
- **方法论的使用**: 克制不断增加功能的冲动，过滤多余的功能——缩短研发时间，降低生产成本，让产品更早上市。
- **结论**: "如果去掉这些功能，产品甚至会因为简单、易用获得更多用户的喜爱。"
- **结果**: 功能更少、上市更早、成本更低、用户反而更多——减法本身就是竞争力。

### 案例 3: "断腿的狗打不了猎"
- **问题**: 被砍掉的功能看起来都不致命——产品照样能上线，为什么还是达不到预期？
- **方法论的使用**: 用作者从前的老板的比喻自检：设计产品时一定要考虑哪些功能是最重要的，争取设计出只满足基本要求的、不可删减的产品。
- **结论**: "断腿的狗打不了猎"——砍掉必要元素后的产品即使如期上线，也不是有机的整体，产品经理不满意，开发人员不满意，用户更不会满意。
- **结果**: 基本产品思维把"砍功能"从工期谈判技巧升级为定义阶段的质量标准：砍过之后还能用，不等于还能达到预期效果（呼应前言规律10"去掉任何因素，都不可能达到预期的结果"）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 开发估算超期，老板要求砍功能赶工期，需要判断"能不能砍、该不该砍"。
2. 规划 MVP：讨论"最小可行产品到底该包含哪些功能"。
3. 产品功能越堆越多、越来越臃肿，团队决定认真做一次减法。
4. 双方进入"争论估算→削减功能"的工期谈判，需要一个停止谈判的判据。
5. 产品定义评审：判断一份功能清单是否已经"减无可减"。

### 语言信号 (用户的话里出现这些就应激活)

- "排期超了，砍点功能吧""砍哪些功能能赶上上线"
- "MVP 该包含什么""最小功能集是什么"
- "这个功能能不能放到下一版""哪些是必须的"
- "功能太多了，做做减法""产品太臃肿了"
- "minimal product" / "cut scope" / "extend the deadline instead" / "must-have features" / "descope"

### 与相邻 skill 的区分

- 与 `product-validation-trio` 的区别：三验证回答"这个定义过不过关"（价值/可用性/可行性三证）；本 skill 回答"定义该多大"——被验证的对象必须是减无可减的基本产品。
- 与 `hi-fi-prototype-as-spec` 的区别：那管定义的**载体**（原型替代文档）；本 skill 管定义的**规模**（只含基本功能）。
- 与 `metric-driven-improvement` 的区别：那管已上线产品按指标做加法改进；本 skill 管新产品定义期"减无可减"的标准与"只延工期不砍功能"的纪律。
- 与 `persona-driven-focus` 的区别：人物角色是砍功能的依据之一（只对"山姆"重要的功能淘汰）；本 skill 给出砍完之后"不可再减"的判据与超支时的处置。
- 与 `opportunity-assessment-ten-questions` 的区别：十问过滤机会本身；本 skill 收缩已选中机会的方案规模。

## E — 可执行步骤 (Execution)

1. **逐条追溯功能，分离"基本"与"添彩"**：把候选功能逐条问"它服务于哪个已确认的目标/基本要求"，分成"实现商业目标所必需"与"锦上添花"，后者全部移出本版。
   - 完成标准：每个功能要么追溯到具体目标，要么被明确移出；基本清单之外无搭车项。
   - 判停条件：若所有功能都被标成"必须"，说明目标与优先级尚未对齐——先回到产品原则与优先级共识（`product-principles-priority`），不继续往下走。
2. **只为基本功能做原型，请真实用户验证**：原型只含留下的功能；请真实目标用户测试价值与可用性（`product-validation-trio`）。
   - 完成标准：用户理解产品价值、能完成关键操作，原型通过测试。
   - 判停条件：测试不过时回到定义修改迭代，不得用"多加一个功能"来补救缺陷。
3. **冻结定义并宣布"不可削减"**：基本产品通过测试后锁定范围；开发估算超支时明确只延工期、不砍功能。
   - 完成标准：有书面的基本产品清单＋通过测试的证据；超支决策记录为"延期"而非"裁剪"。
   - 判停条件：若此时还能砍出功能而不破坏预期效果，承认当初定义的不是基本产品，回到第 1 步重做定义。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已上线产品的功能精简与下线——那是改进与性能问题，用指标检验（`metric-driven-improvement`），本 skill 管的是定义期。
- 团队尚未与真实用户交流、目标未对齐时的"拍脑袋砍功能"——砍出来的不是基本产品，只是粗糙产品。
- 探索验证阶段的原型本身——原型可以随意修改、用完即弃，"不可削减律"只适用于通过用户测试之后的基本产品定义。

### 作者在书中警告的失败模式

- 老式流程的砍法四连——争论估算是否准确、削减功能、缩小测试范围、雇佣额外开发人员，最后"开发出来的产品完全不是有机的整体，产品经理不满意，开发人员不满意，用户更不会满意"，而很多团队把这看成理所当然（第20章）。
- 把砍功能当成工期谈判技巧而非定义质量问题——"如果还能削减，那说明你定义的不是基本产品"（第20章）。
- 进入开发环节后随意修改设计——过去产品经理经常要求更改设计，主要是一开始构思不全面、不彻底（第20章）。

### 作者的盲点 / 时代局限

- 2008 年的语境是一次性大版本发布；持续交付与灰度发布时代"工期"形态变了，但"通过验证的范围不可拆"的纪律仍适用于一个特性簇/一次发布的完整性。
- 作者未讨论网络效应型产品——有些功能的价值依赖其他用户的存在，"基本功能"实际是最小网络，单独裁剪的判断标准不同。
- "延工期不砍功能"对不可动的死线（展会、合规、合同违约）没有给出变通方案，需要结合发布节奏管理自行取舍。

### 容易混淆的邻近方法论

- MVP（精益创业的最小可行产品）：作者的基本产品是"通过三验证的完整概念、减无可减"，不是"可以很糙、先发再改"——粗糙发布恰恰违背基本要求。
- MoSCoW 优先级法：MoSCoW 假设可以按级砍掉 Should/Won't；基本产品论认为通过测试后无可再砍——还能砍出一份优先级清单，本身就是定义不良的症状。
- "做减法"的产品简化主义：本 skill 的减法发生在定义期且有用户测试兜底，不是上线后的功能下线。
