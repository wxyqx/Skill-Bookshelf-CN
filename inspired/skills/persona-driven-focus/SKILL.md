# 人物角色聚焦

## R — 原文 (Reading)

> "人物角色可以用来筛选重要的产品功能。假设目标用户是'玛丽'，就该添加对'玛丽'重要的功能；如果某项功能只是针对'山姆'的，就该被淘汰。……面面俱到的产品往往一无是处。"
>
> — Marty Cagan，第17章《产品人物角色》

---

## I — 方法论骨架 (Interpretation)

人物角色（persona）是通过与用户沟通交流建立的人格化虚拟原型，重点关注**行为、态度、目标**。设计界把它当设计工具，作者的独特用法是把它当**产品管理的决策工具**，用途有五：①筛选重要功能——只做对关键角色重要的，淘汰只服务其他角色的；②防止团队把自己的需求当成用户需求；③给不止一种的用户类型排优先级，而不是"每种用户都加一点功能"最后一团乱麻；④向团队描述目标用户是谁、怎么用产品、关心什么；⑤和产品原则一样帮团队达成共识，让产品、设计、文案、开发、测试在数千个细节决策上不必事事请示。

三条注意事项同样是纪律：**别束之高阁**——回避挑选关键角色的难题、宣称老少皆宜是自欺欺人，每个发布周期要竭尽全力聚焦一类关键人物角色；**别凭想象编**——不与真实用户交流、按刻板印象造出来的角色会系统性失真；**别只测关键角色**——原型测试要邀请多样化的用户，覆盖角色设定之外。

一句话概括：**决定谁不是目标用户，与决定谁是目标用户同样重要。**

## A1 — 书中的应用 (Past Application)

### 案例 1: 玛丽 vs 山姆的功能筛选
- **问题**: 销售说大客户"山姆"式的用户要某功能，客服说"玛丽"式的典型用户根本用不了，听谁的？
- **方法论的使用**: 先问人物角色清单——产品这个版本的关键人物是谁；再逐一检查功能归属。
- **结论**: 该添加对"玛丽"重要的功能；某项功能只是针对"山姆"的，就该被淘汰。
- **结果**: 功能取舍从"谁的声音大"变成"谁是我们这版的关键人物"，避免面面俱到导致的一无是处。

### 案例 2: 凭想象编角色栽跟头
- **问题**: 团队不接触用户，闭门凭想象和刻板印象创建人物角色，看起来还挺像回事。
- **方法论的使用**: 作者自述"我在这方面栽过不少跟头"，此后坚持没接触真实用户之前不先入为主下结论；与目标用户面对面交流是创建角色必不可少的环节，这项工作不能外包。
- **结论**: 虚构角色看似合理，实则系统性地扭曲真实用户的行为、态度与目标，用它做决策越走越偏。
- **结果**: 产品经理必须亲自参加用户交流、用户调查和所有可用性测试，角色才立得住。

### 案例 3: 每个版本只聚焦一类关键人物
- **问题**: 用户类型多，怕得罪任何一类，于是每版都试图照顾所有人。
- **方法论的使用**: 每个发布周期集中精力关注一类关键人物角色，把产品优势发挥到极致；这不是说该版本对其他用户没价值，而是强调每版只针对一类目标用户做到极致。
- **结论**: 宣称产品老少皆宜是自欺欺人，面面俱到的产品往往一无是处。
- **结果**: 聚焦带来锋利的版本定位，其余用户类型的诉求进入后续版本的排序。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 功能清单越堆越长，需要一个裁决"这个功能给谁用、不服务谁"的机制。
2. 销售带来大客户需求、客服带来小白用户抱怨，两边都想加功能，不知听谁的。
3. 要写 PRD/立项文档，得先回答"目标用户是谁"。
4. 发现团队讨论里全是"我觉得用户会……"，怀疑在给自己（超级用户）做产品。
5. 用户类型不止一种，需要给它们排序而不是每种都塞一点功能。

### 语言信号 (用户的话里出现这些就应激活)

- "我们的目标用户是谁？""这个功能是给谁用的？"
- "用户画像/人物角色怎么建？""帮我建几个 persona"
- "大客户要这个功能，做不做？""小众用户要不要伺候？"
- "是不是在做自己想用的东西，不是用户想用的？"
- "user persona" / "target user" / "who is this for?" / "feature doesn't fit our persona"

### 与相邻 skill 的区分

- 与 `product-principles-priority` 的区别：产品原则裁决"什么更重要"（价值排序），人物角色裁决"为谁而做"（用户排序）；第17章原文把两者并列为共识工具，争论方案时经常要同时援引。
- 与 `user-research-limits` 的区别：那是调研数据能不能当需求的边界法；人物角色是调研之后的**聚焦决策工具**——第16章也把人物角色列为调研方法之一，但本 skill 管的是建好之后怎么用。
- 与 `charter-user-program` 的区别：特约用户是真实的人（不超过十位开发伙伴），人物角色是抽象原型；前者提供一手输入，后者把输入固化为全团队的决策依据——两者是上下游，不是二选一。

## E — 可执行步骤 (Execution)

1. **建角色：从真实用户中来**
   - 做法：与目标用户面对面交流，产品经理亲自参加用户调查与可用性测试，提炼典型类型。
   - 完成标准：每个角色写明行为、态度、目标三要素；能清楚回答"谁不是目标用户"；角色的每条特征都能追溯到真实交流，而非想象。
   - 判停条件：发现角色出自会议室里的想象或刻板印象——立即停用，先去见真实用户再继续，否则后续所有决策都在放大失真。
2. **排序聚焦：确定本版本的关键人物**
   - 做法：给多类用户角色排优先级，明确本发布周期聚焦哪一类关键人物角色。
   - 完成标准：写出一句话版本定位——"本版为 X 优化，Y 不是本版目标用户"；没有任何一类被含糊地标成"都是重点"。
   - 判停条件：若所有类型都被标为关键（老少皆宜）——自欺欺人，退回重排；排序僵持不下时切换到 `product-principles-priority` 的优先级共识步骤。
3. **用角色筛选功能并校验**
   - 做法：逐一检查候选功能"对哪类角色重要"；只针对非关键角色的功能淘汰或移入后续版本；原型测试同时邀请角色设定之外的多样化用户。
   - 完成标准：进清单的每个功能都能指认服务对象；测试覆盖不只关键角色，反馈被用来修正角色设定或功能判断。
   - 判停条件：真实用户的反应与角色设定冲突时，先修改角色再修改方案——不能反过来硬拗用户。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 营销投放与市场细分——营销用角色是找准目标消费者、激发需求，产品用角色是分析需求与行为，目的不同不能混为一谈（作者明言）。
- 纯技术基建、无用户界面差异的内部功能——"给谁用"不构成取舍维度。
- 用户群单一且团队就是用户的小工具——建一整套角色流程的成本高于收益，直接与用户交流即可。

### 作者在书中警告的失败模式

- 创建后束之高阁，回避挑选关键人物的难题，宣称老少皆宜——自欺欺人（第17章注意1）。
- 凭想象和刻板印象编角色，不与真实用户交流——作者"栽过不少跟头"（注意2）。
- 把自己的需求当成用户需求——团队是超级用户，与真实用户的忍受度相去甚远（用途2）。
- 简单针对每种用户添加功能，"结果会是一团乱麻"。

### 作者的盲点 / 时代局限

- 沿用 Alan Cooper《交互设计之路》的静态角色画像，缺少数据化手段（行为聚类、留存分群）做量化校验，角色代表性依赖创建者的交流质量与自省。
- 对平台/多边市场，多类角色互相构成彼此的体验，"每版只聚焦一类"需要更复杂的多边权衡，书中未展开。

### 容易混淆的邻近方法论

- 用户画像/人口统计细分：标签（年龄性别地域）≠ 行为、态度、目标；第35章更警告情感人群无法用人口统计划分。
- 用户旅程图：刻画过程的时间轴，人物角色聚焦的是"谁"这个对象，常配合使用但不可互替。
- Cooper 原版 personas（设计驱动）：作者明确扩展为产品管理决策工具，用途从指导设计扩展到筛选功能、排用户类型优先级。
