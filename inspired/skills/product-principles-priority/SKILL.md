# 产品原则与目标优先级共识

## R — 原文 (Reading)

> "产品原则是对团队信仰和价值观的总结，用来指导产品团队做出正确的决策和取舍。……在我看来，每当团队内出现严重的意见分歧时，并非是大家对事实的认定有争议，而是对目标和目标的优先级有不同的理解。"
>
> — Marty Cagan，第13章《产品原则》

---

## I — 方法论骨架 (Interpretation)

产品团队最大的隐形成本不是做错决策，而是**每次决策都要重新吵一遍**——因为缺少一把共同的尺子。作者的做法分两层。

第一层是**制定产品原则**：一套价值判断框架，回答"什么更重要"。它不是功能清单，而是整条产品线的战略指南；好的原则甚至能反过来激发设计灵感。两条纪律：①**必须按重要性排序**——所有产品都想既易用又可靠，但总有要先牺牲的那个；②**别犯两类错误**——原则空泛到谁都能援引（等于没有），或把"为用户提供清晰导航"这类设计原则误当成产品原则。

第二层是**用它化解方案之争**。作者诊断：会上各持己见、僵持不下，根源不是大家掌握的事实不同，而是各自用不同的优先级在量方案。所以方案讨论前先就四点达成共识：要解决什么问题→为哪类人物角色解决→产品要达到什么目标→每项目标的优先级。共识要落在白板上、会前重申、决策过程完全透明。最反直觉的一条：**请高管出面定夺不是解法，是病征**——需要裁决本身就说明沟通方式有问题，靠职位压出来的决定会激化矛盾。

## A1 — 书中的应用 (Past Application)

### 案例 1: 电影网站的影评原则
- **问题**: 某制片厂希望借网站发表评论，接还是不接？
- **方法论的使用**: 该网站事先确立了一条产品原则——相信社区用户的影评比专业人士的影评更有价值。
- **结论**: 产品团队无需逐次争论，直接根据这条原则决定是否采纳；原则把"什么更重要"变成了可执行的取舍依据。
- **结果**: 外部诱惑由事先公开的价值排序裁决，个案之争变成原则应用。

### 案例 2: 目标优先级写在白板上
- **问题**: 产品会议没完没了、既无议程也无结果，高管还扔下没头没脑的意见拂袖而去，怎么办？
- **方法论的使用**: 讨论方案前先在四点上达成共识（问题/人物角色/目标/目标优先级），把目标从最重要到最不重要逐项排序写在白板上，会前再次强调。
- **结论**: "切不可囫囵吞枣地把所有目标都贴上'关键'和'重要'的标签"——分歧的根源是优先级未对齐，不是利益冲突；统一尺子后方案之争自然化解。
- **结果**: 决策过程与依据完全透明，"每位同事都可以看到评估方案和制定决策的确切依据"；再起争执就先回顾优先级共识。

### 案例 3: 拒绝特例产品的制度依据
- **问题**: 大客户带着特殊要求上门，决定权在 CEO，产品经理拿什么说话？
- **方法论的使用**: 公司事先根据企业文化树立产品原则；关键时刻按产品原则决定是否接受客户提出的特殊要求，产品经理据此协助 CEO 寻找其他解决途径。
- **结论**: 产品原则是特例产品防御的前置条件——没有事先的原则排序，每次"接不接"都会沦为临场博弈。
- **结果**: 拒绝有了制度依据，而且回绝的理由对全公司透明（详见第32章特例产品分析）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品会上两派为方案吵了几个小时僵持不下，有人提议"请老板拍板"。
2. 新官上任或组建新团队，要把一群聪明人从"各有一套判断"变成"用同一把尺子"。
3. 两个功能/两种方案都"重要"，争不出谁先谁后。
4. 大客户、合作伙伴提出特殊要求，团队需要事先说好的裁决依据。
5. 想制定团队价值观/产品准则，但写出来的都是空话套话。

### 语言信号 (用户的话里出现这些就应激活)

- "团队吵起来了，谁也说服不了谁""帮我定个规矩"
- "这两个都重要，到底先做哪个？"
- "要不要让 CEO 来拍板？"
- "我们的产品原则/价值观应该是什么？"
- "product principles" / "how do we prioritize?" / "team can't agree"

### 与相邻 skill 的区分

- 与 `opportunity-assessment-ten-questions` 的区别：那是过滤单个机会的立项闸门；本 skill 建立贯穿所有后续决策的价值标尺——先有原则排序，机会评估才有裁决依据。
- 与 `persona-driven-focus` 的区别：产品原则裁决"什么更重要"，人物角色裁决"为谁而做"；第17章明言两者同为团队共识工具，常需配套使用。
- 与 `special-product-defense` 的区别：那是面对定制化勒索时说"不"的具体框架；本 skill 提供说"不"的依据来源——没有事先排序的原则，防御框架无从启动。

## E — 可执行步骤 (Execution)

1. **制定并排序产品原则**
   - 做法：召集团队讨论分析，确定最看重的价值理念；逐条检验，再按重要性排序。
   - 完成标准：每条原则具体到能裁决一次真实取舍（像"社区影评比专业影评更有价值"那样）；明确区分产品原则与设计原则（"清晰导航"不算）；能回答"最重要的究竟是易用性，还是可靠性"。
   - 判停条件：两条原则排序时人人答案不同且争不出——说明理念还没想清楚，退回讨论，不要强行发布一份没人真信的清单。
2. **方案之争先对齐四点共识**
   - 做法：讨论任何方案前，依次确认要解决什么问题、为哪类人物角色解决、产品要达到什么目标、每项目标的优先级。
   - 完成标准：目标从最重要到最不重要逐项排序、写在白板上、会前重申；没有人把所有目标都贴"关键/重要"标签。
   - 判停条件：连第一点"要解决什么问题"都无法达成共识——停止方案讨论，回到机会本身重新评估。
3. **用共识裁决并保持透明**
   - 做法：在共识之上辩论方案的合理性与可行性；对外说明每个决策的依据和理由，清楚展示每一个决策环节。
   - 完成标准：本次决策能明确指出援引了哪条原则/哪个优先级；下次同类取舍无需重吵；分歧重现时按作者做法先回顾目标与优先级。
   - 判停条件：若诊断发现冲突源于部门利益或人事而非优先级认识——共识工具失效，升级到机制层解决（如产品评审团），不要继续在会上消耗。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯技术选型与执行排期之争——那是"怎么做"层面的约束与资源问题，优先级共识救不了排期冲突。
- 一人团队或尚无任何真实取舍的空转期硬造"十条原则"——原则必须从真实取舍中长出来，否则就是墙上标语。
- 用"我们的原则是用户至上"这类空话替代具体排序——空泛原则正是作者点名的第一类错误。

### 作者在书中警告的失败模式

- 原则过于空泛失去指导作用，或把设计原则误当产品原则（第13章两类错误）。
- 囫囵吞枣地把所有目标都贴上"关键""重要"标签——等于没有排序。
- 僵持不下就请高管出面定夺——"会激化团队内部矛盾，得不偿失"。
- 多数团队跳过共识步骤直接争论方案，"在细枝末节上争执不下"。

### 作者的盲点 / 时代局限

- 作者假设产品经理能靠"摆事实、讲道理"促成共识（他自己承认产品经理没有实权）；在销售主导或强矩阵组织里，白板共识可能挡不住职位权力，需要更高层的制度背书。
- 2008 年的硅谷经验以同地办公为默认前提；远程/异步团队需把"白板+会前重申"改造成书面决策记录与公开的决策依据文档。

### 容易混淆的邻近方法论

- OKR/目标管理：OKR 定义目标与度量，本 skill 定义目标之间的先后与取舍裁决，二者互补不可互替。
- 设计原则/设计规范：执行层守则（如导航清晰），层级低于产品原则——混为一谈正是作者点名的第二类错误。
- 企业文化价值观宣言：文化口号面向全公司行为，产品原则必须能裁决具体产品取舍，否则只是墙上的字。
