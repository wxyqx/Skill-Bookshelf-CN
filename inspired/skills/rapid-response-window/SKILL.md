# 发布后快速响应阶段

## R — 原文 (Reading)

> "产品发布后，多数公司会迅速撤走为研发产品和发布产品整合的资源，急于投入下一个项目，殊不知此时正是收集反馈信息、改进产品的最佳时机。急于'撤军'是项目管理和产品开发流程中的大忌。……关键不在于是否会出现问题，而在于能多快解决问题。"
>
> — Marty Cagan，第25章《快速响应阶段》

---

## I — 方法论骨架 (Interpretation)

多数团队把发布当成终点线：冲线、庆功、撤人、扑向下个项目。作者定义了一个被绝大多数流程图省略的**正式阶段**——发布后几天至一周，所有项目成员留出时间，专门处理发布后才暴露的反馈与问题。它不是运维值班，而是产品决策在场的收尾窗口。

骨架有四根柱子。**第一，窗口期是制度而非自觉**：哪怕测试再严格，总有问题发布后才显露端倪；按部就班等下个版本修补，代价太高，所以要在排期上就把这几天圈出来。**第二，分级决定速度**：产品团队（产品经理、交互设计师、主程序员、客服、市场营销）每天至少开一次简短会议，讨论问题的轻重缓急，当场定方案——发补丁、发声明公示处理办法，或记入下版。**第三，指标先行**：发布前就明确用哪些可量化指标评估表现（访问量、注册数、停留时间、转化率、订阅数、广告收益），分出轻重缓急，并事先想好什么算成功、什么算失败。**第四，一线声音直通**：网站分析工具的实时数据之外，客服、销售和合作伙伴的意见同样不容忽视。

作者对回报的判断毫不含糊：这点投资"绝非其他项目阶段可比"——因为问题在用户热情还在、数据最新鲜、团队最齐整的时候被处理。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 企业软件上门安装——"不装好别想离开"
- **问题**: 企业级产品发布后，问题往往在真实客户的安装与使用现场才暴露，隔着重重支持流程怎么办？
- **方法论的使用**: 派产品团队成员（产品经理、设计师、开发人员等）亲自上门为客户安装软件，团队上下明白"不安装好产品就别想离开"。
- **结论**: 人到了现场，责任就到了现场——问题总能被迅速发现、迅速解决。
- **结果**: 这是作者在企业级产品上对快速响应阶段的落地形式：把响应窗口从"等工单"提前到"贴着客户装"。

### 案例 2: 每天简短会议分级响应
- **问题**: 发布后反馈从各个渠道涌进来，团队怎么避免手忙脚乱或互相踢皮球？
- **方法论的使用**: 一旦问题反馈回来，产品团队每天至少召开一次简短会议，讨论问题的轻重缓急，确定最佳解决方案——通过网站发布补丁，或发表声明公示处理办法。
- **结论**: 响应速度来自预案：团队事先认识到这个阶段的重要性，大幅提高质量便指日可待。
- **结果**: 反馈有了统一的分诊台和出口，问题按轻重缓急流动而不是按嗓门大小流动。

### 案例 3: 发布后撤军是大忌
- **问题**: 产品发布后，资源是撤走去开新项目，还是留场观察？
- **方法论的使用**: 作者要求稍微延长项目周期，留出几天观察用户反应；配合可量化指标（借助谷歌分析等工具看哪些页面最受欢迎、用户停留多久、访问间隔等）评估表现。
- **结论**: 急于撤军是大忌——"此时正是收集反馈信息、改进产品的最佳时机"，投资之小、回报之高"绝非其他项目阶段可比"。
- **结果**: 发布从庆功典礼变成一段有人值守的观察期，问题在代价最小的时刻被消化。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品即将发布或刚发布，团队想立刻解散转入下一个项目。
2. 上线后冒出零星用户抱怨，要决定哪些紧急处理、哪些记入下版。
3. 制定发布计划，要安排发布周的人员值守与响应预案。
4. 发布后第一次看数据，不知道该盯哪些指标、怎么判断成败。
5. 大版本上线当天出了故障，要组织跨职能快速响应。

### 语言信号 (用户的话里出现这些就应激活)

- "刚上线/刚发布，出了问题怎么办？"
- "上线后炸了，要不要发 hotfix？"
- "发布周该安排谁值班、盯什么？"
- "launch week / post-launch / war room / rapid response / P0 bug"
- "发完版是不是就可以撤了？"

### 与相邻 skill 的区分

- 与 `smooth-deployment` 的区别：那是发布**前**控制步幅、管理用户适应成本；本 skill 是发布**后**几天内全员在场快速补救——部署做得越平滑，窗口期的问题量越小，两者是同一发布事件的两半。
- 与 `metric-driven-improvement` 的区别：窗口期是几天内的急救（目标是"多快解决"），指标改进是常态化的规划周期（目标是"推动哪个指标"）；窗口期结束的出口就是转入后者。
- 与 `special-product-defense` 的区别：企业级上门安装是响应动作，不是定制开发——上门的目标是发现问题、收集反馈，客户当场塞来的定制要求仍要走特例产品防御。
- 与 `product-validation-trio` 的区别：三验证在写代码前用原型排除价值/可用性/可行性风险；窗口期处理的是"验证过也防不住"的长尾意外，不能互相替代。

## E — 可执行步骤 (Execution)

1. **发布前把窗口期写进计划。**
   - 完成标准：排期表上明确"发布后几天至一周"的窗口，列出留场人员名单（产品经理、交互设计师、主程序员、客服、市场）与每天例会时间；下个项目不得提前占用这段时间。
   - 判停条件：资源已被承诺给下一个项目——至少争取最小窗口（哪怕只延长项目周期几天），并明确承诺问题响应时限；完全无人值守的发布不应被批准。
2. **备好指标与分级预案。**
   - 完成标准：指标清单与产品商业目标挂钩、分出轻重缓急，且"什么结果算成功、什么算失败"心中有数；问题分级规则明确（当场发补丁/发声明公示处理/记入下版），反馈渠道（分析工具、问卷、邮件讨论、留言板、现场测试、客服销售伙伴）有人认领。
   - 判停条件：说不出成败分界线——先补指标定义再上线；无法预定义分级时，至少约定"影响正常使用的问题"为最高级。
3. **每天短会闭环，直到退潮。**
   - 完成标准：每天至少一次简短会议，每个问题有归属（已修复/已公示处理方案/记入下版并留档）；客服、销售、合作伙伴的反馈被同步纳入；实时数据每天过一遍。
   - 判停条件：关键指标企稳、新问题流明显退潮→宣布窗口期结束，问题存档转入 `metric-driven-improvement` 的常态化清单；若爆出影响正常使用的重大问题→回到第 2 步的的最高级预案，必要时配合 `smooth-deployment` 的回滚纪律。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 日常例行运维值班——本 skill 的本质是**产品团队**（产品经理、设计师）在场做产品决策，纯工程可用性值班不等于快速响应阶段。
- 发布前的部署方案设计——步幅、通知、旧版保留是 `smooth-deployment` 的领地；窗口期只管发布后的响应。
- 窗口结束后的长期改进——几天至一周后问题流入常态清单，继续"全员每天短会"会拖垮团队，出口是指标驱动的常规改进。

### 作者在书中警告的失败模式

- 急于"撤军"：发布后迅速撤走资源、扑向下个项目，错失收集反馈与改进产品的最佳时机（第25章）。
- 坐等问题出现、按部就班等下次发布再修——"这样做的代价太高"（第25章）。
- 特例产品挤占响应资源：特例产品的维护正是吞噬快速响应能力的隐性开销（第32章反面印证）。

### 作者的盲点 / 时代局限

- "几天至一周"的窗口设计针对 2008 年的分版本发布节奏；SaaS 持续部署时代已演化为 on-call 轮值与发布值守制度，但作者强调的"产品经理与设计师亲自在场"仍区别于纯工程值班——这是本 skill 至今成立的部分。
- 未讨论全球化产品跨时区响应的安排；窗口期长度对长销售周期的企业级产品（实施以月计）需要拉长或按客户分级。
- 指标示例（页面访问量、注册数）带有 Web 时代印记，移动端与订阅制产品需替换为留存、活跃、付费转化等现代等价物。

### 容易混淆的邻近方法论

- SRE on-call / 故障响应：目标是系统可用性（SLO），响应主体是工程；本 skill 的响应主体是跨职能产品团队，处理对象还包括体验与价值层面的反馈。
- 客服工单流程：客服是反馈输入之一，分级与方案决策仍须由产品团队短会统一裁决，不能让工单队列自动定义优先级。
- 项目复盘会：复盘是事后归档总结；快速响应窗口是发布后实时的、以止损和收集反馈为目的的运行阶段，不可用一场复盘会替代。
