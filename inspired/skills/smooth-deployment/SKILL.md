# 平滑部署

## R — 原文 (Reading)

> "毫无征兆地更新不必要的版本会令用户产生反感。有件事你可能觉得难以置信，但的确是事实：不是所有用户都喜欢新版本的产品。……优秀的产品和服务可以赢得用户的好感，这是宝贵的信任，应该小心保护。不要轻易试探用户的耐心，让好感变成反感。"
>
> — Marty Cagan，第24章《平滑部署》

---

## I — 方法论骨架 (Interpretation)

团队默认"新版本=进步，用户会适应"，作者把这个前提直接掀翻：**用户痛恨被迫适应变化**。他们希望产品更完善，但前提是不改变已有的使用习惯。他把用户反感的来源总结为七条：事前没收到通知而措手不及、没时间适应且没有旧版本可用、新版本无法正常运行、新旧版本不兼容、新功能被认为毫无必要、接二连三的更新让人疲惫、习惯的操作流程被强行改掉。

矛盾在于产品不得不更新——需求更迭、技术进步、市场变化。作者的解法不是不更新，而是**审慎地更新**，即"平滑部署"：①提前通知（公告、邮件、在线教程），但他直言很多人根本不看，效果有限；②加倍测试，确保不会陷入被迫回滚的窘境；③更新影响大规模用户时，用**并行部署**（新旧版本同时运行，邀请愿意尝鲜的用户试用，稳定后再设为默认）或**增量部署**（把更新拆成小块分批上）。并行版本要给旧版本保留一段缓冲期，**公示最后期限**；用户量庞大的服务，过渡可能长达几个月。

这条纪律背后的时代判断是：互联网让口碑无论好坏都迅速传播，糟糕的版本若不及时补救，等于给竞争对手递刀子。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 并行版本+旧版保留期限
- **问题**: 一次更新会影响大规模用户，怎么把风险和反感降到最低？
- **方法论的使用**: 同时发布两个并行版本，邀请有兴趣、有时间的用户先试用新版；新版运行正常、大部分用户习惯后再设为默认；同时把旧版本保留一段时间，公示为旧版本提供支持的最后期限，让没来得及适应的用户照常使用。
- **结论**: 过渡期可能长达几个月，产品经理还要准备好承担来自开发团队和运维团队的压力——支持并行版本不是件容易的事，但这是值得付的代价。
- **结果**: 用户按自己的节奏适应变化，更新从"强行搬家"变成"给钥匙慢慢搬"。

### 案例 2: 区域性逐步部署
- **问题**: 影响面更大的更新，连并行版本都兜不住怎么办？
- **方法论的使用**: 先在某个区域内部署新版本，观察运行情况与用户反应，然后逐步扩大范围；还可以把更新项分割成几个较小的部分逐步发布（增量部署）。
- **结论**: 无论哪种方式，关键都是全面考虑更新的"副作用"，方便用户在空闲时适应变化。
- **结果**: 影响被切分成小步，每一步出问题都来得及补救，不会一次性押上全部用户的好感。

### 案例 3: 口碑时代坏消息迅速传播
- **问题**: 过去发布一个"副作用"极大的不兼容版本，为什么没出过大事？
- **方法论的使用**: 作者对比前后两个时代——过去信息不对称，用户只能分别投诉，抱怨形不成规模；现在互联网让口碑迅速传播，糟糕版本发出去若不及时补救，"那你就有麻烦了"。
- **结论**: 用户的好感是宝贵的信任资产，部署策略必须按"坏消息会传播"来设计。
- **结果**: 这成为平滑部署的底层理由：不是所有用户都喜欢新版本，互联网时代尤其如此。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 大改版/大版本要上线，担心老用户反弹，要设计上线方案。
2. 敏捷团队发布频繁，用户抱怨"又改版了"，疲惫感明显。
3. 新旧版本数据不兼容、需要迁移，或准备让旧版本下线。
4. 改版上线后被用户骂上热搜，复盘该怎么做。
5. 评审发布计划，要判断步幅是不是太大了。

### 语言信号 (用户的话里出现这些就应激活)

- "下个月大改版上线，怕老用户闹"
- "用户在骂改版，要不要回滚？"
- "旧接口/旧版本什么时候下线合适？"
- "灰度发布 / canary release / rollout plan / rollback / deprecation timeline"
- "又双叒改版了，用户都烦了"

### 与相邻 skill 的区分

- 与 `rapid-response-window` 的区别：本 skill 是**发布前**把步幅放缓、把适应成本设计进方案；那是**发布后**几天内全员待命快速补救——一个防患，一个救火。
- 与 `metric-driven-improvement` 的区别：那管"改什么"（指标映射），本 skill 管"怎么发布"；部署方案评审时两者衔接——每次改版本身也是一次指标改进，但发布节奏单独受本 skill 约束。
- 与 `tech-headroom-20percent` 的区别：可靠性余量是"加倍测试、避免被迫回滚"能兑现的工程前提；本 skill 是产品策略（用户心理、保留期限、沟通），余量不足时部署方案必须更保守。
- 与 `minimal-product-definition` 的区别：那是定义阶段克制功能数量；本 skill 管的是已定版本的交付方式——哪怕功能定义得再对，强行切换也会激起反感。

## E — 可执行步骤 (Execution)

1. **发布前对照七条反感原因逐条自检。**
   - 完成标准：对七条（通知/适应时间与旧版/新版本故障/兼容性/功能必要性/更新频率/习惯流程）逐条写出应对措施；更新频率这一条要回答"这次更新是否必要，能不能减少不必要的更新"。
   - 判停条件：新版本无法正常运行，或与旧版本数据不兼容且无迁移方案——不要发布，先解决再谈部署。
2. **按影响面选部署方式，公示旧版期限。**
   - 完成标准：小影响面→提前通知+加倍测试；大规模影响→并行部署或区域性/增量部署，且明确写出旧版本保留时长、最后期限公示文案、以及回滚预案；用户量庞大的服务预留数月过渡期。
   - 判停条件：开发/运维资源撑不起并行版本——收缩步幅改用增量部署，绝不以"没资源"为由强行全量切换。
3. **分步上线并盯住过渡期。**
   - 完成标准：每扩大一步都有运行数据与用户反馈检查点；坏口碑渠道（社区、客服、社交）有人值守；发现影响正常使用的问题能在承诺时间内补救。
   - 判停条件：出现可靠性/性能类的正常使用障碍→立即回滚或暂停扩大范围，公开发声补救，然后按增量方式重走，而不是硬撑着"教育用户"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 1.0 首发产品——用户对产品没有成见，无须担心历史兼容性与老用户习惯，这是作者明说的"最轻松"场景。
- 必须立即上线的安全修复——作者同样反对"因噎废食"，安全与可靠性优先于过渡仪式，但事后沟通仍适用本 skill。
- 内部工具/极小用户群——并行版本与数月过渡的成本高于收益，提前通知+充分测试即可。

### 作者在书中警告的失败模式

- "毫无征兆地更新不必要的版本"——用户措手不及，好感变反感（第24章）。
- 保留旧版本却不敢公示最后期限，或根本不提供旧版本，用户被迫在过渡期裸奔（第24章）。
- 过度频繁的更新让用户疲惫不安——敏捷团队尤甚，"除非达到产品经理的要求，否则不要轻易发布新版本"（第26章秘诀8）；企业级软件更要把升级之痛当回事（第38章）。

### 作者的盲点 / 时代局限

- 2008 年的语境是 Web 服务；移动应用商店时代的强制更新、审核节奏、多版本并存受限，使"并行版本"的实施形态完全不同，需转译为现代手段。
- 作者讲的是产品策略而非技术方案——今天的灰度发布、feature flag、蓝绿部署已把"区域性逐步部署"工程化、自动化，本 skill 的价值集中在用户心理与沟通纪律（期限公示、过渡期长度、何时回滚）。
- "大多数用户不愿意花时间适应新方式"的判断，对协作类、社交类产品的网络效应迁移（用户被整个关系网绑定）需要补充分析维度。

### 容易混淆的邻近方法论

- 蓝绿部署/灰度发布（工程实践）：关注流量切换与故障半径；本 skill 关注用户适应成本与信任资产，二者互补不可互替。
- 变更管理（ITIL）：面向企业流程合规；本 skill 面向大众用户的情感与习惯，评审对象是"用户被改变多少"。
- 用户教育/操作引导（onboarding tour）：是平滑部署的辅助手段之一，不能替代旧版本保留与步幅控制——作者明言提前通知"效果有限"。
