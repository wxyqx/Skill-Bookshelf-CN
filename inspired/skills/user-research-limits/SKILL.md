# 市场调研的作用与边界

## R — 原文 (Reading)

> "虽然市场调研很重要，但我从来没听说过仅仅通过市场调研就成功定义出来的产品。……调查结果为获得解决方案提供了一条途径，但不是解决方案本身。哪怕所有用户都回答喜欢X特性，我们还是可以通过提供Y特性更实际地解决他们的需求。"
>
> — Marty Cagan，第16章《市场调研》

---

## I — 方法论骨架 (Interpretation)

作者对市场调研持一种**精确的双面立场**，反对两个极端：市场部门夸大调研的作用，产品部门只看到其局限——前者让产品陷入偏执，后者让产品偏离方向。

先划出调研**能回答的六个关键问题**：谁是目标用户；用户会怎样使用产品；用户能想明白怎样使用吗、障碍在哪里；用户为什么选用你的产品；用户喜欢产品哪些特点；用户希望如何改进、增加哪些功能。再划出它**回答不了的根本问题**：打造什么产品。那需要两种调研给不出的认识——深入理解用户需求，以及明白什么样的解决方案在现阶段可行。Google、eBay、iPod、iPhone、Facebook、MySpace 无一仅靠调研产生。

对具体工具也有纪律：调查问卷措辞不能先入为主；调查结果只是"获得解决方案的一条途径"，用户嘴上要 X，你可能该用 Y 更实际地解决问题。用户研讨会则被作者判了刑：他保证会上讨论不出成功的产品——用户不知道什么可行，没见到产品不知道自己想要什么，人群聚集还会放大善于表达者的一家之言。最后一条出路：调研结果的正当用途是**完善现有产品**；若按客户要求简单拼装产品，只会陷入不断加功能、改架构的缝缝补补怪圈。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: "92% 用户想要 X 功能"的调研报告
- **问题**: 用户调查报告显示绝大多数（如 92%）用户希望增加某特性，这是不是验证了需求、该照做了？
- **方法论的使用**: 把调查结果当"获得解决方案的一条途径"而非方案本身；回到报告背后的需求本质，检查是否存在更实际的解法。
- **结论**: "哪怕所有用户都回答喜欢X特性，我们还是可以通过提供Y特性更实际地解决他们的需求"——用户表达的是痛点，不是产品规格。
- **结果**: 避开"用户说要 X 就做 X"的功能加工厂路径；解决方案交由产品探索（原型+用户测试）验证。

### 案例 2: 用户研讨会开不出产品
- **问题**: 想组织用户研讨会，让目标用户坐在一起讨论出产品方向。
- **方法论的使用**: 用作者的两个根本原因逐一检查——①用户不知道什么样的想法可行，多数人对现有技术一无所知；②用户没见到实际产品，很难凭空想象自己需要什么；再加群体互动失真与主持人难得。
- **结论**: "我保证在用户研讨会上不可能讨论出成功的产品"；比起了解需求，这种形式更适合搞政治运动。
- **结果**: 需求验证改道原型测试；若必须办研讨会，产品经理亲自参加，信息收集与分析绝不外包。

### 案例 3: 六个成功产品无一来自调研
- **问题**: 市场部与产品部争论：调研到底能不能决定产品方向？
- **方法论的使用**: 用可检验的事实对照——Google、eBay、iPod、iPhone、Facebook、MySpace，逐个核对是否"仅通过市场调研定义出来"。
- **结论**: 一个都没有；调研结果"可以作为研发产品的依据和参考，但不能决定产品研发的方向"。
- **结果**: 分工就此明确——调研完善现有产品，新产品方向靠产品探索得出，不要指望从调研中发现下一个 Facebook。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 有人拿着调研数据/问卷结果论证"用户要这个功能，做吧"。
2. 团队计划组织用户研讨会、焦点小组，指望讨论出产品方向。
3. 市场部与产品部为"调研算不算需求依据"吵翻天。
4. 需求池里塞满用户反馈、客服记录、销售传话，不知哪些能当需求。
5. 要评估一份外部购买或用户研究团队提交的调研结论。

### 语言信号 (用户的话里出现这些就应激活)

- "调研显示 X% 的用户想要……""问卷/访谈结果是……"
- "我们做个用户研讨会/焦点小组，听听用户怎么说"
- "用户就是要这个，还能有假？"
- "市场调研该不该信？""调研能告诉我们做什么产品吗？"
- "survey says" / "focus group" / "user research" / "92% of users want"

### 与相邻 skill 的区分

- 与 `prototype-testing-playbook` 的区别：可用性测试是作者最推崇的调研工具、有完整操作法；本 skill 划定包括它在内的一切调研工具的能力边界——回答"完善"不回答"定义"。
- 与 `opportunity-assessment-ten-questions` 的区别：机会评估做价值判断（要不要做），调研收集事实（谁在用、怎么用）；第11章与第16章是上下游分工，调研不代替第一问。
- 与 `metric-driven-improvement` 的区别：调研反馈用于完善现有产品时，须映射到关键指标检验，不能照单全收——"改进产品不是简单地满足个别用户的要求"。

## E — 可执行步骤 (Execution)

1. **先给问题分类：属于六问，还是"打造什么产品"？**
   - 做法：把待回答的问题对照六问清单（谁在用/怎么用/障碍在哪/为何选用/喜欢什么/想怎么改进）归类。
   - 完成标准：能明确说出本次调研回答的是六问中的哪一问，以及它不负责回答什么。
   - 判停条件：若指望调研回答"该打造什么产品"——立刻叫停，改走产品探索（原型+用户测试），调研数据在此没有裁决力。
2. **选对工具并守住收集纪律**
   - 做法：按问题选工具（产品使用分析、数据挖掘、拜访用户、可用性测试、同类产品分析）；问卷措辞结合具体情景、不先入为主；拜访用户实地考察。
   - 完成标准：每条收集到的"用户要求"都被翻译回需求本质；数据渠道覆盖的是实际目标用户，而非公司同事或尝鲜者。
   - 判停条件：样本全是尝鲜者、同事或单一渠道二手汇报（如客服月报）——结论无效，不能进入决策。
3. **结果只用于完善，方案另行验证**
   - 做法：把调研发现用于修补现有产品的不足、精益求精；每条改进候选检查是否存在更实际的 Y 方案，并映射到可量化指标。
   - 完成标准：改进项与指标挂钩、经原型测试验证后进入开发；没有把任何"用户说要 X"直接当规格实现。
   - 判停条件：出现"按客户/用户要求拼装产品"的迹象——缝缝补补怪圈启动，暂停拼装，回到需求本质重新探索。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 把本 skill 当成"不做调研"的挡箭牌——作者明确肯定调研对完善现有产品极其有效，他反对的是高估而非使用。
- 已面市产品有活跃用户时的打磨与漏斗优化——这正是调研的主场，此时该用 `metric-driven-improvement` 配合调研。
- 需要原型测试具体操作（物色、主持、判停）的场合——那是 `prototype-testing-playbook` 的地盘。

### 作者在书中警告的失败模式

- 市场部门夸大调研作用、产品部门只看局限——忽视调研则产品偏离方向，太依赖则陷入偏执（第16章开篇）。
- 按客户要求设计产品，陷入不断加功能、改架构的缝缝补补怪圈，无暇思考创新方案。
- 指望用户研讨会讨论出成功产品；"呆板的报告里"（72%的用户要求提高分辨率之类）洞察不出需求。
- 从调查数据里"读出"下一个爆款——"不要指望从市场调研中发现下一个FaceBook、Flickr、YouTube"。

### 作者的盲点 / 时代局限

- 2008 年的数据手段以问卷、访问日志为主；现代大规模 A/B 测试与行为数据科学能更精确地回答"喜欢什么"，使"完善"与"定义"的边界在实践中更模糊——但"该打造什么"仍无法外包给数据。
- 作者未展开调研在新品类早期探索（概念测试、原型前验证）中的辅助作用，只以"从没听说过"一刀切断，论证方式偏经验归纳。

### 容易混淆的邻近方法论

- Jobs-to-be-Done 深访：挖掘任务与动机与作者"深入理解用户需求"兼容，但同样回答不了"现阶段什么可行"。
- NPS/满意度调查：度量现状的工具，不是定义方向的依据；混用正是"夸大调研作用"的典型。
- 数据驱动决策（A/B 测试）：数据证明的是已上线方案的表现差异，不能代替对未建方案的探索与验证。
