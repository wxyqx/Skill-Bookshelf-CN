# 事业部副总经理四项关键业绩与四条警示

## R — 原文 (Reading)

> "·对产品和关键流程进行竞争性分析；·了解当今技术水平知识，掌握多个事业部信息；·制定事业部战略，领导事业部实现竞争优势；·建立支持创新持续提升的工作环境；·建设高绩效组织，实现技术和领导上的双重高绩效；·建立从多个事业部角度思考的流程，建立和睦融洽的业务团队关系。"
>
> — 斯蒂芬·德罗特，第5章·事业部副总经理要实现的业绩（fulltext L4542–L4552）

> "因为他们都是凭借自己过硬的技术而得到提拔的，所以肯定不会轻易放弃自己的技术优势，技术就是他们的安全伞。……事业部副总经理必须要引领员工的沟通，而不仅仅是作为其中的一员。"
>
> — 斯蒂芬·德罗特，第5章·警示（fulltext L4572–L4574）

> "事业部副总必须要面对那些阻碍进程的人，层级划分僵化只有在领导允许它存在时才存在，而最糟糕的情形就是，事业部副总经理自己也变成了层级划分僵化中的一员。"
>
> — 斯蒂芬·德罗特，第5章·警示（fulltext L4578）

## I — 方法论骨架 (Interpretation)

事业部副总经理（职能副总）是职能条线在事业部的最高负责人，职责不是"把本职能做深"，而是把本职能部门做成事业部竞争优势的来源。验收看四项关键业绩：

1. **竞争性分析**：对产品与关键流程做竞争分析，而且要看对手的"人与财务做法"，不只是产品参数。
2. **技术水平对标**：了解当今技术水平并掌握多个事业部信息——对标之后有意识地选择技术路线，而不是无知落后或盲目追新。
3. **战略与组织**：制定事业部战略、领导事业部实现竞争优势；建立支持创新持续提升的工作环境；建设高绩效组织，做到技术与领导双重高绩效（隐含要求：至少培养一位本岗位接班人）。
4. **多事业部视角**：建立从多个事业部角度思考的流程、建立和睦融洽的业务团队关系——本职能的决策要经得起公司层面的检验。

四条警示（四条失败路径）：
- **只重技术业绩**：亲自解决所有难缠技术问题，下属依赖其专业能力而不学着解决；技术是"安全伞"，放不下就升不上去。
- **只做"事业部一员"**：按部门既有视角评估优劣、做欠佳决策，无法客观决定保留什么、摒弃什么，也无法公正选才；副总必须"引领员工的沟通"，而不只是其中一员。
- **自我孤立**：营销副总泡在客户里、工程副总泡在实验室、财务副总加班做分析——与上司和同事日益疏远；事业部之间不协同，最终工作失败。
- **层级划分僵化**：自己成为信息、建议、计划、问题上下流动的堵点；"僵化只有在领导允许它存在时才存在"，最糟的是副总本人变成僵化的一部分。

判断法则：只要"技术业绩"仍是他时间与自豪感的主要来源，他就还在一线层级；副总的工作是让整个职能（含人）成为竞争优势。

## A1 — 书中的应用 (Past Application)

### 案例 1: 克莉丝：出色的营销副总为何被孤立
- **问题**: 克莉丝是出色的营销副总，只顾销售增长，不评估运营承受能力，只训技术技能不培养领导技能（没有接班人），无视公司财务风控流程，日程全被客户占满。到了第三年中期，她和同事们几乎疏远了，利润增长率只有销售增长率的一半。
- **方法论的使用**: 按四项业绩逐条对照她的缺失：①只追增长不评估运营承受力；②只训技术技能、不培养领导技能（无接班人）；③无视本公司财务风控流程；④日程全被客户占满（自我孤立）。
- **结论**: 她做的仍是"更大号的营销负责人"，而不是事业部副总——缺的不是努力，是四项业绩中除"技术"以外的三项与多事业部视角。
- **结果**: 通过一对一收集需求、重写贡献清单、再造日程并授权，问题得到纠正；团队关系与利润质量随之改善。

### 案例 2: 作者对"技术安全伞"的判断示范
- **问题**: 为什么技术出身的管理者普遍难以转型为称职的职能副总？
- **方法论的使用**: 用警示一分析动机结构——他们是因过硬技术被提拔的，技术代表安全与他人的依赖，"亲自去解决所有难缠的技术性问题"会损害业务发展，因为本该用于未来的时间精力被用在今天的问题上。
- **结论**: 偶尔帮忙并教会方法是可取的；一味替下属解决大多数问题则非常不明智。
- **结果**: 该判据写入第5章，成为职能副总自查与上级教练的标准问题。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 一位技术/营销出身的副总（或候选人）自问："怎样才算真正达到副总层级？"或上司想评估其是否完成层级转型。
2. 某职能副总被指"圈在自己的部门里"，跨事业部协同不畅，需要诊断缺了哪一项业绩。
3. 公司要为职能副总设KPI/业绩标准，想知道除专业指标外必须包含什么（接班人、跨事业部视角）。
4. 出现"信息到副总这里就断"的情况：下层想法上不来、上层意图下不去，怀疑层级僵化。
5. 职能副总本人觉得被同级轻视/被孤立，想弄清这是个人关系问题还是其层级工作方式问题。

### 语言信号 (用户的话里出现这些就应激活)

- "技术出身的副总怎么转型？" / "technical expert promoted to functional VP"
- "这项工作到底算不算副总层级的工作？" / "is this VP-level work?"
- "只重技术/泡在客户里/泡在实验室" / "stuck in functional silo"
- "信息到他那层就断了" / "bottleneck, information doesn't flow"
- "职能副总该考核什么？" / "what should a functional VP deliver?"

### 与相邻 skill 的区分

- 与 `functional-manager-maturity`（b5-f10）的区别: 后者评估职能主管的"成熟度"通用维度；本 skill 是册2 第5章给出的该层级具体业绩清单与警示，更贴验收项。
- 与 `business-manager-complexity-triangle`（b5-f13）的区别: 后者是事业部总经理的协同三角形（更高一层、跨职能整合）；本 skill 是事业部内职能条线负责人（副总）的业绩。
- 与 `job-essence-two-factors`（b2-f07）的区别: 后者判断"岗位是否是同一工作"；本 skill 告诉该岗位"该交什么"，不问岗位本质。
- 与 `management-technical-dual-track`（b5-f36）的区别: 后者给不愿做管理者的技术专家一条技术发展路径；本 skill 处理已进入管理轨道的职能副总的转型。

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行：

1. **确认对象与层级**
   - 明确被评估者是事业部内的职能副总（营销/工程/财务/人力等），不是事业部总经理，也不是部门总监；确认其所在层级边界。
   - 完成标准: 对象层级与职能范围界定清楚；若对象实际是事业部总经理，改用 b5-f13 相关 skill。

2. **四项业绩逐项验收**
   - ① 是否对产品与关键流程做竞争性分析（含对手的人与财务做法）？
   - ② 是否掌握当今技术水平并了解多个事业部？对标后是否有意识地做技术选择？
   - ③ 是否制定事业部战略、领导事业部实现竞争优势？团队是否技术与领导双高绩效、是否培养出至少一位本岗位接班人？
   - ④ 是否建立从多个事业部角度思考的流程与团队关系？
   - 完成标准: 每项标注"达标/部分达标/缺失"，并各附至少一条事实证据。

3. **四条警示体检**
   - 只重技术业绩？只做"事业部一员"？自我孤立？层级划分僵化？逐条对照其日程、沟通对象与决策方式。
   - 完成标准: 每条警示给出有无及证据；无证据的警示不得凭印象判定。
   - 判停条件: 若发现"层级划分僵化"（其本人即为信息堵点），先处理流动问题，再谈其余业绩——这是四条中最需要重视的。

4. **定位缺口并转成发展动作**
   - 针对缺失项给出可执行动作：如把技术难题交回给下属并教方法；建立跨事业部协同机制；把接班人培养写入其业绩标准；重排日程腾出战略时间。
   - 完成标准: 每个缺口配1项动作、时间点与验收方式。

5. **落回标准与考核**
   - 若用于设标准：把四项业绩与"至少培养一位本岗位接班人"写入该层级业绩标准，与运营计划对齐。
   - 完成标准: 修订后的标准文本；考核口径明确"技术业绩之外的部分占比"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 对象尚未担任副总或组织尚无该层级：不要用该清单要求一线经理/部门总监，会制造不必要的挫败。
- 把"不该亲自解决技术问题"绝对化：作者明确"偶尔帮助下级员工解决某个问题，同时教授他们学会解决的办法，这样做是可取的"；禁止教条化解读为"技术问题一概不碰"。
- 用它评判个人去留：四项业绩是工作要求与辅导框架，涉及调岗/解雇须依当地劳动法与公司程序，并提供改进机会（系列级伦理边界）。
- 组织本身没有多事业部结构：第四项"多个事业部角度"需替换为相应组织现实，不可照搬。
- 用户只是想解决具体技术难题：这不是本 skill 的用途。

### 作者在书中警告的失败模式

- **只重技术性业绩（b2-ce16）**：技术是安全伞与自豪感来源，"肯定不轻易放弃自己的技术优势"；结果是亲自解决大多数技术难题，下属不学着自己解决——领导者被拖在今天的问题里，未来工作无人做。
- **只做"事业部一员"（b2-ce16）**：按部门既有视角评估优劣、做欠佳决策，无法客观决定保留/摒弃，无法公正选才；"必须引领员工的沟通，而不仅仅是作为其中的一员"。
- **自我孤立（b2-ce16）**：营销泡客户、工程泡实验室、财务加班做分析——一旦事业部工作不支持业务发展战略，最终导致副总工作失败。
- **层级划分僵化（b2-ce16）**：成为信息与想法上下流动的堵点，问题不能及时发现、变革速度变慢；最糟情形是副总本人成为僵化的一环。
- **互不往来的文化（b2-ce05）**：抑制信息自由流动、阻碍跨部门关系建立的壁垒，会让领导者的参照系只限于可见范围，"工作岗位定义和预期工作结果不一致"。

### 作者的盲点 / 时代局限

- **科层制预设**：四项业绩以GE式多事业部大公司为原型；在扁平化或矩阵组织中"事业部副总"的边界与协同方式不同，框架需要重新落地。
- **技术与管理的二分被简化**：把"仍重视技术"一律视为未转型有时代色彩；在研发驱动/技术密集行业，职能副总保持技术判断力可能恰是竞争优势（书中未区分情境）。
- **接班人要求缺少配套**：要求"至少培养一位本岗位接班人"但未讨论岗位编制约束、被继任者的职业预期与心理影响。
- **美式样本偏差**：案例均为作者咨询的西方大公司，缺少失败企业与对照；四条警示缺乏效度验证。

### 容易混淆的邻近方法论

- 与 `functional-manager-maturity`（b5-f10）：册5 的成熟度是通用评估视角；本 skill 是册2 的具体业绩与警示清单，选型取决于用户要"评估成熟度"还是"对齐该层业绩"。
- 与 `business-manager-complexity-triangle`（b5-f13）：层级不同（事业部总经理 vs 事业部内职能副总），勿混用。
- 与 `management-technical-dual-track`（b5-f36）：那条路为不愿走管理的技术人才设计；本 skill 面向已在管理轨道的副总。
