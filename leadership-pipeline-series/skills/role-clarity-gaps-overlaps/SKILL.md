# 明确职责三步法与职责断裂/重叠检查

## R — 原文 (Reading)

> "近20年以来，企业的裁员潮和不断停滞的发展进程已经造成领导层级的断裂，一些职责变得随意而漂浮不定。相对于某个人的上级以及直线下属，他本人的领导职责应当是什么呢？有人思考过他们的职责可能存在重叠或断裂吗？"
>
> — 查兰/诺埃尔/德罗特，第9章（L11564）

> "职责断裂　◆ 缺乏上级对下级绩效的反馈，造成问题反复发生。……职责重叠　◆ 事业部副总经理和部门总监都对同一个一线经理下指示。◆ 事业部总经理和销售经理都认为产品开发计划是自己的首要职责。"
>
> — 同上，第9章（L11576–L11586）

> "（1）使用领导梯队模型来确定特定工作所处的领导层级。（2）与其他经理沟通，确定他们的领导层级以及该层级所要求的领导技能、时间管理能力和工作理念。（3）让领导梯队上的领导者都了解相邻层级之间可能存在的职责断裂和重叠，并采取行动纠正上述问题。"
>
> — 同上，第9章（L11590–L11594）

## I — 方法论骨架 (Interpretation)

职责不清不能靠"开会分权"解决，要用层级图做逐对比对。核心动作是：把一个人的岗位放到六阶段层级图上画一个圈，再把他上级、下属的岗位也各画一个圈，然后检查三种病。

- **断裂**：某件事在相邻两圈之间没人认领。典型形态是"计划由上级制定、要求下属执行，但评估资源、获取资源两头都认为不属于自己"，于是计划空转；也包括上级从不给下级反馈，导致问题反复发生。
- **重叠**：同一件事两个层级都认为是自己的。典型形态是两级同时对同一个一线经理下指示、两个层级都声称产品开发计划是自己首要职责；结果是下级无所适从、上级互相踩脚。
- **错层**：同一个领导层级上坐着几类不同职责的人（大型组织尤其常见，例如某职能主管的下属和下属的下属都是部门总监），看似同级、实际要求不同，必须逐对区分。

三步法：①定位——用层级模型确定这个岗位属于哪一层；②对齐——与该岗位的上级、同级、下属沟通，确认各自层级及其技能/时间/理念要求；③纠偏——让整个链条上的人都知道断裂与重叠在哪里，并采取行动修正。

关键顺序：先把职责清干净，再谈绩效标准；职责未清就设标准，等于把标准建在流沙上。

## A1 — 书中的应用 (Past Application)

### 案例 1: A 公司生物科技——部门总监干了 75% 的一线经理工作
- **问题**: 部门总监角色与实际工作严重不符，高层感觉"中层在忙，但该管的事没人管"。
- **方法论的使用**: 用纵向架构诊断逐岗位比对层级要求，访谈后发现"部门总监所做的工作中75%实际上一线经理的工作"——直接管一线员工、做周计划、分析测试数据。
- **结论**: 这是典型的职责错层与向下挤压：总监占了一线经理的圈，一线经理的职责反而被架空；解决办法不是训人，而是把层级要求写清楚并据此澄清角色。
- **结果**: 公司建起业绩梯队并增加"发展需求指标"栏传达不可接受行为；培训后部分一线经理回归自我管理者岗位、优秀者扩大带队规模、不合理的用人申请被撤回；但"教会部门总监选拔培养一线经理（而非凭技术）"成为最大挑战。

### 案例 2: 书中的双职务示例——两级同指一人
- **问题**: 作者列出"普遍存在的职责断裂和重叠现象"：事业部副总经理和部门总监都对同一个一线经理下指示；事业部总经理和销售经理都认为产品开发计划是自己的首要职责。
- **方法论的使用**: 把这两个岗位分别放进层级图，逐对比对各自层级的技能/时间/理念要求，重叠处一目了然。
- **结论**: 重叠的根因是层级要求未被定义，而不是两个人抢权；纠正方式是明确"谁在哪一层、该层要求是什么"，让当事人自己看见重叠。
- **结果**: 作者给出的通用建议是让整个梯队上的领导者都了解相邻层级的断裂与重叠并采取行动，作者在实践中用"工作设计会议"（每人写下自己对工作的界定并贴到挂板）让依赖关系、重叠与漏洞当场显形，跨行业客户均能有效完成。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 两个部门/两个层级长期为"这件事归谁"扯皮，会议开了很多次仍无解。
2. 新任领导到岗，发现岗位说明书与实际工作对不上，或前任留下了大量"既像他的活又像我的活"的模糊地带。
3. 组织经历裁员、重组、合并后，出现"没人管"的空白区（某类计划无人评估资源、某类反馈无人提供）。
4. 同一层级的几个岗位职责差异很大，绩效评价时无法用同一把尺子，引发内部不公平感。
5. 用户要给自己或团队做一次职责体检，为后续的绩效标准、继任、人才评估打地基。

### 语言信号 (用户的话里出现这些就应激活)

- "这事到底归谁管？/ 职责不清 / 边界不明"
- "我们两个部门都说是自己的活 / 两个领导都给我下指令"
- "岗位说明是这么写的，但实际干的完全不是这回事"
- "role ambiguity" / "overlapping responsibilities" / "who owns this" / "whose job is it" / "dotted line confusion"

### 与相邻 skill 的区分

- 与 `b5-f02 three-dimension-transition` 的区别: 后者判断一个人转型是否到位（技能/时间/理念）；本 skill 判断岗位与岗位之间的边界是否画错、画漏、画重。
- 与 `b5-f23 performance-gap-circle` 的区别: 本 skill 先做——把职责圈画清楚；绩效圆圈与缺口是下一步——清完职责再定标准、再谈缺口（顺序不能颠倒）。
- 与 `b5-f19 diagnosis-five-steps` 的区别: 五步法用于诊断个人/团队绩效问题；本 skill 专门处理"职责边界"这一层，是诊断时可调用的前置动作。
- 与 `b5-f08 managing-managers-role` 的区别: 后者讲部门总监这一层该做什么；本 skill 讲"任何一层与相邻层之间怎么划界"的通用方法。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **画层级图并定位岗位**
   - 完成标准: 列出一张自上而下的层级清单，把争议涉及的每个岗位标到对应层级上；对每个岗位写出一句话的"本层存在目的"。
   - 判停条件: 若组织连层级清单都没有，先与用户把层级数与名称定下来（可借用六阶段模型，但要换成公司自己的职位语言），再进入步骤 2。

2. **逐对齐：与该岗位的上级、下属、关键同级核对要求**
   - 完成标准: 对每个关键岗位产出"本层技能/时间/理念要求"三栏，且已与当事人或其上级确认过；列出各自认为"绝对属于我"和"绝对不属于我"的工作清单。

3. **做断裂/重叠/错层三查**
   - 完成标准: 输出三张清单——无人认领的工作（断裂）、两人以上都认领的工作（重叠）、同层但要求差异大的岗位（错层）；每条附上具体事件证据（会议记录、指令流、计划落空的事实），不做泛泛而谈。
   - 判停条件: 若三查未发现结构性问题而冲突仍持续，提示用户这可能不是职责问题，转人际/激励/政治层面另行处理，不要硬套框架。

4. **召开工作设计会当场纠偏**
   - 完成标准: 让相关人各自写下自己对工作的界定并公开比对，会上直接标出依赖关系、重叠与漏洞；对每一条断裂/重叠指定"归入谁"的结论与生效时间。

5. **把结论写回制度，并锁定顺序**
   - 完成标准: 更新岗位职责文件与汇报关系图；在职责澄清完成之前，明确声明"暂不启动绩效标准/考核调整"，避免在错位上叠加标准。
   - 完成标准 (复核): 约定 3–6 个月后复查断裂与重叠清单，确认没有随组织变化重新长出来。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 冲突的真实原因是资源争夺、权力斗争或个人恩怨，而非职责定义——层级图只会给斗争提供新靶子。
- 组织没有稳定的层级结构（小团队、临时项目组、完全自组织的团队），套用六阶段层级会造成空转。
- 用户只是想要一份漂亮的岗位说明书模板或组织架构图，没有诊断诉求。
- 尚未获得关键当事人的配合时，单方面给别人"重新划职责"会引发抵触，应先把方法变成共同语言。

### 作者在书中警告的失败模式

- **不善于定义工作**: 事业部总经理及以上层级"总是假定承担这些管理职位的人员应该知道要做些什么"，结果"缺陷之所以发生是因为人们晋升到新的领导层级时不了解自己的职责"，事后最常见的评论是"我以为他知道"（b5-ce24，第11章 L12199–L12207、L12268）。
- **角色不清导致微观管理与委员会化**: 岗位角色定义不清、预期业绩不明时，领导会出于自我保护而抓细节、逐级请示、一遇问题就成立工作组，把本应属于管理者的挑战工作转给委员会（b2-ce07，册2 第10章 L5408）。
- **部门总监被当作一线经理使用**: 直接给一线员工反馈与排周计划、只问任务型问题、只做年度计划，上层被迫降级做下级工作（b2-ce17，册2 第6章 L4743–L4753）——这正是职责断裂/重叠的典型后果。

### 作者的盲点 / 时代局限

- **科层制预设**: 模型以大型、分权管理的美国公司为原型，假设"层级天然存在"；对扁平化、项目制、矩阵制的组织，六阶段是否还存在、以什么形态存在未被正面处理（BOOK_OVERVIEW 批判节）。
- **"定义职责"被当作万能钥匙**: 职责写清楚并不自动带来协作，书中未讨论矩阵结构下"两线都合理"的持久张力，也未给出冲突升级的治理路径。
- **诊断不得直接用于人事处置**: 作者自己强调，当公司文化与薪酬制度出问题时"最重要的是不要过早对个人下结论"（第8章 L11438 附近一线观察）；职责诊断的结论应作为发展对话的输入，不得据此单方面给员工贴"错层"标签或启动处置。

### 容易混淆的邻近方法论

- **RACI/责任分配矩阵**: 那是在给定任务上分配角色字母（负责/批准/咨询/知会），不回答"该层级本身应该存在什么职责"；本 skill 先修层级定义，RACI 可在其后作为补充。
- **组织架构设计/事业部制改造**: 那是改变结构本身；本 skill 是在现有结构内澄清每层要求与边界，通常不需要动组织图。
- **岗位分析与 JD 编写**: 那是文书工作，产出的是描述；本 skill 产出的是"断裂/重叠清单＋纠偏决定＋生效时间"。
