# 优化 MVP 是为了学习，不是为了规模

## R — 原文 (Reading)

> "'最小化可行产品的关键在于：你可以定义什么是"最小化"，但什么"可行"得由用户说了算。'精益创业的早期传播者、咨询师大卫·布兰德说：'……优化最小化可行产品是为了学习，不是为了扩大规模。这个道理有些人很难接受，因为他们一辈子都在为了生产而生产，不是为了学习而生产。'"
>
> — 大卫·布兰德（转引自埃里克·莱斯），第 4 章

> "实际情况是，根本不存在任何物质上、组织上、政治上或监管上的实验障碍。唯一的障碍是团队根深蒂固的'习惯的力量'……问题不在于工程师们不懂如何生产最小化可行产品，而在于他们认为这不值得做。"
>
> — 埃里克·莱斯，第 4 章

---

## I — 方法论骨架 (Interpretation)

MVP 是实验载体，不是产品雏形。它的优化方向由学习目标决定，不由生产标准决定：每往 MVP 加一项健壮性、可扩展性、美观度之前，先问"这次加码换来了什么新学习"——没有学习增量，就是为规模而生产，在验证期属于浪费。

这不等于鼓励粗糙。两件事要分清：质量用来服务学习（能产生真实用户行为数据即可），风险用实验设计来控制（限制用户数、设置时限、退款承诺、不贴企业商标），而不是用工程质量来控制。"可行"的定义权在用户手里，不在团队的自我要求里。

最深的障碍往往不是资源而是心理：团队"一辈子为了生产而生产"，觉得给用户看半成品"不值得做"。

## A1 — 书中的应用 (Past Application)

### 案例 1: "习惯的力量"——原型机就在同栋大楼，却三年不给用户看（第 4 章）
- **问题**: 一个内部创业团队的硬件产品通常要 3-5 年完成设计交付；作者想帮他们更快学习，却发现问题不在造不出原型机——为取得安全认证，功能原型机早已造好，就放在他们办公室。
- **方法论的使用**: 作者逐项排查物质/组织/政治/监管障碍：找零售商安排用户接触？公司有示范店。示范店太远？就在同一栋大楼。原型机太沉？有专用小车。
- **结论**: 根本不存在任何实验障碍，唯一的障碍是团队认为"给用户看不值得"的习惯性心理。
- **结果**: 作者把它命名为"习惯的力量"，作为 MVP 心态障碍的标准案例——加码生产容易，直面用户最难。

### 案例 2: X 系列"只卖一台发动机"之争（c01/第 6 章）
- **问题**: 5 年数十亿美元的发动机计划被压缩时间表后，一位主管仍质疑："只卖一台发动机给一名用户有什么意义？"——在他看来，从几十亿的大项目缩到几乎一文不值，投资回报率无法交代。
- **方法论的使用**: 工程师自己找到学习型解法：把现有的 616 型发动机改造一下，只卖一台给专门用户，目的只有一个——测试需求，不影响资产负债表。
- **结论**: 规模思维（卖得越多越好）与学习思维（一台就能验证需求）在同一间会议室正面冲突，冲突的根源是度量基准不同。
- **结果**: "先拿出一台发动机来，边干边学"成为团队共识；该研讨会成为 GE 转型起点。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. MVP 做完了，评审会要求它"也过高可用/安全/性能评审"，团队不知道该照办还是抵制。
2. 争论"这东西这么糙怎么给客户看"，有人想再打磨一个月——需要裁决多糙才够。
3. 有人以"我们现在就得为 100 倍规模做准备"为由提前建设架构、配置客服。
4. 内部实验平台/新流程试点被要求"上线即全公司可用"，实验根本还没开始。

### 语言信号 (用户的话里出现这些就应激活)

- "MVP 也要过高可用评审 / 这样太糙了拿不出手"
- "为 100 倍规模做准备 / 提前建架构 / premature scaling"
- "MVP 到底该做多糙 / 最小可行产品的标准"
- "for learning, not for scale / MVP quality bar"

### 与相邻 skill 的区分

- 与同书 `mvp-trio-and-scorecard`（MVP 三件套头脑风暴与记分卡）的区别: `mvp-trio-and-scorecard` 是"想出多个候选 MVP 并选型"（开工前）；`mvp-for-learning-not-scale` 是"选定之后按什么标准优化它"（评审时）。同一条原则在两道工序上各成 skill。
- 与同书 `good-experiment-four-traits`（好实验四特征）的区别: 当被要求工程加码时，替代方案来自 `good-experiment-four-traits` 的风险控制清单（限用户数、退款承诺、不贴商标）；`mvp-for-learning-not-scale` 给裁决规则，`good-experiment-four-traits` 给替代工具。
- 跨批提示: 与 `organizational-experiment-loop`（精益实验循环五步法）的区别: `organizational-experiment-loop` 是完整循环总纲；`mvp-for-learning-not-scale` 只处理循环中"MVP 打磨标准"这一个争议点。
- 与 `pivot-persevere-cadence`（转型/坚持会议节奏设计）的衔接: ce21（提前投资可扩展基础设施）的对冲机制一半靠本原则，一半靠转型会议节奏。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **写出本轮学习目标**
   - 一句话说明本轮 MVP 要验证哪条假设、以什么用户行为数据为准。
   - 完成标准: 学习目标 + 绑定假设编号（无绑定假设则先回到 `leap-of-faith-assumption-audit` 做审计）。

2. **逐项审计加码要求**
   - 对每项要求（高可用/安全加固/美观/扩展性/客服配置）问："它增加什么学习？"
   - 完成标准: 每项标"有学习增量 / 无"并写明理由。

3. **用风险控制替代无学习增量的工程加码**
   - 有学习增量的照常做；没有的改用实验设计控制风险：限制用户数、设置时限、退款/赔偿承诺、不贴企业商标、参数化预批（`one-page-preapproval`）。
   - 完成标准: 每项无增量加码都有替代的风险控制措施写入实验计划。

4. **判停与升级**
   - 判停条件: 若加码理由全部是"生产/形象/流程规定"且无法用风险控制替代 → 不默默照办，向评审方提议按"学习目标"而非"生产标准"重谈验收口径（引用"由用户说了算"判据与油气案例）。
   - 完成标准: 升级请求包含学习目标、替代风险方案、及按生产标准执行的成本。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已经过假设验证、进入执行期的正式版本——此时质量就是价值本身，"为了学习而生产"不再适用。
- 强监管场景的合规底线（医疗器械、金融、数据安全）——合规不可绕；但注意合规 ≠ 高可用，真正可谈的是把合规参数化（`one-page-preapproval` 一页纸预批）。
- 用"这是 MVP"当借口逃避基本可用性——MVP 仍必须面对真实用户并产生行为数据，坏到无法使用的"实验"测不出任何东西。

### 作者在书中警告的失败模式

- 提前投资可扩展基础设施（ce21）: 产品还没有早期用户就为服务主流用户做打算、配客服、建架构——用执行完美掩盖学习缺失，一旦转型全部沉没。
- "习惯的力量": 原型机就在同栋大楼，零客观障碍，三年不展示——最贵的浪费是心理障碍造成的零学习。

### 作者的盲点 / 时代局限

- "可行由用户说了算"在 B2B 场景会失灵: 真正掏钱的常是采购工程师而非使用者（微波炉 29 个按钮案例，c28）——"用户"是谁需要先审计。
- 书中对"学习够了之后何时切换到规模标准"的切换判据着墨很少，只能由转型/坚持会议（`pivot-persevere-cadence`）的数据来补。
- 案例以 2010 年代工具箱为默认前提（纸板样机、线下示范店），对纯线上/远程团队的等效手段未展开。

### 容易混淆的邻近方法论

- 与《精益创业》正传 MVP 概念的区别: 正传回答"为什么 MVP 要小"；本书独特在"为学习而生产"的优化判据 + "同楼原型机三年零展示"的心理障碍实证 + "谁定义可行由用户说了算"的裁决句。引用时不得只复述正传的"快速迭代"。
- 与敏捷迭代交付的区别: 敏捷的迭代目标是可持续的交付节奏（potential shippable increment）；这里的迭代目标是假设验证，"不可交付"的纸板原型完全合格。
- 与技术债务管理的区别: 技术债视角问"以后还贵不贵"；学习视角问"现在能学到什么"——两者在验证期排序不同，验证期学习优先。
