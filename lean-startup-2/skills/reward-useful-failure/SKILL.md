# 奖励有益的失败，终止叙述权归创业者

## R — 原文 (Reading)

> "传统公司认为'只许成功，不许失败'……他们也许口头上说'拥抱失败'，但奖励、晋升、考核制度却释放着完全不同的信息。现代企业奖励有益的失败，这种失败能让公司明智地改变方向，为公司提供有用信息。"
>
> — 埃里克·莱斯，第 1 章

> "领导者的目标应该是，项目失败由项目创始人负责，是这位创始人没有完成项目目标。听任项目消亡的是创业者——不是某个上级管理者。……失败了还能保持尊严是一种本事。"
>
> — 埃里克·莱斯，第 5 章

---

## I — 方法论骨架 (Interpretation)

"拥抱失败"人人会喊，本书把它落成三个可执行的制度问题：谁来讲、讲什么、奖给谁。

谁来讲——终止的叙述权归项目创始人本人。让中层或上级代讲"我把它毙了"，等于宣布 here 杀项目的是权力而不是证据，下一次就没有人敢提前终止，项目只会拖到失败大到藏不住。失败的项目应该由创业者自己终止，这既是问责（创始人为结果负责），也是尊严（终止是一种判断力而非罪过）。

讲什么——表彰时说的是三件事：测了什么假设、花了多少钱、省下了什么。核心技巧是量化赞美：用"3 万美元加 7 个月"对比"数百万美元加数年"，让"及时证伪"在账面上明显优于"带着信仰硬冲"。叙事化的失败容易变成表演，数字化的失败才是学习。

奖给谁——对照奖励、晋升、考核制度逐条检查：如果口号与制度信号相反，理性员工永远选择表演成功（红绿灯汇报 7 绿 2 黄 1 红）。制度不改，讲什么都白讲；终止后的团队要再配置而不是解散。

## A1 — 书中的应用 (Past Application)

### 案例 1: GE 液体膨胀机团队终止后全员受奖
- **问题**: 团队的商业案例预计年增收一亿美元，但全部建立在假设上；演示型 MVP 测完发现关键市场不成立，转向低温设备市场后又发现市场不够大——要不要终止、终止了怎么向组织交代？
- **方法论的使用**: 团队在转型/坚持会议上自己宣布终止；增长委员会没有接管叙事，而是公开赞许"团队下功夫测试了假设、勇于承认错误"，并把整支团队全员受奖。
- **结论**: "实事求是"被明示为公司级最佳实践——奖励的对象是及时证伪的行为，不是成功的产出。
- **结果**: 公司以 3 万美元、7 个月避免了数百万美元与数年的浪费；团队自述"他们不必投入多年生产一款无法创造价值的产品"。

### 案例 2: 亚马逊 Fire 手机之后的团队再配置
- **问题**: Fire 手机上市即败，市值一夜蒸发 1.7 亿美元；按"只许成功"的文化，接下来该清算 Lab126 部门。
- **方法论的使用**: 亚马逊把失败读作有用的信息，不解散团队，而是把人员重新配置到 Echo、Alexa 等项目——贝索斯明言"失败不是儿戏，但也没那么严重"，重要的是持续实验。
- **结论**: 奖励有益失败的另一面是保留从失败中幸存的能力资产；解散团队等于把学费白交。
- **结果**: Echo/Alexa 相继成功，失败团队成为后续产品线的班底。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 下属负责的内部创新项目黄了，你要在全员会/季度会上讲这件事，纠结怎么讲才不寒了其他团队的心。
2. 团队主动申请终止自己的项目——你要决定是批准+表彰，还是追究"为什么没做成"。
3. 设计容错制度：公司刚出了"宽容失败"的文化倡议，人事部问考核与晋升条款要不要跟着改。
4. 一个及时止损的项目（花了小钱、证伪了关键假设）要不要在内部宣传——担心引发"失败也可以"的误解。
5. 中层管理者被夹在中间：上面要他砍项目，又怕砍了之后没人再敢报真实进展。

### 语言信号 (用户的话里出现这些就应激活)

- "项目黄了，全员会上我该怎么讲"（narrative rights / 失败叙事）
- "该不该奖励失败？会不会鼓励摆烂"（reward failure / 容错制度）
- "我们嘴上说拥抱失败，可考核里失败就出局"（incentive mismatch / 口号与制度）
- "杀掉这个项目的是我还是团队"（who kills the project / 刽子手困境）

### 与相邻 skill 的区分

- 与同书 `one-team-success-is-enough`（只要有一个团队成功就是胜利）的区别: `one-team-success-is-enough` 是事前的组合期望管理（对高层明示"有失败是常态"，防表演性成功）；`reward-useful-failure` 是事后对单次终止的叙事与激励处置（谁来讲、讲什么、奖给谁）。一个管预期，一个管仪式。
- 与同书 `pivot-persevere-cadence`（转型/坚持会议节奏设计）的区别: `pivot-persevere-cadence` 是终止的决策机制（何时、以何节奏、带什么证据决定）；`reward-useful-failure` 是决定之后的处置——叙事权、表彰、团队去向。先开 `pivot-persevere-cadence` 的会，再做 `reward-useful-failure` 的处置。
- 与同书 `innovation-accounting-three-levels`/`audit-against-past-not-plan`（创新核算与审计对照过去）的区别: 那两者解决"学习怎么记账、进步怎么读"；`reward-useful-failure` 解决"学习被确认之后，组织用什么姿态接住失败"。量化赞美的数字来自 `audit-against-past-not-plan` 的审计，二者配套。
- 跨批提示: 与 `wield-the-sword`（舞动宝剑）的区别——`wield-the-sword` 是失败坦白换高层清障的谈判结构（后备电源团队借宝剑完成转向），属事前交换；用户问"怎么跟高管摊牌"是 `wield-the-sword`，问"失败之后怎么讲"是本 skill。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **把叙述权还给创业者**
   - 完成标准: 终止通报的讲者是项目创始人本人（可由领导引荐但不得代讲）；领导角色限于转述委员会的裁决依据。若组织流程默认领导代讲，先改流程再开大会。

2. **补齐三件事，量化赞美**
   - 完成标准: 表彰词中明确含三组信息——测了什么假设（含证伪结论）、实际花了多少（人数/金额/时长）、省下了什么（相对继续投入的对比数字）；至少出现一组"小止损 vs 大浪费"的对照。

3. **检查奖惩制度与口号的一致性**
   - 完成标准: 逐条对照奖励、晋升、考核制度，列出与"拥抱失败"相反的条款（如失败项目即出局、红绿灯必须全绿）；每条不一致处形成修改建议提交责任制负责人（`accountability-method-culture` 因果链的入口）。

4. **给终止团队书面去向**
   - 完成标准: 每位成员有明确的再配置安排（新项目/成熟业务/转岗），禁止"项目黄了先原地待命"；对照亚马逊再配置而非解散的先例。

5. **判停**: 若失败叙事通不过第 2 步的审计——讲不出测了什么假设、只有困难与情怀（ce13 冒牌创业者的失败表演）——则不予表彰，转交增长委员会重新审计学习真实性；奖励只给"有益的"失败。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 确定性生产的质量事故：六西格玛语境里失败仍是缺陷，"奖励失败"会直接摧毁质量体系——`reward-useful-failure` 只覆盖极端不确定下的探索性项目。
- 失败豁免的诉求：奖励的前提是及时证伪+可审计学习；把本 skill 用作"失败不用负责"的挡箭牌是对本书的误读——创业者恰恰要为结果负责。
- 项目尚未终止、正在决策是否终止：先走 `pivot-persevere-cadence` 的转型/坚持会议机制，本 skill 管的是决定之后的处置。

### 作者在书中警告的失败模式

- ce02 "只许成功"文化：管理者假装公司从未失败，员工隐藏失败、粉饰进展，红绿灯汇报永远是 7 绿 2 黄 1 红的标准表演——口号与制度信号相反时，理性选择是表演。
- 中层当刽子手的代价：由上级代讲"我否了它"，下次没人敢提前终止；项目只会僵尸化到无法收拾再爆雷。
- ce13 冒牌创业者与失败表演：失败叙事从不附带"学到了什么/怎么知道的"，屡败者靠讲故事反复获取资源——失败污点豁免被反向利用时，信号失灵。

### 作者的盲点 / 时代局限

- 一线执行者的失败污点与职业代价书中着墨很少（BOOK_OVERVIEW：视角集中于高管/创始人/明星教练）——"失败了还能保持尊严"依赖组织后续真的再给机会，在晋升一票否决的文化里近乎奢望。
- 表彰案例（液体膨胀机、Fire 手机）均来自作者深度合作的公司，存在幸存者偏差与利益关联；且 GE 后来的战略崩塌说明容错文化救不了战略错误。
- 书中未讨论失败补偿的量化设计（奖金多少、绩效如何记），奖励力度留白，实践中易走形为口头表扬。

### 容易混淆的邻近方法论

- 与《精益创业》正传的区别: 正传在初创语境讲"失败是学习的机会"（认识论层）；本书把它落成组织制度（奖励、晋升、公开赞许、团队再配置的具体动作）——调用时勿停留在"要拥抱失败"的姿态层，三问（谁讲/讲什么/奖给谁）才是本 skill。
- 与"火葬仪式"式的失败复盘会的区别: 复盘会聚焦"哪里做错了"，`reward-useful-failure` 聚焦"组织如何接住终止"；前者可能强化失败污点，后者修复激励信号。
- 与 post-mortem/无指责复盘（blameless postmortem）的区别: 无指责复盘是工程事故场景的技术工具；`reward-useful-failure` 是组织层对探索失败的激励设计，对象是项目与职业生涯，不是事故报告。
