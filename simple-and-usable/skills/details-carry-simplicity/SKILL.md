# 细节支撑简单

## R — 原文 (Reading)

> "简单通常要有细节来支撑。"（第8章）
>
> "花上半天时间……也许就能把成千上万次愤怒的用户投诉消弥于无形。"（第8章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第8章

---

## I — 方法论骨架 (Interpretation)

简单是用户的**整体印象**，但整体印象由**最薄弱的细节**决定——一个规划功能近乎满分的地铁应用，漏掉"方向"这一行字，就在站台现场崩塌。细节不是简单的修饰，而是简单的承重结构。

给细节修复定价要用**规模乘法**：单次瑕疵代价 × 受影响用户数 × 使用频率。作者对"花半天修一个下拉菜单、就为省用户几秒钟，值得吗"的回应是：面向大众的软件每天被百万用户使用，每人几秒累积起来就是几年——微小瑕疵乘以百万用户等于灾难。

这改写了排期直觉：按"单次改动收益"排序，小瑕疵永远排不上；按规模乘法排序，**高频路径上的微小缺口优先于低频的大优化**。这里的"高频路径"要用完整用户故事去找——尤其是真实条件下（人多、着急、单手、被打断）的"最后一米"：演示环境里一切正常，恰恰会在那里卡住。

注意这不是完美主义：定价的目的恰恰是取舍——低频且无后果的瑕疵可以放过，把资源集中在决定整体印象的承重细节上。

## A1 — 书中的应用 (Past Application)

### 案例 1: 巴黎地铁应用漏掉"方向"
- **问题**: 一个地铁查询应用，输入起终点就给出最佳路线、换乘与耗时，进地铁站前作者一直觉得它很棒。
- **方法论的使用**: 进站后才发现它漏了关键细节——没说坐哪个方向（巴黎地铁以线路终点站表示方向）。作者只得在摩肩接踵的通道里用手指在屏幕上拖来拖去找终点站。
- **结论**: 简单由细节支撑；设计在理想条件下成立，真实环境会放大缺失的环节。
- **结果**: 一个看似接近满分的应用在站台"崩塌"，成为"微小瑕疵×百万用户=灾难"的亲历佐证。

### 案例 2: 火车票表单的三处错位
- **问题**: 搜索表单功能没问题，用户测试中却人人使用踌躇，毛病出在哪？
- **方法论的使用**: 排查发现 17 个字段里只有 3 个位置不合适（未对齐假想网格）——对齐后一个标签没改、一行代码没写，表单就用起来简单了。
- **结论**: 少数错位的细节足以毁掉整体印象；反之，修好几个关键细节就能撑起整体简单感。
- **结果**: 零文案、零代码改动让测试中的踌躇消失。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审/排期时有人反对修小问题（"只省几秒""用的人少"），需要回应或裁决。
2. 上线前最后一轮检查，要决定哪些细节必须修、哪些放过。
3. 功能都正常但某环节流失异常，或用户投诉集中在"说不清的小别扭"。
4. 设计收尾阶段，要判断哪些细节是"承重的"、哪些是装饰。

### 语言信号 (用户的话里出现这些就应激活)

- "这么小的改动值得吗 / 只省几秒 / 用的人不多 / 值不值得修"
- "上线前还要修哪些 / 小瑕疵 / 最后一米 / polish / 细节打磨"
- "minor fix / worth fixing? / small UX issue / should we bother"

### 与相邻 skill 的区分

- 与 `declutter` 的区别：那是**批量清扫**一类小负担（装饰、冗余链接、废话文字）的工序；本 skill 是给**单个细节修复**定价排序、回应"不值得修"的质疑。
- 与 `simplicity-baseline` 的区别：基准告诉你"什么算简单"；本 skill 回答"哪个细节会毁掉简单"。
- 与 `complexity-placement` 的区别：那处理消不掉的复杂性的分配；本 skill 处理可消除的小瑕疵的定价。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **把瑕疵放进完整使用故事**
   - 定位它在用户必经路径的哪一步、什么状态下撞上（着急/单手/被打断）
   - 完成标准: 一句话说清"谁、在什么真实条件下、在哪一步撞上它"；定位不了就先补用户故事（转 `user-story-craft`）
2. **用规模乘法定价**
   - 计算：单次代价 × 受影响用户数 × 使用频率
   - 完成标准: 得出量化结果（如 3 秒 × 100 万日活 ≈ 每天累计约 3.5 年）；无精确数据时用保守区间估计并注明假设
3. **排序并回应质疑**
   - 高频路径上的细节缺口优先于低频大优化；给反对者一个可复述的回应
   - 完成标准: 排期表上高频"最后一米"缺口位次前移；对"只省几秒"式质疑有一句定价式反驳
4. **上线前"最后一米"检查**
   - 按用户故事在真实条件下走一遍必经之路（人多、着急、单手）
   - 完成标准: 故事里每个必经步骤都有着落；发现的缺口当天修复或挂最高优先级
   - 判停条件: 瑕疵在低频路径（如年度设置项）且无错误后果——记入待办，不强行动用紧缺资源

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 小用户量内部工具（几十人规模）——规模乘法不成立，按常规收益/成本排序即可
- 无边界的完美主义——为"再打磨 0.1 分"无限投入违背定价初衷
- 问题本质是功能缺失或结构性复杂——那是四策略与复杂性放置的领地

### 作者在书中警告的失败模式

- **在理想/演示条件下验收**：巴黎地铁应用进站前"很棒"，进站后第一步就卡住——真实环境（人多、着急、单手）会放大缺失环节（第8章）
- **"花半天就为省几秒？"式默认否决**：微小瑕疵累积成挥之不去的烦恼和成千上万次投诉（第8章）

### 作者的盲点 / 时代局限

- 定价公式没有"足够好"的阈值——乘法能论证一切小细节都该修，修复成本与回归风险曲线未讨论
- 案例是大众消费应用；B2B 小用户量产品不适用同一乘法，书中未区分
- 修细节也可能引入新问题（回归风险），书中未讨论验证工序

### 容易混淆的邻近方法论

- 完美主义/polish 文化：本书不主张无边界打磨，主张按"用户数×频率"定价的针对性修复
- "魔鬼在细节"式格言：只有态度没有算式；本书给出可计算的定价方法
