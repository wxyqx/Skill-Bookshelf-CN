# 极端简单目标

## R — 原文 (Reading)

> "争取你不可能达成的目标有一个重要的好处：保持正确的方向。"（第2章）
>
> "如果把目标设定为'快速响应'而不是'瞬间响应'，那么哪怕把响应时间只缩短1秒钟，你也会满足了。"（第2章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第2章

---

## I — 方法论骨架 (Interpretation)

常识要求目标 SMART、可达成；作者反其道而行：为"简单"设定的目标应该是**不可能达成的极端目标**，因为它唯一的用处不是被达成，而是当方向舵。

书里给出一组固定的替换表：常规的"特殊人群可以使用"换成"**任何人都可以使用**"；"容易使用"换成"**毫不费力地使用**"；"快速响应"换成"**瞬间响应**"；"快速理解"换成"**一目了然**"；"偶尔出错没关系"换成"**不出错、始终工作**"；"在理想条件下可用"换成"**在混乱无序的环境中工作**"。

机制在于妥协滑坡：目标是"快速响应"时，缩短 1 秒就算达标，于是每次设计会议的小让步都"合法"，累积起来产品越来越慢、越来越讨厌；目标是"瞬间响应"时，任何让步都看得见离目标更远，妥协无法悄悄溜过去。

使用前提必须说清：极端目标**不用于验收与考核**（达不成不算失败），只在每个取舍时刻回答"这个决定让我离它更近还是更远"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 八组常规到极端的目标替换（第2章专节）
- **问题**: "简单"如何写成可用的目标，才能防止设计在一次次评审中漂移？
- **方法论的使用**: 作者把自己为简化工作设定的常规可用性目标逐条升格：任何人可以使用、毫不费力、瞬间响应、一目了然、始终工作、不出错、在混乱无序的环境中工作——并明说这些是"不可能达成"的目标。
- **结论**: 不可能达成的目标的好处是保持正确的方向，让每次改变都朝同一方向。
- **结果**: 极端目标成为"明确认识"工作法的组成部分，与基准描述配合使用。

### 案例 2: 橄榄球广告时段的手机促销站
- **问题**: 促销手机站用户停留几分钟就走，负责人盯着页面"看不出违反了哪一条可用性规则"。
- **方法论的使用**: 常规目标在会议室里全能通过；只有极端目标"在混乱无序的环境中工作"能拦住这类缺陷——用户只在电视插播广告的几十秒空档里访问，比赛一开始就离开。
- **结论**: 常规目标合格不等于体验合格，极端目标负责兜住真实使用条件。
- **结果**: 访问用户后谜底揭开，网站"经过好一番设计才达到要求"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 性能/体验目标写成"快 20%""更易用"这类比较级，达成后团队松懈。
2. 评审总以"比上一版好"收尾，几个月下来产品越改越慢、越改越乱。
3. 要在评审中用一个硬标准卡需求，但不想把它误用成 KPI。
4. 写项目章程/设计文档时，需要给"简单"定方向性目标。

### 语言信号 (用户的话里出现这些就应激活)

- "目标定多少合适 / 响应快 20% / 更易用 / 更快更好"
- "达标后就松懈了 / 越改越慢 / 每次评审都说比上一版好"
- "需要一个能卡需求的硬标准 / 极端目标 / stretch goal / aspirational goal"

### 与相邻 skill 的区分

- 与 `simplicity-baseline` 的区别：基准回答"判断是否简单的标准是什么"（成文文档）；本 skill 是目标的升格工序与防漂移用法，可作为基准的素材。
- 与 `field-observation` 的区别：那是收集真实环境证据；"在混乱无序的环境中工作"这条极端目标要靠那些证据才有牙齿。
- 与 `four-strategies` 的区别：四策略是简化路径；本 skill 是简化之前的目标设定，决定"朝哪个方向简化"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **抓出比较级目标**
   - 列出当前项目所有体验/性能目标，标出其中的比较级与百分比表述
   - 完成标准: 目标清单成形，每条都注明"达成即满足"的滑坡风险
2. **逐条升格为极端目标**
   - 按固定替换表升格：任何人可用/毫不费力/瞬间响应/一目了然/始终工作/不出错/在混乱无序的环境中工作
   - 完成标准: 每条常规目标都有对应极端版本，并合并成一句"简单的体验是什么样"
3. **声明用法边界**
   - 向团队明确：极端目标不用于验收与考核，达不成不算失败
   - 完成标准: 用法规则成文（评审允许说"达不到，但必须朝它靠近"）
4. **妥协时刻过闸**
   - 每个取舍决定问一句"这个让我离极端目标更近还是更远"，并留记录
   - 完成标准: 妥协决定均有方向判断；"更远"的决定触发重新设计而非默认接受
   - 判停条件: 极端目标与法规/平台硬约束直接冲突时，标记为边界例外并写明理由，不强求

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 对外承诺的合同 KPI/SLA——那里必须 SMART 可达成，极端目标不进考核
- 一次性交付、没有后续迭代——没有"妥协时刻"，方向舵无处使用
- 团队尚未约定"不用于验收"的用法之前——会被当成画饼或苛政

### 作者在书中警告的失败模式

- **"快 1 秒也算快"**：目标是"快速响应"时缩短 1 秒即满足，一次次小让步累积成"更慢、更令人讨厌"的产品（第2章）
- **目标全是比较级**：更快/更好/更容易没有一票否决的底线，每次评审"比上一版好"即通过，滑坡没有警报

### 作者的盲点 / 时代局限

- 只论证了防漂移作用，未讨论为逼近极端目标（如"不出错"）付出的成本曲线与过度设计风险
- 未给出极端目标与商业指标冲突时的裁决方法
- "瞬间响应"等表述锚定 2011 年的硬件环境，今天需按当下技术基线重新校准

### 容易混淆的邻近方法论

- OKR 的 stretch goal：OKR 仍用于打分考核；本书极端目标明确不用于验收
- "精益求精"口号：没有固定替换表与妥协过闸动作，只是态度
