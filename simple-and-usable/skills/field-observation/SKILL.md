# 真实环境观察

## R — 原文 (Reading)

> "用户体验是否简约必须要在纷乱、多变的环境中才能考察出来。"（第2章）
>
> "无法控制用户使用软件的环境，而只能使软件设计符合环境需求。"（第2章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第2章

---

## I — 方法论骨架 (Interpretation)

作者把一条朴素的事实讲得很硬：评审发生在安静的会议室，人人投入十分注意力；而用户在办公室被打断、在家里一心多用、在户外强光下排队。两种注意力水平下的体验没有可比性——很多设计"在会议室里完美"，到真实环境第一步就走不下去。

所以判断简不简单，必须到用户真实使用的地方去。作者给三类环境留了观察清单：办公室看打断与多任务（多久被打断一次、回来能不能接上）；家里看分心（边看电视边上网）；户外看光线、噪音、姿态（单手、行走、排队）。观察的问题不是"用户会不会用"，而是"环境允许用户用什么"。

方法论立场随之确定：无法控制用户的环境，只能让设计适应环境。"在理想条件下工作"不是及格线，"在被打断的间隙生存"才是——环境约束要翻译成设计要求（更短的任务块、更强的状态恢复），而不是翻译成更多提醒和确认。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 经销商玻璃墙与橄榄球促销站
- **问题**: 其一，汽车经销商编写营销计划的软件难用；同事上门拜访，发现经理隔着玻璃墙紧盯展厅、随时跑出去接待客户，谈话不断被打断——家家如此。其二，橄榄球锦标赛促销手机站，用户呆几分钟就走，负责人从离开的页面看不出违反了哪条可用性规则。
- **方法论的使用**: 到现场观察环境约束后，设计思想从"合并组件"改为"把组件切成更细的块+任务检查表"，让经理每次花很短时间完成一块、回来能接上进度；橄榄球站则访问用户找谜底——他们只在电视插播广告的空档上网，比赛一开始就回电视机前。
- **结论**: 评审在安静会议室，使用在纷乱现场；"整块时间不存在、任务要在几十秒的间隙内完成"这类决定性约束，不走出办公室就看不见。
- **结果**: 经销商软件按短任务重构；橄榄球网站经过好一番设计才达到要求——两案共同确立"无法控制环境，只能适应环境"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 可用性测试全过/评审通过，但真实用户抱怨难用、支持工单多、数据异常（高跳出、短停留）。
2. 新产品要进入一个你没待过的使用现场（门店、车间、户外、车上），要预判环境约束。
3. 设计评审中双方都在想象"用户会怎么用"，没人去过现场。

### 语言信号 (用户的话里出现这些就应激活)

- "用户实际怎么用 / 去现场看看 / 走出办公室 / 实地走访"
- "测试室没问题但用户说难用 / 停留很短 / 跳出率很高 / 用两步就走了"
- "被打断 / 午高峰 / 单手操作 / 强光下排队 / context of use / field study"

### 与相邻 skill 的区分

- 与 `simplicity-baseline` 的区别：观察产出的情景是基准的原材料，基准是成文的裁决标准——顺序是先观察后成文。
- 与常规可用性测试的区别：测试室回答"能不能用"，现场回答"环境允不允许用"——本 skill 不替代测试，补的是测试测不出的那一层。
- 与 `mainstream-user-lens` 的区别：分型回答"为谁设计"，观察回答"在什么条件下设计"；压力之下的主流用户正是两者交界——主流用户在真实环境里永远处于匆忙状态。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **列出环境三清单**
   - 按办公室/家里/户外（或该产品的对应现场）列出：打断源、注意力水平、姿态与手、光线噪音
   - 完成标准: 清单里至少有一项"会议室里想不到"的约束
2. **到现场看完整的一次使用**
   - 跟踪一次真实任务从开始到完成/放弃
   - 完成标准: 记录了打断发生的时刻、用户回来后的接续动作、环境造成的任何变通或绕行（影子流程）
3. **把约束翻译成设计要求**
   - 如"午高峰单手持机"→大按钮、短任务块；"随时被打断"→状态可恢复
   - 完成标准: 每条环境约束对应一条可验证的设计要求，设计明确"在被打断的间隙生存"
4. **判停检查**
   - 例外: 现场观察与测试室结论冲突时——以现场为准，回炉基准（转 `simplicity-baseline`）；根本进不了现场时——用最接近的替代现场并明确标注为假设，禁止把会议室想象当情景
   - 完成标准: 冲突已裁决，或假设已标注

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 产品只在受控环境使用（标准工位的呼叫中心、有锁屏规范的手术室设备）——环境变量确实可控，测试室结论权重更高
- 观察会显著改变被观察者行为（敏感场景）——改用日志/埋点数据或长期驻场，一次走访会失真
- 问题已经明确是用户分型或立场之争——先转 `mainstream-user-lens`，现场解决不了"听谁的"

### 作者在书中警告的失败模式

- 会议室评审代替现场：人人投入十分注意力，设计隐含"用户有连续整块时间"的假设——真实环境里这个假设从不成立
- 只盯着离开页面找错：橄榄球促销站负责人"从离开的页面看不出违反哪条可用性规则"，因为离开发生在环境里、不发生在页面上——不看现场永远找不到谜底
- 把"适应环境"做成"功能加码"：环境嘈杂就加提醒、加确认——方向反了；适应是让任务块更短、状态更可恢复，不是往嘈杂环境里塞更多东西

### 作者的盲点 / 时代局限

- 书中观察样本是个案式走访（经销商、橄榄球站），未讨论样本量与系统化采样；自我报告与实际行为的差距问题在小样本测试里更明显（BOOK_OVERVIEW）
- 2011 年的三类环境清单以办公/家庭/户外为主；移动互联网时代环境更碎（推送、多设备切换、通勤场景），清单需要扩展而非照抄（BOOK_OVERVIEW 时代局限）

### 容易混淆的邻近方法论

- 常规实验室可用性测试：控制变量 vs 引入变量——本 skill 刻意要的就是"纷乱"本身，两者互补而非竞争
- 使用情景故事（`simplicity-baseline`）：写出来的情景必须来自观察，否则是小说
