# 貌似简单排查

## R — 原文 (Reading)

> "这些做法的特点是能解决眼下的问题，相对便宜，而且不会引起什么争议。"（第1章）
>
> "大多数用户根本不会看使用说明，他们只想拿过来就用。"（第1章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第1章

---

## I — 方法论骨架 (Interpretation)

作者在第1章给"真简单"划了一条下边界：有一类做法看起来在解决问题，实际上让事情更复杂——他称之为"貌似简单"。识别靠三个特征：只解决眼下的问题、相对便宜、不会引起争议。第三个特征最要命：正因为无争议，这类方案在设计会议上总是最先胜出；而且失败了无人追责，做的人还能说"我一直在努力"，于是它们层出不穷。

三类最流行的假捷径各有破绽。说明书把失败的责任推给用户——言下之意是"解释得这么清楚你还不懂，是你的问题"，而事实是用户根本不看说明；操作向导用分步流程剥夺用户的控制权，步骤越长体验越差；卡通助手假装计算机能预知你的需求，"牵着鼻子走"只会招人反感。

排查的产出不是"把向导做得更好"，而是换问句：一个产品如果非靠教程才能用，说明设计本身还有没解决的问题——讨论应该回到"哪个功能该删、哪个步骤该消"。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 貌似简单的假捷径家族
- **问题**: 团队遇到设计难题时，习惯性诉诸说明书、操作向导、卡通助手；这些做法被业界普遍接受，从未被当作问题本身。
- **方法论的使用**: 作者用三特征解释它们为何层出不穷（解决眼下问题、便宜、无争议），再逐一指认破绽：说明书推责给用户、向导剥夺控制权、卡通助手假装预知需求。
- **结论**: 它们实际让事情更复杂、效果更差，是伪装成补救措施的假捷径；热衷表面文章的人永远造不出简单的用户体验。
- **结果**: 为全书划定"真简单"的边界——之后的删除、组织、隐藏策略都不允许退回这三条假捷径。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审或需求讨论中，有人提出"加个新手引导 / 向导 / 说明页 / 帮助中心"来救一个难用的产品。
2. 你要判断某个"看起来能救场"的方案（教程、FAQ、弹窗提示、卡通形象）是真补救还是假捷径。
3. 产品已经堆了说明书或向导，但用户依然不会用、支持请求不减，需要解释为什么会这样。

### 语言信号 (用户的话里出现这些就应激活)

- "加个新手引导就简单了 / 用户不会用就写个说明书"
- "做个操作向导 / 引导页 / onboarding wizard / 卡通助手"
- "用户看不懂，我们解释一下就行 / 这是业界通行做法"

### 与相邻 skill 的区分

- 与 `four-strategies` 的区别：四策略回答"怎么真正简化"；本 skill 是防伪检查——先识别并否决假方案，把讨论拉回真策略。
- 与 `hide-strategy` 的区别：渐进展示、适时出现是正面设计手法（藏好非核心功能，在用户关注点上给入口）；向导是把学习负担整包塞给用户的假捷径，两者形态相似、方向相反。
- 与 `business-case-for-simplicity` 的区别：本 skill 负责否决假方案；否决后真方案在组织内遇到阻力时，转商业论证。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **抓住提案，过三特征检查**
   - 对"说明书 / 向导 / 助手"类提案逐项问：是不是只解决眼下问题？是不是相对便宜？是不是不会引起争议？
   - 完成标准: 三条全中即打上"貌似简单"标签并给出判定依据；有任何一条不成立则停止否决
2. **指认责任去向**
   - 问这个方案把失败的责任放在谁头上：用户不看说明书算谁的？向导中途退出后用户能否自己走完？它替用户做了哪些本该用户自己做的决定？
   - 完成标准: 能一句话说清该方案"把失败推给了谁、剥夺了什么控制权"
3. **判停检查（豁免条件）**
   - 例外: 用户群体必须受训（专业软件、法规合规、安全要件）时，说明文档是产品的一部分而非假捷径——转入文档质量设计而非否决
   - 完成标准: 明确走"否决"还是"豁免"分支，豁免须给出具体依据
4. **换问句，回到真策略**
   - 把讨论从"怎么教会用户"换成"哪个功能该删、哪个步骤该消"，转入 `four-strategies` / `remove-strategy`
   - 完成标准: 产出至少一个指向设计本身的改进行动，而不是只指向教用户的行动

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 用户群体明确是受训专业人员，文档是合规或安全要件——此时说明书是产品的一部分
- 问题真的是信息缺失而非设计缺陷：用户找得到、看得懂功能，只是不知道某个参数的含义——此时一句出现在用户关注点上的及时帮助是正当设计（适时出现）
- 提案其实是渐进展示或阶段展示的正当设计——不要把所有"分步"都当假捷径误杀

### 作者在书中警告的失败模式

- 说明书假捷径：把失败责任推给用户（"不明白是你的问题"），而用户根本不看——上线后说明书阅读量几乎为零、支持请求不减
- 向导假捷径：步骤在版本迭代中越加越长，剥夺控制权；向导不会讲故事、满口术语、信息块过大或过小（第6章补充）
- 无人追责的循环：因为"所有人都知道这些做法有效"，失败也不追责，做的人还能说"我一直都在努力"——组织普遍接受的低效循环

### 作者的盲点 / 时代局限

- 作者对向导一概否定，但书成于 2011 年；此后 onboarding 已演化出"分步引导+可跳过+情境提示"的成熟中间态，书中未讨论"引导何时正当"这条线
- 站在大众消费产品视角立论；对必须培训的专业软件，"用户不看说明书"这个前提不成立

### 容易混淆的邻近方法论

- 渐进展示 / 适时出现（`hide-strategy`）：同样是"需要时才出现"，区别是它藏好功能、在关注点给入口，而不是用分步流程牵着用户走
- 阶段展示：向导的正当替代——每一步符合用户心理预期、说用户的语言、信息块自洽；判断标准是块的质量而非步骤数量
