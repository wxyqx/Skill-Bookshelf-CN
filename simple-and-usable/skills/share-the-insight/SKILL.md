# 分享认识

## R — 原文 (Reading)

> "跟参与项目的每一个人复述你的故事……直到你讲得自己都厌烦了。"（第2章）
>
> "科尔维尔开始在公司里到处张贴海报，承诺该项目会让机顶盒'简单、稳定、快速'。"（第2章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第2章

---

## I — 方法论骨架 (Interpretation)

设计者对"什么是简单"的认识只存在自己脑子里时，它会随着会议、人员流动和部门立场不断稀释——**你不在场，决定就跑偏**。作者的解法不是加审批流程，而是把判据内化给所有人，让任何人在你不在场时也能做出和你一致的决定。

工序有三步。第一步**压缩**：把认识压成两三个可判断的词（Telewest 的"简单、稳定、快速"）——短到能贴海报，每个词都能据此回答"是/否"。第二步**传播**：到处张贴、逢会必讲，强度标准是"讲到自己都厌烦了"——你觉着腻的时候，别人才刚记住。第三步**内化为过滤句**：每次评审对每个提案固定问"这样能更简单、更稳定、更快速吗"，让判据从标语变成决策反射。

内化成功的标志不是"大家都能背"，而是**别人开始用你的判据否决提案**——Telewest 项目里，一位项目经理否决某功能的理由正是"能更简单、更稳定，但不能更快"。

## A1 — 书中的应用 (Past Application)

### 案例 1: Telewest 机顶盒"简单、稳定、快速"
- **问题**: 机顶盒软件太复杂、问题多、速度慢，公司上下厌恶改变，任何改进都推不动。
- **方法论的使用**: 2002 年艾伦·科尔维尔负责升级项目，把目标压成三个词到处张贴海报，每次开会固定问"这样可以让体验更简单、更稳定、更快速吗"，让三个词成为所有决定的指导原则。
- **结论**: 判据公开并反复复述后，团队在你不在场时也能独立做出正确决定。
- **结果**: 软件发布后求助电话很少，仅此一项至少节省 300 万英镑。

### 案例 2: 万豪主页改版的共同愿景
- **问题**: 人人都说主页太乱（77 个链接），又都认为自己的内容必须保留，改版方案被部门立场撕扯。
- **方法论的使用**: 团队立一个"根本无法变通"的清晰方案（链接减到 43 个、只留一个特色推荐位），用实时站点数据把愿景证据化去说服干系人，并给业务方打好"上线初期指标会跌"的预防针。
- **结论**: 共同愿景要压成可复述的目标并配上证据，才能穿过组织立场完成传播。
- **结果**: 预订量未降，四个月后满意度反超原有水平。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 自己不在场（评审会、跨部门会）时，产品决定总跑偏。
2. 团队对"什么是好的体验"没有共识，每次争论都从零开始。
3. 设计判据/原则写成文档后没人看、没人用，沦为墙上的标语。
4. 新成员加入或多团队协作，判断标准传递总走样。

### 语言信号 (用户的话里出现这些就应激活)

- "我不在场他们就乱来 / 决定总跑偏 / 没有共识 / 各说各话"
- "设计原则怎么落地 / 判据 / 贴出来没人看 / alignment / shared vision"
- "讲了很多遍没人记住 / 新人不懂我们的标准 / how to align the team"

### 与相邻 skill 的区分

- 与 `simplicity-baseline` 的区别：那是**写出**判据（成文标准）；本 skill 是把判据**传播并内化**到每个人——先有基准，再谈分享。
- 与 `business-case-for-simplicity` 的区别：那是用公司方程式对单次简化提案做一次性论证；本 skill 是日常决策层的判据内化，不针对单个提案。
- 与 `user-story-craft` 的区别：故事是判据的载体之一；本 skill 关注传播强度（讲到厌烦）与决策过滤句。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **把认识压成判据**
   - 压成两三个词或一句话（参照"简单、稳定、快速"）
   - 完成标准: 判据短到能贴在海报上；每个词都可独立判断（能据此回答"是/否"）
2. **公之于众并反复复述**
   - 海报/置顶文档/评审开头统一使用同一判据
   - 完成标准: 有传播物存在；复述次数达到"自己已讲到厌烦"的程度，远超自己觉得必要的次数
3. **固化为过滤句**
   - 每个提案固定问"这能让体验更___吗？"
   - 完成标准: 至少一次会议上有非设计岗成员主动引用判据支持或否决某个提案
4. **验证内化**
   - 抽一个自己不在场时做出的最近决定，用判据复盘
   - 完成标准: 能明确判断该决定是否符合判据；跑偏则说明传播强度或可判断性不足，回到第 1 步
   - 判停条件: 判据连续多次无法裁决实际争论（人人都说"都符合"或"都不符合"）——判据太抽象，停下重写得更可判断

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 一人/双人小团队——没有传播对象，直接成文基准即可，不必做传播工程
- 冲突根源是部门利益而非认识不清——判据内化解决不了分配问题，转 `business-case-for-simplicity`（组织内算账）
- 判据本身还没想清楚——先做基准描述，否则传播的是噪音

### 作者在书中警告的失败模式

- **只讲一遍就以为大家懂了**：传播强度不足，判据沦为墙上的标语——标准是"讲到自己都厌烦了"（第2章）
- **判据含糊不可判断**："做好体验"式的判据让过滤句永远产生不了否决力
- **没有判据的组织**：公司上下厌恶改变，任何简化都被"某位重要客户"式的个案反对拖垮（第1章案例佐证）

### 作者的盲点 / 时代局限

- Telewest 的成功依赖咨询者位置与高层支持，书中未讨论判据内化在强层级组织中的失败率
- 300 万英镑的节省归因单一（求助电话减少），未排除同期其他因素
- 未讨论判据的更新机制——产品成熟后"简单、稳定、快速"可能需要换代

### 容易混淆的邻近方法论

- 设计原则/Design Principles 文档：写出来不等于内化；本 skill 的核心是传播强度与过滤动作
- North Star Metric：那是业务指标；判据是体验判断标准，两者可并存但不可互替
