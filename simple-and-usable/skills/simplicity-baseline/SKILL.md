# 简单基准描述

## R — 原文 (Reading)

> "这个认识将成为判断自己是否保持简单的一个标准。"（第2章）
>
> "在面对设计功能对照表而犹豫不决时，我就会暂时停下来，问我自己'做这个表是为了什么'"（第2章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第2章

---

## I — 方法论骨架 (Interpretation)

作者主张：动任何简化之前，先成文地回答"什么才算简单"。没有这条基准，后面每一个删除、组织、隐藏的决定都会退化成个人口味之争；有了它，"简单"才从感觉变成可判定的标准。

基准有两档写法，按项目规模选：较小或较清楚的改进，用一句话写出来——设计什么、要遵循哪几条设计规则（Flip 的基准就是"拍摄和分享视频"）；更大或更含糊的项目，写成使用情景故事——有环境、角色、情节的那种。两档的共同底线是具体：具体到能拿去判断一个具体的取舍，而不是"少即是多"式的口号。

它的用法是当自检句：面对功能对照表犹豫不决时，停下来问"做这个是为了什么"，拿基准逐条对照。另有一条心智保护：设计过程中复杂感上升是正常曲线（乔布斯的三个阶段），不等于跑偏——跑偏与否看基准，不看中途的手感。

## A1 — 书中的应用 (Past Application)

### 案例 1: Telewest 机顶盒"简单、稳定、快速"
- **问题**: 2002 年 Telewest 升级机顶盒软件，此前版本太复杂、发布后问题多，公司上下厌恶改变，各团队对"什么算好"没有共识。
- **方法论的使用**: 艾伦·科尔维尔把核心认识压成三个词——"简单、稳定、快速"——到处张贴海报，并让每次开会都问一遍"这样可以让体验更简单、更稳定、更快速吗？"
- **结论**: 基准公之于众后，连他不在场时团队也能做出正确决定；一位项目经理照着否决了"更简单更稳定但不更快"的功能。
- **结果**: 软件发布后求助电话很少，仅此一项至少节省 300 万英镑。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 简化/改版项目启动，团队对"什么算简单"只有"别太乱""少即是多"式的口号。
2. 为一个字段/按钮/选项争论数日，各方都有道理，缺一个裁决标准。
3. 验收或评审时被问"你怎么证明这版更简单了"，需要可判定的依据。

### 语言信号 (用户的话里出现这些就应激活)

- "什么算简单 / 简单的标准 / 判断基准 / 设计目标是啥"
- "这个字段要不要 / 吵了两周 / 谁说了算 / 验收标准"
- "baseline / success criteria / definition of simple"

### 与相邻 skill 的区分

- 与 `field-observation` 的区别：观察采集基准的原材料（真实情景），本 skill 把材料写成裁决标准——先有观察，后有成文；情景若全靠想象，先出门。
- 与 `four-strategies` 的区别：四策略是动作层（删/组/藏/转），基准是判断层（按什么判）——四策略的每一步都要回基准对照。
- 与极端可用性目标（第2章相邻方法，阶段 3 确认 slug）的区别：基准描述"做的是什么、为谁"；极端目标把"简单"各维度推到不可达成以保持方向——前者管取舍，后者管防漂移。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **选写法**
   - 按项目规模二选一：小型改进写一句话（设计什么+几条规则）；大/含糊项目写使用情景（环境、角色、情节）
   - 完成标准: 写法已定，且团队知道为什么选这一档
2. **写出草稿并压到可判定**
   - 删掉所有含糊词（"好用""直观""友好"），拿当前争议最激烈的一个具体问题试判一次
   - 完成标准: 基准每一条都能对具体设计问题给出可判定答案；试判能实际分出胜负
3. **挂进评审流程当自检句**
   - 后续每次取舍（加/删/改）都过一遍基准，而非靠职位或嗓门裁决
   - 完成标准: 评审规则中明确以基准为裁决依据
4. **判停检查**
   - 例外: 若争议双方引用的是不同基准（或根本没有基准）——停设计，先重写基准；若基准与真实使用情景冲突——转 `field-observation` 补观察
   - 完成标准: 明确"继续设计"还是"回炉基准"

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 纯技术重构（不改变用户可感知行为）——没有"简单感"可裁决，基准写了也用不上
- 干系人拒绝共同确认基准（各怀目标）——先解决政治问题，否则写出来的基准只会被各自引用
- 问题只是个人审美偏好之争——先确认争的是"用户觉得简不简单"，不是"我觉得好不好看"

### 作者在书中警告的失败模式

- 没有基准漏掉决定性细节：巴黎地铁应用进站前"很棒"，进站后才发现没告诉用户该坐哪个方向——演示与评审环境一切正常，真实情景的第一步就卡住
- 口号式基准：把"少即是多"当基准——不可判定，等于没有；基准必须落到能裁决一个具体争议
- 妥协滑坡：基准若写成"更快、更好"的比较级，每次小让步都合法（缩短 1 秒也算达标），产品越改越慢——基准要向"瞬间""毫不费力"式的极端表述看齐才立得住

### 作者的盲点 / 时代局限

- 作者假设基准可由设计师离身写出；行为科学后来指出自我报告与实际行为有差距，书中依赖的可用性测试样本量小（BOOK_OVERVIEW 未证假设）
- 基准的维护未被讨论：产品生命周期内用户构成会变化，一次写就的基准可能过期（BOOK_OVERVIEW 未证假设）

### 容易混淆的邻近方法论

- `field-observation`：原料（观察到的情景）与裁决标准（成文基准）——形态相似、阶段不同
- 用户故事法（第2章相邻方法，阶段 3 确认 slug）：使用情景式基准在形态上就是用户故事，区别在用途——故事用于理解与共情，基准用于裁决取舍；同一个故事可两者兼用
