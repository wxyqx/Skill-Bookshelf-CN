# 转移策略

## R — 原文 (Reading)

> "只在遥控器上保留具备最基本功能的按钮，将其他控制转移到电视屏幕上的菜单里。"（第3章）
>
> "设计简单体验的一个秘密，就是把正确的功能放到正确的平台或者正确的系统组件中去。"（第7章）
>
> — Giles Colborne，《简约至上：交互式设计四策略》第3、7章

---

## I — 方法论骨架 (Interpretation)

转移容易被读成"把活推给用户"，方向正好反了：它是把复杂性放到**成本最低、体验最好**的位置。DVD 遥控器的解法不是把按钮藏完，而是只留播放暂停，其余搬进电视屏幕菜单——复杂性还在，只是换了地方。

三种去向，各配一张分工表：

1. **人机之间**：人擅长设定目标、估算、想象、处理模棱两可；机器擅长精确保存、记忆、检索、计算、格式化。所以结构化是机器的活——让用户按自然格式写"截止到 1 月 27 日"，机器负责识别；反过来逼用户填"11 位不带符号的手机号"，是把机器的方便建立在用户的麻烦上。
2. **平台之间**：移动端随身、有传感器、适合采集；桌面端大屏、输入方便、适合展示与复杂操作。把功能在两端简单复制是最省事也最错的方案——整体体验等于各平台长板之和。
3. **交给自动化/系统**：识别、默认值、错误约束。但自动化不是银弹，先问机器做错时用户能否察觉、代价多大。

两个前提：**信任**——我们习惯把用户当孩子、剥夺决定权；转移的前提是相信用户能行，不确定就用原型测试验证，而不是用预防代码表达不信任。**度**——高频核心操作不能绕路：把所有功能搬进菜单后，"孤零零的遥控器"就失去了存在的意义。

## A1 — 书中的应用 (Past Application)

### 案例 1: RunKeeper 的平台分工
- **问题**: 跑步记录应用要同时服务采集（路上）和查看（桌前）两个场景，小屏幕两边都装不下。
- **方法论的使用**: 按平台长短板分工：手机端点一下开始、装进口袋，自动生成路线、里程、配速——按时间收集数据是手机的强项；查看数据时手机只给简单摘要，全部细节留给大屏网站展示。
- **结论**: 把正确的功能放到正确的平台，整体体验就简单了。
- **结果**: 手机负责采集、网站负责展示，两端各司其职。

### 案例 2: Ta-da List 与强制格式表单
- **问题**: 任务列表要不要设"截止日期"专用字段？表单要不要强制用户按机器格式输入？
- **方法论的使用**: 37signals 有意不设日期字段——需要截止日期的用户自然在任务描述里写"截止到 1 月 27 日"；正面的机器侧示范是邮件程序自动识别"下周二"和电话号码，转为日历约会或拨号链接。反例是最讨厌的表单：信用卡号不许有空格、电话号码不许用括号。
- **结论**: 人写自由文本，机器负责识别和结构化——别让百万用户各自迁就一次机器的格式。
- **结果**: Ta-da List 的用户自发发明了自己的日期格式，输入零负担。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 表单逼用户按机器格式输入（电话不许括号、日期必须特定写法），错误率高。
2. 产品要做移动端和桌面端，或者两平台功能在简单复制。
3. 争论某个任务该自动化还是留给用户，机器能不能接得住。
4. 觉得"让用户自己做"是偷懒甩锅，需要判断哪些任务适合交还用户。
5. 软件处处替用户做主（确认弹窗、禁用状态泛滥），用户在绕开产品。

### 语言信号 (用户的话里出现这些就应激活)

- "自动化 / 让机器来做 / 别让用户填格式 / 智能识别"
- "移动端和桌面端怎么分工 / 两边都要做吗 / platform"
- "该软件做还是用户做 / 转移 / transfer / automation / structured input / 人机分工"

### 与相邻 skill 的区分

- 与 `four-strategies` 的区别：总纲管策略选择；本 skill 是转移策略的执行（分工表怎么用、表单怎么改、平台怎么排）。
- 与 `complexity-placement` 的区别：四问是四策略用尽后的终局决策框架（"自动化还是用户控制"是其中一问）；本 skill 在执行层给具体分工。
- 与 `open-experience` 的区别：分工表回答"这一步谁做"；开放式体验回答"要不要把定义成功的模糊性留给用户"——那是转移的进阶形态。
- 与 `mainstream-user-lens` 的区别：信任用户 ≠ 听专家的——专家要的精确控制不是主流用户的掌控感。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **给任务两端记账**
   - 列出流程中每一步谁在干（人/机器），标注用户负担：输入量、格式约束、要记的东西
   - 完成标准: 全流程分工清单，每步有负担标记
2. **按长短板重新分配**
   - 人擅长的（目标设定、估算、判断、命名）留给人；机器擅长的（记忆、检索、精确计算、格式化、结构化）交给机器；平台按"移动采集 vs 大屏展示"分工，不复制功能
   - 完成标准: 每步注明"交给谁+依据的长短板"；格式约束全部从用户侧移除
3. **给自动化设置前提**
   - 先问：机器做错的概率与代价？用户能否察觉？有没有兜底？
   - 完成标准: 每项自动化有失败兜底或可察觉信号；未经此问的自动化不做
4. **原型验证信任并判停**（判停条件：若转移后高频操作需要绕路，退回部分核心入口；若用户侧复杂性总量没降，转 complexity-placement 做终局分配）
   - 完成标准: 原型测试中，被转移给用户的任务用户能顺利完成且愿意用

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 高频核心操作要转移到多级菜单——每次使用都多付"绕路税"，总成本反升
- 用户身处高压环境（匆忙、被打断、单手操作）——交给用户的任务要少而轻
- 机器做错代价高且用户难察觉的环节——自动化会把错误一起放大
- 用户明确表示不想被"帮忙"的判断类环节——尊重其控制感

### 作者在书中警告的失败模式

- **智能旅行规划程序（机器评判用户）**：程序自动排行程、行程太满就警告，用户觉得"不断被评判"，产品最终未上线——设定目标与组织记录是人擅长的活，机器接不住
- **强制格式表单**：输信用卡号不许有空格、电话号码不许用括号——几行后台代码就能解决的事，让百万用户各自迁就机器的格式，是"懒惰和无礼的表现"
- **把用户当孩子**：确认弹窗、禁用状态、代劳一切——各角色的"防错"职业习惯系统性低估用户，用户失去指挥权便怨恨计算机
- **孤零零的遥控器（转移过度）**：全部功能进屏幕菜单，播放个 DVD 都要先进菜单找命令——转移目标界面自身的简化问题一个不少

### 作者的盲点 / 时代局限

- 书中把"转移给机器"近乎当成无代价的解法——现实中自动化会把错误一起放大且更难被用户察觉（自动纠错、自动推荐皆然）
- 转移后两套界面（App+网站）的维护与一致性成本，书中着墨少

### 容易混淆的邻近方法论

- `complexity-placement`：四问是统摄四策略的终局决策；本 skill 是转移这一策略的执行层
- `open-experience`：把"定义成功"留给用户是转移的进阶形态，归工具设计
- 甩锅式"让用户自己想办法"：转移是各放所长，不是推卸
